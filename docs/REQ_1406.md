# REQ-1406: fix(hut-sector) — Reclassify HUT from real_estate to construction

status: READY_FOR_ARCHITECT
sprint: 143
po_vision: HUT (Tasco — toll roads, highway concessions) must not trigger "Bất động sản giảm đồng loạt" cascade alerts

## User Story

As a Vietnamese stock investor using Claude,
I want HUT (Tasco Joint Stock Company) classified under the correct infrastructure/construction sector,
So that BĐS cascade alerts fire only for genuine real estate stocks and I do not receive false-positive sector-drop alerts for HUT.

---

## Root Cause (confirmed by BA investigation 2026-04-18)

**Single source of truth**: `src/domain/services/sectorPeers.ts:66`

```
real_estate: [
  ...
  { code: "HUT", exchange: "HNX" },   // ← WRONG
  ...
]
```

`getStockProfileMap()` builds a lazy reverse index from `SECTOR_PEERS` (line 242–255).
`getStockProfile("HUT")` therefore returns `{ domain: "real_estate", exchange: "HNX" }`.

This profile is used in:
- `schema.ts:575` — watchlist seed: inserts `domain = "real_estate"` into the DB `watchlist` table
- `cascadeEngine.ts` — sector cascade rules fire against `domain: "real_estate"` stocks
- `sectorComparisonTools.ts:498`, `kinhDichTools.ts:243`, `portfolioTools.ts:197` — sector peer comparisons include HUT in BĐS bucket
- `scanMarket` / `syncSectorPeers` — context stock fetch includes HUT in real_estate peer set

**Correct classification**: `construction` (DomainType already exists in `bctc-schema.ts:43`).
Peers in that sector: HHV, CTD, VCG, HBC, FCN — all general construction/infrastructure, which matches HUT's business (BOT highway concessions, toll-road operator).

HUT is NOT in:
- `docs/data/stock-classification.json` watchlist array (confirmed — that file is a separate user-facing summary, not the alert engine source)
- `data/market.db` watchlist table — the DB row's `domain` column is seeded from `SECTOR_PEERS` via `getStockProfile()` in `schema.ts:566-575`; it will self-correct once `SECTOR_PEERS` is fixed and the watchlist row is updated

## Functional Requirements

### FR-1: Move HUT from real_estate to construction in SECTOR_PEERS

- **Description**: Remove `{ code: "HUT", exchange: "HNX" }` from the `real_estate` array and add it to the `construction` array in `sectorPeers.ts`.
- **Input**: `sectorPeers.ts` — `SECTOR_PEERS` constant
- **Output**: `getStockProfile("HUT")` returns `{ domain: "construction", exchange: "HNX" }` instead of `{ domain: "real_estate", ... }`
- **Business rule**: `construction` already has the comment "HHV, CTD, VCG, HBC — infrastructure CAPEX". HUT fits: BOT highway concessions + construction subsidiary.
- **DDD layer**: domain

### FR-2: Invalidate the in-process SECTOR_PEERS cache

- **Description**: `_stockProfileCache` in `sectorPeers.ts` is a module-level singleton lazily built on first call. Because it is built from `SECTOR_PEERS`, fixing the constant (FR-1) is sufficient — the cache rebuilds from the corrected data on next access.
- **No code change required** beyond FR-1 — this is a correctness note for the Dev agent.
- **DDD layer**: domain

### FR-3: Update DB watchlist domain for HUT

- **Description**: The DB watchlist row for HUT may persist `domain = "real_estate"` from a previous seed. The watchlist `add_stock` tool re-derives domain from `getStockProfile()` on each add; however, existing rows are not auto-updated. Dev must either:
  - (a) add a one-shot UPDATE migration in `schema.ts` (preferred, idempotent), or
  - (b) document that removing + re-adding HUT via the MCP tool will self-correct.
  - Preferred: migration `UPDATE watchlist SET domain = 'construction' WHERE code = 'HUT' AND domain = 'real_estate'` — safe, idempotent.
- **Input**: `data/market.db` — `watchlist` table
- **Output**: `SELECT domain FROM watchlist WHERE code = 'HUT'` returns `construction`
- **DDD layer**: infrastructure (migration in `schema.ts`)

### FR-4: TDD — RED then GREEN

- **Description**: Write a failing test asserting HUT is NOT in the `real_estate` peer list and IS in the `construction` peer list, then make it pass.
- **Test file**: `src/__tests__/1406-hut-sector-reclassify.test.ts`
- **Test cases** (minimum 3):
  1. `getSectorPeers("real_estate", new Set(), Infinity)` — result must NOT contain `{ code: "HUT" }`.
  2. `getSectorPeers("construction", new Set(), Infinity)` — result MUST contain `{ code: "HUT", exchange: "HNX" }`.
  3. `getStockProfile("HUT")` — must return `{ domain: "construction", exchange: "HNX" }`.
- **DDD layer**: domain (test of pure domain service, no DB I/O)

## Non-Functional Requirements

- **Performance**: No impact — `SECTOR_PEERS` is a compile-time constant; cache rebuild is O(n) over ~100 tickers, happens once per process.
- **Data freshness**: DB migration must run before any cascade alert is evaluated post-deploy. Migration in `schema.ts` ensures this.
- **Language**: No user-facing strings change in this sprint. `SECTOR_NAME_VI["construction"]` already = `"Xây dựng & Hạ tầng"` (sectorPeers.ts:202).
- **Regression guard**: `1282-sector-classification-dedup.test.ts` must continue to pass — it asserts no ticker appears in multiple sector lists. After FR-1, HUT moves from `real_estate` to `construction`; dedup constraint is preserved.

---

## Edge Cases & Data Quality

- [ ] Cache poisoning: if server runs long before restart, old cache may still hold `real_estate` for HUT. The DB migration (FR-3) ensures the DB value is correct regardless; the in-process cache is irrelevant post-restart.
- [ ] HUT present in `config.ts:434` default watchlist array — this is the watchlist code list only (no sector), not the sector source. No change needed there.
- [ ] `stockAliases.ts:299` — HUT aliases are correct (tasco, thu phi duong bo tasco); no change needed.
- [ ] `cascadeEngine.ts` — does not hardcode HUT by ticker; all cascade rules fire against `domain` field. Fixing `SECTOR_PEERS` (and the DB row via migration) is sufficient.
- [ ] No `infrastructure` DomainType exists — do NOT create a new type. Use `construction` (already in `bctc-schema.ts:43`).
