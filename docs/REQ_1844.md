## Context

Sprint 1842 delivered `run_backtest` (tool #120) which saves each completed run to the
`backtest_runs` SQLite table via `IBacktestResultRepository.saveRun()`. Runs accumulate
silently with no read path exposed to the user. Sprint 1844 adds two read-only MCP tools
so the user can list and inspect past runs without writing code.

---

## Deliverable 1 — `get_backtest_runs` MCP tool (#124)

### Functional Requirements

- **FR-1-1 (List by strategy):** When `strategy` is provided, return all stored runs
  whose `strategy` column equals that value, sorted by `runAt` DESC, limited to `limit`
  rows. Delegates to `IBacktestResultRepository.getRunsByStrategy(strategy, limit)`.

- **FR-1-2 (List all strategies):** When `strategy` is omitted, return runs across all
  strategies, still sorted by `runAt` DESC, limited to `limit` rows. This is a new query
  path — `getRunsByStrategy()` only accepts a strategy string; listing all strategies
  requires either a separate repo method or a wildcard convention. See Blockers.

- **FR-1-3 (Limit):** `limit` is optional integer, default 10, max 50. Values above 50
  are clamped to 50. Values below 1 are rejected with a validation error.

- **FR-1-4 (Output shape):** Each item in the returned array contains exactly:
  `id`, `strategy`, `startDate`, `endDate`, `runAt`, `totalReturn`, `benchmarkReturn`,
  `maxDrawdown`, `sharpeRatio`, `winRate`, `tradeCount`.
  `resultJson` is NOT included — this is a summary list, not a full record.

- **FR-1-5 (Empty result):** When no runs match, return an empty array `[]` with HTTP 200
  (not an error).

### Non-Functional Requirements

- **NFR-1-1 (Layer):** Tool lives in `interface/mcp/tools/backtesting/`. No domain or
  infrastructure logic in the tool handler — delegates entirely to application layer or
  directly to the injected repository (retrieval-only use cases may skip a dedicated use
  case file if trivial; Architect decides).
- **NFR-1-2 (DDD golden rule):** Tool must not import domain service files or SQLite
  adapters except to instantiate them for injection. All business rules stay in domain.
- **NFR-1-3 (Error isolation):** SQLite errors are caught; return `{ error: "..." }` JSON
  content block, never a thrown exception to the MCP caller.

### Acceptance Criteria

- **AC-1-1:** `get_backtest_runs({ strategy: "kinh-dich-high-confidence", limit: 5 })`
  returns an array of up to 5 objects each containing all 11 summary fields, sorted
  `runAt` DESC, and `resultJson` is absent from every object.
- **AC-1-2:** `get_backtest_runs({})` (no args) returns up to 10 runs across all
  strategies sorted `runAt` DESC.
- **AC-1-3:** `get_backtest_runs({ limit: 0 })` returns a validation error content block.
- **AC-1-4:** `get_backtest_runs({ limit: 99 })` returns at most 50 results (clamped).
- **AC-1-5:** When the `backtest_runs` table is empty, returns `[]` with no error.
- **AC-1-6:** SQLite failure (e.g. table missing) returns `{ error: "..." }` JSON, does
  not throw.

## Deliverable 2 — `get_backtest_run` MCP tool (#125)

### Functional Requirements

- **FR-2-1 (Retrieve by ID):** Given a required `id` string, return the full
  `BacktestRunRecord` including `resultJson` (which contains the trade log, equity curve,
  and warnings from the original `BacktestReport`).

- **FR-2-2 (Not found):** When no row matches `id`, return an error content block:
  `{ "error": "Backtest run <id> not found." }`. Do not return null or throw.

- **FR-2-3 (Output shape):** Return all 12 fields of `BacktestRunRecord`:
  `id`, `strategy`, `startDate`, `endDate`, `runAt`, `totalReturn`, `benchmarkReturn`,
  `maxDrawdown`, `sharpeRatio`, `winRate`, `tradeCount`, `resultJson`.
  `resultJson` is included here (unlike the list tool) because this is the full detail
  view.

- **FR-2-4 (resultJson parsing):** The tool returns `resultJson` as a raw string.
  Callers (agent or user) parse it. The tool does not re-parse or validate it.

### Non-Functional Requirements

- **NFR-2-1:** Same layer and DDD constraints as NFR-1-1 / NFR-1-2 / NFR-1-3.
- **NFR-2-2 (ID format):** `id` is a UUID string. Zod validates `z.string().uuid()`.
  Non-UUID strings return a Zod validation error before hitting the DB.

### Acceptance Criteria

- **AC-2-1:** `get_backtest_run({ id: "<valid-uuid>" })` where the run exists returns a
  single object with all 12 fields including `resultJson` as a non-empty string.
- **AC-2-2:** `get_backtest_run({ id: "<valid-uuid>" })` where the run does not exist
  returns `{ "error": "Backtest run <id> not found." }` content block.
- **AC-2-3:** `get_backtest_run({ id: "not-a-uuid" })` returns a Zod validation error
  content block without touching the database.
- **AC-2-4:** `get_backtest_run({ id: "<valid-uuid>" })` where the underlying SQLite call
  throws returns `{ "error": "..." }` JSON, does not throw to MCP caller.
- **AC-2-5:** `resultJson` in the returned object is the verbatim string stored in the
  DB — not pretty-printed, not re-serialised.

## Deliverable 3 — `IBacktestResultRepository.getRunById()` status

### Finding (from code inspection)

Both the domain port and the SQLite implementation already exist and are complete:

- **Interface** — `apps/mcp-server/src/domain/repositories/IBacktestResultRepository.ts`
  line 41: `getRunById(id: string): BacktestRunRecord | null;`

- **Implementation** — `apps/mcp-server/src/infrastructure/db/backtestResultRepo.ts`
  lines 102-119: `getRunById()` uses `.get(id)`, maps via `rowToRecord()`, returns null
  on miss, catches SQLite errors and returns null.

No code change is required for Deliverable 3. The Architect and Developer should confirm
via `bun test` that existing tests cover this method before adding new tests in 1844.

### What IS missing — `getAllRuns(limit: number)` (required by FR-1-2)

The interface has no method to retrieve runs across all strategies. `getRunsByStrategy()`
requires a strategy string. To support `get_backtest_runs` with no `strategy` argument,
one of the following is needed (Architect decides):

- **Option A:** Add `getAllRuns(limit: number): BacktestRunRecord[]` to the interface and
  SQLite implementation. Query: `SELECT ... FROM backtest_runs ORDER BY run_at DESC LIMIT ?`.
  Clean, explicit, follows existing pattern.

- **Option B:** Add an optional overload: `getRunsByStrategy(strategy?: string, limit: number)`.
  Risks muddying the interface semantics.

- **Option C:** Handle the "no strategy" case entirely in the MCP tool by passing a
  sentinel value, bypassing the domain port. Violates DDD layer separation — do not use.

Recommended: Option A.

## Edge Cases

- **Empty table:** Both tools must handle a freshly initialised DB with zero rows in
  `backtest_runs`. Return empty array / not-found error respectively — no crash.

- **resultJson size:** A large backtest over 30 tickers and 2 years will produce a
  `resultJson` blob potentially 200-500 KB. The tool returns it as a string. No
  truncation — callers are responsible for handling large payloads. MCP transport is
  local stdio; size is not a network concern.

- **Null numeric fields:** `benchmarkReturn` and `sharpeRatio` are nullable in the domain
  model (runs before VNI benchmark data existed, or too few trades for Sharpe). Both
  tools must serialise these as `null` in the JSON output, not `undefined` or omitted.

- **Concurrent reads during a running backtest:** The existing mutex in `runBacktest.ts`
  is write-only. Read tools do not need to check the mutex — SQLite handles concurrent
  readers natively.

- **Strategy name casing:** Strategy IDs are stored and queried as lowercase kebab-case
  (e.g. `"combined-high-confidence"`). The `strategy` input should be validated against
  the known enum values. Passing an unknown-but-valid-string returns an empty array, not
  an error — consistent with FR-1-5.

## Blockers

- **BLK-1 (Tool slot gap):** The sprint goal assigns tools #124 and #125. The last
  registered tool is #120 (`run_backtest`). Slots #121, #122, #123 appear unregistered
  (grep confirmed no references). Architect must confirm: are 121-123 reserved for
  in-flight tasks, or can 1844 use #121 and #122 instead? Using non-contiguous slots is
  harmless functionally but breaks the sequential comment history in `registry.ts`.

- **BLK-2 (getAllRuns design):** FR-1-2 requires listing runs across all strategies. The
  existing `getRunsByStrategy()` interface does not support this. Architect must choose
  Option A or B (see Deliverable 3). This is a domain interface change — it must be
  decided before implementation starts.

- **BLK-3 (File organisation):** The existing `backtestTools.ts` registers one tool
  (`run_backtest`). The two new tools can be added to the same file or a separate
  `backtestQueryTools.ts`. Architect decides based on file length and cohesion preference.
  Both approaches satisfy DDD constraints.
