## Root Cause Analysis

### Bug A — storeReport writes to the wrong DB instance

`parseBctcReport.ts → storeReport()` calls `getDb()` at line 147, which returns the **module-level
singleton** from `schema.ts`.

The singleton is initialised once and pinned to the path resolved at module load time:
`data/market.db` (or `DB_PATH` env var at that moment).

When `bctcReparseJob` is called in **production** the problem does not surface at the job level,
but `parseBctcReport` calls `await initDatabase()` immediately before `storeReport`. If the
singleton was previously opened in a different context (e.g. a prior import chain during server
start that set `DB_PATH` differently), `initDatabase` silently operates on that already-open
connection. The `financial_reports` table is created — but the table is created on a DB file
that either differs from the file the inspection query targets, or the WAL checkpoint has not
flushed the rows to the main db file before the query runs.

The concrete failure modes in order of probability:

1. **WAL visibility gap** — `storeReport` writes rows inside WAL mode. Another connection
   (e.g. the `sqlite3` CLI or a second `getDb()` call in a test) opens the DB file without
   first seeing a WAL checkpoint. Rows appear in WAL, not in the main file, so a reader that
   does not share the same WAL reader connection sees 0 rows.

2. **DB_PATH mismatch across import chains** — Server startup imports `schema.ts` with
   `DB_PATH=data/market.db`. `parseBctcReport` later imports the same module; because the
   singleton `_db` is already set it reuses that connection. BUT if tests or a secondary
   process set `DB_PATH` to a different path after module load, the subsequent `getDb()` call
   in `storeReport` returns the stale, already-open connection to the original path. Rows are
   written to the original path, not to the path the observer queries.

3. **Silent exception in storeReport** — `storeReport` is a plain synchronous `void` function
   with no try/catch. Any SQLite constraint violation or schema mismatch (column count
   mismatch if the DDL was updated after the connection was opened without migration) throws
   synchronously. Because `parseBctcReport` does not wrap the `storeReport(...)` call in a
   try/catch, and because `fetchParseAndStoreBctc` wraps `parseBctcReport` in a try/catch
   that logs and returns `null`, a storeReport throw is swallowed: `fetchParseAndStoreBctc`
   logs `parseBctcReport failed`, returns `null`, and then logs `pipeline complete` only if it
   did NOT return null — however if the throw happens AFTER the parse step returns a value and
   only during the persist step, `parseBctcReport` itself propagates the throw, which
   `fetchParseAndStoreBctc` catches, returns `null`, and yet the bctcReparseJob interprets the
   null return as `success = false` and increments `reparse_attempts`. The job logs
   "pipeline complete" only from within `fetchParseAndStoreBctc` at line 356, which is
   reached BEFORE `parseBctcReport` throws — meaning the "pipeline complete" log can appear
   even when the SQLite write failed.

   Re-reading `fetchParseAndStoreBctc`: line 356 `logger.info(... 'pipeline complete')` runs
   AFTER step 3 (`parseBctcReport`) returns. If `parseBctcReport` throws, execution never
   reaches line 356. The "pipeline complete" message is therefore evidence that
   `parseBctcReport` returned successfully — which means `storeReport` did NOT throw. This
   makes WAL visibility gap (failure mode 1) or a DB_PATH mismatch (failure mode 2) the most
   likely root cause rather than a silent exception inside storeReport itself.

4. **`initDatabase()` race** — `parseBctcReport` calls `await initDatabase()` which is
   async, but `initDatabase` itself calls `getDb()` synchronously and executes all DDL
   synchronously (Bun SQLite `exec` is sync). The `await` is harmless but the function is not
   truly async. However, if `financial_reports` table DDL (imported from `SQLITE_DDL` in
   `bctc-schema.ts`) is not being executed because the singleton was already opened and
   `initDatabase` is a no-op (it is NOT idempotent-guarded per connection — it runs every
   time it is called but uses `CREATE TABLE IF NOT EXISTS` so it is safe), this path is
   fine.

## Functional Requirements

### FR-1: Diagnose and fix the financial_reports persistence gap

- **Description**: Identify which of the four failure modes above is the actual root cause and
  apply a targeted fix. The fix must ensure that after `fetchParseAndStoreBctc` returns a
  non-null `FinancialReport`, a `SELECT COUNT(*) FROM financial_reports` on the same DB file
  used by the server returns >= 1 row for that ticker+period.
- **Input**: A call to `fetchParseAndStoreBctc({ actionCode: "VNM", year: 2025, quarter: "Q4", pdfTextOverride: "<real pdf text>" })` on the production server.
- **Output**: One row in `financial_reports` with `action_code = "VNM"`, `period_year = 2025`, `period_quarter = 4`.
- **Business rule**: The fix must not break the existing test suite for tasks 042–047, 121, 240, 291.
- **DDD layer**: application (`src/application/usecases/parseBctcReport.ts`) and/or infrastructure (`src/infrastructure/db/schema.ts`)

### FR-2: Add explicit error propagation in storeReport

- **Description**: Wrap the `storeReport` call inside `parseBctcReport` in a try/catch that
  re-throws with a descriptive message. This ensures any SQLite constraint or schema error is
  surfaced to `fetchParseAndStoreBctc`'s existing error handler and logged as
  `parseBctcReport failed` (not silently swallowed).
- **Input**: Any SQLite error thrown by `stmt.run(...)` inside `storeReport`.
- **Output**: Error propagates to `fetchParseAndStoreBctc` caller; appears in logger.error output; `bctcReparseJob` increments `reparse_attempts`; does NOT log "pipeline complete".
- **Business rule**: LanceDB failure is already marked non-fatal (Sprint 048 design). SQLite persistence failure MUST be fatal — if the row is not stored, the report does not exist.
- **DDD layer**: application (`src/application/usecases/parseBctcReport.ts`)

### FR-3: WAL checkpoint call after storeReport

- **Description**: After a successful `storeReport` call, trigger a WAL checkpoint on the
  production DB singleton (`PRAGMA wal_checkpoint(PASSIVE)`) so that rows written during the
  reparse cycle are visible to any reader that opens the DB file independently (e.g. the
  `sqlite3` CLI, a diagnostic query from another process). This is a targeted, lightweight
  checkpoint — not the full daily checkpoint in `checkpoint.ts`.
- **Input**: Successful `INSERT OR REPLACE` in `financial_reports`.
- **Output**: WAL pages flushed to main DB file; `sqlite3 data/market.db "SELECT COUNT(*) FROM financial_reports;"` returns >= 1 immediately after.
- **Business rule**: `PASSIVE` checkpoint (not `FULL` or `RESTART`) — must not block the server's ongoing write traffic.
- **DDD layer**: application (`src/application/usecases/parseBctcReport.ts`)

### FR-4: Fix 308-tool-registry.test.ts assertion

- **Description**: Update the stale `toBe(57)` assertion to `toBe(59)`. Update the comment
  history chain in the same file to document the two missing increments (task 1166 and task
  1180). The test description string should also be updated to remove the stale "57 entries"
  reference.
- **Input**: `toolRegistry.length` from `src/interface/mcp/tools/registry.ts`.
- **Output**: Test passes; comment chain accurately reflects history through sprint 071.
- **Business rule**: Count must always match the actual exported array length. Future tool additions must update both the registry file AND the test comment chain.
- **DDD layer**: interface (`src/__tests__/308-tool-registry.test.ts`)

### FR-5: Integration smoke test — financial_reports row after reparse

- **Description**: Add a new test `src/__tests__/1181-financial-reports-persist.test.ts` that
  proves end-to-end persistence. The test uses `pdfTextOverride` to bypass SSC network calls,
  injects the real SQLite in-memory DB (with full schema via `initDatabase`), calls
  `fetchParseAndStoreBctc`, and asserts that `financial_reports` contains one row for the
  given ticker+period.
- **Input**: In-memory SQLite (`:memory:`), `pdfTextOverride` containing a minimal but
  parseable Vietnamese BCTC text block (balance sheet + income statement + cash flow keywords
  present so extractors return non-zero values).
- **Output**: `SELECT COUNT(*) FROM financial_reports WHERE action_code = 'VNM'` returns 1 after the call.
- **Business rule**: This test must use the SAME DB connection that `parseBctcReport → storeReport → getDb()` uses during the call — the test must reset the singleton before and after (`closeDb()` + `DB_PATH` env override).
- **DDD layer**: test layer (`src/__tests__/`)

## Non-Functional Requirements

- **Performance**: WAL checkpoint (FR-3) must complete in < 100 ms for the row sizes involved. `PASSIVE` mode guarantees non-blocking behaviour.
- **Data freshness**: After the fix, `financial_reports` must reflect the most recent successful `bctcReparseJob` run within the same server process lifetime.
- **Idempotency**: `storeReport` uses `INSERT OR REPLACE` — re-running the reparse cycle for the same ticker+period must not create duplicate rows.
- **Language**: All new log messages in English (existing convention). Test assertions in English.
- **Test isolation**: FR-5 test must not leave state in the global DB singleton. Use `closeDb()` in `afterEach` / `afterAll`.

## Edge Cases & Data Quality

- [ ] `getDb()` singleton already open to a different path — FR-1 fix must address the mismatch or document clearly that `DB_PATH` must be set before any module is imported.
- [ ] `storeReport` called with a `FinancialReport` where all numeric fields are 0 (extraction yielded nothing useful) — INSERT must still succeed; confidence score will be 0.0, and `validation_status` will be `failed`. Row is written; section 5 shows "BCTC data low confidence" rather than "(no data)".
- [ ] `financial_reports` table does not exist at the time `storeReport` runs — possible if `initDatabase` was never called. FR-2 try/catch will surface this as a clear error rather than silent swallow.
- [ ] WAL checkpoint `PASSIVE` returns `busy` (another writer holds a read lock) — this is non-fatal; log a debug warning, do not retry in the hot path.
- [ ] Test for FR-5 uses `:memory:` — WAL mode is not applicable to `:memory:` DBs. The checkpoint call must be guarded with `if (dbPath !== ':memory:')` or wrapped in a no-op try/catch.
- [ ] Vietnamese number format in BCTC PDF: `1.234.567` (dots as thousand separators) vs `(234.567)` (parentheses = negative) — handled by existing domain extractors; FR-1 fix does not touch extractors.
- [ ] SSC portal geo-block — not relevant to this sprint; reparse path uses local PDF text via `pdfTextOverride`.
