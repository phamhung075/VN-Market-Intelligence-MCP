# REQ-076: Pipeline Watchdog — Stale-Pipeline Telegram Alert

status: READY_FOR_ARCHITECT
sprint: 076
task: 1190
po_vision: Eliminate silent pipeline failures by sending an automated Telegram alert when the news pipeline goes quiet for more than 90 minutes.

## User Story

As a Vietnamese stock investor living in France who cannot babysit the server during VN market hours,
I want the system to proactively alert me on Telegram the moment the news pipeline has been silent for 90 minutes,
So that I know about a pipeline failure before the evening report runs empty.

---

## Context and Motivation

Sprint 075 delivered `get_pipeline_health` (task 1189) — a pull tool the operator can invoke from
Claude Desktop. This is reactive: the operator must think to check.

On 2026-04-13 the evening report produced `topStories: []` because the news pipeline silently stopped
inserting `rag_analyses` rows hours before the 22:30 summary job ran. No alert fired.

Sprint 076 delivers a push notification: a scheduler job that polls `getPipelineHealth()` every
30 minutes and alerts the `work` channel automatically when `staleMins > 90`.

## Functional Requirements

### FR-1: Scheduled 30-minute watchdog job

- Description: A new scheduler file `src/scheduler/jobs/pipelineWatchdogJob.ts` that runs once
  every 30 minutes, 24/7 (no market-hours restriction — pipeline failures can happen at any time,
  including during the overnight intelligence cycle).
- Input: No external input. The job calls `getPipelineHealth()` internally.
- Output: One of four result strings (used internally for logging and tests):
  - `"ok"` — pipeline is healthy (`staleMins` is non-null AND `staleMins <= 90`)
  - `"no-data"` — `staleMins` is null (rag_analyses table empty; no rows ever inserted)
  - `"alert-sent"` — stale detected, alert dispatched to `work` channel
  - `"cooldown"` — stale detected but alert suppressed (within 3-hour cooldown window)
  - `"notify-failed"` — stale detected, alert attempted but `sendTelegramWork` returned false or threw
- Business rule: The cron pattern is `*/30 * * * *`. Register with `{ timezone: 'UTC' }` (no VN
  business-hour restriction). Emit `[pipelineWatchdog] healthy` at DEBUG level when result is `"ok"`.
- DDD layer: scheduler

### FR-2: Staleness gate — `staleMins > 90`

- Description: After calling `getPipelineHealth()`, read `result.ragRows.staleMins`. If the value
  is null, treat as `"no-data"` and take no action (no alert). If `staleMins > 90`, proceed to
  the cooldown check (FR-3). If `staleMins <= 90`, return `"ok"`.
- Input: `PipelineHealthResult.ragRows.staleMins` (number | null).
- Output: Decision to alert or not.
- Business rule:
  - `staleMins === null` — no rows ever inserted; do not alert (could be a fresh install or
    test environment). Log at DEBUG.
  - `staleMins <= 90` — pipeline healthy. Log at DEBUG. Return `"ok"`.
  - `staleMins > 90` — pipeline stale. Proceed to cooldown check.
- Edge case: `staleMins` can theoretically be 0 (last insert happened this minute). No special
  handling needed — the `<= 90` branch covers it.
- DDD layer: scheduler (decision logic in `pipelineWatchdogJob.ts`)

### FR-3: 3-hour cooldown to prevent alert flooding

- Description: During a sustained pipeline outage, the watchdog fires every 30 minutes. Without
  a cooldown the `work` channel would receive 6 alerts per hour. Apply a 3-hour cooldown:
  once an alert is sent, do not send another until at least 3 hours have elapsed — OR until the
  pipeline recovers (`staleMins <= 90`) and then goes stale again.
- Input: Module-level timestamp `lastAlertAt` (epoch ms, starts at 0).
- Output: If `now.getTime() - lastAlertAt < COOLDOWN_MS`, return `"cooldown"` without sending.
  Otherwise proceed to send the alert and update `lastAlertAt = now.getTime()`.
- Business rule:
  - `COOLDOWN_MS = 3 * 60 * 60 * 1000` (3 hours = 10 800 000 ms).
  - `lastAlertAt` is a module-level `let` variable initialised to `0` (never alerted).
  - Cooldown does NOT reset automatically when the pipeline recovers. The next stale trigger
    after recovery will also be subject to the cooldown. This is intentional: recovery then
    immediate re-failure should not re-flood. The cooldown is time-based only.
  - Export `_resetWatchdogCooldown(): void` for test isolation (sets `lastAlertAt = 0`).
- DDD layer: scheduler

### FR-4: Telegram alert payload to `work` channel

- Description: When the stale gate and cooldown both pass, call `sendTelegramWork(message)` with
  a plain-text message that gives the operator everything needed to assess severity at a glance.
- Input: `PipelineHealthResult` fields: `ragRows.staleMins`, `ragRows.today`,
  `ragRows.lastInsertedAt`, `vpsPushLast24h`.
- Output: Plain-text Telegram message sent to `channel: "work"`. No Markdown formatting
  (`parseMode: ""`). Return value of `sendTelegramWork` determines whether result is
  `"alert-sent"` (truthy) or `"notify-failed"` (false or exception).
- Business rule: Message format (exact template):

  ```
  [Pipeline Watchdog] News pipeline silent.
  Stale for: <staleMins> min
  Today's rag_analyses rows: <ragRows.today>
  Last insert: <ragRows.lastInsertedAt ?? "never">
  VPS news pushes (24h): <vpsPushLast24h ?? "unknown">

  Check intelligenceCycleJob logs and VPS vn-news-fetch.service.
  ```

  Replace `<...>` with actual values. If `vpsPushLast24h` is null (table absent), render
  `"unknown"`. If `ragRows.lastInsertedAt` is null, render `"never"`.
- DDD layer: scheduler (infrastructure call via `sendTelegramWork`)

### FR-5: Job registration in `src/scheduler/jobs.ts`

- Description: Register the new cron key and wire it up in `startScheduler()` inside
  `src/scheduler/jobs.ts`, following the same `recordJobRun` wrapper pattern used by other jobs.
- Input: `CRONS.pipelineWatchdog` cron key.
- Output: A `cron.schedule(CRONS.pipelineWatchdog, ...)` block that calls
  `runPipelineWatchdog()` and wraps it in `recordJobRun(getDb(), 'pipelineWatchdogJob', ...)`.
- Business rule:
  - Add to the `CRONS` object: `pipelineWatchdog: Bun.env.CRON_PIPELINE_WATCHDOG ?? '*/30 * * * *'`.
  - Register with `{ timezone: 'UTC' }`.
  - The `recordJobRun` return value should include `{ staleMins: <value> }` for observability
    in `cron_job_runs`.
  - Update the jsdoc comment block at the top of `jobs.ts` to list the new job.
- DDD layer: scheduler

### FR-6: Update `docs/data/cron-registry.json`

- Input: New job metadata.
- Output: Updated `cron-registry.json` with:

## Non-Functional Requirements

- Performance: `getPipelineHealth()` already executes in < 50 ms (per REQ-075). The watchdog
  adds negligible overhead — no additional DB queries beyond what `getPipelineHealth` already does.
- Reliability: The watchdog must never crash the scheduler. All errors from `getPipelineHealth()`
  or `sendTelegramWork()` must be caught, logged, and swallowed with a `"notify-failed"` result.
- Testability: `runPipelineWatchdog()` must accept injected `now`, `notify`, and `getPipelineHealthFn`
  parameters so unit tests can run without a real DB or Telegram credentials.
- Language: Alert message in English (same as `vpsProxyWatchdogJob.ts`). The `work` channel is
  operator-facing, not investor-facing.
- Schedule: `*/30 * * * *` runs at :00 and :30 of every hour, 24/7.

## Edge Cases and Data Quality

- [ ] `staleMins === null` (empty table) — treat as `"no-data"`, no alert sent. This prevents
      false alarms on a fresh install or test environment with an empty `rag_analyses` table.
- [ ] `staleMins` is 0 (last insert happened seconds ago) — falls into `<= 90` branch, returns
      `"ok"`. No special handling needed.
- [ ] `getPipelineHealth()` throws an unexpected exception — catch in `runPipelineWatchdog()`,
      log at `error` level, return `"notify-failed"` (or a new `"health-check-failed"` string —
      Architect's choice; tests must cover it).
- [ ] `sendTelegramWork` returns `false` (Telegram API unreachable) — return `"notify-failed"`.
      Do NOT update `lastAlertAt` so the next run retries the send.
- [ ] `sendTelegramWork` throws an exception — catch, log, return `"notify-failed"`. Same cooldown
      behaviour as the `false` case above: do not advance `lastAlertAt`.
- [ ] Server restart during a sustained outage — `lastAlertAt` resets to 0 because it is
      module-level. The next run after restart will re-alert if stale. This is acceptable (the
      operator gets at most one extra notification after a restart).
- [ ] Dual cron collision: `intelligenceCycleJob` runs every 15 min on `*/15 * * * *`. The
      watchdog runs on `*/30 * * * *`. They will overlap at :00 and :30 each hour. Both are
      async and independent — no shared lock needed. DB is SQLite WAL mode; concurrent reads
      are safe.

## Implementation Notes for Architect

### Module signature

```typescript
// src/scheduler/jobs/pipelineWatchdogJob.ts

export const STALE_THRESHOLD_MINS = 90;
export const COOLDOWN_MS = 3 * 60 * 60 * 1000; // 3 hours

let lastAlertAt = 0;

export function _resetWatchdogCooldown(): void {
  lastAlertAt = 0;
}

export type WatchdogResult =
  | "ok"
  | "no-data"
  | "alert-sent"
  | "cooldown"
  | "notify-failed";

export async function runPipelineWatchdog(options?: {
  now?: Date;
  notify?: (message: string) => Promise<boolean>;
  getPipelineHealthFn?: (opts?: GetPipelineHealthOptions) => Promise<PipelineHealthResult>;
}): Promise<WatchdogResult>;
```

### Cooldown behaviour on notify failure

Only advance `lastAlertAt` when `notify` resolves to a truthy value. If `notify` returns
`false` or throws, leave `lastAlertAt` unchanged so the next run retries:

```typescript
const ok = await notify(message);
if (ok !== false) {
  lastAlertAt = now.getTime();
  return "alert-sent";
}
return "notify-failed";
```

### Default production wiring (no injection)

In production (no options injected) the job should import `getPipelineHealth` from
`../../application/usecases/getPipelineHealth.js` directly and call `sendTelegramWork` from
`../../infrastructure/notifiers/telegram.js`. These are only replaced in tests.
