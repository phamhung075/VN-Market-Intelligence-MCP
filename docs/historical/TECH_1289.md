## Executive Summary

**The Problem:** 784 parse errors in last 24h (threshold >50). ≥2 prior fix attempts (Sprint 228, 1288) have not eliminated the root cause.

**The Root Cause:** The foreign flow pipeline lacks **end-to-end schema validation at write time**. Valid data passes through, but invalid data from VPS payloads is coerced silently or rejected by the parser without diagnostics. The three prior fixes (Sprint 228 parse hardening, Sprint 1288 fallback fetcher) treated the **symptom** (data unavailability), not the **cause** (silent parse failures in the payload → storage path).

**The Real Issue:** When `writeForeignFlowToOhlcv()` is called (by VPS push endpoint OR fallback fetcher), it receives `WriteForeignFlowItem[]` from `foreignFlowFetcher.ts`. That data is validated in the fetcher's `isValidForeignFlowItem()` type guard. However:

1. The validator rejects items with invalid `code` or `date` but **silently filters** them (line 267 in fetcher).
2. If filtering removes ALL items, `writeForeignFlowToOhlcv()` writes nothing, but the endpoint returns HTTP 200 (success).
3. The caller (scheduler or fallback) assumes success and caches empty result or moves on.
4. Daily_ohlcv rows never receive foreign_flow data, making it appear as if VPS payload was empty.
5. Loop repeats: every cycle, all items are filtered due to schema mismatch, yet logs show "success" because the database write succeeded (zero rows = success).

**Why Prior Fixes Failed:**
- **Sprint 228:** Added parse hardening + validation to the POST endpoint. But the validator is in `foreignFlowValidator.ts` (domain), which is **not called by the fallback fetcher**. Fallback uses the inline `isValidForeignFlowItem()` check in `foreignFlowFetcher.ts`, which silently filters. Schema validation never happened.
- **Sprint 1288:** Added fallback strategy (primary → cache → SSE → none). Fallback masks the problem: when primary fails, fallback returns cached data or empty, never diagnosing that primary's payload schema is mismatched.

**The Fix:** Unify schema validation across **all entry points** (VPS push endpoint + fallback fetcher). Use the same strict validator (`foreignFlowValidator.ts`) everywhere. **Fail loudly on schema violations** instead of silently filtering. Log detailed diagnostics (item index, field name, expected type) to enable VPS debugging.

## Architecture Decision

**Three-part diagnosis:**

### Part 1: Identify the Silent Filter Bug

The `isValidForeignFlowItem()` type guard in `foreignFlowFetcher.ts` (lines 344–355) is too lenient:

```typescript
function isValidForeignFlowItem(item: unknown): item is WriteForeignFlowItem {
  if (!item || typeof item !== "object") return false;

  const obj = item as any;
  return (
    typeof obj.code === "string" &&
    typeof obj.date === "string" &&
    typeof obj.foreignBuyVol === "number" &&
    typeof obj.foreignSellVol === "number" &&
    (typeof obj.putThroughVol === "number" || obj.putThroughVol === undefined)
  );
}
```

Usage (line 267):
```typescript
return json.data
  .filter((item: unknown) => isValidForeignFlowItem(item))  // ← SILENT FILTER
  .map((item: any) => ({...}));
```

**Problem:** If VPS returns 30 items but item[5] has `code: 123` (number instead of string), the filter silently discards it. Loop continues, writes only 29 items, returns `changes: 29` as if success. No error logged. Caller thinks: "success, 29 items written". But 30 items were sent. Over days, this gap accumulates.

**Why Tests Didn't Catch It:** Sprint 1566's `validateForeignFlowPayload()` is domain-pure (zero I/O). It was tested in isolation. But the fallback fetcher uses a different validation path (`isValidForeignFlowItem` inline filter). Tests for fallback (Sprint 1288) mock valid items; they don't test what happens when VPS sends invalid schema.

### Part 2: Understand the Cascading Failure

When silent filtering occurs:

```
Day 1: VPS sends [30 items with schema mismatch in item[5,10,15]]
       Filter discards 3 items → writes 27
       Logs: "changes: 27" ✓ success
       DB: 27 rows updated
       Cycle complete, assume success

Day 2: Same payload format (VPS hasn't changed)
       Same 3 items filtered → writes 27
       Logs: "changes: 27" ✓ success

...repeat for 10 days...

Day 11: Circuit breaker NOT open (writes succeed, just fewer rows)
       But vps_push_log shows all "ok" status
       Missing rows: 30 in total
       Alert latency increases (missing buy/sell signals)
       MARKET-SIDE error: "foreign flow data stale"
       But ROOT cause: VPS payload schema changed, silently filtering
```

### Part 3: Solution Design

**Strategy:** Fail loudly + unify validation.

1. **Replace silent filter with strict validation** in both paths:
   - VPS push endpoint: call `validateForeignFlowPayload()` from domain, reject on error (HTTP 400)
   - Fallback fetcher: call `validateForeignFlowPayload()`, reject on error (log WARN, skip primary)

2. **Reject partial success:**
   - If any items fail validation, return error (don't write partial data)
   - This forces VPS to fix schema, not work around it

3. **Log diagnostics for every rejection:**
   - Item index, field name, expected type, actual value
   - Example: `"Item 5: code expected string, got 123 (type: number)"`

4. **Add circuit breaker for validation errors:**
   - If 5+ validation errors in succession, open breaker (same as DB errors)
   - Signals to downstream: "data quality issue, not a timeout"

## Proposed Solution Details

### Option A: Strict Validation + Fail Loudly (**RECOMMENDED**)

**Why this is the right fix:**

1. **Eliminates silent filtering** — validates all items, rejects none
2. **Breaks the cascading failure loop** — VPS payload issues are caught on day 1, not day 11
3. **Uses existing validator** — `validateForeignFlowPayload()` already implemented in Sprint 1566, just not called from fetcher
4. **Works with both entry points** — POST endpoint and fallback fetcher use the same validator
5. **Minimal code change** — replace 2–3 lines (the silent filter) with 1 call to validator
6. **Backward compatible with VPS** — if VPS payload is already correct schema, no change needed

**Implementation:**

#### Change 1: foreignFlowFetcher.ts

**Before:**
```typescript
async function fetchPrimaryVpsEndpoint(...): Promise<WriteForeignFlowItem[] | null> {
  const json = (await response.json()) as { data?: unknown };
  if (!Array.isArray(json.data)) {
    throw new Error("Invalid response format: expected .data array");
  }

  // ← SILENT FILTER (current code)
  return json.data
    .filter((item: unknown) => isValidForeignFlowItem(item))
    .map((item: any) => ({
      code: item.code,
      date: item.date,
      foreignBuyVol: item.foreignBuyVol,
      foreignSellVol: item.foreignSellVol,
      putThroughVol: item.putThroughVol ?? 0,
    }));
}
```

**After:**
```typescript
async function fetchPrimaryVpsEndpoint(...): Promise<WriteForeignFlowItem[] | null> {
  const json = (await response.json()) as { data?: unknown };
  if (!Array.isArray(json.data)) {
    throw new Error("Invalid response format: expected .data array");
  }

  // ← STRICT VALIDATION (new code)
  const { validateForeignFlowPayload } = await import("../../domain/services/market-data/foreignFlowValidator.js");
  const validationResult = validateForeignFlowPayload(json.data);

  if (validationResult.errors.length > 0) {
    // Fail loudly with diagnostic details
    const errorSummary = validationResult.errors
      .slice(0, 5) // Limit to first 5 errors
      .map(e => `Item ${e.itemIndex}: ${e.field} — ${e.reason}`)
      .join("; ");
    throw new Error(`VPS payload validation failed: ${errorSummary}. Total errors: ${validationResult.errors.length}`);
  }

  // All items validated; no filtering needed
  return validationResult.valid;
}
```

**Before:**

const json = (await response.json()) as { data?: unknown };

**After:**
```typescript
const json = (await response.json()) as { data?: unknown };
if (!Array.isArray(json.data)) {
  return res.writeHead(400), res.end(JSON.stringify({ error: "expected .data array" }));
}

// ← STRICT VALIDATION (new code)

    status: "error",

    error: "Validation failed",
    details: errorSummary,
    totalErrors: validationResult.errors.length,

}

// All items validated
const { changes } = await writeForeignFlowToOhlcv(validationResult.valid);
logVpsPush({ service: "foreign-flow", itemsCount: changes, status: "ok" });
```

#### Change 3: Update fetchForeignFlowWithFallback to handle validation errors

When `fetchPrimaryVpsEndpoint()` throws a validation error, catch it and log with context:

```typescript
try {
  const result = await breakers.foreignFlow.execute(async () => {
    return await fetchPrimaryVpsEndpoint(overrides?.fetchFn ?? fetch, 5000);
  });
  // ... (success path unchanged)
} catch (err) {
  const errMsg = err instanceof Error ? err.message : String(err);

  // ← Log diagnostic if it's a validation error
  if (errMsg.includes("validation failed")) {
    logger.warn("[fallback] VPS payload schema validation failed", {
      error: errMsg,
      timestamp,
      hint: "Check VPS API response format — schema may have changed",
    });
  } else {
    logger.warn("[fallback] primary endpoint failed", { error: errMsg });
  }
}
```

### Why Not Other Options

**Option B: Add validation to circuit breaker (distinguish parse errors from network errors)**
- Would require new circuit breaker state ("validation_failed")
- Doesn't fix the root cause (silent filtering still happens)
- Adds complexity without solving the silent filter bug

**Option C: Add retry logic with exponential backoff**
- Assumes the error is transient (it's not; schema mismatch is persistent)
- VPS will keep sending invalid payload, retry will keep failing
- Wastes cycles

**Option D: Implement a dead-letter queue for failed items**
- Expensive: requires new DB table, cleanup logic, UI to review
- Doesn't fix the root cause (validation error should be caught at ingest, not stored separately)

## Prevention Checklist (for future foreign flow changes)

**To avoid repeating this bug:**

1. **All entry points must use the same validator** — no custom type guards that filter silently
2. **Fail loudly on schema errors** — reject invalid items, log diagnostics, don't filter
3. **Test both valid and invalid payloads** — test suite must include schema violation cases
4. **Log error diagnostics** — item index + field name + expected type + actual value
5. **Document validation rules** — keep `foreignFlowValidator.ts` as SSOT for schema
6. **Review circuit breaker logs** — if validation errors are high, check VPS API schema (not a network issue)
