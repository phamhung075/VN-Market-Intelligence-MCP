## Functional Requirements

### FR-1: DB isolation — set DB_PATH=:memory: before all imports

- Description: Add `process.env["DB_PATH"] = ":memory:";` as the absolute first line of `src/__tests__/137-fix-alert-pipeline.test.ts`, before all `import` statements.
- Input: File as currently written (line 1 is the JSDoc comment block).
- Output: File with `process.env["DB_PATH"] = ":memory:";` on line 1, JSDoc comment shifted to line 3.
- Business rule: Bun evaluates `process.env` assignments before module resolution when placed before static imports only if the assignment precedes all imports at the top of the file. Dynamic `import()` calls inside `runIntelligenceCycle` resolve `getDb()` via `schema.js` — which reads `process.env["DB_PATH"]` at open time. Without the override, `schema.js` opens the production SQLite file, triggers WAL replay, and each test hits the 30s `CYCLE_TIMEOUT`.
- Pattern reference: `src/__tests__/1192-*.test.ts` already uses this pattern (confirmed existing convention).
- DDD layer: test (no production code touched)

### FR-2: Inject getRecentAlertHistoryFn in all 4 Step E test fixtures

- Description: Add `getRecentAlertHistoryFn: async () => []` to every `runIntelligenceCycle(...)` call in the Step E describe block.
- Input: The 4 Step E test fixtures in the `"Task 137 — Step E: alerts flow through to sendAlertsFn"` describe block (lines 270–456).
- Output: All 4 `runIntelligenceCycle` calls include `getRecentAlertHistoryFn: async () => []` in their deps object.
- Business rule: When `getRecentAlertHistoryFn` is absent, step E falls through to the `else` branch at `intelligenceCycleJob.ts` lines 820-848, which calls `getCooldownDb()` — a live `getDb()` call that opens the production SQLite file even after FR-1 is applied. Injecting the stub short-circuits the fallthrough entirely.
- Affected fixtures (by test name — all 4 in the Step E describe block):
  1. "passes DB alerts to sendAlertsFn and returns correct count (AC-1)" — lines 282–298
  2. "marks alerts as notified_telegram = 1 after successful send (AC-1)" — lines 315–331
  3. "second cycle sends 0 alerts after first marks them notified (AC-1 idempotency)" — lines 347–363
  4. "does not mark alert when sendAlertsFn returns 0 (AC-2)" — lines 383–399
- Note: The 5th test "telegramAlertsSent = 0 when no unnotified HIGH/CRITICAL alerts exist" (lines 409–428) and the 6th test "Step E runs unconditionally" (lines 430–455) already provide `readUnnotifiedAlertsFn: async () => []` — they do NOT provide `getRecentAlertHistoryFn`. These two also need the injection to prevent the real-DB fallthrough.
- Revised affected fixture count: all 6 tests in the Step E describe block require the injection (tests 5 and 6 were previously borderline — they supply no alerts so the cooldown loop body never executes, but injecting the stub is still correct defensive isolation).
- DDD layer: test (no production code touched)
