status: READY_FOR_ARCHITECT

I want to review the Telegram MARKET alerts and briefings that fired while I slept (GMT+7 market hours = 02:00-09:00 France time),

## Functional Requirements

### FR-1: market_messages SQLite table

- Description: Add a new `market_messages` table to `src/infrastructure/db/schema.ts` (inside `initDatabase()`). The table records every message sent to the MARKET channel with enough metadata for the user to reconstruct context and post a verdict.
- Input: N/A — DDL only
- Output: Table created on `initDatabase()` call

Exact DDL:

```sql
CREATE TABLE IF NOT EXISTS market_messages (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  from_agent   TEXT    NOT NULL,
  message_type TEXT    NOT NULL,
  ticker       TEXT,
  content      TEXT    NOT NULL,
  sent_at      TEXT    NOT NULL DEFAULT (datetime('now')),
  verdict      TEXT,
  verdict_note TEXT,
  reviewed_at  TEXT
);

CREATE INDEX IF NOT EXISTS idx_mm_sent_at    ON market_messages(sent_at DESC);
CREATE INDEX IF NOT EXISTS idx_mm_from_agent ON market_messages(from_agent);
CREATE INDEX IF NOT EXISTS idx_mm_verdict    ON market_messages(verdict);
CREATE INDEX IF NOT EXISTS idx_mm_ticker     ON market_messages(ticker);
```

Column definitions:

| Column       | Type    | Nullable | Description |
|--------------|---------|----------|-------------|
| id           | INTEGER | NOT NULL | Auto-increment primary key |
| from_agent   | TEXT    | NOT NULL | Identifies the sender: one of the canonical values in the `FROM_AGENT` registry (see FR-2) |
| message_type | TEXT    | NOT NULL | Categorises the message content: one of the canonical values in the `MESSAGE_TYPE` registry (see FR-2) |
| ticker       | TEXT    | NULL     | Stock ticker if the message is stock-specific (e.g. "VCB"); NULL for market-wide messages (briefings, digests) |
| content      | TEXT    | NOT NULL | Full text of the message as sent to Telegram (may be multi-chunk; full join of all chunks) |
| sent_at      | TEXT    | NOT NULL | ISO 8601 UTC timestamp of the send attempt, default `datetime('now')` |
| verdict      | TEXT    | NULL     | Human label: `"signal"` or `"noise"`. NULL = unreviewed |
| verdict_note | TEXT    | NULL     | Optional free-text annotation from the user (e.g. "VCB did drop 3% next session") |
| reviewed_at  | TEXT    | NULL     | ISO 8601 UTC timestamp when the verdict was set |

Verdict constraint: only `"signal"` and `"noise"` are valid verdict values. Enforced in the store layer (not a SQLite CHECK constraint — avoids schema migration pain if values expand in Sprint 069+).

- Business rule: the table is append-only from the writer side. Only `review_market_message` (FR-5) mutates existing rows (verdict columns). No row is ever deleted by the system.
- DDD layer: infrastructure (`src/infrastructure/db/schema.ts`)

### FR-3: marketMessageStore — INSERT and query helpers

- Description: Create `src/infrastructure/db/marketMessageStore.ts` with the CRUD functions that all callers use. This module is the single write owner of `market_messages`. It accepts an explicit `db` parameter throughout (injectable for tests).
- Input: bun:sqlite Database, message metadata
- Output: inserted row id (INSERT), typed row arrays (queries)

```ts
/** Shape of a row returned by the query helpers */
export interface MarketMessageRow {
  id: number;
  from_agent: string;
  message_type: string;
  ticker: string | null;
  content: string;
  sent_at: string;
  verdict: string | null;
  verdict_note: string | null;
  reviewed_at: string | null;
}

/**
 * Insert a new market_messages row.
 * Best-effort: never throws — callers (sendTelegramMarket wrapper) must not
 * have their primary flow broken by a DB failure.
 *
 * @returns inserted row id, or 0 on failure
 */
export function insertMarketMessage(
  db: Database,
  params: {
    from_agent: MarketMessageAgent | string;
    message_type: MarketMessageType | string;
    ticker?: string | null;
    content: string;
  },
): number

/**
 * Return unreviewed rows (verdict IS NULL), newest first.
 * Optionally filtered by ticker.
 *
 * @param limit  - max rows to return (1-100, default 20)
 * @param ticker - when provided, filter to this ticker only
 */
export function getUnreviewedMarketMessages(
  db: Database,
  limit?: number,
  ticker?: string | null,
): MarketMessageRow[]

/**
 * Set the verdict on a row. Idempotent — calling again overwrites the
 * previous verdict.
 *
 * @returns true if the row existed and was updated, false if id not found
 */
export function reviewMarketMessage(
  db: Database,
  id: number,
  verdict: "signal" | "noise",
  note?: string | null,
): boolean
```

Exact SQL for `insertMarketMessage`:

```sql
INSERT INTO market_messages (from_agent, message_type, ticker, content, sent_at)
VALUES (?, ?, ?, ?, datetime('now'))
```

Exact SQL for `getUnreviewedMarketMessages` (no ticker filter):

```sql
SELECT id, from_agent, message_type, ticker, content, sent_at,
       verdict, verdict_note, reviewed_at
FROM market_messages
WHERE verdict IS NULL
ORDER BY sent_at DESC
LIMIT ?
```

Exact SQL for `getUnreviewedMarketMessages` (with ticker filter):

```sql
SELECT id, from_agent, message_type, ticker, content, sent_at,
       verdict, verdict_note, reviewed_at
FROM market_messages
WHERE verdict IS NULL
  AND ticker = ?
ORDER BY sent_at DESC
LIMIT ?
```

Exact SQL for `reviewMarketMessage`:

```sql
UPDATE market_messages
SET verdict = ?,
    verdict_note = ?,
    reviewed_at = datetime('now')
WHERE id = ?
```

- Business rule: `insertMarketMessage` is wrapped in a try/catch inside its implementation body. The caller (`sendTelegramMarket`) must be able to call it fire-and-forget without any error propagation.
- DDD layer: infrastructure (`src/infrastructure/db/marketMessageStore.ts`)

### FR-4: Auto-INSERT on every sendTelegramMarket() call

- Description: Modify `sendTelegramMarket()` in `src/infrastructure/notifiers/telegram.ts` to INSERT a row into `market_messages` after every successful send. The INSERT is best-effort and must not change the function's return type or error behaviour.

Implementation contract:

```ts
export async function sendTelegramMarket(
  text: string,
  options: SendTelegramOptions & {
    /**
     * Metadata for market_messages persistence.
     * When omitted, defaults apply (see below).
     */
    persist?: {
      from_agent?: MarketMessageAgent | string;   // default: "unknown"
      message_type?: MarketMessageType | string;  // default: "unknown"
      ticker?: string | null;                     // default: null
    };
  } = {},
): Promise<boolean>
```

Behaviour after `coreSend()` returns:

1. If `result.ok === false`: no INSERT (message was not delivered; no point persisting).
2. If `result.ok === true`: call `insertMarketMessage(db, { from_agent, message_type, ticker, content: text })` wrapped in try/catch. Log a warning on failure but DO NOT change the return value.
3. The `db` reference is obtained via `getDb()` inside the try block — same pattern as `sendTelegramBug`.

Default values when `options.persist` is omitted or fields are undefined:
- `from_agent` → `"unknown"`
- `message_type` → `"unknown"`
- `ticker` → `null`

Callers that do NOT pass `persist` continue to work without change (fully backward-compatible — all existing call sites remain valid TypeScript).

- Business rule: only successful sends are persisted. A Telegram API error must not create a `market_messages` row because the user never received the message.
- DDD layer: infrastructure (`src/infrastructure/notifiers/telegram.ts`)

### FR-9: Calibration engine connection (read path only)

- Description: The `market_messages` verdict corpus is not consumed by the calibration engine in Sprint 068. The connection is defined here as a data contract so Sprint 069 can implement it without revisiting the schema.

Sprint 065 built the calibration engine around `prediction_claims` (resolved Polymarket claims with Brier scores). The `market_messages` verdicts extend this with human labels on system-generated alerts, covering:
- Alerts that fired but the underlying move did not materialise (`verdict = "noise"`)
- Alerts that fired and correctly predicted a move (`verdict = "signal"`)

The Sprint 069 calibration enhancement will:
1. Join `market_messages` (where `verdict IS NOT NULL AND message_type = 'alert' AND ticker IS NOT NULL`) with `market_prices_history` to compute an outcome score.
2. Feed these additional resolved claims into `calibrationReportJob.ts`.

This sprint delivers the write path (persist + label). The read path (score computation) is OUT OF SCOPE for Sprint 068.

- Business rule: no schema changes are needed in Sprint 069 — the `market_messages` table design is forward-compatible with the calibration join described above.
- DDD layer: N/A — design note only

## Non-Functional Requirements

- Performance: `insertMarketMessage` is a single parameterized INSERT with no joins. Expected < 1ms on local SQLite. The MARKET channel sends ~5-20 messages per day — no batching needed.
- Atomicity: `sendTelegramMarket` does not use a transaction wrapping the Telegram send + DB INSERT. The DB write is best-effort post-send. A crash between send and INSERT produces a lost row — acceptable (the message was sent; the user saw it).
- Data freshness: `get_unreviewed_market_messages` reads live rows — no caching, no TTL.
- Language: tool descriptions in English (consistent with other MCP tools). Output text bilingual: English structure, Vietnamese content preserved as-is from stored `content`.
- Test isolation: `marketMessageStore.ts` accepts `db` as a parameter throughout — no global singletons in the store module. Tests use `:memory:` DB.
- Backward compatibility: existing callers of `sendTelegramMarket` that do not pass `persist` continue to compile and run without change. The `persist` option is fully optional with safe defaults.

## Edge Cases and Data Quality

- [ ] Large content: a morning briefing can be ~3000 characters. `content` is TEXT with no length limit in SQLite — store the full string. Chunked sends (multi-part messages) are joined into one row using the full original `text` argument (before `splitMessage()` splits it). The DB row represents the logical message, not the Telegram chunks.
- [ ] Telegram send fails: `result.ok === false` from `coreSend()` — no INSERT performed. The function returns `false` as before.
- [ ] DB not initialised at startup: `getDb()` / `initDatabase()` has not been called yet when the first send fires. Guard: `insertMarketMessage` calls `getDb()` which itself creates the DB if absent; `initDatabase()` is called at server startup in `index.ts` before any scheduler job runs. This ordering is already established.
- [ ] Concurrent writes: SQLite WAL mode is enabled at startup (`PRAGMA journal_mode = WAL`). Concurrent inserts from multiple scheduler jobs are serialised safely by WAL — no additional locking needed.
- [ ] `review_market_message` called with unknown id: `reviewMarketMessage` returns `false`. The MCP tool returns `"Message {id} not found."`.
- [ ] `verdict` value outside `"signal"` | `"noise"`: rejected by the Zod schema in the MCP tool before reaching the store. The store itself also validates at runtime and throws if an unexpected value is passed.
- [ ] `ticker` column for briefings: set to `null` for market-wide messages (morning briefing, evening summary, alert digest). Set to the stock code for per-stock alerts.
- [ ] `content` for multi-chunk messages: store the full `text` argument (the pre-split original). Do not store chunks separately.
- [ ] Growth / retention: the table is unbounded. At 20 messages/day, 1 year = ~7300 rows. Each row ~1KB content = ~7MB/year. No auto-purge in Sprint 068. Retention policy is deferred to a future sprint.
- [ ] `weatherCheckJob` sends via dynamic import — it already destructures `{ sendTelegramMarket }` from the module. Passing `persist` requires updating the destructured call. This is low-value metadata (`weather` type, no ticker) but should still be updated for completeness.
