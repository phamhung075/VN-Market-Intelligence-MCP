# REQ-065: Prediction Claim Resolution Loop

status: READY_FOR_ARCHITECT
sprint: 065
po_vision: Fix the broken prediction engine feedback loop so calibration has real data

## User Story

As a Vietnamese stock investor using Claude,
I want the prediction engine to actually resolve its forward claims and learn from the results,
So that the system's agent calibration scores reflect real predictive accuracy over time.

## Bug Analysis

### Root Cause Chain

The calibration subsystem is completely idle due to two compounding defects:

**Defect 1 — `create_prediction_claim` hardcodes `target_price: null`**
File: `src/interface/mcp/tools/evidenceTools.ts` line 339
```
target_price: null,   // hardcoded — never derived from actual price
```
Every claim ever inserted has `target_price = NULL` in the database.

**Defect 2 — `evaluateOutcome()` returns `null` for any `null` target_price**
File: `src/scheduler/predictionResolutionJob.ts` lines 62-63
```typescript
function evaluateOutcome(actualPrice, direction, targetPrice) {
  if (targetPrice == null) return null;   // all claims fall here
  ...
}
```
With `targetPrice = null`, the function immediately returns `null`. Back in the
resolution loop (line 211-214), `outcome === null` causes `result.skipped++` and
`continue` — the claim is never resolved. The calibration loop is permanently frozen.

**Downstream impact:**
- `calibration_snapshots` table stays empty forever
- `get_calibration_report` returns "no data yet" on every call
- Agent 08 (Prediction Synthesizer) gets no feedback signal
- `evidence_likelihood_ratios` cannot update because Brier scores never arrive
- The entire feedback loop from Sprint 059–060 is non-functional

## Functional Requirements

### FR-1: Add `expected_move_pct` parameter to `create_prediction_claim`

- Description: The tool must accept a new required numeric parameter `expected_move_pct`
  representing the expected percentage move. The tool then looks up the latest close price
  from `daily_ohlcv` and computes an absolute `target_price`.
- Input:
  - `expected_move_pct`: `number`, range `0.001` to `0.50` (0.1% to 50%). Zod schema:
    `z.number().min(0.001).max(0.5).describe(...)`.
  - `direction` (new required field, type `"bullish" | "bearish"`): determines whether
    to add or subtract the expected move. Zod schema: `z.enum(["bullish", "bearish"])`.
  - All existing parameters retained: `stock`, `claim_text`, `probability`,
    `horizon_days`, `resolution_criteria`.
- Output: confirmation text including `target_price` in VND and `creation_price` in VND.
- Business rule:
  - Fetch latest close: `SELECT close FROM daily_ohlcv WHERE code = ? ORDER BY date DESC LIMIT 1`
  - If no row found: return error text `"No price data found for {ticker} — cannot compute target_price"`. Do NOT insert the claim.
  - `target_price` computation:
    - `bullish`: `target_price = creation_price * (1 + expected_move_pct)`
    - `bearish`: `target_price = creation_price * (1 - expected_move_pct)`
  - Round `target_price` to nearest integer (VND trades at whole numbers; `Math.round()`).
  - `creation_price` (the fetched close) is stored in the new `creation_price` column.
  - `direction` from the new tool parameter replaces the hardcoded `"bullish"` default.
- DDD layer: interface (MCP tool handler in `evidenceTools.ts`)

### FR-2: Add `creation_price` column to `prediction_claims` schema

- Description: Store the price at claim-creation time so the direction-only resolution
  fallback (FR-3) has a baseline. The column is nullable for migration safety — all
  legacy rows that existed before this sprint have `creation_price = NULL`.
- Input: populated by `insertPredictionClaim()` at insert time.
- Output: `creation_price REAL` column visible in all store read functions.
- Business rule:
  - DDL: `creation_price REAL` (no NOT NULL constraint — nullable for legacy rows).
  - Added via `ALTER TABLE prediction_claims ADD COLUMN creation_price REAL` in the
    `initDb()` migration guard (safe to run multiple times with `IF NOT EXISTS` pattern
    using a try/catch around the ALTER).
  - `insertPredictionClaim()` in `predictionClaimStore.ts` must accept `creation_price`
    in `PredictionClaimInput` (optional, `number | null`, default `null`) and bind it
    in the INSERT statement.
  - `PredictionClaimRow` and `ClaimDbRow` interfaces must include `creation_price: number | null`.
- DDD layer: infrastructure (`predictionClaimStore.ts`, `schema.ts`)

### FR-3: Fix `evaluateOutcome()` — direction-only fallback for null `target_price`

- Description: When `target_price` is null (all legacy claims), resolution falls back
  to comparing `close_on_resolution_date` against `creation_price`. If `creation_price`
  is also null (pre-sprint-065 legacy rows that predate FR-2), the claim is skipped.
- Input: `actualPrice: number`, `direction: string`, `targetPrice: number | null`,
  `creationPrice: number | null` (new parameter).
- Output: `0 | 1 | null`
- Business rule (updated decision table):

  | `target_price` | `creation_price` | direction | result               |
  |----------------|-----------------|-----------|----------------------|
  | non-null       | any             | bullish   | `actual >= target ? 1 : 0` |
  | non-null       | any             | bearish   | `actual <= target ? 1 : 0` |
  | null           | non-null        | bullish   | `actual > creation_price ? 1 : 0` |
  | null           | non-null        | bearish   | `actual < creation_price ? 1 : 0` |
  | null           | null            | any       | `null` (skip)        |
  | any            | any             | neutral   | `null` (skip)        |

  Note: direction-only uses strict inequality (`>` / `<`). Target-price mode uses
  inclusive inequality (`>=` / `<=`) as before.

- The resolution loop must pass `claim.creation_price ?? null` as the fourth argument.
- DDD layer: scheduler (`predictionResolutionJob.ts`)

### FR-4: Pass `creation_price` through resolution loop

- Description: The resolution loop in `runPredictionResolution()` must read
  `claim.creation_price` and forward it to the updated `evaluateOutcome()`.
- Input: `PredictionClaimRow` now includes `creation_price`.
- Output: no change to `resolveClaim()` interface — `creation_price` is read-only context.
- Business rule: No other changes to the loop. Existing retry window logic (5 days),
  `markClaimUnresolvable()`, and `recordJobRun` wrapper are untouched.
- DDD layer: scheduler (`predictionResolutionJob.ts`)

## Non-Functional Requirements

- Performance: `daily_ohlcv` has index `idx_daily_ohlcv_code_date ON daily_ohlcv(code, date DESC)`. The price lookup in FR-1 is a single `LIMIT 1` scan — O(log n).
- Migration safety: `ALTER TABLE ... ADD COLUMN` is wrapped in try/catch. If the column already exists (re-run of `initDb()`), the error is swallowed silently.
- Data freshness: `creation_price` reflects the most recent VPS-pushed OHLCV close at claim creation time. The VPS pushes prices intraday; stale data risk is accepted (no requirement to guarantee same-day price).
- Language: tool output text in English (consistent with existing tool responses).
- Type safety: `bun tsc --noEmit` must pass after all changes. `PredictionClaimInput`, `PredictionClaimRow`, and `ClaimDbRow` interfaces must be updated consistently.

## Edge Cases & Data Quality

- [ ] No OHLCV row for ticker at claim time: FR-1 returns error, no insert. Agent must handle the error text response gracefully.
- [ ] Vietnamese stock prices are integers in VND (e.g., VNM = 68,500 VND). `Math.round()` ensures no fractional prices are stored.
- [ ] Legacy claims with `target_price = NULL` and `creation_price = NULL` (rows inserted before this sprint): `evaluateOutcome()` returns `null` → skipped. These claims accumulate in the "skipped" counter indefinitely. Acceptable — they cannot be resolved without a baseline.
- [ ] `expected_move_pct = 0` edge case: Zod min is `0.001` so zero is rejected at the schema layer.
- [ ] `direction = "bearish"` with `expected_move_pct = 0.5`: target = `creation_price * 0.5`. Valid range — no additional guard needed.
- [ ] `ALTER TABLE` re-run guard: if `initDb()` is called twice (e.g., in tests), the second ALTER must not throw. Use try/catch pattern matching existing migration guards in `schema.ts`.
- [ ] `horizon_days` union of `5 | 10 | 20`: unchanged. `resolution_date` is already computed correctly from today + horizon_days.
- [ ] UNIQUE constraint `(stock, claim_text, resolution_date)`: unchanged. Duplicate detection still fires correctly regardless of `creation_price` or `target_price`.

## Implementation Notes for Architect

### Schema migration pattern

`schema.ts` already contains migrations wrapped in try/catch (see Sprint 063 insider
transactions migration). Use the same pattern:

```typescript
try {
  db.exec(`ALTER TABLE prediction_claims ADD COLUMN creation_price REAL`);
} catch {
  // column already exists — safe to ignore
}
```

Place this block immediately after the existing `prediction_claims` CREATE TABLE block
(around line 1289 in schema.ts).

### `insertPredictionClaim` INSERT statement

The INSERT must be extended from 7 bound parameters to 8:

```sql
INSERT OR IGNORE INTO prediction_claims
  (stock, agent_id, claim_text, direction, target_price,
   resolution_date, confidence, creation_price)
VALUES (?, ?, ?, ?, ?, ?, ?, ?)
```

### `evaluateOutcome` new signature

```typescript
function evaluateOutcome(
  actualPrice: number,
  direction: string,
  targetPrice: number | null,
  creationPrice: number | null,
): 0 | 1 | null
```

### Tool parameter additions

The two new Zod fields to add to `create_prediction_claim`:

```typescript
direction: z.enum(["bullish", "bearish"])
  .describe("Direction of the prediction"),
expected_move_pct: z.number().min(0.001).max(0.5)
  .describe("Expected percentage move, e.g. 0.05 for 5%"),
```

The existing `resolution_criteria` parameter is validated but not stored (no schema
column for it currently). This is pre-existing behaviour — do not add a column for
it in this sprint.

### Test file scope

The single test file `065-prediction-resolution-loop.test.ts` must cover:
- AC-1 through AC-8 above
- Use an in-memory SQLite database (`:memory:`) with `initDb()` for isolation
- Do not mock `daily_ohlcv` reads — insert real rows into the test DB
