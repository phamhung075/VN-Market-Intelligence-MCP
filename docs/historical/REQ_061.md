## Functional Requirements

### FR-1: VPS Script Extension — Poll Foreign Flow per Stock

- **Description:** Extend the VPS Singapore `fetch-prices.sh` bash script to also poll the VPS API for daily foreign trading totals for each watchlist stock. The script already calls `bgapidatafeed.vps.com.vn` for prices; the same host exposes foreign flow data per stock via a separate endpoint. After each price-fetch loop iteration, the script fetches foreign flow for the same stock list and POSTs a batch to the new `/api/push-foreign-flow` MCP endpoint.
- **VPS API endpoint for foreign flow (to be confirmed by Architect — see Blocker B1):**
  - Expected form: `GET https://bgapidatafeed.vps.com.vn/getliststockdata/{symbols}` or a dedicated foreign flow path
  - Fields of interest per stock: `fRoom` (foreign room remaining), `fBuyVol` / `fSellVol` (today's foreign buy/sell volume), or `fCurrentRoom` / `fTotalRoom` / `foreignPercent`
  - The Architect must confirm the exact field names by inspecting VPS API responses from the Singapore server
- **Input (script side):** Watchlist stock codes (same list used for prices, sourced from `GET /api/get-stock-codes`)
- **Output (script side):** `POST /api/push-foreign-flow` with JSON body — see FR-2 for payload schema
- **Fetch frequency:** Once per price-fetch loop iteration — effectively every 5 minutes during VN market hours (09:00–15:30 GMT+7 Mon–Fri). Outside market hours, foreign flow is static (no trading), so the script may skip foreign flow polls outside trading hours or send the last-known values once at market close.
- **Deployment target:** VPS Singapore — the existing `vn-price-fetch.service` systemd service runs `fetch-prices-loop.sh`. The updated loop script calls foreign flow fetch after each price cycle.
- **Error handling in script:** If the foreign flow API call fails (HTTP error, timeout), log to stderr and continue — do not abort the price-fetch loop. Foreign flow is a secondary signal; price continuity is mandatory.
- **DDD layer:** infrastructure (VPS side) — `vps/fetch-prices.sh` and `vps/fetch-prices-loop.sh` (files live on VPS, not in the MCP repo — the Architect must specify the exact VPS path and update procedure)

### FR-2: `POST /api/push-foreign-flow` Endpoint

- **Description:** New HTTP endpoint on the MCP server that receives a batch of foreign flow records from the VPS proxy, validates them, and upserts into `vnstock_trading_stats`. Follows the exact same auth, logging, and error-handling pattern as the existing `POST /api/push-prices` endpoint in `src/interface/mcp/server.ts`.
- **Authentication:** Same `x-api-key` header check using `VPS_PUSH_API_KEY` env var — reuse the existing auth block verbatim.
- **Request payload:**

```json
[
  {
    "code": "VNM",
    "date": "2026-04-12",
    "foreign_volume": 15234000,
    "foreign_room": 412000000,
    "holding_ratio": 0.4887,
    "fetched_at": "2026-04-12T08:45:00Z"
  },
  ...
]
```

- **Field semantics:**
  - `code` — VN stock ticker, required
  - `date` — ISO date `YYYY-MM-DD`, VN calendar date of the trading session, required
  - `foreign_volume` — cumulative foreign volume held (not today's delta), shares, integer, required
  - `foreign_room` — remaining foreign ownership room in shares, integer, optional (null allowed)
  - `holding_ratio` — current foreign ownership as a decimal fraction (e.g. `0.4887` = 48.87%), optional (null allowed)
  - `fetched_at` — ISO 8601 UTC timestamp, optional (server uses `datetime('now')` if absent)

- **Upsert logic:** For each item in the array:
  ```sql
  INSERT OR REPLACE INTO vnstock_trading_stats
    (code, date, foreign_room, foreign_volume, current_holding_ratio, fetched_at)
    VALUES (?, ?, ?, ?, ?, ?)
  ```
  The `max_holding_ratio`, `avg_volume_2w`, `high_52w`, `low_52w`, `pct_from_high_52w`, `pct_from_low_52w` columns are NOT written by this endpoint — they remain from the existing `storeTradingStats` path (which is fed by the vnstockBridge Python fetcher). The upsert must NOT overwrite these columns if they already have values. Use `INSERT OR REPLACE` only on the five foreign-flow-specific columns; the Architect must decide between `INSERT OR REPLACE` (resets all columns) and a targeted `INSERT ... ON CONFLICT(code, date) DO UPDATE SET foreign_volume = ?, ...` (preserves non-foreign columns). Recommendation: use the targeted `DO UPDATE SET` form to avoid zeroing out price columns.
- **Response on success:** `{ "ok": true, "upserted": <count> }` with HTTP 200
- **Response on auth failure:** HTTP 401 `{ "error": "Unauthorized" }`
- **Response on bad payload:** HTTP 400 `{ "error": "Expected non-empty array" }` or `{ "error": "Invalid JSON" }`
- **Logging:** Call `logVpsPush({ service: "foreign-flow", itemsCount: count, status: "ok" })` on success. Call with `status: "error"` on failure. Reuses existing `vpsPushLogStore` — no new logging infra needed.
- **DDD layer:** interface — `src/interface/mcp/server.ts` (add the new `if (method === "POST" && pathname === "/api/push-foreign-flow")` block after the existing `push-prices` block)

### FR-3: `foreignFlowAlertJob.ts` — Daily 16:30 VN Market-Close Scan

- **Description:** A new scheduler job that runs daily at 16:30 VN time (09:30 UTC), 1 hour after market close. It scans all watchlist stocks, loads their `getForeignFlowHistory()`, calls `analyzeForeignFlow()`, and for each HIGH-severity signal: (a) inserts an alert row, (b) sends a WORK channel digest, and (c) calls `insertEvidenceFragment` to feed the prediction engine.
- **Cron schedule:** `30 9 * * 1-5` (09:30 UTC = 16:30 GMT+7, weekdays only)
  - Scheduled after VPS has had time to push the final 15:30 session data
  - The predictionResolutionJob runs at 16:30 UTC — no schedule conflict
- **Input:** All codes from the `watchlist` table
- **Processing per stock:**
  1. Call `getForeignFlowHistory(code, 10)` — returns up to 10 daily rows DESC
  2. If fewer than 2 rows returned (insufficient history), skip silently
  3. Call `analyzeForeignFlow(history)` — returns `ForeignFlowSignal | null`
  4. If signal is null or `severity !== "high"`, skip (no alert for MEDIUM/LOW — too noisy daily)
  5. For HIGH severity: proceed to steps 6–8
- **Step 6 — Insert alert row:**
  ```
  storeAlerts([{
    code,
    type: "foreign_flow",
    severity: "high",
    message: `[DÒNG TIỀN NGOẠI] ${code}: ${signal.reasoning}`,
    data: JSON.stringify({ signal }),
  }], db)
  ```
- **Step 7 — WORK channel digest (not MARKET):**
  - The job sends to WORK channel only, not MARKET. MARKET alerts for foreign flow are handled by the Alert Commander agent reading the alert rows via its existing signal check. This follows the pattern established in Sprint 054 (marketScanJob noise retirement): the scheduler inserts to DB + notifies WORK; the Alert Commander decides if/when to escalate to MARKET.
  - WORK digest format:
  ```
  [foreignFlowAlertJob] 2026-04-12 16:30 VN
  HIGH foreign flow signals: 3 stocks

  VNM: smart money accumulation — 4 consecutive net buy days, +285k shares (3d); foreign ownership up 0.8% over 5d
  FPT: smart money exit — 3 consecutive net sell days, -142k shares (3d)
  VCB: smart money accumulation — 3 consecutive net buy days, +201k shares (3d)

  Alert rows inserted. Alert Commander should escalate HIGH signals to MARKET.
  ```
  - If 0 HIGH signals, send a single-line WORK message: `[foreignFlowAlertJob] 2026-04-12 — no HIGH foreign flow signals today.`
- **Step 8 — Evidence fragment write (HIGH signals only):**
  ```
  insertEvidenceFragment(db, {
    stock: code,
    evidence_type: "foreign_flow_institutional",
    direction: signal.netFlowDirection === "net_buy" ? "bullish" : "bearish",
    magnitude: 0.8,
    confidence: 0.75,
    source_agent: "foreignFlowAlertJob",
    ttl_days: 5,
  })
  ```
  - `magnitude: 0.8` — foreign flow is a strong signal in VN markets
  - `confidence: 0.75` — cumulative volume data is reliable but lagged 1 day
  - `ttl_days: 5` — a 3-day streak has roughly 5 days of predictive relevance
  - `neutral` direction signals do not produce evidence fragments (only `net_buy` / `net_sell`)
- **Step 9 — recordJobRun:** Call `recordJobRun` wrapper (Task 1101 pattern) for cron health observability.
- **DDD layer:** scheduler — `src/scheduler/foreignFlowAlertJob.ts` (new file)

### FR-4: `get_foreign_flow` MCP Tool (+1 tool, 89 → 90)

- **Description:** On-demand MCP tool that returns the latest `ForeignFlowSignal` for a given stock code, plus a raw summary of the last N days of foreign volume history. Used by analysis agents (Alert Commander, Market Watcher) and directly by the user via Claude.
- **Tool name:** `get_foreign_flow`
- **Input schema:**
  ```
  code: string   — stock ticker, e.g. "VNM"
  days?: number  — history window, default 10, max 30
  ```
- **Processing:**
  1. Call `getForeignFlowHistory(code, days)` from `vnstockStore`
  2. If fewer than 2 rows: return "Insufficient foreign flow data for {code}. Data starts accumulating from first VPS push after deploy."
  3. Call `analyzeForeignFlow(history)` — returns `ForeignFlowSignal | null`
  4. Format and return text output
- **Output format (when data available):**
  ```
  Foreign Flow — VNM (last 10 days)

  Direction: net_buy | Severity: HIGH | Consecutive days: 4
  Net volume 3d: +285,000 shares | Net volume 5d: +412,000 shares
  Holding ratio change 5d: +0.80% (from 48.07% → 48.87%)

  Reasoning: smart money accumulation: 4 consecutive net buy days, total +285k shares (3d); foreign ownership up 0.8% over 5d

  Daily history (most recent first):
    2026-04-12: held=15,234,000  room=412,000,000  ratio=48.87%
    2026-04-11: held=14,949,000  room=412,285,000  ratio=48.07%
    2026-04-10: held=14,664,000  room=412,570,000  ratio=47.17%
    ...

  Data source: VPS Singapore proxy | Last updated: 2026-04-12T09:45:00Z
  ```
- **Output format (no data / all-zero columns, pre-deploy state):**
  ```
  Foreign Flow — VNM: no data available.
  All foreign_volume values are zero — VPS push not yet deployed or no data for this stock.
  Run get_foreign_flow after the VPS script update is deployed and at least one trading session has completed.
  ```
- **Business rule — zero detection:** If all rows returned by `getForeignFlowHistory` have `foreignVolume === 0`, the tool should output the "no data" message rather than running the analyzer (which would return `neutral` on zero deltas — misleading).
- **DDD layer:** interface — `src/interface/mcp/tools/foreignFlowTools.ts` (new file), registered in `src/interface/mcp/tools/registry.ts` and `src/interface/mcp/server.ts`
- **Tool count delta:** +1 (89 → 90)

### FR-5: Evidence Fragment Auto-Write for HIGH-Severity Events

- **Description:** HIGH-severity `ForeignFlowSignal` events must be written as evidence fragments to feed the prediction engine. This is implemented inside `foreignFlowAlertJob.ts` (FR-3, Step 8) — there is no separate file.
- **Evidence type string:** `"foreign_flow_institutional"` — a new soft-enum value (no DB constraint to update)
- **Direction mapping:**
  - `signal.netFlowDirection === "net_buy"` → `direction: "bullish"`
  - `signal.netFlowDirection === "net_sell"` → `direction: "bearish"`
  - `signal.netFlowDirection === "neutral"` → skip (HIGH+neutral is impossible given analyzer logic — HIGH requires a directional streak)
- **Magnitude and confidence rationale:**
  - `magnitude: 0.8`: foreign institutional flow is the highest-quality signal in VN markets (retail-dominated exchange where foreign buys signal informed money)
  - `confidence: 0.75`: data is accurate but reflects yesterday's session (T+0 settlement lag), so not 100% certainty
- **Integration with base rate computer:** The `baseRateComputationJob` (Sprint 059) already processes all `evidence_type` values including new ones — no changes needed there. The `evidence_likelihood_ratios` table will accumulate data for `"foreign_flow_institutional"` automatically after the first weekly Sunday run.
- **DDD layer:** scheduler — colocated in `src/scheduler/foreignFlowAlertJob.ts`

## Edge Cases and Data Quality

- [ ] **Zero foreign volume (pre-deploy state):** `getForeignFlowHistory` returns rows with `foreign_volume = 0`. The `get_foreign_flow` tool detects all-zero and returns the "no data" message. `foreignFlowAlertJob` calls `analyzeForeignFlow` on zero-delta arrays, which returns `severity: "low"` and skips silently — correct behavior.
- [ ] **Fewer than 2 rows in history (new stock or first deploy day):** `analyzeForeignFlow` returns null. Both `foreignFlowAlertJob` and `get_foreign_flow` handle null gracefully with a skip/message.
- [ ] **VPS API field name mismatch:** VPS API field names for foreign flow must be confirmed by Architect (Blocker B1). The bash script will need to extract the correct JSON keys. If field names differ from what the script author expects, the push will contain zeros — the system degrades silently to the pre-deploy state (no broken alerts, no crashes).
- [ ] **holding_ratio > 1.0 (data error):** VPS API sometimes returns holding ratio as a percentage (48.87) instead of a decimal (0.4887). The VPS script or the push endpoint must normalize: if `holding_ratio > 1`, divide by 100 before storing. Add a guard in the push endpoint: `if (item.holding_ratio > 1) item.holding_ratio /= 100`.
- [ ] **foreign_volume decreasing day over day:** This is valid — represents net sell. `analyzeForeignFlow` handles negative deltas correctly. Do not filter these out.
- [ ] **Weekend / holiday rows:** VPS does not push on weekends. The `vnstock_trading_stats` table will have gaps (no Saturday/Sunday rows). `analyzeForeignFlow` computes streaks by array position, not by calendar continuity — a gap in trading days does not break the streak logic. This is correct behavior: a streak means N consecutive trading sessions, not N calendar days.
- [ ] **UNIQUE(code, date) conflict on re-push:** The endpoint uses `INSERT OR REPLACE` (or `ON CONFLICT DO UPDATE`). Re-pushing the same stock+date is safe — it overwrites with the latest values. This handles VPS script restarts mid-day.
- [ ] **Large foreign_volume numbers in Vietnamese format:** VPS API returns numbers as integers (not Vietnamese dot-formatted strings). No parsing complexity here — contrast with BCTC PDFs.
- [ ] **Alert Commander Hao 4 scoring:** The Sprint Goal mentions "Kinh Dich Hao 4 reading foreign flow". This is a Cowork agent concern (the `05-alert-commander.md` may use foreign flow signals in its Kinh Dich analysis). This is OUT of scope for this sprint's server-side implementation — no code changes to `kinhDich/` are needed. The Alert Commander can read `get_foreign_flow` results and incorporate them in its hexagram interpretation at the Cowork level.
- [ ] **`storeTradingStats` vs targeted upsert conflict:** The existing `storeTradingStats` function writes ALL columns of `vnstock_trading_stats` (including non-foreign fields). The new push endpoint writes only foreign-flow columns. If both run on the same row, the last writer wins. Since `storeTradingStats` is fed by the vnstockBridge Python fetcher (runs infrequently, based on staleness) and the new push runs every 5 minutes, there is a small risk of `storeTradingStats` overwriting foreign flow data with zeroes. The Architect must resolve this by using the `DO UPDATE SET` form targeting only the foreign-flow columns in the new push endpoint, not `INSERT OR REPLACE`.
