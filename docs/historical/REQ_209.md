# REQ_209 — Modular Monolith Refactor: Phase 1 Schema Split

## Business Context

`src/infrastructure/db/schema.ts` is 1,571 lines. Every agent task touching DB (schema changes, new tables, query debugging) forces a full load of all 1,571 lines even when the task only concerns a single domain. With 117 direct `getDb()` calls across 67 tool files and no module boundaries, context waste per task is ~80% for schema work and ~57% average across all agent tasks.

The architect has analyzed the codebase and proposed a 3-phase Modular Monolith refactor. Phase 1 (this sprint) addresses the highest-impact problem: schema size.

## Goal

Split `schema.ts` into 9 per-domain schema slice files. The main `schema.ts` becomes a thin orchestrator (~150 lines) that imports and calls each slice's `init` function. No file moves, no call-site changes — zero risk to existing code.

## Acceptance Criteria

### AC-1: Domain schema slices created
Nine slice files created under `src/infrastructure/db/`:

| File | Domain | Key tables |
|------|--------|-----------|
| `schema-market-data.ts` | Market data | `market_prices`, `market_prices_history`, `daily_ohlcv`, `commodity_prices`, `commodity_prices_history` |
| `schema-financial-reports.ts` | Financial reports | `financial_reports`, `balance_sheets`, `income_statements`, `cash_flows`, `financial_ratios` |
| `schema-news.ts` | News & analysis | `rag_analyses`, `news_sources`, `source_health` |
| `schema-alerts.ts` | Alerts | `alerts`, `alert_history`, `cooldown_state` |
| `schema-portfolio.ts` | Portfolio | `positions`, `portfolio_snapshots`, `portfolio_history` |
| `schema-briefings.ts` | Briefings | `market_messages`, `briefing_history` |
| `schema-macro.ts` | Macro | `macro_indicators`, `tracked_indicators`, `sbv_rates`, `prediction_signals` |
| `schema-sector.ts` | Sector intel | `sector_rotation`, `watchlist` |
| `schema-system.ts` | System | `cron_job_runs`, `system_logs`, `scheduler_locks`, `telegram_reports`, `change_log` |

Each slice exports one function: `initXxxSchema(db: Database): void`

### AC-2: schema.ts becomes thin orchestrator
`schema.ts` retains only:
- `getDb()` singleton
- `initDatabase()` that calls all 9 `initXxxSchema(db)` functions in order
- Imports of all 9 slice files
- Total: ≤200 lines

### AC-3: No call-site changes
All existing imports of `schema.ts` (`getDb`, `initDatabase`) continue to work unchanged. No other files modified except the 9 new slice files + `schema.ts`.

### AC-4: Each slice independently testable
Each slice file's `init` function must work when called with a fresh in-memory DB (`:memory:`). A new TDD test verifies this for all 9 slices.

### AC-5: TDD test GREEN
`src/__tests__/1527-schema-slices.test.ts` (new) covers:
- (a) Each of the 9 slices creates its expected tables when called alone on a blank DB
- (b) `initDatabase()` (full orchestrator) still initializes all tables correctly
- (c) No duplicate table creation error when `initDatabase()` called twice (idempotent DDL via `IF NOT EXISTS`)
- (d) `getDb()` singleton still returns same instance across calls

### AC-5: Quality gates
- `bun tsc --noEmit` clean
- Full test suite: ≥ current baseline pass count, 0 new failures
- `schema.ts` line count ≤ 200 (verified by test assertion)

## Out of Scope

- Phase 2: barrel `index.ts` per module (next sprint)
- Phase 3: full folder restructure into `src/modules/`
- Migrating 117 `getDb()` call sites
- Any new tables or schema changes

## Risk Notes

- DDL extraction must preserve exact column definitions, constraints, and index names — no silent schema drift
- All DDL must keep `IF NOT EXISTS` — already present in current schema, must not be stripped
- `kinhdich_readings` table: verify it belongs in `schema-system.ts` or a dedicated `schema-kinhdich.ts` — Architect to decide
- `scheduler_locks` moved to `initDatabase()` in Sprint 170 — must be in `schema-system.ts`, not re-split

## Dependencies

None. Phase 1 is purely additive — no production behavior changes.
