### Task 1328i — Vietnamese diacritics NFC normalization in `telegram.ts`

**File:** `apps/mcp-server/src/infrastructure/notifiers/telegram.ts`

**Injection point:** `coreSend()` function at line 158, before the `splitMessage(text)` call
(line 178). Add NFC normalization:

```typescript
// Normalize Vietnamese diacritics to NFC before sending
const normalizedText = text.normalize("NFC");
const chunks = splitMessage(normalizedText);
```

**Background:** Vietnamese text composed on macOS may use NFD (decomposed) form for diacritical
marks (e.g. `ă` as two codepoints: `a` + combining breve). Telegram renders NFD inconsistently —
some clients show correct glyphs, others show raw combining characters. NFC normalization
consolidates to precomposed form, ensuring consistent display across Android/iOS/Web Telegram.

**Note:** `TelegramMessageFactory` already uses `Intl.Segmenter` for grapheme-aware truncation
(lines 24–47 of telegramMessageFactory.ts). NFC normalization should happen before the factory
methods are called, not inside them, to avoid double-normalization. The correct injection point
is at the send boundary in `coreSend()`.

**DDD layer:** infrastructure/notifiers

**Acceptance criteria:**
- `"ă".normalize("NFD")` (2 codepoints) sent through `coreSend()` arrives as `"ă".normalize("NFC")` (1 codepoint)
- Existing tests for `sendTelegramMarket/Work/Bug` continue to pass
- Test: mock `fetchFn`, pass NFD string, assert sent body contains NFC form
- No change to `TelegramMessageFactory` — normalization is upstream

## Edge Cases and Risks

### Vietnamese data quality

- **Diacritics in headlines:** `agentSignalsMajority` is ASCII only ("BUY"/"SELL"/"NEUTRAL") —
  no diacritics risk. But `headline` field in `ChainCatalystFindingData` may contain NFD-encoded
  Vietnamese from RSS feeds. NFC normalization in 1328i covers this at the send boundary.
- **Number formatting:** `newsSentiment` is a float [-1.0, 1.0] — not affected by Vietnamese
  locale. Safe.
- **Kinh Dich confidence:** Stored as integer [0, 100] in `alertPolicyChecker.ts` (confirmed in
  `WatchlistOpportunityInput.kinhDichConfidence`). Schema column is `REAL` (1328c) — compatible.

### Migration safety

- All three ALTER TABLE statements in 1328c use `try/catch` (matching existing pattern in
  schema-news.ts lines 73–93). Safe on existing production DB.
- No backfill needed — new columns default NULL, existing rows unaffected.
- `finding_data` JSON already stores arbitrary keys — existing consumers reading `finding_data`
  will not break when new fields are present.

### Conviction scorer backward compatibility

- `ConvictionInput` fields are all optional. Adding new optional fields is non-breaking.
- `enrichDimensionScores()` is a pure function — callers that do not call it get identical
  behavior to today.
- `WEIGHTS` sum must remain 1.0 — any rebalancing (Q1 above) requires explicit PO approval.

### Alert truncation risk (1328e)

- `TelegramMessageFactory.formatAlertMessage()` (telegramMessageFactory.ts line 82) truncates
  to 100 graphemes. If the conviction breakdown is passed through this method, it will be
  silently cut. The spec explicitly routes conviction output through `splitMessage()` instead.
  This must be enforced in code review.

### Three-channel routing (1328h)

- Alert Commander exclusivity rule is already in CLAUDE.md. 1328h codifies it into each agent
  prompt — no new enforcement mechanism, just documentation clarity.
- Risk: cowork agent files not yet read — routing may already be partially correct or incorrect.
  Architect must audit all cowork-*.md files before writing 1328h implementation.
