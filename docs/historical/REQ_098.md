# REQ-098: TA Alert Real-Time Delivery

status: READY_FOR_ARCHITECT
sprint: 098
po_vision: Close the TA alert delivery gap — RSI/BB alerts written every 15 min reach the user within 15 min, not 8+ hours later in the evening digest.

## User Story

As a Vietnamese stock investor using Claude,
I want RSI overbought/oversold and Bollinger Band breakout alerts delivered to my Telegram within 15 minutes of the signal firing,
So that I can act on intraday TA signals during the VN market session rather than reviewing them after close.

## Functional Requirements

### FR-1: Query unnotified TA alerts

- Description: Read all rows from the `alerts` table that have not yet been delivered and are of a TA alert type.
- Input: `alerts` table (SQLite, injected `db`)
- Output: Array of alert rows ordered by `triggered_at ASC`
- Business rule: Filter is `notified_telegram = 0 AND json_extract(signals_json, '$[0].type') IN ('ta_overbought', 'ta_oversold', 'ta_bb_breakout_up', 'ta_bb_breakout_down')`. Non-TA types (`position-danger`, `macro_deviation`, etc.) are never fetched. Parameterized SQL only — no string interpolation.
- DDD layer: scheduler (direct DB query — no alertStore import required; keeps the job self-contained)

### FR-2: Format a compact Vietnamese Telegram message

- Description: Render one Telegram message for the entire batch (all unnotified TA alerts in this cycle).
- Input: Array of alert rows from FR-1
- Output: Single UTF-8 string
- Business rule:
  - Header line: `"TA Alert [HH:MM VN]:"` where `HH:MM` is the Vietnam time formatted from `nowFn()` (`UTC+7`).
  - One line per alert row, format by `signals_json[0].type`:
    - `ta_overbought`      → `"{code}: RSI={value} quá mua"`
    - `ta_oversold`        → `"{code}: RSI={value} quá bán"`
    - `ta_bb_breakout_up`  → `"{code}: giá vượt BB trên — bứt phá tăng"`
    - `ta_bb_breakout_down`→ `"{code}: giá dưới BB dưới — bứt phá giảm"`
  - `code` is extracted from `json_extract(affected_actions_json, '$[0].code')`.
  - `value` (RSI) is extracted from `signals_json[0].message` or re-parsed from the stored message string — exact source must be consistent with the insert schema used by `taAlertScanJob.ts` (message field already contains the RSI number: `"VCB: RSI(14) = 74.2 — quá mua"`).
  - Cap at 10 alert rows per message to prevent oversized messages. If >10, send first 10 and log warning; remaining rows are still marked notified (they are already stale by next cycle).
  - No trailing newline.
- DDD layer: scheduler

### FR-3: Send batch Telegram message to market channel

- Description: Send the formatted message to `channel="market"`.
- Input: Formatted string from FR-2
- Output: Void (side effect: Telegram HTTP call)
- Business rule: Call injected `sendFn` (defaults to `sendTelegramMarket`). `from_agent: "ta-notifier"`, `message_type: "ta_alert"`. This job IS the delivery mechanism — sending to market channel is its sole purpose, consistent with `foreignFlowAlertJob` pattern.
- DDD layer: scheduler

### FR-4: Mark each alert notified after successful send

- Description: After `sendFn` resolves without throwing, mark every alert row in the batch `notified_telegram = 1`.
- Input: Array of alert IDs from FR-1
- Output: Updated rows in `alerts` table
- Business rule:
  - Execute `UPDATE alerts SET notified_telegram = 1 WHERE id = ?` per row — parameterized, one statement per row.
  - **Only execute after `sendFn` resolves successfully.** If `sendFn` throws, no rows are marked — they will be retried in the next 15-minute cycle.
  - Wrap each UPDATE in a per-row try/catch. One UPDATE failure does not stop others. Log a warning per failure.
- DDD layer: scheduler

### FR-5: Return job result summary

- Description: Return `{ sent: number, skipped: number }` after every run.
- Input: Execution outcome
- Output: `TaAlertNotifierResult` — `sent` = count of rows successfully marked `notified_telegram=1`; `skipped` = 0 in normal flow (WHERE clause excludes already-notified rows; field exists for future audit use).
- Business rule: Return `{ sent: 0, skipped: 0 }` with no Telegram call when FR-1 returns an empty array.
- DDD layer: scheduler

### FR-6: Register job in cron scheduler

- Description: Wire `taAlertNotifierJob.ts` into `jobs.ts` and update both registry files.
- Input: `src/scheduler/jobs.ts`, `docs/data/cron-registry.json`, `docs/data/project-stats.json`
- Output: Job fires every 15 minutes during VN market hours
- Business rule:
  - Cron expression: `*/15 2-8 * * 1-5` (matches `taAlertScanJob` and `bbAlertScanJob` window exactly — delivery job must run in same window as scan jobs).
  - Job name: `taAlertNotifierJob`.
  - `schedulerFileCount` incremented to **32** in both `cron-registry.json` and `project-stats.json`.
- DDD layer: scheduler

## Non-Functional Requirements

- Performance: Query touches only unnotified rows — index on `notified_telegram` is already present from prior schema work. Batch size cap (10 rows) prevents message truncation by Telegram API (4096 char limit).
- Data freshness: Job runs at same 15-min cadence as scan jobs. Maximum delivery latency = 15 min from alert insertion.
- Language: Vietnamese alert body (`quá mua`, `quá bán`, `bứt phá tăng`, `bứt phá giảm`). Header uses `"TA Alert"` (mixed — established pattern in codebase).
- Idempotency: `notified_telegram = 0` WHERE clause ensures no duplicate sends. If the job crashes after send but before UPDATE, the same alerts are re-sent on the next cycle (acceptable — better than silent drop).
- Error isolation: Per-row try/catch on UPDATE (FR-4). If `sendFn` throws the job returns without marking any rows. No retry loop inside the job — next cron tick handles it.

## Edge Cases & Data Quality

- [ ] Empty alerts table (no TA rows) → return `{ sent: 0, skipped: 0 }` silently, no Telegram
- [ ] `sendFn` throws network error → no rows marked, retry next cycle
- [ ] `signals_json` malformed / `$[0].type` returns NULL → row not matched by WHERE clause; never fetched
- [ ] `affected_actions_json` malformed / `$[0].code` is NULL → format line as `"(unknown): ..."` — log warning, still send
- [ ] Batch > 10 rows → send first 10, log warning with count of rows truncated, mark all 10 notified (remaining rows picked up next cycle)
- [ ] `notified_telegram` column missing from test DDL → test setup must include full alerts DDL (matches `src/__tests__/1133-foreign-flow-alert-job.test.ts` pattern)
- [ ] Job fires outside market hours (e.g., weekend cron misconfiguration) → empty query result, no send — safe
- [ ] Vietnamese number format in RSI value: value already formatted by `taAlertScanJob` as `rsi.toFixed(1)` → reuse stored `message` field from alert row directly instead of re-parsing `signals_json` to avoid double-formatting risk

## Acceptance Criteria

### AC-1: No-op when no unnotified TA alerts

**Given** the `alerts` table is empty (or contains only notified rows / non-TA types)
**When** `runTaAlertNotifier()` is called
**Then**
- `sendFn` is NOT called
- Returns `{ sent: 0, skipped: 0 }`

### AC-2: Sends Telegram for one unnotified ta_overbought alert

**Given** one row `{ notified_telegram: 0, signals_json: '[{"type":"ta_overbought",...}]', affected_actions_json: '[{"code":"VCB"}]', message: "VCB: RSI(14) = 74.2 — quá mua" }`
**When** `runTaAlertNotifier()` is called
**Then**
- `sendFn` is called exactly once
- The message string contains `"VCB"` and `"quá mua"`
- The message string starts with `"TA Alert"`

### AC-3: Marks notified_telegram=1 after successful send

**Given** one unnotified TA alert row
**When** `runTaAlertNotifier()` completes without error
**Then**
- `SELECT notified_telegram FROM alerts WHERE id = ?` returns `1`
- Returns `{ sent: 1, skipped: 0 }`

### AC-4: Does NOT mark notified_telegram=1 if sendFn throws

**Given** one unnotified TA alert row and `sendFn` injected to throw
**When** `runTaAlertNotifier()` is called
**Then**
- `SELECT notified_telegram FROM alerts WHERE id = ?` still returns `0`
- Returns `{ sent: 0, skipped: 0 }`

### AC-5: Skips non-TA alert types

**Given** one row with `signals_json: '[{"type":"position-danger",...}]'` and `notified_telegram: 0`
**When** `runTaAlertNotifier()` is called
**Then**
- `sendFn` is NOT called
- The row's `notified_telegram` remains `0`

### AC-6: Skips already-notified rows

**Given** one row with `notified_telegram: 1` and a TA alert type
**When** `runTaAlertNotifier()` is called
**Then**
- `sendFn` is NOT called

### AC-7: Batches multiple tickers into one message

**Given** three rows with types `ta_overbought` (VCB), `ta_oversold` (HPG), `ta_bb_breakout_up` (FPT)
**When** `runTaAlertNotifier()` is called
**Then**
- `sendFn` is called exactly once
- The single message contains `"VCB"`, `"HPG"`, and `"FPT"`
- Returns `{ sent: 3, skipped: 0 }`

### AC-8: Handles ta_bb_breakout_up and ta_bb_breakout_down types

**Given** one `ta_bb_breakout_up` row and one `ta_bb_breakout_down` row
**When** `runTaAlertNotifier()` is called
**Then**
- Both rows are included in the single Telegram message
- Returns `{ sent: 2, skipped: 0 }`

### AC-9: Message header contains "TA Alert"

**Given** any non-empty batch
**When** `runTaAlertNotifier()` is called
**Then**
- The message string begins with `"TA Alert"`

### AC-10: Job registered in jobs.ts and registry files updated

**Given** the implementation is complete
**Then**
- `jobs.ts` contains a cron entry `*/15 2-8 * * 1-5` with name `taAlertNotifierJob`
- `cron-registry.json` contains the `taAlertNotifierJob` entry and `schedulerFileCount: 32`
- `project-stats.json` contains `schedulerFileCount: 32`
- `bun tsc --noEmit` exits 0
