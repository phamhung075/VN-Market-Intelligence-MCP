# REQ-123: OHLCV Backfill Queue — Auto-seed daily_ohlcv via VPS Pull Pattern

status: APPROVED
sprint: 123
po_vision: Auto-trigger the OHLCV backfill so daily_ohlcv is seeded with 60 days of history within hours of startup, not 15 trading days. Mirrors the BCTC queue pattern.

## User Story

As a Vietnamese stock investor using Claude,
I want TA signals (RSI, MA, Bollinger Bands) to appear in the evening report within hours of the system starting,
So that I don't have to wait 15 trading days for the ohlcvDailyAggregatorJob to accumulate enough data.

---

## Root Cause Context

| Symptom | Root cause |
|---------|-----------|
| `taSummary: []` in every evening report | `daily_ohlcv` sparse — VPS backfill script exists but has never been triggered automatically |
| `taDiag.tickersBelowThreshold = N` every morning | Startup probe alerts devs via WORK channel but requires manual SSH + script run |
| Manual backfill = operator dependency | No queue mechanism exists to signal the VPS to run the backfill |

---

## Functional Requirements

### FR-1: `ohlcv_backfill_queue` table

| Field | Type | Default | Notes |
|-------|------|---------|-------|
| id | INTEGER | PK AUTOINCREMENT | |
| status | TEXT | 'pending' | 'pending' or 'done' |
| requested_at | TEXT | — | ISO timestamp, set on insert |
| completed_at | TEXT | NULL | ISO timestamp, set by POST /api/ohlcv-backfill-done |

`CREATE TABLE IF NOT EXISTS` — safe to add to existing schema.

### FR-2: `GET /api/ohlcv-backfill-queue`

- Auth: `X-API-Key` header must match `VPS_PUSH_API_KEY` env var → 401 if missing/wrong
- Response 200: `{ pending: true }` if any row with `status='pending'` exists, else `{ pending: false }`
- VPS polls this endpoint every 30 min from `ohlcv-backfill-poll.sh`

### FR-3: `POST /api/ohlcv-backfill-done`

- Auth: same `VPS_PUSH_API_KEY` check → 401
- Action: UPDATE the most recent `pending` row → `status='done'`, `completed_at=<now ISO>`
- Response 200: `{ ok: true }`
- No-op if no pending row exists (idempotent)

### FR-4: `ohlcvStartupProbe.ts` modification

- After detecting sparse tickers (existing logic unchanged): check `ohlcv_backfill_queue` for any `status='pending'` row
- If none: INSERT one row `(status='pending', requested_at=<now ISO>)`
- If pending row already exists: skip — no duplicate
- This fires only when `sparseTickers.length > 0`

### FR-5: `vps-scripts/ohlcv-backfill-poll.sh`

- Standalone bash script (not a new systemd service — operator adds to crontab or runs in loop)
- Every iteration: `GET /api/ohlcv-backfill-queue`
  - If `pending: false` → sleep 30 min, repeat
  - If `pending: true` → run `fetch-ohlcv-backfill.sh` (already exists), then `POST /api/ohlcv-backfill-done`
- Uses same env vars: `MCP_BASE_URL`, `API_KEY`
- Idempotent: second run with `pending=false` → skips backfill

## Non-Functional Requirements

| NFR | Requirement |
|-----|------------|
| Auth | All new endpoints use same `VPS_PUSH_API_KEY` pattern as existing VPS push endpoints |
| Idempotency | Probe never inserts duplicate pending rows; done endpoint never errors on double-call |
| No SSH | MCP Bun server never SSH-connects to VPS (architecture invariant) |
| No new systemd service | `ohlcv-backfill-poll.sh` is a standalone script; adding to crontab is operator's task |
| DDD compliance | Table + endpoint in infrastructure/interface layers — no domain/ changes |

## Out of Scope

- New systemd service on VPS (script only)
- Automatic crontab registration on VPS
