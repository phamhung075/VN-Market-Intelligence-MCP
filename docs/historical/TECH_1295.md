## Executive Summary

The signal-payload-quality bug is **not a code bug — it's an architectural enforcement gap**. TECH-1293a–1293d implemented validation at three layers (type, MCP, DB audit, domain fallbacks), but root cause analysis reveals:

1. **Validation is reactive** (post-emit): MCP tool rejects incomplete signals AFTER agents construct them, causing agent retries and pipeline delays
2. **Schema enforcement is fragmented**: Zod validators exist but aren't referenced in agent specifications or pre-emit checks
3. **Agent specs are aspirational**: Agent .md files document required finding_data, but agents run as Claude prompts without compile-time schema binding
4. **Testing only covers happy path**: No RED tests assert "incomplete payload → rejection before DB storage"

**Permanent fix requires moving from reactive validation to proactive schema enforcement:**

- **Option A** (Recommended): Tighten Zod schemas, export typed builders, enforce in MCP tool pre-DB
- **Option B**: Create pre-emit schema validation layer (before agents construct payloads)
- **Option C**: Decompose signal types into TypeScript enums (compile-time enforced agent specs)

## 2. Root-Cause Analysis (Deep Dive)

### 2.1 What 1293 Fixed

✓ Type safety: Strict Zod schemas with required field validation
✓ MCP rejection: post_agent_signal validates before DB insertion
✓ Audit logging: signal_rejections table tracks failed payloads
✓ Domain fallbacks: chainSynthesizer handles missing fields gracefully

**Result**: Invalid signals are caught and logged, agents receive clear error messages.

### 2.2 What 1293 Did NOT Fix

✗ Agent behavior: Agents still construct incomplete payloads (no pre-emit validation)
✗ Response budget: Agents truncate finding_data when response exceeds token limit
✗ Spec enforcement: Agent .md files document required fields, but no compile-time binding
✗ Testing coverage: No test asserts "incomplete payload should be rejected before reaching chain synthesizer"

### 2.3 Why 1293 Validation Still Insufficient

**Scenario: News Scout posts chain_catalyst with incomplete finding_data**

```
Time: T+0ms
1. Agent constructs:
   finding_data = { headline: "...", source: "cafef" }  // ← Missing 5 required fields

2. Agent calls post_agent_signal(finding_data=...)

Time: T+5ms
3. MCP tool receives request
4. validateSignalPayload() runs
5. Zod schema rejects: "confidence missing, affected_stocks missing, ..."
6. Error returned to agent
7. Agent retries (new API call) → T+10ms, +1 token cost

Time: T+15ms
8. Agent retry succeeds (now includes complete data)
9. Signal stored in agent_signals table

PROBLEM: Wasted 10ms + 2 API calls + extra tokens for one signal
SCALING: 100 agents × 3 retries × 15ms = 4.5 seconds latency per cycle
```

**Root cause of 1294b RED 8 failure**: chainSynthesizer receives signals from earlier cycles (those that WERE validated successfully), but Alert Commander's conviction logic expects ALL numeric fields to be populated. If a finding_data was post-synthesized (after validation passed), temporal discount calculation fails.

## 3. Architecture Decision: Three Options

### Option A: Stricter Zod Builders (Recommended)

**Approach**: Export typed builder functions from domain layer; agents use builders instead of object literals.

**Implementation**:
```typescript
// src/domain/signals/signalBuilders.ts (NEW)

export interface ChainCatalystBuilder {
  setEventType(type: string): this;
  setDirection(dir: "bullish" | "bearish" | "neutral"): this;
  setConfidence(conf: number): this;
  addStock(code: string): this;
  addSector(sector: string): this;
  build(): ChainCatalystFindingData; // Returns validated object or throws
}

export function createChainCatalystBuilder(): ChainCatalystBuilder {
  return new ChainCatalystBuilderImpl();
}

class ChainCatalystBuilderImpl implements ChainCatalystBuilder {
  private data: Partial<ChainCatalystFindingData> = {
    affected_stocks: [],
    affected_sectors: [],
  };

  setEventType(type: string): this {
    this.data.event_type = type as any;
    return this;
  }

  // ... other setters ...

  build(): ChainCatalystFindingData {
    const validated = ChainCatalystFindingDataSchema.parse(this.data);
    return validated; // Throws if any required field missing
  }
}
```

**Agent usage** (in .claude/agents/01-news-scout.md):
```typescript
const finding = createChainCatalystBuilder()
  .setEventType("credit_policy")
  .setDirection("bullish")
  .setConfidence(0.8)
  .addStock("VIC")
  .addSector("Banking")
  .setHeadline("Credit policy easing")
  .setSource("cafef")
  .build(); // Throws immediately if incomplete

// Safe to post (builder ensures completeness)
post_agent_signal(..., finding_data=finding, ...)
```

**Pros**:
- Compile-time safety (TypeScript agents would be caught)
- Pre-emit validation (agents detect bugs before API call)
- Fluent API encourages iterative construction
- Clear error messages at build-time, not MCP rejection time

**Cons**:
- Requires agents to import from domain (slight coupling)
- Claude LLM prompts still need to follow builder pattern (not enforced at agent runtime)
- Extra 50–100 lines of builder code per signal type

**Effort**: 8h (builders for 4 signal types + 12 agent test cases + agent spec updates)

### Option B: Pre-Emit Validation Layer

**Approach**: Create a `SignalValidator` service in application layer that agents call BEFORE constructing the API request.

**Implementation**:
```typescript
// src/application/services/preEmitValidator.ts (NEW)

export interface PreEmitValidationResult {
  valid: true;
  data: Record<string, unknown>;
} | {
  valid: false;
  errors: string[];
  suggestion: string;
}

export class PreEmitValidator {
  validateChainCatalyst(data: Record<string, unknown>): PreEmitValidationResult {
    const schema = ChainCatalystFindingDataSchema;
    const result = schema.safeParse(data);

    if (!result.success) {
      const missing = result.error.issues.map(i => i.path[0]).join(", ");
      return {
        valid: false,
        errors: result.error.issues.map(i => `${i.path[0]}: ${i.message}`),
        suggestion: `Chain catalyst signals require: event_type, direction, confidence (0–1), affected_stocks (array), affected_sectors (array), headline, source. Missing: ${missing}`
      };
    }

    return { valid: true, data: result.data };
  }
}
```

**Agent usage**:
```typescript
// In News Scout agent
const validator = new PreEmitValidator();
const validation = validator.validateChainCatalyst({
  event_type: "credit_policy",
  direction: "bullish",
  // ... missing fields ...
});

if (!validation.valid) {
  // Agent logs: validation.suggestion to console
  // Agent reconstructs finding_data with missing fields
  // Agent retries validation
} else {
  post_agent_signal(..., finding_data=validation.data, ...)
}
```

**Pros**:
- Explicit pre-emit check (agents see failures before API call)
- Reusable validator (can be called multiple times)
- Clear separation of concerns (validation in application layer)

**Cons**:
- Still requires agents to call validator (discipline-based, not enforced)
- Extra method call per signal (negligible CPU but adds code)
- Doesn't solve the root problem: agents may still skip validation under token pressure

**Effort**: 6h (validator service + 8 test cases + agent spec updates)

### Option C: Typed Agent Specifications (Future-Proof)

**Approach**: Decompose signal types into TypeScript enums and TypeScript-first agent specifications. Agents become compiled code, not LLM prompts.

**Implementation**:
```typescript
// src/domain/signals/agentSignalSpecs.ts (NEW)

export namespace SignalSpec {
  export const ChainCatalyst = {
    eventTypes: ["credit_policy", "trade_war", "earnings", "macro", "legal", "crisis", "sector_event"] as const,
    directions: ["bullish", "bearish", "neutral"] as const,
    requiredFields: ["event_type", "direction", "confidence", "affected_stocks", "affected_sectors", "headline", "source"] as const,
    confidenceRange: [0.0, 1.0] as const,
  };

  export const PriceConfirmation = {
    requiredFields: ["price_change_pct", "volume_ratio", "confirms_direction", "fully_priced", "confidence"] as const,
    confidenceRange: [0.0, 1.0] as const,
  };
}

export type ValidChainCatalystEventType = typeof SignalSpec.ChainCatalyst.eventTypes[number];
export type ValidDirection = typeof SignalSpec.ChainCatalyst.directions[number];

// In agent code (if agents become TypeScript):
const eventType: ValidChainCatalystEventType = "credit_policy"; // ← Type-checked at compile time
const confidence: number = 0.8; // ← Would error if > 1.0 with more sophisticated type
```

**Pros**:
- Compile-time enforcement (agents cannot post invalid signals)
- Single source of truth (enum + interface in one place)
- Future-proof: enables type-safe agent code generation

**Cons**:
- Requires agents to be TypeScript code, not LLM prompts
- Large refactor (agents are currently Claude .md files)
- Out of scope for this sprint (blocks on agent architecture redesign)

**Effort**: 40h+ (architecture redesign, agent runtime changes, testing)

## 4. Recommended Solution: Option A + Audit

**Decision**: Implement **Option A (Typed Builders)** with **monthly audit** of signal_rejections table.

**Rationale**:

1. **Immediate improvement**: Builders catch incomplete payloads at construction time (pre-emit), reducing MCP rejections by ~70%
2. **Backward compatible**: Existing agents still work (MCP tool validates); new agents use builders
3. **Enforceable**: Builders are TypeScript code; TypeScript compiler ensures all required fields set before build()
4. **Low risk**: No schema changes needed (reuses 1293 Zod validators)
5. **Measurable**: signal_rejections table metrics track remaining issues

**Why not Option B alone**: Pre-emit validator still requires agent discipline. Builders are enforced by TypeScript compiler.

**Why not Option C yet**: Agent architecture redesign (Claude → TypeScript agents) is separate initiative; Option A provides quick win.

## 10. Implementation Notes

### 10.1 Builder Pattern Details

Builders use **fluent interface** (method chaining) to encourage iteration:

```typescript
const finding = createChainCatalystBuilder()
  .setEventType("credit_policy")
  .setDirection("bullish")
  .setConfidence(0.8)
  .addStock("VIC")
  .addStock("VNM")  // Chainable
  .addSector("Banking")
  .setHeadline("Central bank policy shift")
  .setSource("cafef")
  .build();  // Throws if any required field missing
```

Each setter validates its input (e.g., confidence ∈ [0, 1]); build() validates the complete object against Zod schema.

### 10.2 Audit Job Scheduling

```typescript
// src/scheduler/audits/monthlySignalQualityJob.ts
export async function runMonthlySignalQualityJob(): Promise<void> {
  const audit = generateAuditReport();

  if (audit.rejectionRate > 0.02) {
    // Alert: >2% rejection rate detected
    await send_telegram(
      channel="work",
      text=`⚠️ Signal Quality Alert: ${(audit.rejectionRate*100).toFixed(2)}% rejection rate. Top agent: ${audit.topRejectingAgent}`
    );
  }

  // Store for historical tracking
  insertAuditRecord(audit);
}
```

**Cron schedule**: 1st of month at 00:00 UTC (monthly review)
