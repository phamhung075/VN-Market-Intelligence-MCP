## Component 1: SQLite WAL Hardening

### Context (from incident log)

Three corruption events: 2026-04-17, 2026-04-25 ~01:00 UTC, 2026-04-25 ~03:37 UTC.

Root cause confirmed in ops session:
- 5 Docker microservices open simultaneous write connections to `market.db` via volume mount
- WAL checkpoint is SIGTERM-only (`checkpoint.ts:83–98`) plus a 6-hourly cron (`jobs.ts:370–374`), but the 6-hourly cron uses `PRAGMA wal_checkpoint(TRUNCATE)` which blocks when readers are active
- No WAL size sentinel: the 44 MB WAL file (first incident) grew undetected
- No single-writer enforcement: Python microservices (`pdf-extractor`, `rag-service`) write directly to `market.db` via the volume mount
- docker-compose restart mid-WAL produces corrupt page when WAL is not fully synced at shutdown

### Current State Inventory

| File | Current Behaviour | Gap |
|------|------------------|-----|
| `apps/mcp-server/src/infrastructure/db/checkpoint.ts` | `runWalCheckpoint()` → TRUNCATE; `registerShutdownHook()` → SIGTERM/SIGINT | No WAL size check before checkpoint; shutdown hook has no grace period guard |
| `apps/mcp-server/src/scheduler/walCheckpointAlert.ts` | Sends WORK alert when remaining frames > 50,000 | Threshold is 50,000 frames (~200 MB) — far too high; incident happened at 44 MB (11,000 frames) |
| `apps/mcp-server/src/scheduler/jobs.ts:105` | `walCheckpoint: '0 */6 * * *'` | 6-hour interval; no WAL file size check on disk |
| Docker compose | All services mount `market.db` as shared volume | No write-routing through mcp-server API |

### Functional Requirements

**FR-WAL-1: Periodic FULL checkpoint every 30 minutes (not 6 hours)**

- Change `CRONS.walCheckpoint` default from `'0 */6 * * *'` to `'*/30 * * * *'`
- Use `PRAGMA wal_checkpoint(FULL)` (not TRUNCATE) during live hours to avoid blocking readers
- Use `PRAGMA wal_checkpoint(TRUNCATE)` only in `registerShutdownHook()` (unchanged) and during 03:00–05:00 UTC off-hours window
- File: `apps/mcp-server/src/scheduler/jobs.ts` line 105 (CRONS constant) + line 370 (cron handler)
- File: `apps/mcp-server/src/infrastructure/db/checkpoint.ts` — add `mode` parameter to `runWalCheckpoint(mode: 'FULL' | 'TRUNCATE' = 'FULL')`

**FR-WAL-2: WAL size sentinel — alert threshold lowered to 10,000 frames (~40 MB)**

- Change `WAL_STUCK_THRESHOLD` in `walCheckpointAlert.ts` line 11 from `50_000` to `10_000`
- Add secondary alert level at 5,000 frames (warning, not critical) — same WORK channel, different message prefix
- Rationale: incident occurred at ~11,000 frames (44 MB); 50,000 threshold would never fire

**FR-WAL-3: WAL file size guard on disk (pre-checkpoint sentinel)**

- Before running checkpoint, check actual `.db-wal` file size via `Bun.file(dbPath + '-wal').size`
- If size > 10 MB: log error + send WORK channel alert immediately, then attempt FULL checkpoint
- If size > 40 MB: send WORK channel alert with severity CRITICAL, attempt TRUNCATE checkpoint
- Inject `dbPath` from `Bun.env.DB_PATH ?? 'market.db'` (already used in `schema.ts`)
- New exported function: `checkWalFileSize(dbPath: string): Promise<{ bytes: number; warningFired: boolean }>` in `checkpoint.ts`

**FR-WAL-4: Shutdown hook grace period**

- Current `registerShutdownHook()` calls `process.exit(0)` immediately after checkpoint
- Add 200ms settle delay (`await Bun.sleep(200)`) before `process.exit(0)` to allow in-flight writes to complete
- This addresses the race condition: docker-compose sends SIGTERM, mcp-server begins checkpoint, but a concurrent scheduler write is mid-transaction
- File: `apps/mcp-server/src/infrastructure/db/checkpoint.ts` lines 86–96

**FR-WAL-5: Single-writer enforcement documentation + python service read-only flag**

- Python microservices (`apps/pdf-extractor/`, `apps/rag-service/`) must open SQLite in read-only mode: `sqlite3.connect(db_path, check_same_thread=False)` → add `uri=True` with `?mode=ro`
- All writes from Python services must route through mcp-server HTTP API (`POST /api/push-*` endpoints)
- This is architectural enforcement, not a code change in the TS layer
- Document in `docker-compose.yml` as a comment on the volume mount
- BA assessment: confirm with Architect whether the Python services currently write to `market.db` directly or only read

**FR-WAL-6: Daily backup rotation**

- After the nightly TRUNCATE checkpoint (03:00 UTC), copy `market.db` → `market.db.backup` using `Bun.file` copy
- Keep only 1 backup (overwrite); purpose is recovery from next-day corruption, not full history
- File: new helper `backupDatabase(dbPath: string): Promise<void>` in `checkpoint.ts` or a new `apps/mcp-server/src/infrastructure/db/backup.ts`

### Non-Functional Requirements

- NFR-WAL-1: Checkpoint must complete within 5 seconds; if it does not, log warning and return (do not block scheduler)
- NFR-WAL-2: All checkpoint functions must be injectable for tests (pattern already established in `CheckpointDeps` interface at `checkpoint.ts:21`)
- NFR-WAL-3: No new external dependencies — only Bun built-ins and existing `logger.ts`

**Sprint 1329 target:** Add IMF as a 7th dimension in `computeConviction()`, sourced from `imf_indicators` DB table via a repository read at the application layer.

## Edge Cases

### WAL-specific
- `Bun.file(dbPath + '-wal').size` returns 0 when WAL does not exist (fresh DB) — treat as healthy, no alert
- `PRAGMA wal_checkpoint(FULL)` returns `{ busy: 1, log: N, checkpointed: M }` when readers are active — `remaining = log - checkpointed` may be non-zero; this is expected, not a corruption risk
- Multiple scheduler jobs running simultaneously at the 30-minute boundary — the SQLite WAL mode serializes concurrent writers; only one checkpoint will run at a time via Bun's single-threaded event loop

### IMF-specific
- `imf_indicators` table empty on fresh DB (after corruption recovery) — `getImfMacroScoreForConviction()` must return 0, not throw
- All IMF indicators stale (age > 60 days) — `classifyImfIndicators()` already returns `{ sentiment: 0, confidence: low }` in this case (`imfDataClassifier.ts:222–233`); pass-through correctly
- IMF poller circuit breaker open (API unreachable) — `imf_indicators` table retains last known values; staleness check (24h) handles this correctly
- Vietnamese IMF news with `"quỹ tiền tệ quốc tế"` in headline — covered by `imfSentimentClassifier.ts:22` keyword list
- Weight rescaling arithmetic: when adding 7th dimension, sum of 7 weights must equal exactly 1.0000; use integer arithmetic in tests to avoid floating-point drift
