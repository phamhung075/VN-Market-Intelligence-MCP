**status:** READY_FOR_ARCHITECT

## User Story

As a Vietnamese stock investor using Claude,
I want macro context (CPI, GDP, interest rates) to be fresh and automatically updated daily,
So that Financial Analyst (02) + Market Watcher (04) agents have current macro perspective for informed cascade analysis and signal quality.

## Problem Statement

| Symptom | Root Cause | Impact |
|---------|-----------|--------|
| `macro_indicators` table is **400+ days stale** (fetched_at = 2025-03-01) | No dedicated refresh job exists. `fetchMacroIndicators()` called only sporadically in intelligence cycle. Fetch failures are not escalated or retried. | Macro analysis layer downstream (Financial Analyst + Market Watcher agents) operates on 12-month-old GDP/CPI/rate data. Cascade rules weight stale macro context = degraded signal quality. |
| `push-tradingeconomics` / `push-gso` endpoints receive data from VPS but may not be triggered or routed correctly | MCP server endpoints parse TE/GSO payloads but no confirmation that VPS services are actually calling them with fresh data | Data freshness SLA unenforceable. No visibility into whether macro fetch succeeds daily. |
| No SLA monitoring for macro data age | Staleness undetected until agents fail downstream. Alert Commander has no way to escalate stale macro context. | Silent degradation: agents post signals with stale macro context; users don't know analysis is compromised. |

### FR-2: Implement macroIndicatorRefreshJob — Daily Scheduled Fetch

**Description:** Create a dedicated daily scheduler job that fetches macro indicators from Trading Economics (primary) with multi-source fallback (SBV → GSO).

**Inputs:**
- Schedule: **01:00 UTC daily** (08:00 VN, market pre-open)
- Sources (in priority order):
  1. **Yahoo Finance** (via `fetchMacroIndicators()` in tradingEconomics.ts — web scraper)
  2. **SBV (State Bank of Vietnam)** — direct API for interest rates
  3. **GSO (General Statistics Office)** — direct API for CPI/GDP

**Outputs:**
- New file: `src/scheduler/macro/macroIndicatorRefreshJob.ts`
  - Function signature: `export async function runMacroIndicatorRefreshJob(): Promise<MacroRefreshResult>`
  - Result type tracks: `{ durationMs, sourceUsed, rowsUpdated, fetchedAt, success, error }`
  - Fetch → parse → validate → store (use `storeMacroIndicators()` from tradingEconomics.ts)
  - Log each step: fetch start, source result, store confirmation
  - Timestamp all fetches in UTC ISO format

**Business rules:**
- **Multi-source fallback:** If Yahoo/TE returns all nulls, try SBV endpoint. If SBV fails, try GSO. Return first successful partial result (not zero-partial).
- **Circuit breaker:** Wrap every HTTP call in `breakers.macroindicators` (new entry in `circuitBreakerRegistry.ts`)
- **Rate limiter:** Call `rateLimiter.check("macro-refresh")` before any fetch
- **Upsert semantics:** `INSERT OR REPLACE` to handle existing "vietnam" row (schema already supports this)
- **Idempotent:** Running the job twice on the same day should produce identical DB state (no duplicate rows)
- **Error recovery:** Log error but do not throw — job must complete even if one source fails
- **Timezone:** All timestamps in UTC; convert for VN display only (GMT+7)

**DDD layer:** interface/scheduler (cron job orchestration)

### FR-3: SLA Enforcement — Stale-Data Detection + Escalation

**Description:** Monitor macro data freshness; escalate to Alert Commander when age exceeds 24 hours.

**Inputs:**
- After successful store in FR-2, query `macro_indicators` table for "vietnam" row
- Compute age: `NOW() - fetched_at`
- Check: age > 24 hours?

**Outputs:**
- Stale-data detection logic in `macroIndicatorRefreshJob.ts`
  - If age > 24h: log WARN + call escalation callback
  - Escalation callback: `notifyUser(channel="work", msg=`[ALERT] Macro data stale >24h...`)
- Result object includes: `{ isStalenessAlert: boolean, ageDays: number }`
- Threshold configurable via env: `MACRO_FRESHNESS_SLA_HOURS` (default 24)

**Business rules:**
- SLA check runs **after successful fetch**, not as a separate job
- If fetch fails entirely (all sources down), do not send escalation (failure != staleness)
- If fetch succeeds but new data is older than 24h (e.g., TE not updated for 2 days), escalate
- Escalation is 1 message per day max (24h cooldown); use `alertCooldown` pattern from existing code
- Alert Commander (agent 05) responds to `channel="work"` alerts; do not call MARKET channel

**DDD layer:** domain/services (pure staleness-check logic) + interface/scheduler (callback invocation)

## Edge Cases & Data Quality

| Case | Handling |
|------|----------|
| **TE scraper returns 503 (cloudflare/rate limit)** | Log WARN, try SBV. If all sources return 503, do not update DB; log escalation. |
| **SBV/GSO API timeout (>10s)** | Circuit breaker trips; skip to next source. Log timeout reason. |
| **Partial success (TE has CPI + GDP, missing interest_rate)** | Store partial row (nulls for missing fields). Log which fields were null. |
| **Duplicate "vietnam" row in DB** | UNIQUE(country) constraint + INSERT OR REPLACE handles automatically. No error. |
| **fetched_at timestamp is NULL in database** | Query returns age=infinity; escalate staleness immediately. Migrate existing NULLs to 2025-03-01 in diagnostic step. |
| **TE HTML page structure changes** | Parse returns all nulls. Log "parse failure" + try fallback. Over time, may require TE selector re-tuning (not in this sprint). |
| **Job runs twice within same second (clock skew)** | Circuit breaker + rate limiter ensure idempotency; second call blocked by rate limiter. Logged as "rate-limited". |
| **Vietnam market is closed / no price updates expected** | Macro job runs regardless (macro is asynchronous to market hours). No impact on market-hours jobs. |

## Acceptance Criteria

### AC-1: Macro Fetch Succeeds + Data Stored

**Given** macroIndicatorRefreshJob runs at 01:00 UTC
**When** trading_economics source is healthy
**Then**
- HTTP GET to TE succeeds (200 OK)
- HTML parse extracts cpi, gdpGrowth, interestRate (not all null)
- Row inserted/replaced in macro_indicators table with `country='vietnam'`
- `fetched_at` timestamp is current (within 1 minute of run time)

### AC-2: Multi-Source Fallback — TE → SBV → GSO

**Given** Trading Economics returns all nulls (parse failure)
**When** SBV API endpoint is healthy
**Then**
- Job skips TE after timeout/parse failure
- Calls SBV API (interest_rate only)
- Updates macro_indicators row with SBV value
- Logs source fallback chain (TE: failed, SBV: success)

### AC-3: SLA Enforcement — Staleness Alert

**Given** macroIndicatorRefreshJob completes successfully
**When** `NOW() - fetched_at > 24 hours`
**Then**
- Job computes staleness age
- Sends escalation alert to WORK channel via `notifyUser()` (not MARKET)
- Alert format: `[MACRO-STALE] Data is 2.5 days old (last fetch: 2025-03-01). Check VPS services.`
- Alert suppressed if escalation sent within last 24h (cooldown)

### AC-4: Circuit Breaker + Rate Limiting

**Given** TE endpoint returns 503
**When** circuit breaker trips (after 3 consecutive failures)
**Then**
- `breakers.macroindicators.isOpen()` returns true
- Job skips TE immediately (no retry)
- Logs "circuit breaker open for macro; trying SBV"
- Calls fallback sources

### AC-5: Idempotency — Same Day, Same State

**Given** Job runs twice in same calendar day (UTC)
**When** Both fetches succeed with identical data
**Then**
- First run: inserts/updates macro_indicators row
- Second run: `INSERT OR REPLACE` overwrites with same data
- DB has exactly 1 row for country='vietnam'
- No duplicate rows or transaction conflicts

### AC-6: Error Logging + Non-Fatal Failure

**Given** All three sources (TE, SBV, GSO) fail simultaneously
**When** Job completes
**Then**
- Logs ERROR for each source attempt + reason (timeout, 503, parse)
- Does **not** throw/crash job
- Does **not** update DB (preserves stale data with old timestamp)
- Returns `MacroRefreshResult { success: false, error: "all sources exhausted" }`
- Server continues running (no impact on other jobs)

### Data Contracts

**Input: none (scheduled job)**

**Output: MacroRefreshResult**
```typescript
export interface MacroRefreshResult {
  /** Duration in milliseconds from start to finish */
  durationMs: number;

  /** Which source provided the data: 'trading_economics' | 'sbv' | 'gso' | null */
  sourceUsed: string | null;

  /** Number of rows updated in macro_indicators (0 or 1) */
  rowsUpdated: number;

  /** ISO 8601 timestamp of the fetched data */
  fetchedAt: string;

  /** Job succeeded (all steps completed without throwing) */
  success: boolean;

  /** Error message if success=false; null otherwise */
  error: string | null;

  /** Age of the data in hours (freshness SLA check) */
  ageHours: number;

  /** True if age exceeds threshold + escalation was sent */
  isStalenessAlert: boolean;
}
```

## Risk & Mitigation

| Risk | Probability | Impact | Mitigation |
|------|-------------|--------|-----------|
| **TE scraper breaks** (HTML structure change) | Medium | Job fails all TE attempts, falls back to SBV/GSO | Circuit breaker + fallback chain handles; monitor TE selector in logs |
| **SBV/GSO APIs unreachable from France** (geo-block) | High | All sources fail; macro data never updates | Route through VPS (Vinahost) — discovered in FR-1 diagnosis; may require task 1499-style integration |
| **Rate limiter blocks job** (if macro-refresh is called elsewhere) | Low | Job skipped; staleness escalation sent | Investigate competing callers; rate limit configured conservatively (1 call per 5min) |
| **Staleness escalation spam** (daily alerts to WORK) | Medium | Channel noise; user ignores | Escalation cooldown (24h default) prevents multi-alert; log first + subsequent attempts |
| **Partial nulls in parsed data** | Medium | Stale/incomplete macro context | Handled correctly: partial row stored, partial nulls logged; agents handle null gracefully |
