## 1. Sprint Vision

Sprint 054 makes the system position-aware and narrows the alert surface to two high-confidence signal types. It introduces an async question queue (/ask) backed by a new Cowork QA Responder agent, extends the position ledger with weighted-average cost and sell semantics, adds `/set_position` and `/check_position` Telegram commands, and makes Kinh Dich readings a mandatory layer on every stock analysis. All server-side code ships as new MCP tools or extensions to existing stores; the Cowork agent .md rewrites (E7, E8) are handled separately by the Cowork Refactory Expert in Phase 6.

## 2. User Stories

### E1 — Position Ledger Extension

**As a Vietnamese stock investor using Claude,**
I want to manage my positions via `/set_position TICKER PRICE QTY` with correct weighted-average cost tracking and sell-clamping semantics,
So that my portfolio always reflects the real cost basis even after partial buys and sells.

#### FR-E1-1: Weighted-average cost computation on buy

- Description: When `qty > 0`, recompute avg cost using the weighted-average formula.
- Input: existing `PositionRow` `{code, shares, avg_price}` from `positions` table + new `{price, qty}`.
- Output: updated row with `avg_price = (old_shares * old_avg_price + qty * price) / (old_shares + qty)`, `shares = old_shares + qty`.
- Business rule: `avg_price` rounds to 0 decimal places (integer VND). `shares` is always an integer.
- Explanation message emitted: `"Mua thêm {qty} @ {price} VND → avg cost mới: {new_avg_price} VND (tổng {new_shares} CP)"`
- DDD layer: domain
- Target: `src/infrastructure/db/positionStore.ts` — extend `upsertPosition()` or add `buyPosition()` helper

#### FR-E1-2: Sell semantics with clamping

- Description: When `qty < 0`, reduce holdings by `abs(qty)` clamped to current holdings; never allow negative shares.
- Input: existing `PositionRow` + new `{price, qty}` where `qty < 0`.
- Output:
  - If `abs(qty) <= shares`: `shares = shares - abs(qty)`. `avg_price` unchanged (partial sell does not change avg cost).
  - If `abs(qty) > shares`: clamp to full holdings (`shares = 0`); emit clamped explanation.
- Explanation messages:
  - Normal sell: `"Bán {abs(qty)} CP @ {price} VND → còn lại {remaining} CP @ {avg_price} VND"`
  - Clamped sell: `"Chỉ bán được {old_shares} CP (không đủ số lượng) → đã thanh lý toàn bộ vị thế"`
- If resulting `shares == 0`: call `closePosition(db, code)` to set `closed_at`.
- No realized P/L tracking — side effect is holdings update only.
- DDD layer: domain
- Target: `src/infrastructure/db/positionStore.ts` — new `sellPosition()` helper

#### FR-E1-3: Clear position (`price=0 qty=0`)

- Description: When `price == 0 AND qty == 0`, delete all holdings for the ticker (set `closed_at`).
- Output: position row closed. Explanation message: `"Đã xóa toàn bộ vị thế {TICKER}"`
- DDD layer: domain
- Target: `src/infrastructure/db/positionStore.ts` — extend `closePosition()` or dispatch in `applyPositionCommand()`

#### FR-E1-4: Unified command dispatcher `applyPositionCommand()`

- Description: Single entry point that dispatches to buy/sell/clear based on `{ticker, price, qty}` tuple.
- Routing:
  - `qty > 0` → FR-E1-1 (buy)
  - `qty < 0` → FR-E1-2 (sell with clamp)
  - `price == 0 AND qty == 0` → FR-E1-3 (clear)
  - `qty == 0 AND price > 0` → invalid input, return error message
- Returns: `{ ok: boolean; message: string }` — message is the Vietnamese explanation string.
- DDD layer: domain
- Target: `src/infrastructure/db/positionStore.ts`

#### Acceptance Criteria — E1

**AC-E1-1: Buy then partial sell**
Given a position VCB: 1000 shares @ 75000 VND
When `applyPositionCommand({ticker:"VCB", price:80000, qty:500})`
Then avg_price = (1000*75000 + 500*80000) / 1500 = 76667 VND, shares = 1500
When `applyPositionCommand({ticker:"VCB", price:82000, qty:-300})`
Then shares = 1200, avg_price = 76667 (unchanged), explanation includes "còn lại 1200 CP"

**AC-E1-2: Clamped sell**
Given a position FPT: 200 shares
When `applyPositionCommand({ticker:"FPT", price:100000, qty:-500})`
Then shares become 0, closePosition is called, explanation includes "Chỉ bán được 200 CP"

**AC-E1-3: Clear**
Given a position HPG: 3000 shares
When `applyPositionCommand({ticker:"HPG", price:0, qty:0})`
Then `positions` row has `closed_at IS NOT NULL`, explanation: "Đã xóa toàn bộ vị thế HPG"

**AC-E1-4: Buy from zero (new position)**
Given no position for VHM
When `applyPositionCommand({ticker:"VHM", price:45000, qty:1000})`
Then new row: shares=1000, avg_price=45000

### E2 — Telegram Commands: /set_position and /check_position

**As a Vietnamese stock investor,**
I want to manage and inspect my positions directly from Telegram,
So that I can adjust holdings without opening a separate session.

#### FR-E2-1: `/set_position` command handler

- Description: Parse and dispatch `/set_position TICKER PRICE QTY` in `telegramCommands.ts`.
- Input format: `/set_position FPT 80300 5100` or `/set_position FPT 0 0` (clear)
- Parse rules:
  - Token 1 = TICKER (uppercase, 2–10 chars, alpha only — reject numeric or punctuation)
  - Token 2 = PRICE (float, >= 0, in VND — user enters full VND, not thousands)
  - Token 3 = QTY (integer, may be negative)
  - Malformed input → Vietnamese usage hint
- Calls `applyPositionCommand({ticker, price, qty})` from `positionStore.ts`
- Reply: the explanation message returned by `applyPositionCommand`.
- DDD layer: interface
- Target: `src/infrastructure/notifiers/telegramCommands.ts`

#### FR-E2-2: `/check_position` command handler

- Description: List all open positions with live P/L, stop-loss suggestion, and TP ladder.
- Calls `listOpenPositions(db)` (already returns `PositionWithPnl[]`).
- Response format per position:
  ```
  {TICKER} — {shares} CP
    Avg cost:     {avg_price} VND
    Giá hiện tại: {currentPrice} VND  (N/A nếu không có dữ liệu)
    P/L:          {sign}{pct}% ({sign}{vnd} VND)
    Stop-loss:    {stop_loss} VND
    TP ladder:    +10% @ {tp1} | +20% @ {tp2} | +30% @ {tp3}
  ```
- Stop-loss displayed = `avg_price * 0.93` (hard floor only — ATR14 requires `daily_ohlcv` query handled in E5; `/check_position` uses the simpler floor for the Telegram reply to avoid blocking).
- TP ladder: `tp1 = avg_price * 1.10`, `tp2 = avg_price * 1.20`, `tp3 = avg_price * 1.30`.
- If no open positions: `"Chưa có vị thế nào. Dùng /set_position TICKER GIÁ SỐ_LƯỢNG để thêm."`
- DDD layer: interface
- Target: `src/infrastructure/notifiers/telegramCommands.ts`

#### FR-E2-3: Update `/help` text

- Add `/set_position` and `/check_position` to the HELP_TEXT constant in `telegramCommands.ts`.

### E3 — /ask Queue (DB + Telegram Handler)

**As a Vietnamese stock investor,**
I want to type `/ask <any question>` in Telegram and receive an AI-researched answer within 12 minutes,
So that I can ask complex questions without waiting synchronously.

#### FR-E3-1: `ask_queue` table DDL

- New table in `src/infrastructure/db/schema.ts` inside `initDatabase()`.
- Schema:
  ```sql
  CREATE TABLE IF NOT EXISTS ask_queue (
    id                     INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id                TEXT    NOT NULL DEFAULT 'default',
    message                TEXT    NOT NULL,
    received_at            TEXT    NOT NULL DEFAULT (datetime('now')),
    status                 TEXT    NOT NULL DEFAULT 'pending',
    answered_at            TEXT,
    answer_text            TEXT,
    processing_started_at  TEXT
  );
  CREATE INDEX IF NOT EXISTS idx_ask_queue_status   ON ask_queue(status);
  CREATE INDEX IF NOT EXISTS idx_ask_queue_received ON ask_queue(received_at);
  ```
- Status values: `pending` | `processing` | `answered` | `failed` | `escalated`
  - `pending` = inserted, awaiting agent pick-up
  - `processing` = agent has called `get_pending_ask_questions()` and is working on this row
  - `answered` = agent posted answer to MARKET and called `answer_ask_question()`
  - `failed` = agent encountered an unrecoverable error
  - `escalated` = question too complex for automated answer; paste-ready prompt sent to user
- DDD layer: infrastructure
- Target: `src/infrastructure/db/schema.ts`

#### FR-E3-2: `askQueueStore.ts` helper functions

- New file: `src/infrastructure/db/askQueueStore.ts`
- Functions:
  - `insertAskQuestion(db, message, userId?)` → inserts `status='pending'`, returns `id`
  - `getPendingAskQuestions(db, limit?)` → returns FIFO list ordered by `received_at ASC`, `status='pending'`, default `limit=10`
  - `markAskProcessing(db, id)` → sets `status='processing'`, `processing_started_at=datetime('now')`
  - `answerAskQuestion(db, id, answerText, status: 'answered'|'escalated'|'failed')` → sets `status`, `answered_at`, `answer_text`
- All functions use parameterized SQLite queries.
- DDD layer: infrastructure
- Target: `src/infrastructure/db/askQueueStore.ts`

#### FR-E3-3: `/ask` Telegram command handler

- Parse: everything after `/ask` is the question text. Empty → usage hint.
- Calls `insertAskQuestion(db, message)`.
- Reply (Vietnamese): `"Câu hỏi đã ghi nhận (#${id}), sẽ trả lời trong 12 phút."`
- DDD layer: interface
- Target: `src/infrastructure/notifiers/telegramCommands.ts`

**As the dev team,**
I want a scheduler that fires every 12 minutes to signal the QA Responder agent when there are pending questions,
So that Cowork answers within the SLA without polling overhead.

#### FR-E4-1: `askQueueCheckJob.ts` scheduler

- New file: `src/scheduler/askQueueCheckJob.ts`
- Schedule: `*/12 * * * *` (every 12 minutes)
- Logic:
  1. Query `getPendingAskQuestions(db, 1)` — check if at least 1 pending question exists.

### E5 — Alert Policy Rewrite

**As a Vietnamese stock investor,**
I want to receive only high-confidence alerts — position-danger and watchlist-opportunity — instead of routine noise,
So that every Telegram alert I receive in the MARKET channel is actionable.

#### FR-E5-1: `alertPolicy` section in `mcp.config.json`

- Add new top-level section `alertPolicy`:
  ```json
  {
    "alertPolicy": {
      "positionDanger": {
        "singleDayDropPct": 5.0,
        "newsSentimentThreshold": -0.5
      },
      "watchlistOpportunity": {
        "kinhDichConfidenceMin": 70,
        "newsSentimentMin": 0.3
      },
      "alertCooldownMinutes": 0
    }
  }
  ```
- DDD layer: infrastructure (config)
- Target: `mcp.config.json`

#### FR-E5-2: `alertPolicyChecker.ts` domain service

- New file: `src/domain/services/alertPolicyChecker.ts`
- Two pure functions (no I/O):

  **`checkPositionDanger(input: PositionDangerInput): boolean`**
  ```typescript
  interface PositionDangerInput {
    stopLossHit: boolean;       // currentPrice <= computedStopLoss
    singleDayDropPct: number;   // positive value, e.g. 5.2 means 5.2% drop
    newsSentiment: number;      // -1.0 to 1.0
    thresholds: {
      singleDayDropPct: number; // from config: 5.0
      newsSentimentThreshold: number; // from config: -0.5
    };
  }
  ```
  Returns `true` only when ALL THREE conditions met:
  1. `stopLossHit === true`
  2. `singleDayDropPct >= thresholds.singleDayDropPct`
  3. `newsSentiment <= thresholds.newsSentimentThreshold`

  **`checkWatchlistOpportunity(input: WatchlistOpportunityInput): boolean`**
  ```typescript
  interface WatchlistOpportunityInput {
    kinhDichConfidence: number;   // 0-100
    kinhDichSignal: string;       // "BUY" | "SELL" | "NEUTRAL"
    newsSentiment: number;        // -1.0 to 1.0
    agentSignalsMajority: string; // "BUY" | "SELL" | "NEUTRAL"
    thresholds: {
      kinhDichConfidenceMin: number; // from config: 70
      newsSentimentMin: number;      // from config: 0.3
    };
  }
  ```
  Returns `true` only when ALL FOUR conditions met:
  1. `kinhDichConfidence >= thresholds.kinhDichConfidenceMin`
  2. `kinhDichSignal === "BUY"`
  3. `newsSentiment >= thresholds.newsSentimentMin`
  4. `agentSignalsMajority === "BUY"`

- DDD layer: domain
- Target: `src/domain/services/alertPolicyChecker.ts`

#### FR-E5-3: Stop-loss computation helper

- New file: `src/domain/services/stopLossComputer.ts`
- Function: `computeStopLoss(avgCost, atr14, nearestSupport): number`
  - Returns `Math.max(avgCost - 2 * atr14, nearestSupport, avgCost * 0.93)`
  - All inputs in VND. Result in VND (integer rounded).
  - If `atr14 <= 0` or `nearestSupport <= 0`: fall back to `avgCost * 0.93` only.
- DDD layer: domain
- Target: `src/domain/services/stopLossComputer.ts`

#### FR-E5-4: Retire noise alert generators

The following alert-generation behaviors are retired from automatic MARKET channel firing. They may still insert rows into the `alerts` table for audit but must NOT call `send_telegram(channel="market")`:

| Alert type | Current location | Retirement action |
|------------|------------------|-------------------|
| Medium price moves (2–5% drop/rise) without SL hit | `src/scheduler/marketScanJob.ts` | Remove Telegram send; keep DB insert |
| Single-source news signals without multi-agent confirmation | alert composition in Cowork agents | Handled by E7 agent rewrite (Phase 6) |
| Routine watchlist price heartbeats | `src/scheduler/marketScanJob.ts` | Remove Telegram send; keep DB insert |
| Volume spike alerts without other signal confirmation | alert pipeline | Remove Telegram send; keep DB insert |

- DDD layer: scheduler / interface
- Target: `src/scheduler/marketScanJob.ts` (primary), Cowork agent .md (Phase 6)

Then returns `false` (singleDayDrop < 5.0 threshold)

**AC-E5-2: position-danger fires**
Given `stopLossHit=true, singleDayDropPct=6.0, newsSentiment=-0.7`
When `checkPositionDanger(input)`
Then returns `true`

**AC-E5-3: watchlist-opportunity partial match**

**AC-E5-4: watchlist-opportunity fires**

**AC-E5-5: stop-loss computation**
Given `avgCost=75000, atr14=1500, nearestSupport=72000`

### E8 — 07-qa-responder Cowork Agent (Phase 6, agent .md only)

So that I receive researched answers in the MARKET channel within 12 minutes.

## 4. Edge Cases and Data Quality

### Position ledger

- [ ] `/set_position` with non-numeric PRICE or QTY → return Vietnamese error, do not write to DB
- [ ] TICKER contains numbers or special chars (e.g. "123", "VCB!") → reject with usage hint
- [ ] Fractional QTY entered (e.g. "1500.5") → round to nearest integer, emit note
- [ ] avg_price arithmetic rounding: always `Math.round()` to integer VND — avoid floating point drift across multiple buys
- [ ] Position not found on sell/clear → return "Không tìm thấy vị thế {TICKER}"
- [ ] Concurrent writes (two Telegram messages at once) → SQLite WAL + transaction isolation handles this; no extra lock needed

### Ask queue

- [ ] `/ask` with message length > 2000 chars → truncate to 2000 chars, store note in `answer_text`
- [ ] Duplicate rapid `/ask` from same user → both enqueued; processed FIFO — no dedup
- [ ] QA Responder crashes mid-processing → row stays as `status='processing'`; recovery: `askQueueCheckJob` should detect rows with `processing_started_at > 20 min ago AND status='processing'` → reset to `'pending'` (stale-processing recovery)
- [ ] `answer_text` field length → no SQLite TEXT limit; Telegram has 4096-char limit; QA Responder truncates if needed

### Alert policy

- [ ] ATR14 unavailable (no `daily_ohlcv` data for ticker) → `computeStopLoss` falls back to `avg_cost * 0.93` only
- [ ] `nearestSupport` not computed → pass `0`, function ignores it per FR-E5-3 fallback rule
- [ ] `newsSentiment` not available for ticker → do NOT fire either alert type; log warning
- [ ] `kinhDichConfidence` not computed (no hexagram data) → `watchlist-opportunity` condition fails; no false positive
- [ ] `agentSignalsMajority` computation: defined as `BUY` if more than 50% of `agent_signals` for the ticker (within last 30 min, `status='unread'`) are `BUY`. Tie = `NEUTRAL`.

### Kinh Dich wrapper

- [ ] `kinhDichReading` throws (e.g. LanceDB unavailable) → catch, append fallback text, never propagate error to caller
- [ ] Ticker not in watchlist → `get_kinhdich_reading` may have no data → fallback text per FR-E6-2
- [ ] `appendKinhDich` called on a tool that does not have a single `ticker` context (e.g. `get_market_overview` summary section) → pass `"MARKET"` as ticker, call `get_market_hexagram()` instead
