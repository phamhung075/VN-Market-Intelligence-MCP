## Functional Requirements

### FR-1: Remove legacy `pharma` key from `mcp.config.json`

- **Description:** `mcp.config.json → market.referenceStocks` contains two overlapping keys: `pharma` (5 tickers) and `pharmaceutical` (7 tickers). Every ticker in `pharma` is a subset of `pharmaceutical`. This causes: (a) test 1282 assertion `expect(hasPharma && hasPharmaceutical).toBe(false)` to fail, and (b) alert pipeline to potentially fire two alerts per event for DHG/IMP/DMC/TRA/DBD — one via `pharma` and one via `pharmaceutical` sector match.
- **Input:** `mcp.config.json` — current state has both keys at `market.referenceStocks`.
- **Output:** `mcp.config.json` — only `pharmaceutical` key remains (7 tickers: DHG, IMP, DMC, DBD, PME, TRA, OPC). `pharma` key fully removed.
- **Business rule:** `pharmaceutical` is the canonical expanded sector. `pharma` is a legacy alias that was never cleaned up after the sector was renamed and expanded. `sectorPeers.ts` retains its own `pharma` entry (5 tickers) — that is a separate domain-layer concern used for cascade classification only and is NOT changed by this task.
- **DDD layer:** domain (config/data only — no TypeScript source change)

### FR-2: Add `process.env["DB_PATH"] = ":memory:"` guard to test files missing it

- **Description:** `bun test` runs test files in parallel worker threads. Files that open the SQLite singleton (`getDb()`) without first setting `DB_PATH=:memory:` risk: (a) opening the production `data/market.db` file, or (b) racing with another worker that already opened `_db` singleton pointing to a different path. The three confirmed contamination victims are 137, 278, 1294. 74 additional DB-touching test files lack the guard.
- **Input:** Test files that import from `infrastructure/db/schema.js` (or transitively call `getDb()` / `initDatabase()`) but do NOT set `process.env["DB_PATH"] = ":memory:"` as their very first executable statement.
- **Output:** Every such test file has `process.env["DB_PATH"] = ":memory:";` as line 1 (before all imports), OR uses a strategy documented in FR-2 exception rules below.
- **Business rule — guard placement:** The guard MUST appear before any `import` statement because ES module static imports are hoisted and may trigger `getDb()` at module evaluation time. The only correct placement is the very first line of the file.
- **Business rule — exceptions (do NOT add guard to these):**
  - `278-cycle-peer-sync.test.ts`: explicitly documents it cannot use `:memory:` because it relies on `getWatchlistCodesFn` injected mock — no direct `getDb()` call at import time. Its contamination risk is logger writes, mitigated via `TEST_LOG_SUPPRESS`. Leave as-is; investigate separately if it still fails post-1300.
  - `137-fix-alert-pipeline.test.ts`: uses `new Database(":memory:")` directly (bypasses singleton). Sets `Bun.env["DB_PATH"]` inside individual test cases with `closeDb()` cleanup. This pattern is correct — do NOT add top-level guard (it would break the per-test reset pattern).
  - `167-prediction-market-job.test.ts`: sets `DB_PATH` to a `tmpPath` inside specific test cases. Guard would conflict. Leave as-is.
  - `1181-financial-reports-persist.test.ts`: saves/restores `ORIGINAL_DB_PATH` for a real-file test. Leave as-is.
- **Business rule — priority targets:** The 22 known failures in a parallel run originate primarily from files that: (1) import `intelligenceCycleJob` or `alertGenerator`, AND (2) lack the guard. Address those first. Full list of 74 DB-touching files without guard should be fixed in one pass.
- **DDD layer:** test infrastructure (no production code change)
