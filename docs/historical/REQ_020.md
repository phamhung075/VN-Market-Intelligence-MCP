status: READY_FOR_ARCHITECT
sprint: 020
po_vision: Add Polymarket as a Level 1 (global) intelligence source — poll macro and geopolitical prediction markets every 30 minutes, detect abnormal crowd-money flows, and feed those signals into the existing cascade engine so Vietnam-relevant events surface as actionable alerts before traditional news reports them.

---

## User Story

As a Vietnamese stock investor using Claude,
I want the system to monitor Polymarket prediction markets for macro and geopolitical events that affect Vietnam (Fed rate decisions, US-China trade war, oil supply shocks, ASEAN instability),
So that I receive early-warning alerts when crowd money moves significantly on these events — often before traditional news sources confirm them — giving me a timing edge in positioning VNM, FPT, VCB, and VEA.

---

## Context: Why prediction markets as a Level 1 source

Polymarket is a decentralized prediction market where real money is staked on event outcomes (e.g. "Will the Fed cut rates in June 2026?"). The probability prices are continuous, liquid signals that aggregate information from professional traders, hedge funds, and informed participants globally. Because participants have financial incentive to be accurate, large probability shifts — especially those that occur before news is published — represent a high-quality early-warning signal ("the crowd knows first").

Three failure modes this feature addresses:
1. **Latency gap**: Traditional news sources (CafeF, VnExpress, Reuters) report events after they happen. Prediction market probability shifts can precede news by hours or days.
2. **Sentiment-price divergence**: When news sentiment is bullish but prediction market probability of a risk event is rising sharply, the divergence is a warning signal our `sentimentClassifier` and `priceNewsValidator` cannot currently detect.
3. **Manipulation surface**: Wash trading exists in prediction markets (~30% of volume per user's assessment). Using volume alone is unreliable. The spec mitigates this by requiring unique wallet count as a reliability qualifier.

## Functional Requirements

### FR-1: Polymarket REST fetcher (`src/infrastructure/fetchers/polymarket.ts`)

- **Description**: Fetch open prediction markets from two complementary Polymarket APIs. Return typed `PredictionMarket` objects. Never throw — return empty array on any error. Mirror the pattern established by `tradingEconomicsStream.ts`.
- **Primary API (CLOB)**: `GET https://clob.polymarket.com/markets?closed=false&limit=100`
  - Returns live market data: condition_id, question, end_date_iso, yes/no token prices, volume.
  - No authentication header needed for read-only access.
- **Secondary API (Gamma)**: `GET https://gamma-api.polymarket.com/markets?closed=false&limit=100`
  - Returns richer metadata: unique_wallets_count, tags, liquidity, last_trade_price.
  - Used to enrich CLOB results by matching on `condition_id` / `id`.
- **Market discovery filter** — a market is considered Vietnam-relevant if:
  - Its `question` text (case-insensitive) contains at least one keyword from `predictionMarkets.relevantKeywords` config list, OR
  - Its `id` (condition_id) appears in `predictionMarkets.curatedMarketIds` config list.
- **Input**: none (all config-driven).
- **Output**: `PredictionMarket[]` — typed array, empty on error.
- **PredictionMarket data model** (new type, see Data Model section):

  ```
  id: string                 — condition_id from CLOB API
  question: string           — human-readable market question
  endDate: string            — ISO 8601 expiration date
  yesPrice: number           — probability of YES outcome (0.0–1.0)
  noPrice: number            — probability of NO outcome (0.0–1.0)
  volume24h: number          — 24h trading volume in USD
  volumeTotal: number        — all-time total volume in USD
  liquidity: number          — current liquidity pool in USD
  lastTradePrice: number     — most recent trade price
  uniqueWalletsCount: number — distinct wallet addresses that traded (from Gamma)
  tags: string[]             — category tags (from Gamma)
  fetchedAt: string          — ISO 8601 timestamp of this fetch
  ```

- **Timeout**: 15 seconds per API call (same as existing fetchers).
- **Rate limiting**: CLOB API publicly documents a 10 req/min limit for unauthenticated access. At 30-min polling intervals with 2 calls per cycle, we stay well within limits. Add a configurable `rateLimitDelayMs` (default 500 ms) between the two API calls.
- **Error handling**: catch all network errors, HTTP 4xx/5xx, and JSON parse errors. Log at `warn` level and return `[]`. Never propagate exceptions to the caller.
- **DDD layer**: infrastructure/fetchers — may use HTTP. Must not import from domain/.
- **Target file**: `src/infrastructure/fetchers/polymarket.ts`

### FR-2: Prediction signal detector (`src/domain/services/predictionSignalDetector.ts`)

- **Description**: Pure domain function. Takes a snapshot array of `PredictionMarket` objects (current) and a previous snapshot (from in-memory or SQLite cache), and emits `PredictionSignal` objects. Zero I/O, zero side effects — pure computation, fully testable.
- **Signal type 1 — `volume_spike`**:
  - Condition: `market.volume24h >= config.volumeSpikeThresholdUsd` (default $50,000 USD).
  - Reasoning: High volume indicates significant crowd interest in this outcome.
- **Signal type 2 — `probability_shift`**:
  - Condition: `|currentYesPrice - previousYesPrice| >= config.probabilityShiftPct / 100` (default 0.05, i.e. 5 percentage points).
  - Direction: `bullish` if yes price increased, `bearish` if decreased.
  - Reasoning: A sharp probability move in one cycle indicates new information entering the market.
- **Signal type 3 — `insider_timing`** (cross-validation signal — addresses human requirement 1):
  - Condition: A `probability_shift` signal is detected AND the market's `uniqueWalletsCount` has increased by >= 3 wallets since the previous snapshot AND no corresponding news entry exists in `rag_analyses` within the past 2 hours (checked via injected DB query).
  - Reasoning: Probability moving on few wallets with no news could be insider-like information flow.
  - Note: This is the highest-severity signal. DB query is injected as a dependency (not embedded in the pure function) to keep the service testable without SQLite.
- **Signal type 4 — `sentiment_divergence`** (cross-validation signal — addresses human requirement 3):
  - Condition: The market's `yesPrice` for a risk event is >= 0.65 (i.e. crowd assigns 65%+ probability to a risk materialising) AND the current cascade engine's `AnalysisEntry` for the same topic has a `bullish` sentiment direction AND confidence >= 0.6.
  - Reasoning: The crowd is pricing in significant risk while our news sentiment is bullish — a divergence warning.
  - Note: This signal requires a `recentSentiment` parameter injected by the application layer. The pure function itself just evaluates the comparison.
- **Quality filter**: signals where `market.uniqueWalletsCount < config.minUniqueWallets` (default 10) are downgraded to severity `low` regardless of volume or probability shift magnitude, flagging potential wash trading.
- **Output**: `PredictionSignal[]` — see Data Model section below.
- **Signal-to-Signal mapping**: `PredictionSignal` maps to the existing `Signal` interface (from `signalDetector.ts`) for downstream alert generation:
  - `type` maps to new `SignalType` value `"prediction_market"` (FR-4 extends the union).
  - `severity` computed as: `insider_timing` → `high`, `sentiment_divergence` → `medium` to `high` (based on divergence magnitude), `probability_shift` → `medium`, `volume_spike` → `low`.
  - `actionCode` = the watchlist stock code resolved by `predictionCascadeMapper` (FR-3).
  - `confidence`: derived from `uniqueWalletsCount` quality and shift magnitude (formula in implementation notes below).
- **DDD layer**: domain/services — zero imports from infrastructure or application.
- **Target file**: `src/domain/services/predictionSignalDetector.ts`

**Confidence formula**:
```
walletQuality = min(1.0, uniqueWalletsCount / 100)   # 100+ wallets → full quality
shiftMagnitude = min(1.0, |yesPrice - prevYesPrice| / 0.20)  # 20pp shift → full magnitude
confidence = walletQuality * 0.5 + shiftMagnitude * 0.5
# Clamped to [0.1, 0.95]
```

### FR-3: Prediction cascade mapper (`src/domain/services/predictionCascadeMapper.ts`)

- **Description**: Pure domain function. Maps a prediction market question string to one or more `DomainType` sectors and watchlist stock codes. Returns a `CascadeMapping` object. Zero I/O.
- **Input**: `question: string`, `watchlistCodes: string[]`.
- **Output**: `CascadeMapping` — see Data Model section.
- **Keyword rule engine**: The mapper applies an ordered list of `KeywordRule` objects. Each rule has:
  - `keywords: string[]` — one or more terms that must appear in the question (case-insensitive).
  - `domains: DomainType[]` — sectors affected.
  - `stocks: string[]` — specific stock codes directly affected (may be empty if the sector rule covers it).
  - `direction: "bullish" | "bearish" | "neutral"` — whether YES outcome is positive or negative for VN markets.
  - `reasoning: string` — human-readable explanation for the mapping.
- **Mandatory keyword rules** (minimum required coverage):

  | Keywords | Domains | Stocks | YES direction |
  |----------|---------|--------|---------------|
  | fed, rate cut, interest rate cut, federal reserve cut | banking | VCB, TCB, BID, CTG | bullish |
  | fed, rate hike, interest rate rise, federal reserve raise | banking | VCB, TCB, BID, CTG | bearish |
  | us-china trade war, china tariff, trade war | manufacturing, steel | HPG, GAS | bearish |
  | oil price, crude oil, brent | oil_gas, energy | GAS, PLX | varies by direction |
  | vietnam gdp, vietnam economy, vietnam growth | all watchlist | (inject watchlistCodes) | bullish |
  | asean, asean summit, southeast asia | all watchlist | (inject watchlistCodes) | neutral |
  | war, conflict, sanctions, military | all watchlist | (inject watchlistCodes) | bearish |
  | china economy, china gdp, china slowdown | manufacturing, steel, tech | HPG, FPT | bearish |
  | dollar, dxy, usd strength | banking, retail | VCB, VNM | bearish |
  | inflation, cpi | banking, retail | VCB, MWG | bearish |
  | tariff, trade barrier, import duty | manufacturing | HPG, VNM | bearish |
  | taiwan, strait, china taiwan | tech, manufacturing | FPT, HPG | bearish |

- **Multiple rules can match**: all matching domain/stock lists are union-merged. If the same stock appears in multiple rules, it is deduplicated.
- **watchlistCodes injection**: rules tagged with `"all watchlist"` receive the `watchlistCodes` parameter at runtime so the mapper stays pure (no DB access).
- **Zero-match fallback**: if no keyword rule matches, the mapper returns `{ domains: [], stocks: [], matched: false, reasoning: "No Vietnam-relevant keywords found" }`.
- **DDD layer**: domain/services — zero imports from infrastructure or application.
- **Target file**: `src/domain/services/predictionCascadeMapper.ts`

### FR-5: Scheduler integration

- **Description**: Create a new dedicated scheduler job `predictionMarketJob.ts`. Do NOT modify the existing `intelligenceCycleJob.ts` in this sprint (avoid merge conflicts with sprint 019 work still in Review). The job can be promoted to a cycle step in a future sprint.
- **Job name**: `predictionMarketJob`
- **Cron expression**: sourced from `config.scheduler.predictionMarketPoll` (default: `*/30 * * * *`).
- **Job steps**:
  1. Check `config.predictionMarkets.enabled` — if false, skip and log at `debug` level.
  2. Load watchlist from DB.
  3. Load previous market snapshot from `prediction_markets` SQLite table (last stored row per market id).
  4. Call `fetchPolymarkets()` from `polymarket.ts`.
  5. If no markets returned (API down or rate-limited), log at `warn` and exit gracefully.
  6. Store new snapshot to `prediction_markets` table (upsert by market `id`).
  7. Call `detectPredictionSignals(currentMarkets, previousMarkets, watchlist, { db })`.
  8. For each `PredictionSignal`, call `predictionCascadeMapper` to resolve `actionCode`.
  9. Convert to `Signal[]` and call `generateAlerts()` + `storeAlerts()`.
  10. For `HIGH` or `CRITICAL` severity alerts: send Telegram notification in Vietnamese (step 10, reuses existing `sendTelegram` notifier).
- **Concurrency guard**: the job must set and release a boolean lock to prevent overlapping runs (mirrors the pattern in `intelligenceCycleJob.ts`).
- **DDD layer**: scheduler (entry point layer) — may import from application and infrastructure.
- **Target files**:
  - `src/scheduler/predictionMarketJob.ts` — job implementation
  - `src/scheduler/jobs.ts` — register new cron expression `predictionMarketPoll`
  - `src/interface/scheduler/index.ts` — wire new job into `startScheduler()`

## Non-Functional Requirements

### Performance
- Polymarket fetcher must complete within 15 seconds per API (30s total for both APIs combined).
- Signal detection is synchronous and must complete in < 50 ms for up to 100 markets.
- Cascade mapper is synchronous and must complete in < 10 ms per market.
- The prediction market job's total wall-clock time must not exceed 60 seconds end-to-end.

### Data freshness
- Markets are polled every 30 minutes, 24 hours a day, 7 days a week.
- The SQLite snapshot is updated on every successful poll (upsert by market id).
- `get_prediction_markets` MCP tool returns data from the last successful poll. If the last poll was more than 2 hours ago, the tool response should include a `stale: true` flag.

### Reliability / Error handling
- The polymarket fetcher must never throw or crash the server.
- If the Gamma API is unavailable, the fetcher degrades gracefully: CLOB data is returned with `uniqueWalletsCount: 0` and `tags: []`. Signals generated from zero-wallet-count markets are automatically capped at `low` severity (quality filter in FR-2).
- If the CLOB API is unavailable, return `[]` and log at `warn`. The prediction market job exits after step 5 (no-op cycle).
- Rate limiting (HTTP 429 from CLOB): log at `warn`, return `[]`. The next poll cycle will retry automatically.
- The existing circuit breaker infrastructure (`circuitBreakerRegistry.ts`) should wrap the Polymarket fetcher call in `predictionMarketJob.ts`.

### Language
- Telegram alerts: Vietnamese (transliterated plain text as per existing notifier style).
- MCP tool output: English (consistent with all other MCP tools in this codebase).
- Log messages: English (consistent with all other log messages).

### DDD compliance
- `predictionSignalDetector.ts` and `predictionCascadeMapper.ts` must contain zero imports from `infrastructure/` or `application/`.
- `polymarket.ts` must contain zero imports from `domain/`.
- The `prediction_market` SignalType extension must reside in `domain/services/signalDetector.ts`.

## Edge Cases and Data Quality

- [ ] **Empty poll result**: Polymarket API returns HTTP 200 with `[]` — treat as valid (no relevant markets currently). Log at `debug`. No signals generated.
- [ ] **Corrupt JSON**: API returns non-array or malformed JSON — log at `warn`, return `[]`.
- [ ] **Market expired mid-poll**: `end_date` is in the past — skip this market entirely when loading from DB into signal detection. Add `WHERE end_date > datetime('now')` filter in SQLite query.
- [ ] **First-ever poll (no previous snapshot)**: `yesPricePrev` will be `null`. `probability_shift` signals must require a non-null previous price. `volume_spike` signals have no such dependency and fire normally on first poll.
- [ ] **Wash trading / volume inflation**: uniqueWalletsCount < 10 → severity downgraded to `low`. This does not suppress the signal entirely — it remains informational.
- [ ] **Binary market assumption**: the CLOB API returns `yes_price + no_price = 1.0` for binary markets. For multi-outcome markets (e.g. "Which party wins?"), skip and log at `debug` — out of scope.
- [ ] **Price outside 0–1**: if API returns `yesPrice > 1.0` or `yesPrice < 0.0`, clamp and log at `warn`.
- [ ] **Rate limiting (HTTP 429)**: back off and return `[]`. Do not retry within the same poll cycle to avoid multiplying rate-limit risk.
- [ ] **Large number of matching markets**: cap at `config.predictionMarkets.maxMarketsPerPoll` (default 50) after keyword filtering. Take the top-N by `volume24h` descending to retain the highest-signal markets.
- [ ] **Duplicate signal deduplication**: if the same market fires a signal on two consecutive polls, the cooldown mechanism from `alertCooldown.ts` (task 131) applies — the underlying alert will be suppressed within the cooldown window.
- [ ] **Network timeout**: 15-second AbortController timeout per API call (same pattern as all other fetchers). Return `[]` on abort.
- [ ] **`curatedMarketIds` contains a closed market**: the market will appear in the CLOB response with `active: false` (or simply absent). The fetcher must check market status and skip closed markets.

## Acceptance Criteria

### AC-1: Fetcher returns Vietnam-relevant markets

**Given** the Polymarket CLOB API returns at least 5 open binary markets, and at least one has the word "Fed" in its question text,
**When** `fetchPolymarkets()` is called (with a mock HTTP response),
**Then**:
- The function returns a non-empty `PredictionMarket[]`.
- Each returned market has `id`, `question`, `yesPrice`, `noPrice`, `volume24h` populated.
- `yesPrice` is in [0.0, 1.0].
- The market with "Fed" in its question is included.

## Implementation Notes for Architect

### API endpoints to validate before coding

The following endpoints are used unauthenticated. The Architect should verify the exact response shape (field names, nesting) from a live curl before writing the type definitions:

1. CLOB API: `curl "https://clob.polymarket.com/markets?closed=false&limit=5"`
   - Expected fields: `condition_id`, `question`, `end_date_iso`, `tokens` (array with `outcome` and `price`).
2. Gamma API: `curl "https://gamma-api.polymarket.com/markets?closed=false&limit=5"`
   - Expected fields: `id`, `uniqueWallets`, `tags`, `liquidity`, `lastTradePrice`.

The `condition_id` from CLOB must match the `id` from Gamma to enable enrichment joins. If this field name diverges across API versions, the Architect should specify the fallback matching strategy (e.g. normalise both to lowercase).

### Circuit breaker registration

A new entry `"polymarket"` should be added to `circuitBreakerRegistry.ts` (same pattern as `"cafef"`, `"tradingEconomics"`, etc.). This is an infrastructure concern for the Architect to specify in TECH_020.md.

### Previous snapshot storage strategy

For `probability_shift` detection, the fetcher needs to compare current vs previous `yesPrice`. Two options:
- **Option A (in-memory)**: store last snapshot in a module-level `Map<string, PredictionMarket>` inside `predictionMarketJob.ts`. Cleared on server restart.
- **Option B (SQLite)**: read previous snapshot from `prediction_markets` table before each poll. Survives server restarts.

The Architect should choose between these in TECH_020.md. Option B is recommended for production reliability.
