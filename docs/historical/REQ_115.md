# REQ-115: fix(france-summary): stale alerts in France morning digest

status: READY_FOR_ARCHITECT
sprint: 115
po_vision: France morning digest only shows alerts from the last 24 hours; restart near 07:00 UTC does not double-send.

## User Story

As a Vietnamese stock investor based in France,
I want the morning digest to show only alerts from the last 24 hours,
So that I never receive a weeks-old NGHIEM TRONG alert as if it were current intelligence.

---

## Functional Requirements

### FR-1: 24-hour time window on fetchTopAlerts

- Description: `fetchTopAlerts` currently has no `WHERE` clause on `triggered_at`, so it returns the 3 highest-severity alerts ever stored. Add a time-window predicate to restrict results to the rolling 24-hour window.
- Input: SQLite `alerts` table with `triggered_at TEXT` (ISO-8601 UTC).
- Output: At most 3 `AlertRow` objects where `triggered_at >= datetime('now', '-24 hours')`, ordered by severity rank DESC, then `triggered_at DESC`.
- Business rule: An alert older than 24 hours must never appear in the France morning digest. The 24-hour window is calculated in UTC (same timezone as `triggered_at` storage).
- DDD layer: interface/scheduler (`src/scheduler/franceSummaryJob.ts`)

### FR-2: Same-day dedup guard before send

- Description: When the server restarts near 07:00 UTC on a weekday, the cron may fire twice. Add a DB-level guard (identical pattern to `eveningSummaryJob`) that checks `market_messages` before sending.
- Input: `market_messages` table with `from_agent TEXT` and `sent_at TEXT` (server default `datetime('now')`).
- Output: If a row with `from_agent = 'france-summary'` and `sent_at >= date('now')` already exists, return `{ sent: false, moverCount: 0, alertCount: 0, taCount: 0 }` without querying alert/price data.
- Business rule: Fail-open — if the `market_messages` table is unavailable or the query throws, proceed with the send (do not suppress).
- DDD layer: interface/scheduler (`src/scheduler/franceSummaryJob.ts`)

### FR-3: Persist `from_agent = 'france-summary'` on send

- Description: The current `runFranceSummary` calls `sendTelegramMarket(text, { parseMode: "" })` with no `persist` option, so `from_agent` is recorded as `"unknown"` in `market_messages`. Fix the send call to pass `persist: { from_agent: "france-summary", message_type: "france_summary" }` so the dedup guard in FR-2 finds the correct row.
- Input: Successful Telegram send.
- Output: `market_messages` row with `from_agent = 'france-summary'`, `message_type = 'france_summary'`.
- Business rule: The `from_agent` value `"france-summary"` is already declared in `MarketAgent` union in `marketMessageStore.ts` (line 39) — no schema change required.
- DDD layer: interface/scheduler (`src/scheduler/franceSummaryJob.ts`)

### FR-4: `FranceSummaryOptions` — injectable DB for dedup guard

- Description: The dedup guard (FR-2) must use the same injected `db` as the existing query helpers so tests can pass an in-memory SQLite with the `market_messages` table. The production path resolves `db` via `getDb()` (already done in `runFranceSummary`).
- Input: `FranceSummaryOptions.db?: Database`
- Output: No new interface fields required; `db` is already injectable.
- DDD layer: interface/scheduler

## Non-Functional Requirements

- Performance: The two new SQL queries (time-windowed `fetchTopAlerts` + dedup check) each add at most one indexed lookup. Both `triggered_at` and `sent_at`/`from_agent` columns have existing indexes (`idx_alerts_triggered_at` if present, `idx_mm_sent_at`, `idx_mm_from_agent`). No query plan regression expected.
- Data freshness: 24-hour window is intentional. On Vietnam holidays or weekends when no alerts fire, the digest correctly shows "Khong co canh bao." — this is the desired behaviour.
- Language: Digest output remains Vietnamese plain-text. No format change required.
- Backward compatibility: `FranceSummaryResult` shape unchanged (`sent`, `moverCount`, `alertCount`, `taCount`). Existing 12 test cases in `1316-france-summary-rewrite.test.ts` must continue to pass.

## Edge Cases & Data Quality

- [ ] `market_messages` table absent on first boot — dedup guard catches the exception and returns `false` (fail-open), job proceeds normally.
- [ ] All alerts in DB are older than 24 hours — `fetchTopAlerts` returns `[]`; digest shows "Khong co canh bao." — correct.
- [ ] Server restarts exactly at `datetime('now')` boundary (midnight UTC) — `date('now')` in the dedup guard is midnight-aligned, matching the `sent_at` default. Edge case is safe: at worst a duplicate is sent at midnight, not the 07:00 restart scenario.
- [ ] Alert with `triggered_at = NULL` — excluded by `>= datetime('now', '-24 hours')` inequality (NULLs sort low in SQLite comparisons). Safe.
- [ ] `triggered_at` stored in Vietnam timezone (e.g. `+07:00` suffix) — the existing alert pipeline stores UTC via `datetime('now')`. The new filter is also UTC. Consistent.
- [ ] Multiple restarts on the same day — each restart after the first send hits the dedup guard, returns `sent: false`, no duplicate.

## Acceptance Criteria

### AC-1: Alert older than 24 hours is excluded

**Given** the `alerts` table contains one row with `triggered_at = datetime('now', '-25 hours')` and severity `'critical'`
**When** `runFranceSummary` is called with an injected DB
**Then**
- `result.alertCount === 0`
- The alert row is not included in the sent message

### AC-2: Alert within 24 hours is included

**Given** the `alerts` table contains one row with `triggered_at = datetime('now', '-1 hour')` and severity `'critical'`
**When** `runFranceSummary` is called with an injected DB and a capturing `sendFn`
**Then**
- `result.alertCount === 1`
- The sent message contains the alert's severity label

### AC-3: Dedup guard prevents second send on same day

**Given** the `market_messages` table has a row with `from_agent = 'france-summary'` and `sent_at = datetime('now')`
**When** `runFranceSummary` is called a second time with the same DB
**Then**
- `result.sent === false`
- The `sendFn` is not invoked
- No new row is inserted into `market_messages`

### AC-4: First send on a new day proceeds normally

**Given** the `market_messages` table has a row with `from_agent = 'france-summary'` and `sent_at = datetime('now', '-1 day')`  (yesterday)
**When** `runFranceSummary` is called today with movers or alerts present
**Then**
- `result.sent === true`
- `sendFn` is invoked once

### AC-5: Dedup guard is fail-open when market_messages is absent

**Given** the injected DB has no `market_messages` table
**When** `runFranceSummary` is called with movers or alerts present
**Then**
- `result.sent === true` (dedup throws, fails open, job proceeds)

## Implementation Notes for Architect

### fetchTopAlerts SQL delta (FR-1)

Current query (lines 120-126 of `franceSummaryJob.ts`):
```sql
SELECT id, severity, message, triggered_at
FROM alerts
ORDER BY <SEVERITY_CASE>, triggered_at DESC
LIMIT 3
```

Required query:
```sql
SELECT id, severity, message, triggered_at
FROM alerts
WHERE triggered_at >= datetime('now', '-24 hours')
ORDER BY <SEVERITY_CASE>, triggered_at DESC
LIMIT 3
```

### alreadySentToday helper (FR-2)

Copy the pattern from `eveningSummaryJob.ts` lines 27-41, changing `from_agent` value:
```sql
SELECT COUNT(*) AS cnt
FROM market_messages
WHERE from_agent = 'france-summary'
  AND sent_at >= date('now')
```
Fail-open: catch block returns `false`.
