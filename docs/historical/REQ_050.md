# REQ-050: Close the Cycle — Kinh Dich Goes Live + /ask Command

status: READY_FOR_ARCHITECT
sprint: 050
po_vision: Wire Kinh Dich into the autonomous 15-min cycle and give the user a direct /ask line from Telegram.

---

## User Stories

### Track A — Cycle Integration

**US-A1 (Task 303)**
As a Vietnamese stock investor using Claude,
I want the intelligence cycle to automatically compute and persist a Kinh Dich hexagram reading
for every watchlist stock on every 15-minute run,
So that hexagram state is always current and the Market Watcher agent can reference it without
requiring me to trigger anything manually.

**US-A2 (Task 304)**
As a Vietnamese stock investor using Claude,
I want the `get_portfolio_conviction` tool to include Kinh Dich as a sixth, independent
conviction dimension at 15% weight,
So that my conviction scores reflect the Kinh Dich signal alongside price action, volume,
sentiment, cascade, and sector alignment.

### Track B — /ask Telegram Command

**US-B1 (Task 305)**
As a Vietnamese stock investor using Claude,
I want a `user_requests` SQLite table and two MCP tools (`log_user_request` /
`get_pending_user_requests`) that let Claude agents read and write pending questions,
So that the async /ask pipeline has a reliable store-and-forward layer independent of Telegram.

**US-B2 (Task 306)**
As a Vietnamese stock investor using Claude,
I want the intelligence cycle Step F to synthesize a Vietnamese-language answer from live
market data, recent alerts, and the current hexagram state for each pending user request,
and deliver it via Telegram Chat Channel,
So that every question I ask is answered within one 15-minute cycle.

**US-B3 (Task 307)**
As a Vietnamese stock investor using Claude,
I want `/ask <question>` and `/why <TICKER>` Telegram commands to insert a pending request
and immediately confirm receipt in Vietnamese ("Da nhan cau hoi, se tra loi trong 15 phut"),
So that I can ask questions from my phone and know the system heard me.

### Housekeeping

**US-H1 (Task 308)**
As a developer maintaining this MCP server,
I want a single `registry.ts` file that lists all tools so I can add a new tool by editing
only that file instead of touching `server.ts`,
So that tool registration is a one-file change and the risk of merge conflicts is eliminated.

## Functional Requirements

### FR-1: Cycle Step A4 — Auto-compute hexagram per watchlist stock

- **Description**: After Step A3 (vnstock sync) completes, for every code in the watchlist,
  call the domain `computeReading()` function using the same best-effort score pipeline
  as `get_kinhdich_reading` (computeSentimentScore, computeForeignFlowScore,
  computeMacroScore, computeSectorScore, computeMacroIndicatorScore, computePriceVolScore —
  all exported from `kinhDichTools.ts`). Store the result via `storeReading()`. Record
  a Markov transition from the previous hexagram to the new one via `recordTransition()`.
- **Input**: watchlist codes (array of strings from Step 0 or re-queried in Step A4).
- **Output**: one `kinhdich_readings` row per stock per cycle with `source='cycle'` column
  (requires adding `source TEXT DEFAULT 'manual'` to the `kinhdich_readings` DDL via ALTER
  TABLE IF NOT EXISTS — idempotent).
- **Business rule**: if the watchlist is empty, Step A4 silently skips (log debug only).
  If a single stock fails score computation, log WARN and continue the others. Never throw
  from Step A4 — any error increments `errors` count but does not abort the cycle.
- **Performance**: Step A4 must complete within the 2-minute `STEP_TIMEOUT_MS` budget.
  For a 4-stock watchlist all 6 score functions are synchronous DB reads — no I/O bottleneck.
- **DDD layer**: scheduler (intelligenceCycleJob.ts) calls application/domain functions;
  score helpers live in interface/mcp/tools/kinhDichTools.ts (exported); store in infrastructure/db/hexagramStore.ts.

### FR-2: Conviction scorer 6th dimension — kinhDichScore at 15%

- **Description**: Add `kinhDichScore` as a sixth dimension to `computeConviction()` in
  `src/domain/services/convictionScorer.ts`. The dimension weight is 0.15. The existing
  five dimension weights must be scaled proportionally so all six sum to exactly 1.00.
  New weights (exact, no rounding): priceAction 0.255, volumeConfirmation 0.2125,
  sentiment 0.1275, cascade 0.1275, sectorAlignment 0.1275, kinhDich 0.15. Sum = 1.00.
- **Input**: new optional field `kinhDichScore?: number` on `ConvictionInput` (range [-1, +1]
  from the `confidence` and `tradingSignal` of the most recent `kinhdich_readings` row;
  caller is responsible for loading from DB before calling `computeConviction`).
- **Scoring function**: `scoreKinhDich(score: number | undefined): number`:
  - undefined or null → return 0.5 (neutral — no reading available).
  - Map [-1, +1] to [0, 1] linearly: `0.5 + score * 0.5`.
  - Clamp to [0, 1].
- **Output**: `ConvictionResult.dimensions` gains a `kinhDich` field.
  `ConvictionResult.summary` reflects the 6-dimension count where applicable.
- **`get_portfolio_conviction` tool**: for each watchlist stock, before calling
  `computeConviction`, load the most recent `kinhdich_readings` row and derive
  `kinhDichScore = confidence * (tradingSignal includes 'tich cuc' ? 1 : -1)`.
  If no row exists, pass `kinhDichScore: undefined`.
- **DDD layer**: domain (convictionScorer.ts) for scoring logic; interface (portfolioTools.ts)
  for loading the DB row and mapping it to the input field.

## Non-Functional Requirements

- **Performance**: Step A4 (hexagram batch) must complete within 2 minutes for up to 20
  watchlist stocks. Each stock requires 6 synchronous SQLite reads — O(n) with small n.
- **Data freshness**: `kinhdich_readings` rows from cycle runs are tagged `source='cycle'`;
  rows from on-demand `get_kinhdich_reading` tool calls are tagged `source='manual'`.
  `get_portfolio_conviction` reads the most recent row regardless of source.
- **Language**: all Telegram-facing output (receipts, answers) must be Vietnamese.
  Log messages are English. MCP tool descriptions are English (for Claude agent consumption).
- **No external API calls in Step A4**: score computation uses only local SQLite. No HTTP.
- **Backward compatibility**: `computeConviction(input)` callers that do not pass
  `kinhDichScore` must continue to work — the field is optional and defaults to neutral.
- **Idempotent schema migration**: adding `source TEXT DEFAULT 'manual'` to
  `kinhdich_readings` must use `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern
  (SQLite supports `IF NOT EXISTS` via try/catch on the ALTER — wrap in try/catch).

## Edge Cases and Data Quality

### Track A — Hexagram cycle

- [x] **Empty watchlist**: Step A4 reads watchlist codes from the same source as Step 0
  (the `watchlist` table). If the table is empty or returns 0 rows, log debug and return
  without iterating. `hexagramsComputed` count in CycleResult stays 0.
- [x] **Score function returns 0 for all 6 hao**: `computeReading()` with all-zero scores
  is valid — it resolves to Hexagram 1 (Qua Can). Do not special-case. The reading is stored
  and tagged with low confidence.
- [x] **computeReading() throws**: if `scores.length !== 6` or QUE_META lookup fails, catch
  per-stock, log WARN with the stock code, continue to next stock.
- [x] **kinhdich_readings missing `source` column**: older production DBs do not have this
  column. The Step A4 insert must use `INSERT INTO kinhdich_readings (..., source) VALUES
  (?, ..., 'cycle')` only after confirming the column exists via the idempotent ALTER.
  Alternatively, skip the column in the INSERT and set it via a separate UPDATE if present.
  Architect decides which approach. Simplest: wrap ALTER in try/catch in `initHexagramTables`.
- [x] **Markov transition with no prior reading**: first time a stock is computed, there is
  no previous hexagram. `recordTransition(prev, curr, code)` must be skipped if `prev`
  is null. Use `getLatestReading(code)` before `storeReading()` to obtain previous number.
- [x] **Step A4 timeout**: a misbehaving score function could block the cycle. Wrap the
  per-stock loop in `withTimeout` at the batch level (2 min total), not per-stock.
- [x] **Conviction with no kinhdich_readings row**: `get_portfolio_conviction` reads the DB
  for each stock. If no row exists (new stock, first cycle not yet run), pass
  `kinhDichScore: undefined` → neutral 0.5. The tool must not throw on absence.
- [x] **kinhDichScore derivation from tradingSignal text**: the `tradingSignal` field contains
  a string like "MUA (tich cuc)" or "BAN (tieu cuc)". Derive polarity from the suffix in
  parentheses. If the suffix is absent or unrecognised, default to 0 (neutral). Confidence
  is a REAL column and may be null — default to 0 when null.

### Track B — /ask pipeline

- [x] **Empty /ask payload**: `/ask` with no arguments. `handleAsk()` already returns a help
  string — confirm the check covers whitespace-only payloads.
- [x] **Ambiguous /ask (no stock mentioned)**: "What should I do?" has no ticker. Step F
  falls back to RAG-only answer (no price/hexagram enrichment). Answer is still sent.
- [x] **Telegram down during Step F answer send**: `sendTelegramMessage()` may throw or
  return false. In this case: do not mark the request `done`; leave it `pending` so the next
  cycle retries. Cap retries by adding a `retry_count INTEGER DEFAULT 0` column (future
  sprint). For Sprint 050: if send fails, log WARN and leave pending (existing behaviour).
- [x] **Race between Step F (cycle) and userRequestCheckJob**: both read pending rows. The
  existing CAS UPDATE (`SET status='processing' WHERE status='pending'`) in
  `userRequestCheckJob.ts` prevents double-processing. Step F in `intelligenceCycleJob.ts`
  does NOT use CAS — it reads then marks answered inline. Architect must decide whether to
  add CAS to Step F or rely on the separate `userRequestCheckJob`. See Blocker B1.
- [x] **More than 3 pending requests**: Step F processes up to 3 per cycle (existing limit).
  `userRequestCheckJob` processes up to 3 as well. In the worst case, a backlog of 10
  requests drains at 3 per cycle. This is acceptable — document the behaviour.
- [x] **/why with no argument**: `handleAsk(db, "")` → returns help string "Cach dung: /why VCB".
  The fix in Task 307 ensures the payload stored is `why:<TICKER>` not the English sentence.
  `/why` with no argument must NOT insert a `user_requests` row.
- [x] **Duplicate /ask requests**: same question submitted twice. Two rows are inserted with
  distinct IDs. Both are answered independently. No deduplication at insert time (by design —
  each submission is intentional).
- [x] **kinhdich_readings missing for mentioned stock**: Step F's enrichment block queries
  `getLatestReading(code)` — returns null if no row. The answer is sent without hexagram
  enrichment ("Chua co du lieu Kinh Dich cho ma nay").

### Task 308 — Registry

- [x] **server.ts import order**: `registry.ts` must import all `register*Tools` functions.
  Circular import risk is zero because registry.ts is a leaf that only imports from
  individual tool files (no domain/application layer imports).
- [x] **Existing tests that import server.ts directly**: if any test constructs a McpServer
  and calls registerAll, the test should import from registry.ts, not server.ts. Verify
  no existing test is broken by the refactor.

## Blockers (STOP — must answer before coding)

- [ ] **B1 — CAS in Step F**: `intelligenceCycleJob.ts` Step F does not use a
  compare-and-swap claim before processing a user request. `userRequestCheckJob.ts` does.
  With both running (cycle every 15 min, check job every 15 min), the same row could be
  processed twice, sending two Telegram messages for one question.
  **Question for Architect**: should Step F be refactored to use the same CAS pattern as
  `userRequestCheckJob.ts`, or should Step F be removed and the dedicated check job
  become the sole processor? The check job already covers the off-hours throttle gap.

- [ ] **B2 — `source` column migration strategy**: the `kinhdich_readings` table was created
  without a `source TEXT DEFAULT 'manual'` column. The Architect must decide:
  (a) add `ALTER TABLE kinhdich_readings ADD COLUMN source TEXT DEFAULT 'manual'` inside
  `initHexagramTables()` wrapped in try/catch (simplest), or (b) introduce a formal
  migration system. The BA recommends option (a) for Sprint 050 scope.
  **Question for Architect**: confirm approach (a) is acceptable given no migration framework
  currently exists.

- [ ] **B3 — kinhDichScore polarity derivation**: the conviction scorer needs a numeric
  `kinhDichScore` in [-1, +1]. The `kinhdich_readings.trading_signal` column stores a
  string ("MUA (tich cuc)", "BAN (tieu cuc)", "GIU (tich cuc)", etc.) and
  `kinhdich_readings.confidence` stores REAL [0, 1].
  **Proposed formula**: `score = confidence * (signal contains 'tich cuc' ? +1 : signal
  contains 'tieu cuc' ? -1 : 0)`. This means GIU with tich cuc = positive but low
  magnitude.
  **Question for Architect/PO**: is this formula acceptable, or should MUA/BAN/GIU map to
  fixed polarities (+1/–1/0) independent of the tich cuc/tieu cuc suffix?

## Implementation Notes for Architect

### On Task 303 — CycleResult extension

`CycleResult` interface in `intelligenceCycleJob.ts` must gain a `hexagramsComputed: number`
field. `CycleDeps` must gain an optional `computeHexagramsFn?: (codes: string[]) => Promise<number>`
for test injection. Default production implementation calls score helpers + `computeReading` +
`storeReading` inline (no separate use case file needed for Sprint 050 scope).

### On Task 304 — weight precision

The exact weight split for 6 dimensions summing to 1.00:
- priceAction: 0.30 * 0.85 = 0.2550
- volumeConfirmation: 0.25 * 0.85 = 0.2125
- sentiment: 0.15 * 0.85 = 0.1275
- cascade: 0.15 * 0.85 = 0.1275
- sectorAlignment: 0.15 * 0.85 = 0.1275
- kinhDich: 0.15 (fixed)
- Sum = 0.2550 + 0.2125 + 0.1275 + 0.1275 + 0.1275 + 0.1500 = 1.0000

### On Task 306 — Step F enrichment logic (stock extraction)

Stock codes in Vietnamese questions are uppercase 2-4 letter sequences. Extraction regex:
`/\b([A-Z]{2,4})\b/g` applied to `req.payload.toUpperCase()`. Filter results against
known codes from the `watchlist` table to avoid false positives ("AI", "GO", etc.).
If multiple codes are found, enrich for all of them (up to 3 to control message length).

### On Task 308 — server.ts pattern

Current `server.ts` calls ~67 `register*Tools(server)` lines. The refactor replaces all of
them with:
```typescript
import { toolRegistry } from "./tools/registry.js";
toolRegistry.forEach(fn => fn(server));
```
The `registry.ts` file is a flat array literal — no logic. Type is
`Array<(server: McpServer) => void>`.
