## 3. Architect Decisions on Open Questions

### 3.1 FULL vs PASSIVE for 30-minute checkpoint (Q-WAL-2 = B)

**Decision: FULL mode during live hours.**

PASSIVE is non-blocking but leaves frames when readers are active, which is precisely the failure mode that caused the 44 MB WAL incident. FULL blocks new writers (not readers) until all current readers release their read locks, guaranteeing all frames are checkpointed eventually. Given Bun's single-threaded event loop, "blocking new writers" means no new queries start until the checkpoint is satisfied — acceptable for a sub-second operation at 30-minute intervals.

TRUNCATE is reserved for: (a) nightly off-hours 03:00–05:00 UTC when reader pressure is minimal and we want WAL reset to zero, and (b) the SIGTERM shutdown hook.

### 3.2 Python services read-only (Q-WAL-1 = B)

**Decision: documentation-only for Sprint 1329.**

Brownfield analysis confirms `imfDataFetcher.ts` (application layer) writes to `imf_indicators` via `getDb()` — not a Python service. The `pdf-extractor` and `rag-service` Python services use HTTP push endpoints (`POST /api/push-*`) established in Phase 1a/1b of the DDD microservices migration. They do not open `market.db` directly. FR-WAL-5 is satisfied by adding a comment to the docker-compose volume mount for clarity.

### 3.3 `backupDatabase()` placement: `checkpoint.ts` or new `backup.ts`?

**Decision: keep in `checkpoint.ts`.**

The two responsibilities (checkpoint + backup) are tightly coupled: backup is triggered _after_ the nightly TRUNCATE checkpoint and uses the same `dbPath`. Extracting to `backup.ts` would create a one-function file with no reuse elsewhere. The single-responsibility principle is better served here by the module boundary (`infrastructure/db/`) than by file proliferation.

### 3.4 `imfConvictionBridge.ts` placement

**Decision: `application/services/` — confirmed correct.**

DDD layer rule: application layer orchestrates domain services + infrastructure access. The bridge calls `classifyImfIndicators()` (domain) and reads from SQLite (infrastructure). It does not import from `interface/`. Layer direction: `interface → application → domain`. The DB instance is injected as a parameter (ports pattern) — no coupling to `getDb()` singleton.

### 3.5 IMF staleness threshold (Q-IMF-3)

**Decision: `Bun.env.IMF_STALENESS_HOURS ?? 24` at module load time in `imfConvictionBridge.ts`.**

24h default: the IMF poller runs every 6h; at 24h, four consecutive missed cycles would still produce fresh data. Stale data (missed cycles) maps to `sentiment: 0` via `classifyImfIndicators()` allStale path — neutral, not error. The env var allows ops to tighten (e.g. 12h) without code deployment.

## 8. Risk Flags

**R1 — WEIGHTS rescaling breaks existing tests (Medium, Certain)**
The 6 existing weight values change. Tests `312-conviction-kinhdich.test.ts` and `1328d-conviction-enrichment.test.ts` assert exact score values. Developer must update expected values in those tests during 1329e. This is not a bug — it is an intentional change. Add a comment in each updated test citing Task 1329e.

**R2 — 30-minute checkpoint increases DB write pressure (Low, Managed)**
`recordJobRun` inserts one row per checkpoint execution — 48 rows/day vs 4 previously. SQLite handles this trivially. The checkpoint itself is a read-side operation (no data written to user tables). Net I/O increase is negligible.

**R3 — `imfMacroScore` always 0 on fresh DB after WAL corruption recovery (Low, Acceptable)**
After a WAL corruption event and DB recovery, `imf_indicators` table may be empty or stale. `getImfMacroScoreForConviction` returns 0 → neutral (0.5). This is the designed fallback per NFR-IMF-3. Alert quality degrades slightly until the IMF poller refills the table (within 6h of recovery).

**R4 — 1329a/b/c modify the same block in `jobs.ts` (Low, Manageable)**
All three tasks touch the cron handler block at lines 370-375. On parallel branches this creates a merge conflict. Resolution: merge 1329a first, then rebase 1329b onto merged 1329a, then rebase 1329c onto merged 1329b. The conflict is always additive (new lines, no deletions). PM should enforce this merge order.

**R5 — `Bun.file(path).size` on non-existent WAL returns 0 not throws (Low, Confirmed)**
Bun's `Bun.file().size` is documented to return 0 for non-existent files. Confirmed safe. No try/catch needed in `checkWalFileSize` for this path.
