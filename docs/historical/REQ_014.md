### FR-1: Fix Step E — Read unnotified HIGH/CRITICAL alerts from SQLite and send to Telegram (Task 137)

**Context — the exact bug:**
`intelligenceCycleJob.ts` lines 294-306 contain:

```typescript
// Step E: Send HIGH/CRITICAL alerts to Telegram
const alerts: Alert[] = [];          // ← always empty array
telegramAlertsSent = await sendAlertsFn(alerts);
```

Alerts are written to the `alerts` SQLite table by `storeAlerts()` inside `pollNews()` (Step A),
but Step E never reads them back. The `sendAlertsFn` receives an empty array every cycle.

**Schema gap:** The `alerts` table has no `notified_telegram` column. Without it, re-sends
occur on every cycle restart, and there is no idempotency guarantee.

- **Description:** Add `notified_telegram INTEGER NOT NULL DEFAULT 0` column to the `alerts`
  table via `ALTER TABLE IF NOT EXISTS` pattern (try/catch). Update Step E to query:

  ```sql
  SELECT * FROM alerts
  WHERE severity IN ('high', 'critical')
    AND notified_telegram = 0
    AND triggered_at >= datetime('now', '-16 minutes')
  ORDER BY triggered_at ASC
  ```

  After each successful `notifyTelegramAlert()` call, update:

  ```sql
  UPDATE alerts SET notified_telegram = 1 WHERE id = ?
  ```

  The 16-minute window matches the scheduler interval (cron `*/15 * * * *`) with 1-minute
  overlap to absorb drift. The window is hard-coded in the default implementation; it must
  be injectable via `CycleDeps` for test determinism.

- **Input:** SQLite `alerts` table, severity filter `['high', 'critical']`, window of 16 min.
- **Output:** `telegramAlertsSent: number` in `CycleResult`.
- **Business rule:** `notified_telegram = 1` is set only after a successful send (return value
  `true` from `notifyTelegramAlert`). Failed sends leave the flag at 0 so the next cycle retries.
  Critical alerts are never suppressed by the existing cooldown rules
  (`alertQuality.neverSuppressSeverity = ["critical"]`).
- **Migration:** `ALTER TABLE alerts ADD COLUMN notified_telegram INTEGER NOT NULL DEFAULT 0`
  wrapped in try/catch in `initDatabase()`. Add index:
  `CREATE INDEX IF NOT EXISTS idx_alerts_notified ON alerts(notified_telegram, severity)`.
- **DDD layer:** `infrastructure/db/schema.ts` (migration), `interface/scheduler/intelligenceCycleJob.ts`
  (Step E query + loop), `infrastructure/db/alertStore.ts` (new `markAlertNotified()` helper).
- **CycleDeps change:** Add optional `readUnnotifiedAlertsFn?: (windowMs: number) => Promise<Alert[]>`
  to `CycleDeps`. Default reads from SQLite. Tests inject an in-memory stub.

### FR-2: Fix Step D — Replace placeholder with real runImpactChain call (Task 138)

**Context — the exact bug:**
`intelligenceCycleJob.ts` lines 155-159 contain:

```typescript
async function defaultRunImpactChain(): Promise<number> {
  // Impact chain is already run inside pollNews per-entry.
  // This placeholder returns 0 to indicate no additional events were processed.
  return 0;
}
```

The comment is outdated and incorrect. `pollNews` does run a simplified per-entry cascade
(producing `Signal` objects and `Alert` rows), but `runImpactChain` from
`application/usecases/runImpactChain.ts` is a richer pipeline that includes macro context
(commodity + SBV rates) and structured `CausalChain` output. The current placeholder means
`impactEventsRan` is always 0 and the full cascade never runs.

**Data flow gap:** `PollNewsResult` currently does not expose the IDs of newly inserted
`rag_analyses` rows. `intelligenceCycleJob` therefore cannot know which entries to pass to
`runImpactChain`. Step A captures the news but does not surface `insertedIds`.

- **Description:**

  1. Add `insertedIds: string[]` to `PollNewsResult` in `pollNews.ts`. Populate it with the
     `entry.id` of every row where `tryInsertEntry()` returns `true`.

  2. In `intelligenceCycleJob.ts`, update Step A to capture `pollResult.insertedIds`:

     ```typescript
     const pollResult = await pollNewsFn();
     newsFetched = pollResult.fetched;
     const insertedIds = pollResult.insertedIds ?? [];
     ```

  3. Replace `defaultRunImpactChain()` with a real implementation that:
     - Loads the watchlist from SQLite.
     - For each `insertedId`, reads the `rag_analyses` row (summary + source_title fields).
     - Calls `runImpactChain({ newsText: entry.summary, seedEntry: entry, watchlist })`.
     - Returns the count of calls completed without throwing.
     - Is error-isolated per entry (one failure does not abort the rest).

  4. Pass `insertedIds` to `runImpactChainFn` via the injectable `CycleDeps.runImpactChainFn`.
     Update the signature: `runImpactChainFn?: (insertedIds: string[]) => Promise<number>`.

- **Input:** `insertedIds: string[]` from `PollNewsResult`. Watchlist from SQLite.
- **Output:** `impactEventsRan: number` in `CycleResult` (count of `runImpactChain` calls).
- **Business rule:** `impactEventsRan` reflects actual calls processed, not hardcoded 0.
  Empty `insertedIds` results in `impactEventsRan = 0` without any DB calls.
- **DDD layer:** `application/usecases/pollNews.ts` (add `insertedIds` to result),
  `interface/scheduler/intelligenceCycleJob.ts` (wire IDs, replace placeholder).

### FR-3: VN-Index live feed via CafeF index endpoint (Task 139)

**Context:** `get_market_snapshot` already calls `fetchHosePrices(["VNINDEX"])` (line 149 of
`marketTools.ts`) and renders the result in the header. However `fetchHosePrices` only queries
VnDirect (geo-blocked from France) and CafeF banggia at `index=1` (HOSE stocks only).
Neither source returns the VN-Index composite value.

The CafeF index endpoint `https://banggia.cafef.vn/stockhandler.ashx?index=0` returns an
array of index records. The record with `a === "VNINDEX"` carries the composite index value.

- **Description:** Add `fetchVnIndex()` to `src/infrastructure/fetchers/hose.ts`:

  - Endpoint: `https://banggia.cafef.vn/stockhandler.ashx?index=0`
  - Parse the JSON array. Find the record where `a === "VNINDEX"`.
  - The value field mapping (CafeF uses `×1000` for stocks, but index values are full points):
    - `a`: index code (`"VNINDEX"`, `"HNX"`, `"UPCOM"`)
    - `b`: reference value (previous close, stored as raw float — no ×1000)
    - `l`: current value (current index level — no ×1000)
    - `k`: change from reference
    - `totalvolume`: total market volume

  Return a `VnIndexSnapshot` type:

  ```typescript
  export interface VnIndexSnapshot {
    code: string;          // "VNINDEX"
    value: number;         // current index level (e.g. 1247.35)
    previousValue: number; // reference/previous close
    changePct: number;     // ((value - previousValue) / previousValue) * 100
    volume: number;        // total traded volume
    fetchedAt: string;     // ISO 8601
  }
  ```

  Store the result in `market_prices` as a row with `code = "VNINDEX"` (same upsert path as
  stocks, using `storeMarketPrices()`). This enables the existing `marketTools.ts` code at
  line 188 (`vnIndexResult.find((p) => p.code === "VNINDEX")`) to work without modification.

  Wire `fetchVnIndex()` into `fetchHosePrices` as a special-case branch: if the only
  requested code is `"VNINDEX"`, call `fetchVnIndex()` instead of the stock endpoint.
  Return a `MarketPrice[]` with a single element (price = `value`, changePct = computed,
  exchange = `"INDEX"`) so the existing `get_market_snapshot` rendering path requires no
  changes.

- **Input:** HTTP GET to CafeF banggia index endpoint.
- **Output:** `VnIndexSnapshot` (internal), `MarketPrice[]` with one entry for callers of
  `fetchHosePrices(["VNINDEX"])`.
- **Business rule:** If the record `a === "VNINDEX"` is absent from the response, return `[]`
  and log a warning. No failure should be thrown to callers. CafeF index values are floating-
  point points (not ×1000); do not apply the ×1000 multiplier used for stocks.
- **Timeout:** 10s (same as existing `fetchFromCafef`).
- **DDD layer:** `infrastructure/fetchers/hose.ts` (new `fetchVnIndex()` function + routing
  branch in `fetchHosePrices`). No changes needed in `marketTools.ts`.

### FR-4: SQLite WAL checkpoint — daily cron + shutdown hook (Task 140)

**Context:** The server runs with `PRAGMA journal_mode = WAL` (set in `getDb()`). SQLite's
automatic checkpoint fires at 1000 pages, but better-sqlite3 running under Bun does not
trigger it reliably in long-running processes. The WAL file can grow to 2.5x the main DB.

- **Description:** Create `src/infrastructure/db/checkpoint.ts` with:

  ```typescript
  export function runWalCheckpoint(db?: Database): void {
    const target = db ?? getDb();
    target.pragma('wal_checkpoint(PASSIVE)');
    target.pragma('optimize');
    logger.info('[db-checkpoint] WAL checkpoint + optimize complete');
  }
  ```

  Register it in two places:

  1. **Daily cron at 03:00 GMT+7** — add `walCheckpoint: "0 20 * * *"` (= 03:00 +7 in UTC)
     to `mcp.config.json` scheduler section. Create `src/scheduler/walCheckpointJob.ts`
     that calls `runWalCheckpoint()`. Register in `src/interface/scheduler/index.ts`.

  2. **SIGTERM / SIGINT shutdown hooks** — in `src/index.ts` before starting the server:

     ```typescript
     process.on('SIGTERM', () => { runWalCheckpoint(); process.exit(0); });
     process.on('SIGINT',  () => { runWalCheckpoint(); process.exit(0); });
     ```

- **Input:** Live SQLite database (singleton from `getDb()`).
- **Output:** WAL file reduced to near-zero pages. Log line at INFO level.
- **Business rule:** Use `PASSIVE` mode — it does not block active readers or writers. Never
  call `FULL` or `RESTART` mode as they can block the event loop.
- **Schema change:** None. No table or column changes.
- **DDD layer:** `infrastructure/db/checkpoint.ts` (new helper),
  `scheduler/walCheckpointJob.ts` (new cron job),
  `interface/scheduler/index.ts` (register job),
  `src/index.ts` (SIGTERM/SIGINT hooks),
  `mcp.config.json` (add `walCheckpoint` cron expression).

### FR-5: Circuit breaker for external fetchers (Task 136)

**Context:** VnDirect is geo-blocked from France, causing 5-30 second TCP timeout stalls on
every cycle run. The `mcp.config.json` already has:

```json
"circuitBreaker": {
  "failureThreshold": 5,
  "resetTimeoutMs": 60000,
  "halfOpenMaxAttempts": 2
}
```

- **Description:** Create `src/infrastructure/circuitBreaker.ts` with a `CircuitBreaker` class.

  **State machine:**
  ```
  CLOSED  ─(5 consecutive failures)→  OPEN
  OPEN    ─(60s elapsed)→             HALF_OPEN
  HALF_OPEN ─(probe succeeds)→        CLOSED
  HALF_OPEN ─(probe fails)→           OPEN (reset timer)
  ```

  **Public API:**
  ```typescript
  export type CircuitBreakerState = 'CLOSED' | 'OPEN' | 'HALF_OPEN';

  export class CircuitBreaker {
    constructor(name: string, config?: Partial<CircuitBreakerConfig>);
    async execute<T>(fn: () => Promise<T>): Promise<T>;
    getState(): CircuitBreakerState;
    getStats(): CircuitBreakerStats;
    reset(): void;   // for tests only
  }

  export interface CircuitBreakerConfig {
    failureThreshold: number;      // default: 5
    resetTimeoutMs: number;        // default: 60000
    halfOpenMaxAttempts: number;   // default: 2
  }

  export interface CircuitBreakerStats {
    state: CircuitBreakerState;
    failures: number;
    lastFailureAt: string | null;
    lastSuccessAt: string | null;
  }
  ```

  When `state === 'OPEN'`, `execute()` throws `CircuitBreakerOpenError` immediately without
  calling `fn`. The caller must catch this and return a safe default (e.g. `[]`).

  When `state === 'HALF_OPEN'`, at most `halfOpenMaxAttempts` probes are allowed. A success
  closes the breaker. A failure reopens it and resets the timer.

  **Singleton instances** (module-level, exported for `get_system_health`):
  ```typescript
  export const vnDirectBreaker = new CircuitBreaker('vndirect', mcpConfig.circuitBreaker);
  export const cafefBreaker    = new CircuitBreaker('cafef',    mcpConfig.circuitBreaker);
  export const sscBreaker      = new CircuitBreaker('ssc',      mcpConfig.circuitBreaker);
  ```

  **Wrapping targets:**
  - `fetchHosePrices` in `hose.ts`: wrap the VnDirect HTTP call with `vnDirectBreaker.execute()`.
    Wrap the CafeF fallback `fetchFromCafef` with `cafefBreaker.execute()`.
  - `listSscDocuments` in `ssc.ts`: wrap the Puppeteer launch with `sscBreaker.execute()`.

  When a breaker throws `CircuitBreakerOpenError`, the wrapping code logs a WARN and returns
  the safe default (`[]` or `0`) — it must not rethrow.

- **Input:** Any async function returning a value.
- **Output:** The function's return value, or throws `CircuitBreakerOpenError` when OPEN.
- **Business rule:** Config values come from `mcp.config.json` `circuitBreaker` section.
  The existing exponential backoff in `hose.ts` (`_consecutiveFailures`, `_backoffUntil`)
  is **retained** alongside the circuit breaker — the breaker operates at the per-call level,
  backoff operates at the per-session level. They are complementary, not mutually exclusive.
- **DDD layer:** `infrastructure/circuitBreaker.ts` (new class + singletons),
  `infrastructure/fetchers/hose.ts` (wrap VnDirect + CafeF calls),
  `infrastructure/fetchers/ssc.ts` (wrap Puppeteer launch).

## Non-Functional Requirements

- **Performance:** Circuit breaker `execute()` overhead must be under 1ms (no I/O, pure in-memory counter check).
- **Data freshness:** Step E queries `triggered_at >= now - 16min` to match the 15-minute
  cycle cadence with 1-minute overlap tolerance.
- **Idempotency:** `notified_telegram = 1` prevents double-sends across cycle restarts. The
  SQLite UPDATE runs inside a try/catch; a failed update does not abort the Telegram send.
- **No schema regressions:** All migrations use try/catch `ALTER TABLE` or `CREATE ... IF NOT EXISTS`. Existing tests must pass unmodified.
- **Language:** Log messages in English. Tool output text in English.
- **Test isolation:** All new functions must be injectable (accept DB, fetchers, and
  circuit breaker state as parameters) so unit tests run without real network or file I/O.

## Edge Cases & Data Quality

- [ ] `notified_telegram` column already exists (second server start): `ALTER TABLE` throws, catch must swallow silently.
- [ ] No HIGH/CRITICAL alerts in 16-minute window: Step E returns `telegramAlertsSent = 0` without error.
- [ ] Telegram send returns `false` (bot token not configured): `notified_telegram` stays 0; alert is retried next cycle.
- [ ] `insertedIds` is empty (all news was duplicates): Step D returns `impactEventsRan = 0` immediately, no DB queries.
- [ ] CafeF index endpoint returns empty array or the VNINDEX record is missing: `fetchVnIndex()` returns `[]`, logs warning, `get_market_snapshot` shows `VN-Index: N/A`.
- [ ] CafeF index value is floating-point (e.g. `1247.35`): no ×1000 conversion; verify in test that the value is stored as-is.
- [ ] WAL file absent at checkpoint time (fresh DB or already checkpointed): `fs.statSync` on `.db-wal` returns 0 bytes; `get_system_health` returns `walSizeBytes: 0` without error.
- [ ] SIGTERM during active cycle: WAL checkpoint runs but may checkpoint partial WAL; this is safe — PASSIVE mode does not corrupt.
- [ ] Circuit breaker in OPEN state when `fetchHosePrices` is called: `CircuitBreakerOpenError` is caught internally, function returns `[]`, `pricesFetched = 0` in `CycleResult`.
- [ ] `runImpactChain` throws for one entry: error is logged per-entry, `impactEventsRan` counts only successful calls.
- [ ] LanceDB directory does not exist yet: recursive size walk returns 0, no error thrown.
- [ ] `get_system_health` called before first cycle completes: `lastCycleResult` is `null`; all numeric fields are 0 or present from DB queries.
