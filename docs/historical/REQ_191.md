# REQ-191: Cascade Outcome Tracking — Backtesting Schema + Signal Quality Feedback Loop

status: READY_FOR_ARCHITECT
sprint: 191
po_vision: Close signal quality feedback loop — know if cascade alerts were right 3–7 days later.

## User Story

As a Vietnamese stock investor using Claude,
I want the system to record actual price outcomes after cascade rule alerts fire,
So that I can see which cascade rules predict price moves accurately and trust high-confidence alerts more.

## Functional Requirements

### FR-1: Extend `cascade_rule_hits` schema — 5 new columns

- Description: Add outcome-tracking columns to existing table via idempotent ALTER migrations in `initDatabase()`.
- Input: Existing `cascade_rule_hits` table (5 cols: id, rule_key, matched_text, affected_sector, affected_stocks, hit_at).
- Output: Table has 10 cols after migration. Columns nullable by default (populated later by backtest cron, Sprint 192).
- Business rule: Migrations must be idempotent — `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` pattern (SQLite: use `PRAGMA table_info` guard or `try/catch` per column). Re-running `initDatabase()` on an existing DB must not error.
- New columns:

| Column | Type | Default | Purpose |
|--------|------|---------|---------|
| `source_rag_id` | `TEXT` | NULL | FK → `rag_analyses.id` — the news item that triggered the hit |
| `price_impact_3d` | `REAL` | NULL | % price change 3 trading days after `hit_at` (filled by backtest cron) |
| `price_impact_7d` | `REAL` | NULL | % price change 7 trading days after `hit_at` |
| `outcome_correct` | `INTEGER` | NULL | 1 = price moved in predicted direction, 0 = did not, NULL = pending |
| `confidence` | `REAL` | NULL | Computed confidence score 0.0–1.0 (from cascade engine strength) |

- DDD layer: infrastructure → `src/infrastructure/db/schema.ts`

### FR-2: Extend `market_messages` schema — 3 new columns

- Description: Add impact-tracking columns to `market_messages` via idempotent ALTER migrations.
- Input: Existing `market_messages` table (9 cols).
- Output: Table has 12 cols after migration.
- Business rule: Same idempotency requirement as FR-1. Columns NULL by default.
- New columns:

| Column | Type | Default | Purpose |
|--------|------|---------|---------|
| `impact_score` | `REAL` | NULL | Computed importance score 0.0–1.0 for the message |
| `price_at_message` | `REAL` | NULL | Ticker close price at `sent_at` time |
| `price_3d_after` | `REAL` | NULL | Ticker close price 3 trading days after `sent_at` (filled by backtest cron) |

- DDD layer: infrastructure → `src/infrastructure/db/schema.ts`

### FR-3: `cascadeHitStore.updateOutcome()` — write outcome to hit row

- Description: New function in `cascadeHitStore.ts` to write backtest results back to a hit row.
- Input:
  ```ts
  updateOutcome(
    db: Database,
    id: number,
    outcome: {
      priceImpact3d?: number | null;
      priceImpact7d?: number | null;
      outcomeCorrect?: 0 | 1 | null;
      confidence?: number | null;
    }
  ): boolean
  ```
- Output: `true` if row found and updated, `false` if id not found.
- Business rule: Only updates provided fields (non-undefined). Idempotent — repeated calls overwrite previous values without error. Does not touch `source_rag_id` (set at insert time by cascade engine, not at outcome time).
- DDD layer: infrastructure → `src/infrastructure/db/cascadeHitStore.ts`

### FR-4: Extend `recordHit()` — optional `sourceRagId` + `confidence` parameters

- Description: Extend existing `recordHit()` to accept `sourceRagId` and `confidence` at insert time, so the cascade engine can stamp them when firing.
- Input: Add optional params to existing signature:
  ```ts
  recordHit(
    db: Database,
    ruleKey: string,
    matchedText: string,
    sector?: string,
    stocks?: string,
    sourceRagId?: string | null,
    confidence?: number | null,
  ): void
  ```
- Output: Row inserted with `source_rag_id` and `confidence` populated when provided.
- Business rule: Existing callers with 4–5 args continue to work unchanged (new params optional).
- DDD layer: infrastructure → `src/infrastructure/db/cascadeHitStore.ts`

### FR-5: `marketMessageStore.updateImpact()` — write impact data to message row

- Description: New function in `marketMessageStore.ts` to write impact tracking data back to a message row.
- Input:
  ```ts
  updateImpact(
    db: Database,
    id: number,
    impact: {
      impactScore?: number | null;
      priceAtMessage?: number | null;
      price3dAfter?: number | null;
    }
  ): boolean
  ```
- Output: `true` if row found and updated, `false` if id not found.
- Business rule: Idempotent — repeated calls overwrite. Null values explicitly stored (not skipped).
- DDD layer: infrastructure → `src/infrastructure/db/marketMessageStore.ts`

### FR-6: `get_cascade_outcomes` MCP tool

- Description: New MCP tool returning cascade hit rows with outcome data, for signal quality review.
- Input params (Zod schema):
  ```ts
  {
    days: z.number().int().min(1).max(90).default(30),  // look-back window
    ticker: z.string().optional(),                       // filter by affected_stocks LIKE %ticker%
  }
  ```
- Output: JSON array of outcome rows, formatted as text table:
  ```
  Cascade Outcomes — Last 30 days
  ID | Rule | Hit At | Ticker | Impact 3d | Correct | Confidence
  ```
  Each row: `{ id, ruleKey, hitAt, ticker, priceImpact3d, priceImpact7d, outcomeCorrect, confidence, sourceRagId }`.
- Business rule: Returns all hits in window regardless of whether outcome is filled (NULL = pending). Ordered by `hit_at DESC`. Max 200 rows. When `ticker` filter provided: `WHERE affected_stocks LIKE '%<ticker>%'`.
- Registration: `server.tool("get_cascade_outcomes", ...)` in `src/interface/mcp/server.ts`. Tool definition in `src/interface/mcp/tools/cascadeOutcomeTools.ts` (new file, mirrors pattern of `cascadeMetricsTools.ts`).
- DDD layer: interface → `src/interface/mcp/tools/cascadeOutcomeTools.ts` + `src/interface/mcp/server.ts`

## Non-Functional Requirements

- Performance: All ALTER migrations complete in < 100ms on production DB (single-column adds, no data migration).
- Idempotency: Running `initDatabase()` twice on the same DB must produce zero errors.
- Backward compat: `recordHit()` callers with existing arg count unchanged — no call-site edits required.
- Language: MCP tool output in English (column headers); tool description in English.
- Test baseline: Must stay at or above 5681 pass. `bun tsc --noEmit` clean.

## Edge Cases & Data Quality

- [ ] SQLite `ALTER TABLE ADD COLUMN` does not support `IF NOT EXISTS` — must use `PRAGMA table_info` check or try/catch per column.
- [ ] `outcome_correct` is INTEGER (0/1/NULL) not BOOLEAN — TypeScript type must match.
- [ ] `confidence` range 0.0–1.0 — no DB constraint needed but MCP tool should display as percentage.
- [ ] `affected_stocks` is comma-separated TEXT — `LIKE '%ticker%'` filter can false-positive on partial codes (e.g. "VCB" matches "AVCB"). Acceptable for now; exact fix is Sprint 192 scope.
- [ ] `updateOutcome()` with all-undefined outcome fields should be a no-op (no SQL run).
- [ ] `get_cascade_outcomes` with 0 rows in window should return empty array, not error.
- [ ] `price_at_message` and `price_3d_after` are NULL when ticker is NULL in market_messages — callers must guard.

## Implementation Notes for Architect

**SQLite idempotent ALTER pattern** (SQLite has no `ADD COLUMN IF NOT EXISTS`):

```ts
// Pattern: wrap each ALTER in try/catch
const newCols = [
  `ALTER TABLE cascade_rule_hits ADD COLUMN source_rag_id    TEXT`,
  `ALTER TABLE cascade_rule_hits ADD COLUMN price_impact_3d  REAL`,
  `ALTER TABLE cascade_rule_hits ADD COLUMN price_impact_7d  REAL`,
  `ALTER TABLE cascade_rule_hits ADD COLUMN outcome_correct  INTEGER`,
  `ALTER TABLE cascade_rule_hits ADD COLUMN confidence       REAL`,
];
for (const sql of newCols) {
  try { db.exec(sql); } catch { /* column already exists — safe to ignore */ }
}
```

Same pattern for `market_messages` 3 cols. Place these ALTER blocks immediately after the corresponding `CREATE TABLE IF NOT EXISTS` block in `initDatabase()`.

**`updateOutcome()` — partial update pattern**: build SET clause dynamically from provided keys, skip undefined. Use parameterized binding. Return `result.changes > 0`.

**MCP tool file** (`cascadeOutcomeTools.ts`): export `registerCascadeOutcomeTools(server: McpServer): void`. Import in `server.ts` and call during registration phase. Query: `SELECT id, rule_key, hit_at, affected_stocks, price_impact_3d, price_impact_7d, outcome_correct, confidence, source_rag_id FROM cascade_rule_hits WHERE hit_at >= datetime('now', '-' || ? || ' days') [AND affected_stocks LIKE ?] ORDER BY hit_at DESC LIMIT 200`.
