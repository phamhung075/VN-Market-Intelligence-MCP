# REQ-234: VPS Health Dashboard + Data Freshness SLA Enforcement

**status**: READY_FOR_ARCHITECT
**sprint**: 234
**po_vision**: After fallback chains (Sprint 232) go live, we need **visibility into which services are healthy** and **active enforcement of data quality SLAs**. Implement VPS service health polling (all 5 endpoints) + data freshness monitoring with escalation callbacks.

---

## User Story

As a Vietnamese market investor using Claude,
I want **real-time visibility into VPS data service health** and **automatic alerts when source freshness violates SLA thresholds**,
So that I can **trust the signals I receive** and **avoid cascading failures silently degrading analysis quality**.

## Functional Requirements

### FR-1: VPS Service Health Polling (5-minute intervals, all endpoints)

**Description**: Every 5 minutes, poll all 5 VPS services via direct HTTP health checks and record results in the database.

**Services**:
- `vn-price-fetch.service` (60s market hours) → fetch-prices.sh endpoint
- `vn-bctc-fetch.service` (6h) → fetch-bctc.sh endpoint
- `vn-news-fetch.service` (15min) → fetch-vn-news.sh endpoint
- `vn-sbv-fetch.service` (30min) → fetch-sbv.sh endpoint
- `vn-foreign-flow.service` (60s market hours) → fetch-foreign-flow.sh endpoint

**Polling contract**:
- Endpoint: `GET $VINAHOST_IP:8001/health` (configurable per service via `mcp.config.json` → `vpsServices[].healthCheckUrl`)
- Timeout: 5 seconds per endpoint
- Circuit breaker: wrap in `circuitBreakerRegistry.getOrCreateBreaker()`
- Payload: `{ "status": "ok"|"error", "lastRun": ISO-8601, "uptime": seconds, "error": null|string }`
- Expected response code: 200 (status ok) or 500+ (status error)

**Data model** (stored in `vps_service_health` table — see schema):
- service_name: TEXT NOT NULL
- polled_at: TEXT (ISO-8601 datetime)
- health_status: TEXT CHECK(status IN ('healthy','unhealthy','unreachable'))
- response_time_ms: INTEGER
- last_successful_run: TEXT (ISO-8601 from payload)
- uptime_seconds: INTEGER
- error_message: TEXT
- vps_uptime_seconds: INTEGER

**Output**: Query via MCP tool `get_vps_service_health()` (new tool, see FR-4).

### FR-2: Data Freshness SLA Checker (30-minute intervals, source age validation)

**Description**: Every 30 minutes, validate that each data source's age does **not exceed SLA thresholds**. When a source becomes stale, record escalation event and trigger callback to Alert Commander.

**Signal type → SLA threshold mapping**:

| Signal Type | Source Table(s) | SLA Threshold | Fallback Tiers |
|-------------|-----------------|---------------|----------------|
| price | market_prices | 10 min | cache (30m), yahoo (60m), domestic_rss (90m) |
| BCTC | financial_reports, bctc_vps_queue | 6h (overnight), 2h (market hours) | none (async parse) |
| news | rag_analyses, signals | 30 min | 10x RSS feed sources (cached) |
| SBV FX | macro_indicators (sbv_rate) | 30 min | tradingeconomics.com (60m) |
| foreign_flow | market_prices (foreign_buy, foreign_sell) | 10 min | cache (30m) |

**SLA breach logic**:
1. For each signal type, query MAX(created_at) from source table
2. Compute age = NOW - created_at
3. If age > SLA threshold:
   - Record in `sla_breach_audit` table (new — see schema)
   - Trigger escalation callback: `escalateToCommander(signal_type, age, threshold)`
   - Note: if age > threshold × 1.5, severity = CRITICAL; else HIGH
4. If age returns to normal: record "recovery" event in audit table

**Escalation callback behavior**:
- Sends signal to Alert Commander via internal queue (`POST /signal-escalation` or agent signal post_agent_signal tool)
- Signal shape: `{ type: "sla_breach", signal_type, current_age_minutes, threshold_minutes, severity }`
- Alert Commander decides: alert user or silently track (depends on alert policy)
- **Important**: SLA breaches are informational; user alerting is Commander's responsibility

**Data model** (`sla_breach_audit` table — new):
- id: INTEGER PRIMARY KEY AUTOINCREMENT
- signal_type: TEXT CHECK(signal_type IN ('price','bctc','news','sbv_fx','foreign_flow'))
- threshold_minutes: INTEGER
- actual_age_minutes: INTEGER
- status: TEXT CHECK(status IN ('breach_open','escalated','recovered'))
- breached_at: TEXT (ISO-8601)
- recovered_at: TEXT (nullable)
- affected_sources: TEXT (comma-separated source names, JSON optional)
- escalation_callback_sent: BOOLEAN

### FR-3: Escalation Protocol (Callback when SLA violated)

**Description**: When a data freshness SLA is breached, trigger a structured escalation callback that notifies Alert Commander without auto-alerting the user.

**Callback design**:
- Function signature: `escalateToCommander(signalType: string, ageMinutes: number, thresholdMinutes: number, severity: 'HIGH'|'CRITICAL') → Promise<void>`
- Mechanism: call `post_agent_signal()` with validated signal shape (inbound to Alert Commander queue)
- Flow:
  1. Record event in `sla_breach_audit` table
  2. Post signal: `{ type: "sla_breach", signal_type, age, threshold, severity, timestamp }`
  3. Set `escalation_callback_sent = true`
  4. Alert Commander ingests signal in next cycle; decides if user alert is warranted

**Cooldown logic** (reuse from alert policy):
- Do NOT fire escalation more than 1x per 60 minutes for the same signal_type (to avoid alert spam)
- Track in `sla_breach_audit.breached_at` — only escalate if last breach > 60 min ago

### FR-4: Health Dashboard Tools (MCP query tools for real-time status)

**Description**: Expose two new MCP tools for agents to query VPS health and SLA status.

#### Tool A: `get_vps_service_health`
- **Input**: optional `service_name` (filter by specific service, or "all")
- **Output**: Formatted table with latest poll results:
  ```
  Service         Status        Last Poll      Response(ms)  VPS Uptime
  ─────────────────────────────────────────────────────────────────────
  vn-price-fetch  healthy       2 min ago      142           25d 3h 20m
  vn-bctc-fetch   unhealthy     5 min ago      5001 (timeout)  N/A
  vn-news-fetch   healthy       1 min ago      89            ...
  vn-sbv-fetch    healthy       2 min ago      156           ...
  vn-foreign-flow unreachable   10 min ago     error: ECONNREFUSED
  ```
- Used by: Digest & Predict (06), system status checks, developer dashboards

#### Tool B: `get_sla_status`
- **Input**: optional `signal_type` filter (price / bctc / news / sbv_fx / foreign_flow)
- **Output**: Current SLA status for each signal type:
  ```
  Signal Type   Age (min)  SLA (min)  Status    Severity
  ──────────────────────────────────────────────────────
  price         8         10         ok        -
  bctc          25 (market) 120      ok        -
  news          32        30         breached  HIGH
  sbv_fx        28        30         ok        -
  foreign_flow  9         10         ok        -
  ```
- Used by: Alert Commander (05) to contextualize decision-making, Digest & Predict for daily summaries

## Non-Functional Requirements

| Requirement | Specification |
|-------------|---------------|
| **Performance** | VPS health polling <5s total (5s timeout × 5 services, parallelized). SLA check query <500ms. Both jobs back-off on circuit breaker trip. |
| **Data freshness** | Health poll results visible to tools within 1 minute of poll completion. |
| **Availability** | Both jobs run 24/7 (health polling every 5min, SLA check every 30min). No market-hours-only restriction. |
| **Language** | Vietnamese + English (tool output bilingual where applicable: status enums are English, labels are Vietnamese). |
| **Error handling** | Failed polls recorded as `status='unreachable'` + error message; failed SLA checks log to app error stream; no cascading failures. |
| **Audit trail** | All health polls logged to `vps_service_health` table. All SLA breaches logged to `sla_breach_audit` table with timestamps. |
| **Backward compatibility** | Existing `vps_push_log` table untouched. New tables isolated in schema-system.ts. No changes to existing APIs. |

---

## Edge Cases & Data Quality

- **[ ] Empty/null responses**: If health endpoint returns malformed JSON or timeout → record as `status='unreachable'`, error message captures details
- **[ ] Network glitches**: Circuit breaker trips after 5 consecutive failures → back off exponentially, don't spam VPS
- **[ ] Partial SLA breach**: One source (e.g., BCTC) exceeds SLA while others OK → escalate only the breached signal type
- **[ ] Clock skew**: If VPS uptime_seconds > system clock → log warning, don't alert user (infrastructure issue, not data quality)
- **[ ] Stale VPS response**: If VPS lastRun timestamp is old (e.g., 30min ago) but HTTP 200 → record in health poll with warning, SLA checker picks it up as source age
- **[ ] Market hours SLA variance**: BCTC SLA is 2h market hours, 6h overnight → use `tradingWindowLabel()` helper to determine threshold at check time

## Acceptance Criteria

### AC-1: VPS Health Polling Registration & Scheduling

**Given** the cron scheduler is running
**When** time reaches next 5-minute boundary
**Then**
- `vpsServiceHealthJob` executes and calls `pollVpsServiceHealth()` use case
- All 5 service endpoints are polled in parallel (max 5s timeout each)
- Results stored in `vps_service_health` table with columns: service_name, health_status, response_time_ms, polled_at, last_successful_run, uptime_seconds, error_message
- If all 5 polls succeed → job status = 'success'
- If ≥1 poll fails → job status = 'success' (partial failure is OK; results stored)

### AC-2: VPS Health Data Model & Schema

**Given** the application starts
**When** `initDatabase()` is called
**Then**
- `vps_service_health` table exists with columns: [id, service_name, polled_at, health_status, response_time_ms, last_successful_run, uptime_seconds, error_message]
- Indices exist on (service_name, polled_at DESC) for efficient querying
- All health status values stored successfully; query `SELECT * FROM vps_service_health ORDER BY polled_at DESC LIMIT 5` returns latest 5 polls

### AC-3: Data Freshness SLA Checker Job & Thresholds

**Given** the SLA checker job runs every 30 minutes
**When** each of the 5 signal types (price, BCTC, news, SBV FX, foreign_flow) is evaluated
**Then**
- `market_prices.updated_at` is queried; if > 10min old → status = breached (HIGH severity)
- `financial_reports.created_at` max is queried; if > 6h old (or 2h during market hours) → status = breached
- `rag_analyses.created_at` max is queried; if > 30min old → status = breached
- `macro_indicators` SBV FX rate is queried; if > 30min old → status = breached
- `foreign_flow` columns in `market_prices` are checked; if > 10min old → status = breached
- Results recorded in `sla_breach_audit` table

### AC-4: SLA Breach Escalation Callback

**Given** a signal type's source age exceeds its SLA threshold
**When** the freshness SLA job detects the breach
**Then**
- `sla_breach_audit` record is created with status = 'breach_open', breached_at = now
- `escalateToCommander()` is called with (signal_type, age_minutes, threshold_minutes, severity)
- Escalation signal posted to Alert Commander queue (internal signal, not user-facing alert yet)
- `sla_breach_audit.escalation_callback_sent = true`
- 60-minute cooldown enforced: no duplicate escalations for same signal_type within 60min

### AC-5: SLA Recovery Detection

**Given** a previously-breached signal type's source age returns to normal (<= SLA threshold)
**When** the next SLA check runs
**Then**
- `sla_breach_audit` record with matching signal_type is updated: status = 'recovered', recovered_at = now
- No escalation callback sent (data is healthy again)
- If another breach occurs 5 minutes later, a NEW `sla_breach_audit` record is created

### AC-6: Health Poll Tool Registration & Query

**Given** the MCP server is running
**When** an agent calls `get_vps_service_health(service_name='all')`
**Then**
- Tool returns formatted table with latest poll for each of 5 services
- Columns: Service, Status (healthy/unhealthy/unreachable), Last Poll (relative time), Response Time (ms), VPS Uptime (formatted)
- Rows sorted by service_name
- If no poll data exists → returns "No recent health polls" message

### AC-7: SLA Status Tool Registration & Query

**Given** the MCP server is running
**When** an agent calls `get_sla_status(signal_type='price')`
**Then**
- Tool returns table with age, SLA threshold, status, and severity for that signal type
- Thresholds vary based on market hours (e.g., BCTC 2h vs 6h)
- If signal_type='all' → returns table for all 5 types
- Example output: | price | 8 | 10 | ok | - |

## Data Model Details

### New Table: `vps_service_health` (schema-system.ts line 370+)

```sql
CREATE TABLE IF NOT EXISTS vps_service_health (
  id                    INTEGER PRIMARY KEY AUTOINCREMENT,
  service_name          TEXT NOT NULL,
  polled_at             TEXT NOT NULL DEFAULT (datetime('now')),
  health_status         TEXT NOT NULL CHECK(health_status IN ('healthy','unhealthy','unreachable')),
  response_time_ms      INTEGER,
  last_successful_run   TEXT,
  uptime_seconds        INTEGER,
  error_message         TEXT
);

CREATE INDEX IF NOT EXISTS idx_vps_health_service_ts
  ON vps_service_health(service_name, polled_at DESC);
```

### New Table: `sla_breach_audit` (schema-system.ts line ~400)

```sql
CREATE TABLE IF NOT EXISTS sla_breach_audit (
  id                       INTEGER PRIMARY KEY AUTOINCREMENT,
  signal_type              TEXT NOT NULL CHECK(signal_type IN ('price','bctc','news','sbv_fx','foreign_flow')),
  threshold_minutes        INTEGER NOT NULL,
  actual_age_minutes       INTEGER NOT NULL,
  status                   TEXT NOT NULL DEFAULT 'breach_open' CHECK(status IN ('breach_open','escalated','recovered')),
  breached_at              TEXT NOT NULL DEFAULT (datetime('now')),
  recovered_at             TEXT,
  affected_sources         TEXT,
  escalation_callback_sent BOOLEAN NOT NULL DEFAULT 0
);

CREATE INDEX IF NOT EXISTS idx_sla_breach_signal_type
  ON sla_breach_audit(signal_type);
CREATE INDEX IF NOT EXISTS idx_sla_breach_breached_at
  ON sla_breach_audit(breached_at DESC);
```
