# REQ-067: Morning Briefing Intelligence Enrichment

status: READY_FOR_ARCHITECT
sprint: 067
po_vision: Surface insider transactions, foreign flow summary, and evidence scores in the daily morning briefing so the user in France has a complete intelligence picture before placing orders at Vietnam market open.

---

## User Story

As a Vietnamese stock investor in France using Claude,
I want the morning briefing (08:00 VN / 01:00 UTC) to include a summary of overnight insider transactions, the previous day's foreign flow on my watchlist, and the top bullish/bearish evidence scores,
So that I can make informed buy/sell decisions before market open without having to query three separate tools.

### FR-2: Query insider_transactions for recent watchlist activity (assembleBriefing Step 14)

- Description: After existing Step 13 (portfolio P&L), add Step 14 in `assembleBriefing()` that queries `insider_transactions` for rows where `fetched_at >= now() - 24h` AND `code IN (watchlist codes)`.
- Input: production SQLite DB handle, watchlist code list (already fetched in Step 5 as `watchlistRows`)
- Output: `InsiderBriefingRow[]`, max 3 rows, ordered by `executed_volume DESC`

Exact SQL query (parameterized):

```sql
SELECT code, type, executed_volume, insider_name, from_date
FROM insider_transactions
WHERE fetched_at >= ?
  AND code IN (<watchlist_placeholders>)
ORDER BY executed_volume DESC
LIMIT 3
```

Parameters:
- `?` → ISO 8601 string: `new Date(Date.now() - 24 * 3600_000).toISOString()`
- `<watchlist_placeholders>` → one `?` per watchlist code, spread as positional params

Empty-state rule: if watchlist is empty OR query returns zero rows, set `insiderRecent = []` (not undefined — the field must be present and serialisable in the JSON file).

- Business rule: only watchlist stocks are surfaced. Insider rows for non-watchlist stocks are irrelevant to the morning briefing.
- DDD layer: application (assembleBriefing.ts) — read-only query against infrastructure table

### FR-3: Query vnstock_trading_stats for previous-day foreign flow (assembleBriefing Step 15)

- Description: Add Step 15 in `assembleBriefing()` that queries `vnstock_trading_stats` for the most recent `date` entry per watchlist stock (previous trading day), then classifies `net_buy` vs `net_sell` based on `foreign_volume > 0`.
- Input: production SQLite DB handle, watchlist code list
- Output: `ForeignFlowBriefingRow[]`: top 3 net-buy stocks (foreign_volume DESC) + top 3 net-sell stocks (foreign_volume ASC), total max 6 rows. If a stock has `foreign_volume = 0` or NULL it is excluded entirely.

Implementation note: `foreignFlowAlertJob` reads from `vnstock_trading_stats` (column: `foreign_volume`). The `foreign_flow` label used in SPRINT_GOAL refers to this same table. There is no separate `foreign_flow` table in the schema. The correct table is `vnstock_trading_stats`.

Exact SQL query for the most-recent row per watchlist stock:

```sql
SELECT code,
       substr(fetched_at, 1, 10) AS date,
       foreign_volume
FROM vnstock_trading_stats
WHERE code IN (<watchlist_placeholders>)
  AND foreign_volume IS NOT NULL
  AND foreign_volume != 0
  AND (code, fetched_at) IN (
        SELECT code, MAX(fetched_at)
        FROM vnstock_trading_stats
        WHERE code IN (<watchlist_placeholders>)
        GROUP BY code
      )
ORDER BY foreign_volume DESC
```

Parameters: two identical sets of watchlist code placeholders (one for outer WHERE, one for the subquery).

Post-query split in TypeScript:
- `netBuyRows` = rows where `foreign_volume > 0`, take first 3 (already ordered DESC)
- `netSellRows` = rows where `foreign_volume < 0`, take last 3 (ordered ASC = most negative first)
- `foreignFlowSummary` = [...netBuyRows, ...netSellRows]

Empty-state rule: if watchlist is empty OR no rows with non-zero `foreign_volume` exist, set `foreignFlowSummary = []`.

- Business rule: only the most-recent data point per stock is used (not a 10-day window). The morning briefing wants yesterday's snapshot, not a trend analysis — trend analysis belongs to `foreignFlowAlertJob`.
- DDD layer: application (assembleBriefing.ts) — read-only

### FR-4: Query evidence_scores for top conviction stocks (assembleBriefing Step 16)

- Description: Add Step 16 in `assembleBriefing()` that reads the most recent `evidence_scores` row per watchlist stock and surfaces the top 3 bullish leaders and any stock with `net_score < -2.0` as a bearish warning.
- Input: production SQLite DB handle, watchlist code list
- Output: `EvidenceScoreBriefingRow[]`

`net_score` = `bullish_score - bearish_score` (computed in TypeScript after the query, not in SQL, to avoid dialect issues).

Exact SQL query (one row per stock, most recent score_date):

```sql
SELECT stock AS code,
       score_date,
       bullish_score,
       bearish_score,
       fragment_count
FROM evidence_scores
WHERE stock IN (<watchlist_placeholders>)
  AND (stock, score_date) IN (
        SELECT stock, MAX(score_date)
        FROM evidence_scores
        WHERE stock IN (<watchlist_placeholders>)
        GROUP BY stock
      )
```

Parameters: two identical sets of watchlist code placeholders.

Post-query selection in TypeScript:
1. Compute `netScore = bullish_score - bearish_score` for each row.
2. Filter to stocks with `fragment_count >= 1` (exclude stocks with no evidence).
3. `bullishLeaders` = sort by `netScore DESC`, take top 3 where `netScore > 0`.
4. `bearishWarnings` = rows where `netScore < -2.0`.
5. Deduplicate: if a stock appears in both lists (should not happen given thresholds), keep it in `bearishWarnings` only.
6. `evidenceTopScores` = [...bullishLeaders, ...bearishWarnings]

Empty-state rule: if watchlist is empty OR no `evidence_scores` rows exist for watchlist stocks, set `evidenceTopScores = []`.

- Business rule: the `-2.0` threshold for bearish warnings is a business rule, not a magic constant. It represents a net bearish weight of 2.0 after normalisation — a meaningful signal that should prompt caution. This value is defined as a named constant `BEARISH_WARNING_THRESHOLD = -2.0` in the implementation.
- DDD layer: application (assembleBriefing.ts) — read-only

## Non-Functional Requirements

- Performance: all three new DB queries are O(watchlist_size) reads against indexed tables. Expected watchlist size ~30 stocks. Total additional query time < 50ms.
- Data freshness: `insiderRecent` uses a 24h rolling window so it captures records written by `insiderCheckJob` (which runs at the same 08:00 VN time). On weekends the window may be empty — this is correct behaviour.
- Language: section headers in Vietnamese (as specified in FR-5). Log messages in English.
- Test isolation: all new DB queries in `assembleBriefing()` must be injectable via the existing `AssembleBriefingOptions.db` parameter (already in place). No new injection points needed.

## Edge Cases and Data Quality

- [ ] Empty watchlist — `watchlistRows` is empty. All three queries use `IN ()` which is syntactically invalid in SQLite. Guard: if `watchlistRows.length === 0` skip all three queries and set fields to `[]`.
- [ ] Vietnamese `executed_volume` formatting: values are integers in the hundreds of thousands to hundreds of millions. `toLocaleString("en-US")` produces comma-separated groups (e.g. `1,500,000`). Do NOT use Vietnamese dot-separator format here — Telegram plain text, consistent with existing price formatting in the briefing.
- [ ] `foreign_volume` can be negative (net sell) or positive (net buy). `Math.abs()` is applied in the display row. The `direction` field in `ForeignFlowBriefingRow` carries the sign semantics.
- [ ] `vnstock_trading_stats` may have no rows for some watchlist stocks (e.g. stocks added to watchlist before VPS price push was running). These are silently excluded.
- [ ] `evidence_scores` rows only exist after `evidenceAccumulatorJob` has run at least once (nightly at 23:00 VN). On first-day deployment, `evidenceTopScores = []` is the correct empty state.
- [ ] `insiderCheckJob` runs at 08:00 VN — the same time as `morningBriefingJob`. Race condition: if `assembleBriefing()` runs before `insiderCheckJob` completes on the same day, `insiderRecent` may be empty. This is acceptable — the next morning's briefing will include today's data in its 24h window.
- [ ] `net_score = bullish_score - bearish_score` can be zero when both scores are equal. These stocks are excluded from both bullishLeaders (requires `> 0`) and bearishWarnings (requires `< -2.0`). This is correct.
- [ ] `fragment_count = 0` rows in `evidence_scores` indicate a historical artefact and are filtered out by the `fragment_count >= 1` guard.
- [ ] SQL `IN` clause with duplicate watchlist codes: the watchlist table enforces uniqueness by design but if a bug produces duplicates, the query remains correct (SQLite deduplicates IN matches).

## Data Contract Summary

### insider_transactions query input/output

Input params: `[isoString_24h_ago, ...watchlistCodes]`
Output columns: `code TEXT, type TEXT, executed_volume INTEGER, insider_name TEXT, from_date TEXT`
Ordered by: `executed_volume DESC`
Limit: 3

### vnstock_trading_stats query input/output

Input params: `[...watchlistCodes, ...watchlistCodes]` (doubled for subquery)
Output columns: `code TEXT, date TEXT (substr of fetched_at), foreign_volume INTEGER`
Ordered by: `foreign_volume DESC`
Post-filter: exclude `foreign_volume = 0` or NULL (already in WHERE clause)

### evidence_scores query input/output

Input params: `[...watchlistCodes, ...watchlistCodes]` (doubled for subquery)
Output columns: `code TEXT (aliased from stock), score_date TEXT, bullish_score REAL, bearish_score REAL, fragment_count INTEGER`
Post-computation: `netScore = bullish_score - bearish_score`
Selection: top 3 where `netScore > 0 AND fragment_count >= 1`, plus all where `netScore < -2.0 AND fragment_count >= 1`
Constant: `BEARISH_WARNING_THRESHOLD = -2.0`
