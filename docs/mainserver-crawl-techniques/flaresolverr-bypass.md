# Technique — flaresolverr-bypass

**Problem:** Sites protected by Cloudflare Turnstile v2 (interactive JS challenge). curl_cffi and cloudscraper are blocked — warmup GET returns HTTP 403 without executing the challenge JS. Passive `__cf_bm` cookie is not sufficient; the site demands a fresh `cf_clearance` token generated by a real Chromium JS runtime.
**Anti-bot type:** cloudflare_turnstile_v2
**Date documented:** 2026-05-13
**RAM cost:** ~10MB helper process + ~96MB FlareSolverr container (shared across all callers on the compose network). No additional Chromium process per scraper call — Chromium is inside the FlareSolverr container.

## Escalation Context

This technique is step 4 in the escalation ladder (after curl_cffi, cloudscraper fail):
1. requests/httpx — none or simple IP block
2. curl_cffi — TLS fingerprint / CF passive (`__cf_bm`)
3. cloudscraper — CF managed challenge (older sites)
4. **FlareSolverr** — CF Turnstile v2 JS challenge (this doc)
5. Playwright-stealth / Botasaurus — DataDome, PerimeterX, Akamai

## Solution Approach

FlareSolverr v3.x is a self-hosted HTTP proxy that solves Cloudflare JS challenges using an internal headless Chromium (undetected-chromedriver). It exposes a JSON-RPC API:

```
POST http://flaresolverr:8191/v1
{"cmd": "request.get", "url": "<target>", "maxTimeout": 60000}
```

Response envelope:
```json
{
  "status": "ok",
  "solution": {
    "url": "...",
    "status": 200,
    "response": "<html>...",
    "cookies": [{"name": "cf_clearance", "value": "...", ...}],
    "userAgent": "Mozilla/5.0 ..."
  }
}
```

**cf_clearance caching (fast path):** FlareSolverr cold solve takes ~5s. After the first solve, `cf_clearance` is valid for ~30min on investing.com. Cache it in-process and attempt subsequent requests via curl_cffi directly (fast path ~1-2s). Fall back to FlareSolverr only on 403 or challenge detection.

**Architecture:** FlareSolverr container is shared infrastructure — only one instance needed on the compose network. This helper module (`flaresolverr_helper.py`) is a thin client; all Chromium RAM lives in the FlareSolverr container, not per-scraper.

Core API:

```python
    "https://www.investing.com/economic-calendar/",

```

- `fetch_via_flaresolverr(url)` — pure FlareSolverr call, typed error on failure
- `fetch_with_fast_path(url)` — cache-first: curl_cffi fast path + FlareSolverr fallback
- `cache_cf_clearance(url, value)` / `get_cached_cf_clearance(url)` — in-process cache (TTL 25min)

## Libraries Required

- `requests` >= 2.31 (HTTP client for FlareSolverr JSON-RPC call — stdlib-style, no TLS spoofing needed since FlareSolverr is internal)
- `curl_cffi` >= 0.7.1 (fast path after cookie warmup — `pip install curl_cffi`)
- `beautifulsoup4` >= 4.12.0 + `lxml` (HTML parse — `pip install beautifulsoup4 lxml`)

FlareSolverr itself is provisioned by ops: `ghcr.io/flaresolverr/flaresolverr:latest` (v3.4.6).

## Code Snippet — Python helper (core pattern)

```python
import requests

FLARESOLVERR = "http://flaresolverr:8191/v1"

def solve(target_url: str) -> dict:
    """Returns {'response': '<html>', 'cookies': [...]}"""
    resp = requests.post(FLARESOLVERR, json={
        "cmd": "request.get",
        "url": target_url,
        "maxTimeout": 60_000,
    }, timeout=70)
    resp.raise_for_status()
    data = resp.json()
    if data["status"] != "ok":
        raise RuntimeError(f"FlareSolverr error: {data['message']}")
    if data["solution"]["status"] != 200:
        raise RuntimeError(f"Target HTTP {data['solution']['status']}")
    return data["solution"]
```

## Known Limits

- FlareSolverr container must be up on the compose network (`flaresolverr:8191`). If down, all callers fall through to failed status. Ops monitors via Docker healthcheck (curl -f http://localhost:8191/ every 30s).
- `cf_clearance` TTL on investing.com: ~30min. Cache eviction TTL set to 25min for safety. Multi-process deployments do NOT share the cache — each Python process holds its own in-memory dict. For multi-worker setups, externalise cache to Redis.
- CAPTCHA_SOLVER=none in FlareSolverr env — Turnstile (non-CAPTCHA variant) is handled by Chromium JS execution alone; no external solver needed. If investing.com adds hCaptcha, escalation to captcha solver (2captcha/AntiCaptcha) is needed — flag ops.
- Cookie values logged as `[REDACTED]` in all log output — never surface raw cf_clearance in logs.
- Rate limiting: 1s pause between warmup and API POST. Do not call calendar more than once per minute from the same IP.
- Compose network DNS only: `http://flaresolverr:8191` resolves inside containers. From the host (for debugging), use `http://localhost:8191` only if the port is mapped.
