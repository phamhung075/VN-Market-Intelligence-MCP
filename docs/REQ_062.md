# REQ-062: Cron Observability Completion — Close the Health Monitor Blind Spots

status: READY_FOR_ARCHITECT
sprint: 062
po_vision: Every scheduled job writes a cron_job_runs row so cronHealthAlertJob can detect failures across the full fleet.

## User Story

As a Vietnamese stock investor using Claude,
I want every scheduled job to be observed by the cron health monitor,
So that silent failures in morning briefings, intelligence cycles, and portfolio reports are caught and alerted before they affect my investment decisions.

---

## Background

Sprint 055 shipped `recordJobRun` (in `src/infrastructure/db/cronJobRunStore.ts`) and
`cronHealthAlertJob.ts`, which fires daily at 00:00 UTC and sends a WORK-channel alert
when any job has a success rate below 80% over 24 hours.

As of Sprint 062, only **11 of 28** scheduler job files call `recordJobRun`. The other 17
files are invisible to the health monitor. If `morningBriefingJob` throws an unhandled
error or `intelligenceCycleJob` silently skips all steps, `cronHealthAlertJob` records
nothing and sends no alert.

This spec closes that gap. The change is purely mechanical: wrap each missing job's main
function call in `recordJobRun`. No schema changes, no new tools, no new tests beyond
verifying the wrap is present.

## Functional Requirements

### FR-1: morningBriefingJob.ts

- **File**: `src/scheduler/morningBriefingJob.ts`
- **jobName**: `"morningBriefingJob"`
- **Description**: Wrap the `assembleBriefing` execution inside `recordJobRun`. The wrap belongs in `jobs.ts` at the `cron.schedule(CRONS.morningBriefing, ...)` call site, not inside `runMorningBriefing` itself (the job function has its own try/catch and concurrency guard that must remain intact).
- **DB access**: `jobs.ts` must import `getDb` from `schema.js` and `recordJobRun` from `cronJobRunStore.js`.
- **Wrap site**: `jobs.ts` — the `cron.schedule(CRONS.morningBriefing, ...)` callback.
- **rowsWritten**: `null` (briefing jobs do not produce countable DB rows in their return type).
- **DDD layer**: interface/scheduler

**Wrap pattern** (in `jobs.ts`):
```typescript
cron.schedule(CRONS.morningBriefing, async () => {
  await recordJobRun(getDb(), "morningBriefingJob", async () => {
    await runMorningBriefing()
  })
}, { timezone: 'Asia/Ho_Chi_Minh' })
```

### FR-15: cronHealthAlertJob.ts

- **File**: `src/scheduler/cronHealthAlertJob.ts`
- **jobName**: `"cronHealthAlertJob"`
- **Description**: The health alert job itself should be observable — if it throws, the monitor would catch it on the next run. The wrap must not create a circular recording dependency: `recordJobRun` writes to the same `cron_job_runs` table that `runCronHealthAlert` reads. This is safe because `runCronHealthAlert` queries a `days` window and the new row is written after the job completes; it cannot affect the current run's logic.
- **Wrap site**: `jobs.ts` — the `cron.schedule(CRONS.cronHealthAlert, ...)` callback.
- **rowsWritten**: `result.alertsSent`
- **DDD layer**: interface/scheduler

**Wrap pattern** (in `jobs.ts`):
```typescript
cron.schedule(CRONS.cronHealthAlert, async () => {
  await recordJobRun(getDb(), "cronHealthAlertJob", async () => {
    const r = await runCronHealthAlert()
    if (r.alertsSent > 0) {
      log(`[cron-health-alert] degraded=${r.alertsSent}`)
    }
    return { rowsWritten: r.alertsSent }
  })
}, { timezone: 'UTC' })
```

### FR-16: summaryJobs.ts

- **File**: `src/scheduler/summaryJobs.ts`
- **jobName pattern**: `"summaryJob:daily"`, `"summaryJob:weekly"`, `"summaryJob:monthly"`, `"summaryJob:quarterly"`, `"summaryJob:yearly"`
- **Description**: `summaryJobs.ts` owns its own cron registration via `registerSummaryJobs`. The internal `runSummaryJob(periodType)` helper must be wrapped. Because `summaryJobs.ts` does not have access to the global DB singleton at module level (it uses dynamic imports pattern-wise), it must import `getDb` from `schema.js` and `recordJobRun` from `cronJobRunStore.js` directly. The wrap goes inside the `runSummaryJob` helper, not in `jobs.ts`.
- **rowsWritten**: `null` (summaries write to the `intelligence_summaries` table but the count is not returned by `generatePeriodicSummary`).
- **DDD layer**: interface/scheduler

**Wrap pattern** (inside `summaryJobs.ts`, replacing `runSummaryJob`):
```typescript
import { getDb } from "../infrastructure/db/schema.js"
import { recordJobRun } from "../infrastructure/db/cronJobRunStore.js"

async function runSummaryJob(periodType: PeriodType): Promise<void> {
  const db = getDb()
  await recordJobRun(db, `summaryJob:${periodType}`, async () => {
    const start = Date.now()
    logger.info(`[summaryJob] starting ${periodType} summary generation`)
    const summary = await generatePeriodicSummary(periodType)
    const durationMs = Date.now() - start
    logger.info(`[summaryJob] ${periodType} summary complete`, {
      id: summary.id,
      periodStart: summary.periodStart,
      periodEnd: summary.periodEnd,
      newsCount: summary.newsCount,
      alertCount: summary.alertCount,
      durationMs,
    })
  })
}
```

Note: `recordJobRun` already captures errors and writes them to `error_msg`, so the
outer try/catch in the original `runSummaryJob` is superseded by the wrapper. The
`durationMs` local variable is now redundant for error paths but harmless for the
success path log.

## Non-Functional Requirements

- **Performance**: `recordJobRun` makes two SQLite writes per job run (INSERT on start, UPDATE on end). For the most frequent job (`intelligenceCycleJob`, every 15 min = ~96 writes/day) this is negligible.
- **Error swallowing**: `recordJobRun` is documented as never re-throwing. All existing per-job try/catch blocks in `jobs.ts` that wrap the affected calls must be removed to avoid double-catching. The affected jobs.ts call sites with inline try/catch are: `bctcOverdueCheck`, `vpsProxyWatchdog`, `cronHealthAlert`. These three try/catch blocks in `jobs.ts` are replaced by `recordJobRun`.
- **Data retention**: Existing 7-day rolling window in `getCronJobHealthSummary` is unchanged. `purgeOldCronJobRuns` is called from `dataAuditJob.ts` and handles retention automatically.
- **Backward compatibility**: No changes to any public function signatures. Wrap is at the call site in `jobs.ts` (or inside `summaryJobs.ts` for FR-16). All injectable test parameters remain intact.
- **No new schema**: `cron_job_runs` table DDL is already in `initDatabase()`.
- **Language**: No user-facing output changes. This is a backend observability change only.

## Edge Cases & Data Quality

- [x] `intelligenceCycleJob` returns `null` when the concurrency guard fires — wrap must handle `result?.newsFetched ?? 0` safely (see FR-2 pattern).
- [x] `vpsProxyWatchdogJob` returns a string, not void — the string must not be passed to `rowsWritten`; it must be used only for the conditional log (see FR-13 pattern).
- [x] `cronHealthAlertJob` reading from `cron_job_runs` while `recordJobRun` writes to `cron_job_runs` — safe because the write occurs after the function returns (see FR-15 description).
- [x] `summaryJobs.ts` registers its own crons without going through `jobs.ts` — the wrap must be inside the file, not in `jobs.ts` (see FR-16).
- [x] `insiderCheckJob.ts` is not registered — do not instrument (see FR-17).
- [x] `walCheckpoint` calls synchronous `runWalCheckpoint()` with no `async` — this is a SQLite maintenance call, not a domain job. It intentionally does not use `recordJobRun` and is excluded from this sprint.
- [x] Three existing inline try/catch blocks in `jobs.ts` (bctcOverdueCheck, vpsProxyWatchdog, cronHealthAlert) must be removed when wrapping with `recordJobRun` to avoid masking errors before `recordJobRun` can see them.

## Acceptance Criteria

### AC-1: All 17 target jobs write to cron_job_runs

**Given** the server has been running for at least one full cron cycle (15 min)
**When** `get_cron_health` is called with `days=1`
**Then**

- The response includes rows for `morningBriefingJob`, `intelligenceCycleJob`, `eveningSummaryJob`, `alertDigestJob`, `patternWatchJob`, `weeklyPortfolioReportJob`, `predictionMarketPollJob`, `predictionOutcomeJob`, `franceSummaryJob`, `devTeamHeartbeatJob`, `weatherCheckJob`, `davPharmacyJob`, `vpsProxyWatchdogJob`, `bctcOverdueCheckJob`, `cronHealthAlertJob`, and all five `summaryJob:*` variants (once their cron fires)
- Each row has `last_status` of `success` or `error` (never stuck as `running`)

### AC-2: cronHealthAlertJob can now detect failures in all wrapped jobs

**Given** `morningBriefingJob` throws an error during one run
**When** `cronHealthAlertJob` fires at 00:00 UTC
**Then**

- `cron_job_runs` contains a row for `morningBriefingJob` with `status='error'` and a non-null `error_msg`
- `cronHealthAlertJob` detects the degraded success rate and sends an alert to the WORK channel

### AC-3: No regression in existing behaviour

**Given** any of the 17 newly wrapped jobs runs normally
**When** it completes successfully
**Then**

- The job's Telegram output and logging behaviour are unchanged
- The concurrency guard in the job file continues to function (wrapping is at the call site in `jobs.ts`, not inside the guard)
- All existing passing tests continue to pass (`bun test`)

### AC-4: Three jobs.ts inline try/catch blocks removed

**Given** `bctcOverdueCheckJob`, `vpsProxyWatchdogJob`, and `cronHealthAlertJob` are wrapped in `recordJobRun`
**When** inspecting `jobs.ts`
**Then**

- There are no standalone try/catch blocks wrapping these three calls
- Error capture is delegated entirely to `recordJobRun`

### AC-5: summaryJobs.ts self-contained wrap

**Given** `registerSummaryJobs` is called from `jobs.ts`
**When** any summary cron fires
**Then**

- `cron_job_runs` contains a row with `job_name` matching `summaryJob:daily`, `summaryJob:weekly`, etc.
- `jobs.ts` does NOT import `recordJobRun` for the summary jobs (the import is in `summaryJobs.ts` only)
