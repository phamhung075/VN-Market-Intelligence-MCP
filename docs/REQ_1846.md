## Context

Sprint 1842 delivered `run_backtest` (#120). Sprint 1844 added `get_backtest_runs` (#121)
and `get_backtest_run` (#122). Runs accumulate indefinitely with no lifecycle management:
no deletion, no export path, no side-by-side comparison. Sprint 1846 closes these three
gaps and completes the backtest lifecycle surface.

Tool slots assigned: `delete_backtest_run` = #123, `export_backtest_run_csv` = #124,
`compare_backtest_runs` = #125.

### Code baseline confirmed (from code inspection)

- `IBacktestResultRepository` — **does not** contain `deleteRun()`. Sprint 1846 adds it.
- `SqliteBacktestResultRepository` — complete for save/get/list. Needs `deleteRun()`.
- `backtestTools.ts` — registers tools #120, #121, #122 via `registerBacktestTools()` +
  `registerBacktestQueryTools()`. Sprint 1846 adds a third registration function.
- `BacktestReport.trades` — shape confirmed: `ticker`, `entryDate`, `exitDate`,
  `entryPrice`, `exitPrice`, `direction`, `returnPct`, `confidence`, `positionWeight`.
  `holdDays` is **not stored** — it must be derived: `Math.round((exitDate - entryDate) /

  implemented.

## Deliverable 1 — `delete_backtest_run` MCP tool (#123)

### Functional Requirements

- **FR-1-1 (Delete by ID):** Given a required `id` string (UUID), delete the matching
  row from `backtest_runs`. Delegate to `IBacktestResultRepository.deleteRun(id)`.

- **FR-1-2 (Not-found handling):** When no row matches `id`, return
  `{ "error": "Backtest run not found: {id}" }`. Do not throw; do not silently succeed.

- **FR-1-3 (Success response):** When the row is deleted, return `{ "deleted": true, "id": "{id}" }`.

- **FR-1-4 (Idempotency contract):** `deleteRun()` returns `true` if a row was deleted,
  `false` if no row matched. The tool converts `false` to the not-found error response.
  Two calls with the same ID produce: first call → success, second call → not-found error.

### Non-Functional Requirements

- **NFR-1-1 (Layer):** Tool lives in `interface/mcp/tools/backtesting/backtestTools.ts`
  (extend existing file) or a new `backtestLifecycleTools.ts`. Architect decides.
- **NFR-1-2 (DDD golden rule):** Tool handler must not contain SQL. All DB logic in
  `SqliteBacktestResultRepository.deleteRun()`.
- **NFR-1-3 (Error isolation):** SQLite errors are caught in the repo; repo returns `false`
  on error (consistent with `getRunById` returning `null` on error). Tool surfaces as
  `{ "error": "..." }`.

### Acceptance Criteria

- **AC-1-1:** `delete_backtest_run({ id: "<valid-uuid-that-exists>" })` returns
  `{ "deleted": true, "id": "<uuid>" }` and subsequent `get_backtest_run({ id })` returns
  not-found.
- **AC-1-2:** `delete_backtest_run({ id: "<valid-uuid-not-in-db>" })` returns
  `{ "error": "Backtest run not found: <uuid>" }`.
- **AC-1-3:** `delete_backtest_run({ id: "not-a-uuid" })` returns a Zod validation error
  without touching the DB.
- **AC-1-4:** `SqliteBacktestResultRepository.deleteRun("<existing-id>")` returns `true`;
  calling again on the same ID returns `false`.
- **AC-1-5:** SQLite failure inside `deleteRun()` is caught; returns `false` (not thrown).
  Tool responds with `{ "error": "..." }`.
- **AC-1-6:** `IBacktestResultRepository` interface declares
  `deleteRun(id: string): boolean`.

### Repository Extension

| Concern | Layer | File |
|---------|-------|------|
| New port method `deleteRun()` | domain/repositories | `IBacktestResultRepository.ts` (existing — add method) |
| New SQLite impl `deleteRun()` | infrastructure/db | `backtestResultRepo.ts` (existing — add method) |
| Tool registration | interface/mcp/tools | `backtestTools.ts` or new file (Architect decides) |

**SQL:** `DELETE FROM backtest_runs WHERE id = ?`; check `changes` (Bun SQLite
`stmt.run().changes`) to distinguish deleted vs not-found.

### DDD Layer Map

|---------|-------|
| `deleteRun()` domain port | domain/repositories |
| `deleteRun()` SQLite adapter | infrastructure/db |
| Input validation (Zod uuid) | interface/mcp/tools |

## Deliverable 2 — `export_backtest_run_csv` MCP tool (#124)

### Functional Requirements

- **FR-2-1 (Fetch run):** Given a required `id` UUID, retrieve the run via
  `IBacktestResultRepository.getRunById(id)`. Return not-found error if missing.

- **FR-2-2 (Parse trades):** Parse `resultJson` as `BacktestReport`. Extract
  `report.trades: TradeRecord[]`.

- **FR-2-3 (CSV trades section):** Produce a CSV string with:
  - Header row: `date,ticker,direction,entryPrice,exitPrice,returnPct,positionWeight,holdDays`
  - One data row per `TradeRecord`, sorted by `exitDate` ASC.
  - `date` = `exitDate` (the settlement date for the trade; mirrors the equity-curve
    accumulation order used in the engine).
  - `holdDays` = derived as `Math.round((new Date(exitDate) - new Date(entryDate)) /
    86_400_000)`. Minimum value 0 (same-day).
  - Numeric fields: `entryPrice` and `exitPrice` rounded to 2 decimal places;
    `returnPct` and `positionWeight` rounded to 6 decimal places.

- **FR-2-4 (Equity curve section — conditional):** When `includeEquityCurve=true`, append
  to the CSV after a blank separator line:
  ```
  equity_curve
  index,equityValue
  0,1.000000
  1,1.023000
  ...
  ```
  **Blocked by BLK-1** — equity curve is not stored in `resultJson` today. See Blockers.

- **FR-2-5 (Empty trades):** When `report.trades` is empty, return the header row only
  (no data rows). Do not return an error — an empty run is valid.

- **FR-2-6 (Output):** Return the CSV string as a plain text MCP content block
  (`type: "text"`). Callers pipe to file or display directly.

- **FR-2-7 (resultJson parse failure):** If `resultJson` cannot be parsed as valid JSON,
  return `{ "error": "resultJson parse failed for run {id}" }`.

### Non-Functional Requirements

- **NFR-2-1 (No CSV library dependency):** CSV is simple enough to build with string
  concatenation. Do not add a new npm dependency.
- **NFR-2-2 (Layer):** Same layer constraints as FR-1. No SQL in tool handler.
- **NFR-2-3 (Locale):** All numeric output uses JS `.toFixed()` with dot decimal
  separator. No Vietnamese locale formatting (this is machine-readable CSV, not a
  human report).

### Acceptance Criteria

- **AC-2-1:** `export_backtest_run_csv({ id: "<valid>" })` where run has 3 trades returns
  a string with a header line + 3 data lines, sorted by exitDate ASC.
- **AC-2-2:** Each data row contains exactly 8 comma-separated fields in order:
  `date,ticker,direction,entryPrice,exitPrice,returnPct,positionWeight,holdDays`.
- **AC-2-3:** `holdDays` for a trade with `entryDate="2024-01-02"` and
  `exitDate="2024-01-12"` is `10`.
- **AC-2-4:** `export_backtest_run_csv({ id: "<id-with-0-trades>" })` returns header row
  only, no error.
- **AC-2-5:** `export_backtest_run_csv({ id: "<not-found>" })` returns
  `{ "error": "Backtest run not found: <id>" }`.
- **AC-2-6:** `export_backtest_run_csv({ id: "<id-corrupt-json>" })` returns
  `{ "error": "resultJson parse failed for run <id>" }`.
- **AC-2-7 (blocked):** `export_backtest_run_csv({ id: "<valid>", includeEquityCurve: true })`
  — behaviour defined after BLK-1 is resolved by Architect. Until resolved, passing
  `includeEquityCurve=true` returns a `{ "error": "Equity curve not available: not stored in resultJson. See BLK-1." }` content block.

### DDD Layer Map

|---------|-------|------|
| Trade retrieval | infrastructure/db (via repo) | `backtestResultRepo.ts` (existing) |
| `holdDays` derivation | interface/mcp/tools (presentation logic) | tool handler |
| CSV serialisation | interface/mcp/tools | tool handler (no library) |
| Input validation | interface/mcp/tools | Zod `z.string().uuid()` + `z.boolean().default(false)` |

## Deliverable 3 — `compare_backtest_runs` MCP tool (#125)

### Functional Requirements

- **FR-3-1 (Multi-ID fetch):** Given `ids: string[]` (min 2, max 5), fetch each run via
  `getRunById(id)`. If **any** ID is not found, return an error listing all missing IDs:
  `{ "error": "Backtest runs not found: [id1, id2]" }`. Do not return a partial table.

- **FR-3-2 (Comparison table):** Return a structured object — an array of per-run metric
  objects — containing the following fields for each run:

  | Field | Source | Notes |
  |-------|--------|-------|
  | `id` | `BacktestRunRecord.id` | |
  | `strategy` | `BacktestRunRecord.strategy` | |
  | `startDate` | `BacktestRunRecord.startDate` | |
  | `endDate` | `BacktestRunRecord.endDate` | |
  | `runAt` | `BacktestRunRecord.runAt` | |
  | `totalReturn` | `BacktestRunRecord.totalReturn` | fraction |
  | `benchmarkReturn` | `BacktestRunRecord.benchmarkReturn` | null if absent |
  | `maxDrawdown` | `BacktestRunRecord.maxDrawdown` | fraction, negative |
  | `sharpeRatio` | `BacktestRunRecord.sharpeRatio` | null if absent |
  | `winRate` | `BacktestRunRecord.winRate` | fraction 0–1 |
  | `tradeCount` | `BacktestRunRecord.tradeCount` | |

  `resultJson` is excluded (too large for a comparison view).

- **FR-3-3 (Order):** Runs appear in the output array in the same order as supplied in
  `ids`. Do not re-sort by date.

- **FR-3-4 (Duplicate IDs):** If the caller passes the same ID twice, deduplicate before
  fetching. The response contains each unique run once, in first-occurrence order.

- **FR-3-5 (Validation):** `ids` with fewer than 2 elements returns a Zod validation
  error. `ids` with more than 5 elements returns a Zod validation error.

### Non-Functional Requirements

- **NFR-3-1 (No N+1 concern):** With max 5 IDs the per-ID `getRunById` calls are
  acceptable. Architect may batch into a single `WHERE id IN (?)` query for cleanliness
  but it is not required.
- **NFR-3-2 (Layer):** Same DDD constraints. No SQL in tool handler.
- **NFR-3-3 (Error isolation):** SQLite errors per-run are caught; missing ID is treated
  as not-found.

### Acceptance Criteria

- **AC-3-1:** `compare_backtest_runs({ ids: ["<id-A>", "<id-B>"] })` where both exist
  returns an array of 2 objects each containing all 11 fields listed in FR-3-2, in order
  A then B.
- **AC-3-2:** `compare_backtest_runs({ ids: ["<id-A>", "<id-missing>"] })` returns
  `{ "error": "Backtest runs not found: [<id-missing>]" }`.
- **AC-3-3:** `compare_backtest_runs({ ids: ["<id-A>"] })` (only 1 ID) returns a Zod
  validation error without hitting the DB.
- **AC-3-4:** `compare_backtest_runs({ ids: Array(6).fill("<id-A>") })` (6 IDs) returns
  a Zod validation error without hitting the DB.
- **AC-3-5:** `compare_backtest_runs({ ids: ["<id-A>", "<id-A>", "<id-B>"] })` (duplicate)
  returns an array of 2 objects (deduplicated), order: A then B.
- **AC-3-6:** `benchmarkReturn` and `sharpeRatio` are serialised as `null` (not
  `undefined`, not omitted) when absent from the record.

### DDD Layer Map

| Concern | Layer | File |
|---------|-------|------|
| Multi-run retrieval | infrastructure/db (via repo) | `backtestResultRepo.ts` (existing `getRunById` loop) |
| Deduplication | interface/mcp/tools | tool handler |
| Input validation (2–5 items) | interface/mcp/tools | `z.array(z.string().uuid()).min(2).max(5)` |
| Not-found aggregation | interface/mcp/tools | tool handler |

## Deliverable 4 — Repository Interface Extension

### New method: `IBacktestResultRepository.deleteRun(id: string): boolean`

```
deleteRun(id: string): boolean
// Returns true if the row was deleted, false if no row matched or on error.
```

This is an additive change to the existing interface. All three existing implementations
(`saveRun`, `getRunsByStrategy`, `getRunById`, `getAllRuns`) are unchanged.

### SQLite implementation: `SqliteBacktestResultRepository.deleteRun()`

SQL: `DELETE FROM backtest_runs WHERE id = ?`

Use `stmt.run(id).changes` (Bun SQLite statement run result) to determine whether a row
was affected. Return `true` if `changes >= 1`, `false` if `changes === 0`. Wrap in
try/catch; return `false` on error (consistent with the `getRunById` null-on-error
pattern).

## Edge Cases

- **Empty table:** `delete_backtest_run` on a fresh DB returns not-found error. `compare_backtest_runs` returns not-found error. `export_backtest_run_csv` returns not-found error. No crash.

- **resultJson size:** Large runs (30 tickers, 2 years) produce `resultJson` blobs of 200–500 KB. `export_backtest_run_csv` must parse this in memory. MCP transport is local stdio — size is not a network concern. No streaming required.

- **Null numeric fields in comparison:** `benchmarkReturn` and `sharpeRatio` are nullable. `compare_backtest_runs` must serialise these as `null` in the JSON output, never `undefined` or omitted. Tool handler must not filter null fields.

- **holdDays negative guard:** If `entryDate > exitDate` (data corruption), `holdDays` floors at 0. Do not emit negative values.

- **CSV special characters:** Ticker codes are uppercase ASCII (e.g. `VCB`, `HPG`). `direction` is `"BUY"` or `"SELL"`. No commas or quotes expected in any field. Quoting is not required unless Architect foresees future extension.

- **UUID validation in delete and export:** Both tools validate `id` as `z.string().uuid()`. A non-UUID string never reaches the database. This is consistent with the existing `get_backtest_run` tool which uses `z.string().min(1)` (weaker — Architect may standardise to `.uuid()` in Sprint 1846 as a housekeeping step, but it is not required).

- **Concurrent delete + read:** SQLite serialises writes. A delete concurrent with a `get_backtest_run` call returns either the full record (delete not yet committed) or not-found (delete committed). No partial reads. No additional mutex is required.

## Blockers

- **BLK-1 (Equity curve not in resultJson):** `export_backtest_run_csv` with
  `includeEquityCurve=true` requires equity curve data. Currently the equity curve is
  computed as a local `number[]` inside `backtestEngine.ts` (lines 303–306) and is never
  added to `BacktestReport` or serialised to `resultJson`. Options for Architect:
  - **Option A:** Add `equityCurve: number[]` to `BacktestReport` domain type and
    serialise it. Existing stored runs will not have this field (null/absent for old
    records). New runs going forward will include it.
  - **Option B:** Defer `includeEquityCurve=true` to a future sprint. Tool accepts the
    parameter but always returns the "not available" error until Option A is implemented.
  - **Option C:** Recompute equity curve on demand from the trade log when
    `includeEquityCurve=true` — the trades + positionWeight fields contain sufficient
    data. No schema change required. Minor CPU cost for large runs.
  Recommended: **Option C** (no schema migration, works for old runs too). Architect
  decides.

- **BLK-2 (File organisation):** `backtestTools.ts` currently contains ~226 lines
  (tools #120, #121, #122). Sprint 1846 adds 3 more tools. Architect decides whether to
  extend `backtestTools.ts` further or split into `backtestLifecycleTools.ts` (delete)
  and `backtestExportTools.ts` (export, compare). Both approaches satisfy DDD constraints.

- **BLK-3 (UUID validation consistency):** Existing `get_backtest_run` uses
  `z.string().min(1)` for `id` (not `.uuid()`). New tools for Sprint 1846 will use
  `.uuid()`. Architect decides: standardise old tool in the same PR, or leave as-is.
