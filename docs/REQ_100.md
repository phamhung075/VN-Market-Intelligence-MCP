# REQ-100: fix predictionSignals always empty in evening reports

status: READY_FOR_ARCHITECT
sprint: 100
po_vision: Evening report `predictionSignals` field contains active HIGH/CRITICAL prediction signals when they exist

## User Story

As a Vietnamese stock investor using Claude,
I want the evening report to show HIGH/CRITICAL Polymarket prediction signals,
So that I can factor crowd-sourced macro intelligence (Fed rates, China tariffs, oil) into my overnight position decisions.

---

## Root Cause Analysis (confirmed by code + DB inspection 2026-04-15)

Three independent root causes produce the always-empty result. All three must be fixed.

### RC-1 — `prediction_signals` table has no recent data (CONFIRMED)

**Evidence:**
```
prediction_signals total:    5
prediction_markets total:    83
prediction_signals last 24h: 0   ← assembleEveningSummary queries this window
```

The 5 rows that exist were created during task 163 schema tests in early April; two have `severity: "low"`, two `severity: "medium"/"high"` but are 14+ days old. The 24-hour query in `getRecentPredictionSignals` always returns 0 rows.

**Root cause:** `predictionMarketJob.ts` has a per-cycle concurrency guard (`_isRunning = true/false`). The guard is module-level. If the Bun process restarts the guard resets, but if a previous poll cycle ever threw before reaching the `finally` block's `_isRunning = false` — or if the Polymarket API timed out and the job exited early (`return` at line 349) — no signal would be stored. Combined with `enabled: true` in config but Polymarket geo-blocked from France, the `fetchPolymarkets()` call throws on every cycle and the job exits at line 349 without storing anything.

**Verification:** `prediction_markets` has 83 rows (from earlier successful polls via VPS), but `prediction_signals` only has 5 (test data), confirming the signal detection step never ran successfully in production. The gap means `fetchPolymarkets()` has been failing silently for weeks.

### RC-2 — `predictionMarketJob` fetches markets directly, NOT via VPS proxy (CONFIRMED)

The job calls `fetchPolymarkets()` which hits `clob.polymarket.com` directly from the local Bun process. The server runs in France. Polymarket is geo-blocked from France. The fetch throws a network error, the job catches it and returns early (line 345-350 in `predictionMarketJob.ts`):

```typescript
} catch (err) {
  logger.error("[prediction-market-job] fetchPolymarkets failed", { error: String(err) });
  return;   // ← exits before detectPredictionSignals or storePredictionSignals
}
```

No signals are detected, no rows inserted. But existing `prediction_markets` data (83 rows from when the VPS proxy was configured) is never refreshed either.

### RC-3 — `assembleEveningSummary` swallows all errors silently (CONFIRMED)

In `assembleEveningSummary.ts`, the prediction step is wrapped in a bare `try { ... } catch { /* best-effort */ }` block (lines 313-319). If `getRecentPredictionSignals` throws for any reason, the error is discarded silently and `predictionSignals` stays `[]`. No warning is logged, making diagnosis impossible from logs.

## Functional Requirements

### FR-1: Wire Polymarket fetch through VPS proxy

- **Description:** `predictionMarketJob` must route `fetchPolymarkets()` through the VPS proxy (`$VINAHOST_IP`) instead of calling Polymarket directly, consistent with the project-wide geo-block workaround policy.
- **Input:** `mcp.config.json` → `predictionMarkets.clobApiUrl` + `predictionMarkets.gammaApiUrl`
- **Output:** Successful HTTP responses from Polymarket via VPS forwarding
- **Business rule:** All geo-blocked VN/global sources route through VPS. Polymarket is geo-blocked from France. No exceptions.
- **DDD layer:** infrastructure — `src/infrastructure/fetchers/polymarket.ts`

### FR-2: Log a warning (not silently swallow) in assembleEveningSummary

- **Description:** Replace the bare `catch { /* best-effort */ }` in the prediction signals step with `catch (err) { logger.warn(...) }` so errors are visible in logs.
- **Input:** any error thrown by `getRecentPredictionSignals`
- **Output:** Warning log line with error message; `predictionSignals` remains `[]` (graceful degradation preserved)
- **Business rule:** Best-effort is acceptable for non-critical enrichment; silent failure is not.
- **DDD layer:** application — `src/application/usecases/assembleEveningSummary.ts`

### FR-3: Fix or add a diagnostic assertion that `prediction_signals` is populated

- **Description:** Add a TDD test (`src/__tests__/1318-prediction-signals-evening.test.ts`) that:
  1. Inserts a HIGH-severity signal with `detected_at = now()` into an in-memory DB
  2. Calls `assembleEveningSummary({ db })`
  3. Asserts `predictionSignals.length >= 1` and `predictionSignals[0].severity === "high"`
  Also add a test that inserts a signal from >24h ago and asserts `predictionSignals.length === 0` (time-window boundary).
- **Input:** in-memory SQLite with seeded `prediction_signals` + `prediction_markets` rows
- **Output:** passing tests confirming the query path works end-to-end
- **Business rule:** TDD — tests must be written first (failing), then fixed by implementation.
- **DDD layer:** application (test coverage)

### FR-4: Ensure `predictionMarketJob` does not silently exit when fetch fails

- **Description:** When `fetchPolymarkets()` fails, log the error AND fall back to using the last known snapshot from `prediction_markets` table for signal detection (rather than `return`-ing early). This allows the signal detector to run against stale data and emit signals if the probability shift is still present.
- **Input:** DB rows from `prediction_markets` (last known state)
- **Output:** signals detected against the cached snapshot; log entry indicating fallback mode
- **Business rule:** 83 markets are already in the DB. The detector can run with `currentMarkets == previousMarkets` — that produces 0 volume-spike signals but still catches any unresolved probability shifts cached from last successful poll.
- **DDD layer:** interface/scheduler — `src/scheduler/predictionMarketJob.ts`

## Edge Cases & Data Quality

- [x] `prediction_signals` table empty → `getRecentPredictionSignals` already returns `[]`, `assembleEveningSummary` returns `predictionSignals: []`. Correct behavior, no change needed.

## Implementation Notes for Architect

### Polymarket VPS proxy pattern (FR-1)

The `fetchPolymarkets` function in `src/infrastructure/fetchers/polymarket.ts` constructs HTTP requests to `clobApiUrl` and `gammaApiUrl` from config. The VPS proxy pattern used by other fetchers (e.g. `vn-price-fetch.service`) is: configure `clobApiUrl` / `gammaApiUrl` in `mcp.config.json` to point to `http://$VINAHOST_IP:<port>` instead of the Polymarket domain. The VPS's `vn-news-fetch.service` or a new service forwards the request. This is config-level only — no code change to the fetcher function itself may be needed if the URLs are already configurable (they are: `mcp.config.json` already has `"clobApiUrl": "https://clob.polymarket.com"`).

However, if no VPS service forwards Polymarket requests today, the Architect must decide: (a) add a new VPS systemd service, or (b) implement a local SOCKS5/HTTP proxy tunnel. Option (a) matches the existing pattern. The BA has no blocker here — the Architect owns the proxy topology decision.

### Fallback snapshot pattern (FR-4)

Current code in `predictionMarketJob.ts` (lines 330-349):
```typescript
let currentMarkets: PredictionMarket[];
try {
  currentMarkets = await opts.fetchFn();
} catch (err) {
  logger.error("...", { error: String(err) });
  return;   // BUG: exits here, never reaches detectPredictionSignals
}
```

Fix: on catch, set `currentMarkets = loadPreviousSnapshot(db)` (the helper already exists in the same file). Then continue to `detectPredictionSignals(currentMarkets, previousMarkets, ...)`. When `currentMarkets === previousMarkets` the detector emits 0 volume-spike signals, but that is correct (no new volume change) and no-ops are safe.

### assembleEveningSummary error logging (FR-2)

Current code (lines 312-319):
