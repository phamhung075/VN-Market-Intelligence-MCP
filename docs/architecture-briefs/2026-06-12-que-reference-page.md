## 1. Problem Statement

The frontend exposes a tooltip-level hexagram description (2 fields) via `QUE_DESCRIPTIONS`. The user needs a dedicated reference page showing ALL 64 hexagrams with full Vietnamese detail: name, Chinese character, trigrams, extended state interpretation, favorable guidance, warning, and 6-phase hào line glosses.

SSOT (`que-reference.js`) already holds all required fields. The codegen currently emits only the 2-field tooltip set (PO-Q3 contract). This brief rules the codegen extension mechanism and the full page design.

## 3. Design Decisions

### D1 — Codegen extension: ADDITIVE second generated file (do NOT widen the tooltip interface)

**Ruling:** Emit a SECOND generated artifact `apps/frontend/app/lib/que-descriptions-detail.generated.ts` from the same codegen script.

**Rationale:**
- The existing `QueDescription` interface (2 fields) is a named export tested by AC-2 in `QUE-TOOLTIP-DRY-1a-codegen-pipeline.test.ts`. Widening that interface with 10+ new fields would force every consumer of `QueDescription` to carry fields it does not use, and risk breaking the AC-2 "exactly 2 fields" type-check test.
- A separate `QueDetailDescription` type keeps the tooltip contract sealed. The detail page imports from the detail file; `QueName.tsx` is never touched.
- Both files are generated by the same single script invocation (`bun run gen:que`) — one parse pass, two `writeFileSync` calls. Zero duplication of parse logic.
- Precedent: the pattern of two generated artifacts from one codegen source is cleaner than an overloaded interface. Future consumers pick the right import.

**`QueDetailDescription` interface — full field set:**
```typescript
export interface QueDetailDescription {
  id: number;
  name: string;          // Vietnamese romanized name e.g. "Kiền"
  chinese: string;       // Chinese character e.g. "乾"
  upper: string;         // upper trigram name e.g. "Qian"
  lower: string;         // lower trigram name
  upperElement: string;  // e.g. "Kim"
  lowerElement: string;
  coreMeaning: string;        // .vi from SSOT
  marketTrendLabel: string;   // .vi from SSOT
  stateInterpretation: string; // .vi from SSOT
  favorable: string;           // .vi from SSOT
  warning: string;             // .vi from SSOT
  phases: Array<{
    phase: number;    // 1–6
    action: string;   // GIU | TIEN | THAN | LUI
    outcome: string;  // CAT | HUNG | LE
    gloss: string;    // .vi from SSOT
  }>;
}
export const QUE_DETAIL: Record<number, QueDetailDescription> = { ... };
```

**Script change:** `scripts/gen-que-descriptions.ts` gains a second output block. The first block (tooltip) is unchanged. The second block iterates the same parsed `queReference` array and emits `que-descriptions-detail.generated.ts`. Both files share the header comment convention.

**gen:que script entry remains the single command.** No new npm script needed.

### D4 — Page layout and UX

**No server API call.** All 64 descriptions are fully static (codegen artifact imported at module level). The route file exports only a `loader` that returns the static data (or skips it entirely — `useLoaderData` not needed; import `QUE_DETAIL` directly in the component). This makes the page zero-latency and SSR-friendly.

**DDD layer assignment:** The route file is a Remix interface layer component. The `QueDetailDescription` type lives in the generated lib (not a domain model — it is a static reference set). No domain service, no use-case layer needed.

**Page structure (plain-Vietnamese, non-technical):**
```
PageHeader: "Tra cứu Kinh Dịch — 64 quẻ"
SearchBar: client-side text input, placeholder "Tìm theo tên hoặc số quẻ..."
  → filters by id, name (romanized), or chinese character (client-only, no API)
GridOrList: render all 64 QueCard components (responsive grid, mobile-first)
```

**QueCard anatomy (one card per hexagram):**
```
Header: #<id> <chinese> — <name>   (anchor id="que-<id>")
Trigram line: Thượng quái: <upper> (<upperElement>) / Hạ quái: <lower> (<lowerElement>)
Xu hướng thị trường: <marketTrendLabel>   (colored badge: thuận lợi=green, bất lợi=red, trung tính=slate)
Ý nghĩa cốt lõi: <coreMeaning>
Trạng thái hiện tại: <stateInterpretation>
Thuận: <favorable>
Cảnh báo: <warning>
Hào: 6-row table — Hào {phase} | Hành động: {action} | Kết quả: {outcome} | {gloss}
```

All labels in plain Vietnamese. No English. No market jargon.

**Search/filter:** client-side only. `useState(query)` → filter `Object.values(QUE_DETAIL)` by `id.toString().includes(query) || name.toLowerCase().includes(lower) || chinese.includes(query)`. Debounce is optional (64 items, negligible perf). Zero API calls.

### D5 — QueName deep-link ruling: INCLUDE (opt-in, zero tooltip regression)

**Ruling:** Include the deep-link. Implementation: `QueName.tsx` wraps the trigger `<span>` in a client-side `<Link to="/dashboard/kinh-dich-reference#que-{hexagram}">` — OR appends a small "↗" icon link beside the tooltip content. Second option is safer (NFR-1: tooltip markup stays in QueName).

**Preferred implementation:** Add an optional `withDetailLink?: boolean` prop to `QueName`. Default = `false`. Callers that want the link pass `withDetailLink`. This avoids retroactively changing all existing `<QueName>` call sites. Tooltip content renders an additional small link line `<a href="/dashboard/kinh-dich-reference#que-{hexagram}">Xem chi tiết →</a>` inside the `TooltipContent`. No markup moves outside `QueName`. NFR-1 preserved.

**Risk:** none — prop is additive, default false, existing callers unchanged. QA test: assert `withDetailLink` prop renders an anchor; assert default (no prop) renders no anchor.

### D6 — No server proxy route needed

Unlike `dashboard.kinh-dich-signals.tsx` (which has a paired `api.kinh-dich-signals.tsx` proxy), the reference page has no upstream API dependency. All text comes from the generated static file. No `api.kinh-dich-reference.tsx` route is created.

## 4. Risk Flags

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| R1 | AC-2 regression: QUE-TOOLTIP-DRY-1a test asserts "entry does NOT have state_trend" and by implication only 2 fields. Widening existing type would break. | HIGH | D1 uses second file — original interface untouched. |
| R2 | Codegen script grows in complexity — parse errors on second output block silently write 0B file. | MED | Developer adds `[ -s <detailOutPath> ]` check + throw if empty, same guard pattern as any write-path. |
| R3 | gen:que run during CI without the second output file committed — import in route fails build. | MED | Both generated files committed together. CI has no `bun run gen:que` step (script is manual regeneration trigger). Generated files are committed artifacts. |
| R4 | QueName `withDetailLink` creates a nav `<Link>` inside a `<Tooltip>` Radix portal — potential hydration mismatch. | LOW | Use `<a href="...">` (plain anchor) inside TooltipContent instead of Remix `<Link>` — avoids Remix Router context inside portal. |
| R5 | TopNav ANALYST_NAV grows to 25 entries — horizontal overflow on small screens already present. | LOW | Existing design debt; no action in this sprint. Note for future nav-restructure. |
| R6 | Phase action/outcome codes (GIU/TIEN/THAN/LUI/CAT/HUNG/LE) displayed raw. | LOW | Developer maps to plain-VN labels in QueCard. Brief provides the mapping below. |

**Action/outcome label map for developer reference:**
```
action: GIU → "Giữ vững", TIEN → "Tiến", THAN → "Thận trọng", LUI → "Lui"
outcome: CAT → "Tốt lành", HUNG → "Xấu", LE → "Vất vả nhưng thành công"
```
