## 1. Three-Lane Model

### Classification Rule

Every system improvement falls into exactly one lane. Apply in order — first match wins.

```
IF proposed change touches the gate/audit logic itself
   OR the success metric is "user finds this comprehensible"
   OR action is irreversible (data deletion, external notification, prod schema drop)
   → LANE-C (human-only, never auto-close)

ELSE IF a hard, machine-checkable, ungameable success signal exists
   AND that gate can be DEMONSTRATED to go red on a deliberate violation
   → LANE-B (auto-implement behind proven gate, via dev-team chain + QA)

ELSE
   → LANE-A (auto-propose, PO approves, agent-father implements)
```

**Ungameable** means the gate cannot return green on a bad implementation. A test suite where the test file itself is generated by the improvement is gameable. A lint rule where the linter is configured by the improvement is gameable.

### Lane-A — AUTO-PROPOSE + PO-APPROVE

- **Default lane for all flow and agent `.md` changes.**
- Trigger: system-auditor or agents-architect detects a weakness, writes a proposal doc.
- Gate: PO reads proposal + writes mandatory written critique → approves or rejects.
- Impl: agent-father executes the approved `.md` change.
- **Worked examples:**
  - Stale doc (notebook over 150L, outdated pointer in MEMORY.md) → lane-a.
  - Missing flow step in an agent's cycle (e.g., system-auditor missing the D5 handler trigger) → lane-a.
  - Agent `.md` drift from roster standard → lane-a.
  - A new cron time-slot needed for proposal-emit step (depends on host-load budget check) → lane-a after PO critique includes budget check.

### Lane-B — AUTO-IMPLEMENT BEHIND A PROVEN GATE

- **Only for microservice code/tool changes where the success signal is hard and ungameable.**
- The gate MUST be demonstrated red before it is trusted — inject a deliberate violation and confirm it goes red (`feedback_fence_false_green`).
- Impl: dev-team full chain (po → ba → architect → pm → dev-* → qa). Never a shortcut.
- Examples of hard ungameable gates: test suite passes green on known-good + goes red on deliberate regression injected at the test level (not the test-generation level); linter exits non-zero on a deliberate violation inserted in a scratch file; dedup logic rejects a known-duplicate insertion proven by querying the DB.
- **Worked examples:**
  - Signal-accuracy degradation detected (10pp regression over 30-day baseline) → DEGRADATION_CAUSE_MAP lookup → fix hypothesis → dispatch dev-mcp-server to adjust PMI threshold → QA verifies with injected regression test → lane-b.
  - Coverage gap: watchlist stock has zero resolved signal outcomes → rule-table hypothesis → dev dispatch → QA confirms test goes red on missing coverage → lane-b.
  - Missing unit test for a published domain service (test count provably decremented by deletion then returned by PR) → lane-b.

### Lane-C — NEVER AUTO-CLOSE → HUMAN ONLY

- **Permanent lane for subjective quality, irreversible actions, and gate/audit self-edits.**
- The loop cannot escalate a lane-c item by itself — it can only write a WORK message to the human.
- **Items that are lane-c FOREVER:**
  - Plain-Vietnamese comprehensibility of any user-facing output. Anchor case study (binding): the plain-VN MARKET report fix passed the tran-ngoc-bau internal audit (analytically rigorous) but FAILED the user ("too complicated to understand"). Self-audit structurally cannot detect subjective comprehensibility. This axis stays human-judged permanently.
  - Any change to the gate logic, audit rules, or the success criteria of the loop itself. The system must not rewrite the terms by which it judges its own improvements.
  - Irreversible actions: production data deletion, schema drops, external notifications (Telegram to users), removing a cron from the fleet.
  - A lane-c item CANNOT be reclassified to lane-a or lane-b by any automated step — reclassification requires explicit human instruction written outside the loop.
- **Worked examples:**
  - "MARKET reports use too much jargon" → lane-c.
  - "The audit success criteria for signal degradation should be loosened from 10pp to 5pp" → lane-c.
  - "Remove the bctcBatchSweep cron" → lane-c.

## 2. Detect → Propose → Deliberate → Implement Pipeline

### Agents (existing only)

```
DETECT ─────── system-auditor (Tier-2/Tier-3 cron ticks)
                 │  writes: docs/improvement-proposals/<id>.md
                 │  AND: DASHBOARD.md ## po row (type=improvement_proposal)
                 ▼
PROPOSE ──────── agents-architect (cron / on-demand, reads new proposals from DASHBOARD)
                 │  validates lane classification, adds evidence, signs proposal
                 │  updates: docs/improvement-proposals/<id>.md (adds architect-review section)
                 │  writes: docs/signals/<slug>.json → po
                 ▼
DELIBERATE ───── po (dev-team Step 1 → PO triage-signals.md)
                 │  reads proposal doc, writes mandatory critique in po notebook
                 │  updates proposal doc: adds po-critique + verdict fields
                 │  if approved → routes per lane
                 ▼
IMPLEMENT ─────── lane-a: agent-father (edit/create sub-flow)
                  lane-b: dev-team chain (po→ba→architect→pm→dev-*→qa)
                  lane-c: send_telegram(channel="work") → human; STOP
```

**No new agents. No new always-on cron.** The detect step rides the existing system-auditor Tier-2 (every 4h) and Tier-3 (daily 03:00Z) ticks. The propose step runs when agents-architect is invoked (cron or on-demand) and finds DASHBOARD rows of type `improvement_proposal`. The PO gate runs inside the existing `triage-signals.md` flow. Agent-father uses its existing `edit.md` sub-flow.

## 3. Proposal Artifact

### Location

`docs/improvement-proposals/<id>.md`

`<id>` format: `IMP-<YYYYMMDD>-<slug>` (e.g. `IMP-20260527-signal-degradation-price-confirmation`)

### Required Fields

```markdown
# Improvement Proposal <id>

**Created:** <ISO-8601 UTC>
**Created by:** system-auditor | agents-architect
**Status:** DRAFT | ARCHITECT-REVIEWED | PO-APPROVED | PO-REJECTED | IMPLEMENTING | DONE

## Weakness
One paragraph. What is wrong or degraded. Concrete evidence pointer.

## Evidence
- Source: <check_id / audit dimension / dashboard signal>
- Data: <metric, delta, dates>
- Reproducibility: <how to reproduce>

## Proposed Change
What should change. Which file(s). No implementation — description only.

## Lane
LANE-A | LANE-B | LANE-C

### Lane Rationale
Why this lane. For lane-b: what is the hard ungameable gate. For lane-c: which permanent criterion applies.

## Success Signal
How to know the change worked. Must be machine-checkable for lane-b, human-judged for lane-c.

## Rollback
How to undo the change if the success signal is not met within 7 days.

---

## Architect Review
*(filled by agents-architect before routing to PO)*

**Lane confirmed:** LANE-A | LANE-B | LANE-C
**Evidence validated:** yes | no (with reason)
**Proposed change scope:** N files — <list>
**Architect notes:** <any caveats>

---

## PO Critique
*(filled by PO before verdict — MANDATORY, cannot be empty)*

**What could break:** <answer required>
**False-green / silent-swallow risk:** <answer required>
**Is the success signal gameable:** <answer required>
**Host-load impact:** <answer required — include RAM/disk/tick estimate>

**Verdict:** APPROVED | REJECTED | ESCALATED-TO-HUMAN
**Verdict date:** <ISO-8601>
**Verdict rationale:** <1-3 sentences>
```

An approval with an empty PO Critique section is a protocol violation. The PO flow must enforce this.

## 4. PO Critique Gate

**Position in flow:** `docs/agents/po/flow/triage-signals.md` — add a new routing row for `improvement_proposal` signal type. The PO flow MUST:

1. Read the proposal doc at the path in the signal payload.
2. Write the four critique fields into the proposal doc (break-risk, false-green, gameability, host-load) BEFORE writing the verdict.
3. If any critique field is left blank or contains placeholder text → reject the proposal with `verdict: REJECTED` and reason `"critique incomplete"` — this prevents rubber-stamping.
4. Write the verdict + date + rationale into the proposal doc.
5. Route per lane:
   - LANE-A + APPROVED → emit signal to agent-father (type `improvement_approved_md`).
   - LANE-B + APPROVED → create SPRINT-S or SPRINT-M batch entry for dev-team.
   - LANE-C or any REJECTED → write WORK Telegram with the reason; no dispatch.

**Auditable:** The proposal doc carries the full critique + verdict permanently. Any future agent reading the proposal can verify the critique was recorded.

## 5. Proven-Gate Proof Procedure (Lane-B)

The "tests pass / lint exit 0" pattern is NOT proof that a gate enforces anything (`feedback_fence_false_green`). Before any lane-b auto-implement is trusted, the gate must be demonstrated to fail red on a deliberately injected violation. This is QA's acceptance criterion, not an assertion.

### Protocol

For every lane-b proposal, QA must execute:

```
Step GATE-PROOF-1: Identify the gate mechanism (test suite / linter / dedup check / invariant query).

Step GATE-PROOF-2: Inject a deliberate violation INTO THE SUBJECT CODE (not the gate config).
  Examples:
  - Test gate: add a test that calls the function with a known-bad argument and asserts a wrong result.
    Then run the suite — it must go red on that test.
  - Lint gate: insert a deliberately invalid construct (unused import, wrong type) in a scratch file.
    Then run the linter — it must exit non-zero and name the file.
  - Dedup gate: attempt to INSERT a known-duplicate row directly in the test DB.
    Then query — it must have zero duplicates.

Step GATE-PROOF-3: Confirm the gate reports RED. Record the output in the QA report.

Step GATE-PROOF-4: Remove the deliberate violation. Confirm the gate returns GREEN.

Step GATE-PROOF-5: Record in the proposal doc: "Gate proven red on [date] by [method]. Evidence: [output]."
```

**If GATE-PROOF fails** (gate does not go red): the lane-b proposal is reclassified to lane-a (PO must explicitly approve the implementation without the automated gate as backstop). This reclassification is recorded in the proposal doc.

**The SELF_IMPROVE_AUTO_DISPATCH kill-switch** (from Sprint 1948 design) maps to this requirement: `false` by default until GATE-PROOF is recorded for each dispatch path. QA signs off on GATE-PROOF; agent-father sets the env var only after QA sign-off.

## 6. Host-Load Budget Rule

**Rule:** No new always-on agent or new cron tick may be added to this loop without an explicit line-itemed budget approved in the PO critique section.

**Budget template (required in the PO critique `host-load impact` field for any new cron/agent):**

```
New cron/agent: <name>
Schedule: <cron expression>
RAM: ~<N> MB resident (idle) / ~<N> MB peak (active)
Disk: ~<N> KB/day write to docs/
Tick cost: <N> Claude tokens / tick (if cowork agent), 0 (if scheduler job)
Fleet context: current Docker cap = 8GB; current kernel-panic history = memory project_host_memory_panic
Decision: APPROVED (within budget) | REJECTED (exceeds budget, redesign needed)
```

**This loop's footprint:**

- No new Docker services.
- No new cowork agents.
- New cron tick added to `apps/mcp-server/src/scheduler/cronConfig.ts` (selfImproveOrchestratorJob, `0 9 * * *`): ~0 MB incremental RAM (runs inside existing mcp-server process), ~0.5 KB/day to `improve_check_log`. APPROVED.
- New DASHBOARD rows written by system-auditor: these ride the existing Tier-2/Tier-3 ticks. No new tick. ~1–5 rows/day appended to `docs/signals/DASHBOARD.md`. APPROVED.
- `docs/improvement-proposals/` directory: append-only, ~2–5 KB/proposal. APPROVED.
- Agents-architect proposal-review step: rides existing on-demand invocation. Not a new always-on cron. APPROVED.

**Forbidden:** A new dedicated `self-improver` cowork agent running on a new cron slot is explicitly OUT OF SCOPE (host load, token cost, see SPIKE_1947 §3 Option B: REJECTED for Phase 1-2).

## 7. Escalation Boundary (Lane-C)

### How Lane-C Reaches the Human

```
system-auditor OR agents-architect detects a lane-c item
  → writes docs/improvement-proposals/<id>.md with lane=LANE-C
  → DASHBOARD.md row type=improvement_proposal, section ## po
  → po triage-signals.md reads it
  → po MUST NOT dispatch lane-c items to agent-father or dev-team
  → po writes:
      send_telegram(channel="work",
        message="[loop] Lane-C improvement — human decision required: <id> — <one-line summary>")
  → proposal doc marked status=ESCALATED-TO-HUMAN, verdict date set
  → loop STOPS for this proposal; the human chooses to re-open as lane-a/b or close
```

### Why Lane-C Cannot Be Self-Promoted

The classification rule is part of the gate logic. Any change that loosens the lane-c criteria (e.g., "let the loop self-certify comprehensibility") is itself a lane-c item — a change to the gate logic. This creates a logical barrier: to promote a lane-c item to lane-a/b, the loop would need to modify its own classification rule, which is a lane-c action. The loop cannot authorize itself to self-promote.

**The only path out:** the human reads the WORK Telegram, examines the proposal, and instructs the loop to reclassify (or not). This instruction must come from outside the loop.

**Comprehensibility blind spot (anchor):** The self-improvement loop's output is agent flows and code. The loop can check whether a test passes. It cannot check whether the Vietnamese in a MARKET report reads naturally to a non-technical user in France. The plain-VN MARKET fix (2026-05-27) is the standing proof. This blind spot is named here so it is never confused for a solvable technical problem.

## 8. Commit Safety

All agents in this loop share one git index on `main`. Serialization is non-negotiable (`feedback_concurrent_commit_race`, `feedback_merge_gate_cherrypick_serialize`).

**Rules:**

1. Proposal doc writes (`docs/improvement-proposals/<id>.md`) are done by system-auditor and agents-architect on their respective cron ticks, which are non-overlapping (system-auditor Tier-2 every 4h + Tier-3 03:00Z; agents-architect on-demand). No concurrent write risk for proposal docs.

2. PO notebook updates (critique + verdict) use the existing commit-mutex skill: `task_claim commit-mutex:main (TTL=60s) → git add docs/agent-memory/notebooks/po.md docs/improvement-proposals/<id>.md → verify → git commit → task_release`.

3. Agent-father implements approved `.md` changes using the existing `edit-apply.md` task-lock flow. No change to that serialization.

4. Dev-team lane-b implementations follow the existing `execute-tier.md` merge-gate protocol. No change.

5. Proposal docs are committed by whoever writes the last update to them (system-auditor for DRAFT, agents-architect for ARCHITECT-REVIEWED, PO for APPROVED/REJECTED). Each agent commits only its own section update in a single commit. Never batch two agents' proposal-doc edits into one commit.

6. `git add` is always path-explicit: `git add docs/improvement-proposals/<id>.md`. Never `-A` or `.`.
