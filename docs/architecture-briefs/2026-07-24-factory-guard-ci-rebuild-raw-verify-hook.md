## 0. Ticket-premise correction (verify-live catch — the ticket's own words don't fit this repo)

**"attached to the PR" is a category error here.** `gh pr list --state all` returns exactly **one** PR in the repo's entire history (`#1`, `feat: Value Investor Analysis System`, `state: CLOSED`, `mergedAt: null` — never merged via PR). `gh api repos/:owner/:repo/branches/main/protection` → `404 Branch not protected`. This repo's actual, governing workflow (CLAUDE.md: "NO branches — all work stays on `main`") is autonomous direct-push-to-main (`docs/policies/dev-standards.md` § Push Policy, `PUSH-AUTONOMY-1`) — there is no PR to attach anything to, and no branch-protection merge gate a CI check could block. The functional analog of "PR" in this repo is **the commit landing on `main`**.

**The DoD this ticket asks for is not a gap in policy — it already exists, mandatory, in writing.** `docs/policies/dev-standards.md` `PUSH-AUTONOMY-1` §5 (pinned 2026-07-14): *"Post-push REAL-DATA verification task (mandatory): after CI green, po mints a board task `VERIFY-<task-id>-REALDATA` whose verification gate is a RAW-live probe of the SERVING layer with real data... If the change touches serving code, the task's precondition is the single-service rebuild+deploy."* This is word-for-word the "no-fake-data DoD" the audit brief names. The gap is **zero mechanical enforcement that it happens.**

**Compliance evidence (2026-07-24, grep-verified):** across the *entire* `orch-state.json` + `docs/data/orch/archive/*.json` history, exactly **2** `VERIFY-*-REALDATA` task rows have ever existed — `VERIFY-FIX-DAILY-FF-VIEW-JOIN-ANCHOR-REALDATA` (archived, done) and `VERIFY-FIX-VPS-SSH-TRIGGER-FAIL-LOUD-REALDATA` (currently **BLOCKED**, live backlog) — against **54** commits touching `apps/**/src/**`/`apps/**/pkg/**` (serving code) since §5 was pinned. Concrete miss: commit `e3386bdfa` ("TASK-CONF-1 remove DEFAULT-50 confidence mask, wire real severity/finding confidence" — exactly the metric-mask bug class the audit names, self-flagged `rebuild_required: true`) carries zero `RAW-verify`/`REALDATA` attestation anywhere in its message and has no companion `VERIFY-*-REALDATA` row. The written policy is real; the compliance is not.

## 3. Guardrail design — zero-tolerance going forward, no baseline (different reasoning than size-lint's grandfather)

**Sizing call:** this is an inherently **forward-only attestation check** on the diff of a push, not a source-file-pattern sweep — there is no existing-file backlog to grandfather (the 54-commit compliance gap is history; nothing to retroactively "fix" in a child task). Zero-tolerance from day 1, same conclusion as dead-code-gate but for a different reason: not "small enough to fix now," but "there is nothing to fix, only to gate going forward."

**Trigger scope (evidence-scoped, not maximal):** interpreting "any PR touching a hardcode-metric or metric-serving path" maximally would flag nearly every FACTORY-epic commit (its own DoD text says "RAW-verify... after rebuild" on almost every task) — too broad for a cheap bash/grep hook. Scope the trigger by **composing the two already-designed sibling primitives** instead of inventing a third pattern: a file matches if (a) it is under a DB-write/route-serving DDD layer (`apps/*/src/infrastructure/**`, `apps/*/src/interface/**`, `apps/*/pkg/interface/http/**`, `apps/*/pkg/infrastructure/**` — the same tiers `FACTORY-GUARD-CI-depguard-tier-boundaries` fences) **and** (b) its added lines (`git diff` `+` lines) match the metric-mask-lint sibling's own field regex (`confidence|score|impact|magnitude|probability`, case-insensitive).

**Mechanism — `scripts/audits/rebuild-raw-verify-check.sh <base-sha> <head-sha>` (bash/git/grep, no toolchain):** if the trigger (above) fires anywhere in the range, require ONE of: (i) `git log <base>..<head> --format=%B` contains `raw-verify|raw verified|realdata` (case-insensitive); (ii) the range touches `docs/agent-memory/decisions/**` or `reports/TASK_REPORT_*.md` with an added line matching the same token; (iii) an inline `raw-verify-allow: <reason>` annotation on the triggering line (mirrors `metric-mask-allow:`/`size-justification:` escape-hatch idiom). None found → **FAIL**, printing the file:line trigger + a fix hint pointing at `PUSH-AUTONOMY-1` §5.

**Wiring — two layers, primary is the hook not CI (repo has no PR/branch-protection to gate on):** (a) **PRIMARY/blocking** — extend the existing `scripts/git-hooks/pre-push` with a call to this script inside its current `CODE_TOUCHING_REGEX`-gated section (reuses the already-computed diff, same doc-only-push skip fast path); this is the repo's actual pre-merge gate. (b) **SECONDARY/backstop** — a new `rebuild-raw-verify-hook` job in `.github/workflows/ci.yml` running the same script against `${{ github.event.before }}..${{ github.sha }}`, catching any push where the local hook was bypassed (`PRE_PUSH_SKIP_TSC=1`-class escape or a non-hook-installed clone) — red CI on `main` is itself a monitored, actionable signal in this project's practice (auditor/router route `ci_red`), so it retains teeth despite no PR to block.

**Explicitly OUT of scope (deferred):** mechanically verifying a `VERIFY-*-REALDATA` board task was actually minted per §5 — that requires board-state introspection across a LATER, separate push (the task is minted "after CI green," temporally outside the triggering commit range) and is a heavier, different mechanism; this hook checks the lighter, immediately-checkable textual-attestation bar. No change to `PUSH-AUTONOMY-1` §5 itself.
