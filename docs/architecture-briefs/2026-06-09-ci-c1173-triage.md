## 2. Failure Classification

### Verdict: GENUINE ASSERTION-LOGIC failure class — REWRITE (transport-hang)

**Not contamination.** Evidence:

- The 3 failing tests are inside `describe("Task 1173 — AC-4/AC-5 ...")` blocks.
  Both use `makeMcpSetup()` (lines 169–183 of the test file), which calls
  `InMemoryTransport.createLinkedPair()` + `server.connect()` + `client.connect()`.
- The `afterEach` in both describe blocks calls `await client?.close()` and `closeDb()`.
- The failure is a **hook timeout** (beforeEach or afterEach stall at ~5000 ms) —
  not a module-load SyntaxError and not a wrong-value assertion.
- No `mock.module()` call anywhere in `1173-calibration-label-integration.test.ts`.
  The telegram contamination chain (1485→047→1352a→FIX-1290) is irrelevant here.

**Contamination ruling — definitively excluded:**

1. The test file has zero `mock.module()` calls. No ESM stub can be injected into it.
2. The failing tests use `client.callTool()` which fails at transport level (timeout),
   not at assertion level. A stub contaminator would produce an instant-fail
   assertion error at ~1 ms, not a 5000 ms timeout.
3. Files immediately before 1173 in CI file order:
   - 1392-calibration-report-diacritics.test.ts (15:18:20)
   - 1117-evidence-tools.test.ts (15:18:22)
   - 1129-calibration-tools.test.ts (15:18:37) — all passing, uses `_registeredTools`
   None install `mock.module()` for any module imported by 1173's AC-4/AC-5 tests.
4. The passing tests in 1173 itself (AC-1 through AC-3, AC-6 through AC-9) run
   immediately before the failing tests in the same file and all pass at <53 ms.
   A contaminator leaking into 1173 would not selectively skip the first 13 tests.

**Root cause:** InMemoryTransport + `Client.callTool()` hangs in CI (Bun 1.3.13 /
Ubuntu-latest single-process sequential). This is the same mechanism diagnosed in:
- 1124 (24 fails → 0 after `_registeredTools` rewrite, commit 802a4d1b)
- 1129 (5 fails → 0 after `_registeredTools` rewrite, arch-S13 → CI-green confirmed
  in run 27216305674 job 80358657573 — all 5 AC-5/AC-6/AC-7/AC-extra/AC-7b PASS)
- 1134 (12 fails → 0 after `_registeredTools` rewrite, commit 8916675a)

The `afterEach(async () => { await client?.close(); closeDb(); })` in both AC-4 and
AC-5 describe blocks follows the C3 advice (cited in the test comments), but
`client.close()` itself stalls when the underlying `callTool()` transport is hung —
so the afterEach hook itself times out. This accounts for the
"beforeEach/afterEach hook timed out" message observed.
