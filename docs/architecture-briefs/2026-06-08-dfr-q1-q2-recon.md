### Working Request Recipe — vnexpress.vn extension for article-body-fetcher.py

```python
HEADERS = {
    "User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36",
    "Accept": "text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8",
    "Accept-Language": "vi-VN,vi;q=0.9",
    "Referer": "https://vnexpress.net/kinh-doanh",
}

def extract_vnexpress(html: str, url: str) -> dict:
    soup = BeautifulSoup(html, "html.parser")
    container = soup.find("article", class_="fck_detail") or soup.find("article")
    # Remove noise
    for tag in container.find_all(["script", "style", "figure", "figcaption", "ins"]):
        tag.decompose()
    body_text = re.sub(r"\s+", " ", container.get_text(separator=" ", strip=True)).strip()
    # og meta for title and published_at
    og_title = soup.find("meta", property="og:title")
    pub_time = soup.find("meta", property="article:published_time")
    return {
        "title": og_title["content"] if og_title else "",
        "body_text": body_text[:8000],
        "published_at": pub_time["content"] if pub_time else "",
    }
```

**Technique:** plain-requests-open-api (existing technique, no new technique doc required — same pattern as cafef.vn / vneconomy.vn in article-body-fetcher.py).

**Libraries required:** `requests`, `beautifulsoup4` — both already installed on VPS.

**Anti-bot work required:** NONE. Referer header recommended (polite browsing) but not required (probe 5 confirmed bare UA works).

### Architecture: endpoint already exists on port 8765

The `/proxy/article-body` endpoint is **already live** in `vps-proxy-server.js`. It shells out to `/root/article-body-fetcher.py`. The Node service (`vn-vps-proxy.service`, 64 MB cap, 43 MB current RSS) already handles this route for `cafef.vn` and `vneconomy.vn`.

The domain allowlist in `vps-proxy-server.js` line 160:
```js
const ARTICLE_BODY_ALLOWED_DOMAINS = new Set(["cafef.vn", "vneconomy.vn"]);
```

**To add vnexpress.net:** two changes only:
1. Add `extract_vnexpress()` to `/root/article-body-fetcher.py` (extend `ALLOWED_DOMAINS` + dispatch)
2. Add `"vnexpress.net"` to `ARTICLE_BODY_ALLOWED_DOMAINS` in `/root/vps-proxy-server.js` and restart

No new systemd service. No new process. The architecture already exists.

### Recommendation: EXTEND, not NEW SERVICE

**Rationale:**

1. The `/proxy/article-body` endpoint exists and is wired. Adding vnexpress.net is a 2-file patch. Standing up `vn-deep-fetch.service` would duplicate the process isolation the vps-proxy already provides.

2. RAM impact of adding vnexpress.net to article-body-fetcher.py: 1.94 MB peak per call. At MAX 10 concurrent calls (the brief's deepFetchVpsJob cap), worst-case spike = 19.4 MB, absorbed entirely within the 64 MB MemoryMax of `vn-vps-proxy.service`.

3. A NEW `vn-deep-fetch.service` would be warranted only if: (a) the executor needed persistent state (e.g. queue polling loop), or (b) RAM isolation from vps-proxy was required. Neither applies here — the queue lives in mcp-server SQLite, and the VPS is called on-demand by `deepFetchVpsJob.ts`.

4. **Available RAM headroom (469 MB) is sufficient for a new service if the architect decides isolation is worth it.** But the EXTEND path is lower-risk (one less systemd unit to maintain, no service startup race, same port/auth pattern).

**If architect overrides to NEW service:** 64 MB MemoryMax is safe (1.94 MB per call × 10 cap = 20 MB peak). 469 MB headroom confirmed. Name: `vn-deep-fetch.service`.
