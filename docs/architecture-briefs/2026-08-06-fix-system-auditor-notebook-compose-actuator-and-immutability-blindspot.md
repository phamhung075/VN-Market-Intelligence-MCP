**Trigger:** commit `0fcc6a5d220e9673eb1606043a45178f2ac27792` (2026-08-06T06:42:24+02:00 / 04:42:24Z) deleted the pre-existing `## c44 · 2026-08-05T19:13:03Z` header from `docs/agent-memory/notebooks/system-auditor.md`, replaced it with two blank lines, and never wrote a `c45` section anywhere — while the cycle's terminal report claimed "Notebook: Updated with entry c45 (2026-08-06T06:41:47Z)". ## Problem statement

`system-auditor`'s notebook cycle-log write (`docs/agents/system-auditor/flow/main.md` §Notebook write, lines 785–866, mirroring `.claude/skills/notebook-write/SKILL.md` AC-1–AC-6) has three converging defects that together let a genuinely corrupting write land undetected:

1. **The compose step is 100% LLM-narrated prose with no deterministic actuator.** The agent must, in a single turn: read the full existing notebook into its own context, identify `## ` boundaries, increment a `c<NNN>` counter, build a new ≤60L section, prune to the 3-section retention steady state, and then emit either a `Write(path=..., content=<entire settled file>)` (main.md's own literal Step 2) or an `Edit(old_string=<entire file verbatim>, new_string=<settled body>)` (the generic skill's literal AC-3 form — the two documents prescribe two different tool-call shapes for the same step, see Finding E below). Nothing about this step is checked before the write lands except a line-count test (AC-5, `wc -l ≤ 200`), which cannot distinguish "the new section landed" from "an existing heading was blanked and nothing new was added" — both produce files far under the 200L cap.
2. **The mechanical safety net that exists specifically to catch retained-content mutation (AC-2a `_check_notebook_immutability`, a pre-commit hook) is warn-only by default,** and has already fired for `system-auditor.md` at least 6 times since 2026-07-30 (`## c33`, `## c32`, `## c31`, `## c18`, `## c41` ×2, `## c42`, `## c006` — `docs/signals/processed/commit-sweep-guard-*.json`) without ever blocking a commit or triggering an escalation. This is the same class of defect the skill doc's own comment names as having caused "measured recurrence across ≥5 of the last 12 `system-auditor` notebook commits" before AC-2a was added — AC-2a was shipped as a *detector*, and for this file specifically it has been detecting a live, ongoing problem for a week with no actuator wired to it.
3. **Even in `reject` mode, the detector's algorithm cannot see this specific corruption shape.** `_check_notebook_immutability` compares `## `-heading text present on both HEAD and staged sides; a heading present *only on HEAD* is explicitly treated as "dropped whole" (an AC-2-authorized mutation) and is "never flagged" (`scripts/git-hooks/pre-commit` lines 251–253). In this incident, `## c44 · 2026-08-05T19:13:03Z` disappeared from staged content, but its **body did not** — it survived as now-headless preamble text ahead of `## c43`. That is neither "heading present on both sides with different content" (the only case the hook checks) nor a genuine whole-section drop (which would shrink the file by ~7 lines; this commit's net diff was +1 line). The detector's HEAD-only/staged-only dichotomy has no way to represent "heading vanished, body orphaned" — flipping `GIT_NOTEBOOK_IMMUTABILITY_MODE` to `reject` today would **not** have caught this exact commit.

## Ruled out (checked, not assumed)

**User-flagged hypothesis:** does this share root cause with `notebook-auto-prune.sh`'s known newest-first/oldest-first drop-oldest ordering bug (already fixed for `pm.md`, per `feedback_agent_selfreport_metalayer_confabulation` / `feedback_edit_tool_hook_silently_strips_multiline`)?

**No — mechanically ruled out, not just judged unlikely:**
- The corrupted file was 80 lines / 6017 bytes before this write and 81 lines / ~6020 bytes after — both figures are far under the governed caps (`docs/data/file-size-caps.json`: 200L / 12000B for `docs/agent-memory/notebooks/*.md`). `notebook-auto-prune.sh`'s own top-of-file guard (`[ "$LINE_COUNT" -le "$LINE_CAP" ] && [ "$BYTE_COUNT" -le "$BYTE_CAP" ] && exit 0`) means this hook **never entered its section-parsing/drop-oldest logic at all** for this write — it is not in the causal chain for this incident.
- Independently, the ordering-assumption bug itself is **already generically fixed** in the live script (not just for `pm.md`): the current `notebook-auto-prune.sh` self-derives each file's newest-first/oldest-first convention from that file's own distinguishable heading timestamps (decreasing/increasing vote), falls back to `docs/data/notebook-section-order.json` only on a same-day tie with zero self-signal, and only then applies a documented `newest_first` default — a hardcoded oldest-first assumption for a prepending file no longer exists anywhere in this code path (`FIX-NOTEBOOK-AUTOPRUNE-SAMEDAY-TIE-DROPS-NEWEST` / `FIX-NOTEBOOK-AUTOPRUNE-DIRECTION-UNRESOLVABLE-ZERO-TS-NOTEBOOKS`).
- Corroborating evidence: `system-auditor.md` **is** confirmed newest-first (c44 sits above c43 sits above c42 in physical file order — verified via `git log --oneline` + `git show`), matching the premise, but the mechanism that broke it is unrelated to prepend/append direction.

This is a genuinely distinct, third failure mode for this notebook's write path — not a recurrence of the pm.md-class bug.

## Corroborating finding — the commit step also bypassed its own mandated script

`docs/signals/processed/commit-sweep-guard-2026-08-06T064221Z-53613.json` (created 06:42:21Z, 3 seconds before the corrupting commit landed at 06:42:24Z) shows a **bare** `git commit` (no explicit pathspec) was attempted against a working tree that had `docs/agent-memory/notebooks/system-auditor.md` staged, tripped the repo's `sweep-guard` pre-commit hook, and — because this session had already accumulated `prior_warns=7` against `escalate_threshold=3` — was escalated to a hard REJECT (`scripts/git-hooks/pre-commit` lines 829–861: `escalated=true` forces `escalate_effective=reject` regardless of the warn-by-default mode, exit 1, "Index is untouched"). The corrupted content then landed 3 seconds later via a retried, pathspec-scoped commit.

`scripts/auditor-notebook-commit.sh` — the blessed script `docs/agents/system-auditor/flow/main.md` mandates for this exact step, built specifically because "flow-step drift on a narrated sequence cannot be trusted for a hard invariant" (its own header comment, re: the mutex-claim bug it fixed) — **always** commits pathspec-scoped (`git commit -m "$COMMIT_MSG" -- "${PATHS[@]}"`, line 202) and can never produce a bare-commit sweep-guard warning by construction. The fact that this cycle's first commit attempt *did* trip that warning means the agent bypassed the mandated script for the commit step (most likely a raw narrated `git commit -m "..."` before falling back to an explicit-pathspec form on retry) — the identical "the model may skip a scripted step and improvise a raw git command" disease `auditor-notebook-commit.sh` was built to cure for the mutex-claim, recurring for the "always invoke this exact script" contract itself. `prior_warns=7` (accumulated before this incident, in-session) indicates this is not a one-off slip.

This is **not** the source of the wrong content (the corruption was already staged before either commit attempt) — it is independent evidence that this cycle's flow execution deviated from the documented script-only commit contract, and is worth its own fix regardless of the compose-step fix below.

## Recommended fixes (for agent-father)

**A — Convert the compose step into a deterministic script actuator (primary fix).** Mirror the precedent already set for the commit step: a new `scripts/notebook-compose.sh <notebook-path> <new-section-body-file> [max-sections=3] [section-cap=60]` that takes ONLY the new section's already-authored substantive content (small, bounded — the LLM keeps authoring *what happened this cycle*, nothing else) and mechanically performs: read current file, parse `## ` boundaries, derive/consult this file's prepend-vs-append convention (reuse `docs/data/notebook-section-order.json` + the same self-deriving-from-headings logic already proven in `notebook-auto-prune.sh` — do not reimplement a second, divergent copy), enforce the 3-section retention steady state + AC-2b sub-block intra-prune + 60L/200L caps, and perform the single settled write via `mv` from a tmpfile (never a Claude Write/Edit tool call, so it also can never trigger a PostToolUse re-entrancy surprise). Remove the LLM from the "reproduce the entire existing file byte-for-byte" burden entirely — that reproduction requirement is the direct mechanical cause of this failure class, independent of any specific bug in this incident's tool call.

**B — Close the immutability-detector blind spot.** In `scripts/git-hooks/pre-commit` `_check_notebook_immutability`, a dated heading present at HEAD but absent from staged must not be treated as "dropped whole" without corroboration. Minimum viable check: when such a heading disappears, verify the staged file's total line count shrank by approximately that HEAD section's own line span (heading through the line before the next heading/EOF), allowing for the new cycle's own added lines under the existing retention arithmetic. If the shrinkage is absent (file stayed the same size or grew, as in this incident: 80→81 lines while a whole section should have vanished), flag a new, distinct violation class (e.g. `notebook-heading-orphaned-body`) — this is structurally the same kind of headless-content signature `notebook-auto-prune.sh`'s `detect_dup_heading`/`repair_adjacent_dup_heading` already hunts for (adjacent-heading corruption), just the missing-heading variant.

**C — Re-evaluate `GIT_NOTEBOOK_IMMUTABILITY_MODE`.** The skill doc's own stated bar for flipping to `reject` is "after the replay script reads 0 across the full notebook corpus" (`scripts/audits/verify-notebook-immutability-gate.sh`). Given (1) this file has produced ≥6 unactioned WARN hits over the last week and (2) this cycle turned "detected mutation" into confirmed real data loss, recommend agent-father run the replay script now and, if clean (or clean after fix B lands), flip to `reject` — at minimum scoped to `system-auditor.md` first, given it is the file with the observed recurrence, before a fleet-wide flip.

**D — Enforce script-only commits for this step.** Either constrain this agent's Bash tool grant so a raw `git commit` targeting `docs/agent-memory/notebooks/system-auditor.md` is disallowed outside `scripts/auditor-notebook-commit.sh`, or (lower effort) open this as its own recurring-bug ticket — `prior_warns=7` already crossed the fleet's 2+ threshold policy independently of this brief.

**E — Reconcile the two conflicting compose-step specs.** `docs/agents/system-auditor/flow/main.md` (the flow the agent actually executes) prescribes `Write(path=..., content=<settled body>)`; `.claude/skills/notebook-write/SKILL.md` AC-3 — which main.md cites as the authority for "AC-1, AC-2, AC-2a, AC-3, AC-5" — prescribes `Edit(old_string=<entire current file content verbatim>, new_string=<settled body>)` as the primary form and demotes `Write` to "Alternative." Two authoritative-looking documents naming different literal tool shapes for the same step is itself a defect: the `Edit`-with-whole-file-`old_string` form is strictly more fragile (requires an exact byte-for-byte match across an 80+ line block or the call errors unpredictably) and should not be the documented default. Recommend collapsing to one form — `Write` full-overwrite, consistent with main.md and superseded entirely by fix A above once the compose step is scripted.

## Sequencing

A (script actuator) removes the failure surface entirely and should land first. B (detector blind-spot fix) and C (mode flip) are the backstop and should land together — C without B re-enables a gate that still cannot see this exact shape. D and E are independent cleanup, no ordering dependency.
