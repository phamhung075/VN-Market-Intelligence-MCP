## REQUEST 1 — Quẻ Name SSOT/Factory Component

### 1.1 Description Data SSOT — Chosen Seam: A1 (Static Frontend Map, Build-Time Generated)

**Decision: A1.**

Rationale:
- `QUE_DATA: Record<number, QueData>` already exists in `apps/mcp-server/src/domain/services/kinhDich/hexagramLibrary.ts` (line 131+). The file's own header states "Auto-generated from Python kinhdich_logic source — DO NOT EDIT manually." The authoritative source is the Python layer; the TS file is already a generated artifact.
- The served `KinhDichReading` DTO carries only `hexagram` (id, number 1–64), `name`, `signal`, `trend`, `confidence`, `timestamp` — no description. Extending the DTO (A2) requires dev-kinh-dich + dev-mcp-server changes, endpoint rebuild, and adds a round-trip per page load. This delivers zero benefit when the descriptions are static text (they never change at runtime).
- A1 keeps the frontend self-contained: no new tool call, no mcp-server rebuild for a static vocabulary table.

**Anti-drift generation mechanism (mandatory — not hand-copied):**

A new file `apps/frontend/app/lib/que-descriptions.generated.ts` is produced by a codegen script `scripts/gen-que-descriptions.ts` that:
1. Imports `QUE_DATA` and `QUE_META` directly from `apps/mcp-server/src/domain/services/kinhDich/hexagramLibrary.ts` (cross-package relative import, path confirmed in monorepo).
2. Emits a single `export const QUE_DESCRIPTIONS: Record<number, QueDescription>` keyed by hexagram id (1–64), writing `coreMeaning`, `judgment_interpretation`, `image_action`, and `state_trend` — the four trading-relevant fields.
3. Writes a header comment: `// AUTO-GENERATED by scripts/gen-que-descriptions.ts — DO NOT EDIT. Run: bun run gen:que`.
4. Is added to `package.json` scripts as `"gen:que": "bun run scripts/gen-que-descriptions.ts"`.
5. The generated file is committed to the repo (not gitignored) so the frontend build has zero runtime dependency on mcp-server source.
6. When `hexagramLibrary.ts` changes (rare — auto-generated from Python), a developer MUST re-run `gen:que` and commit the updated generated file. This is enforced by: adding a `postinstall` hook comment and a CI check (future) that diffs the generated file against a fresh run.

**Why not hand-copy:** 64 entries, Vietnamese unicode, already has three prior drift bugs in this codebase (VNH sector, analysis-briefs). Hand-copy is explicitly rejected.

**`QueDescription` type (lives in `apps/frontend/app/lib/que-descriptions.generated.ts`):**
```typescript
export interface QueDescription {
  coreMeaning: string;           // Primary hover text
  judgment_interpretation: string; // Secondary — trading judgment
  image_action: string;          // Action guidance
  state_trend: string;           // Market trend state
}
export const QUE_DESCRIPTIONS: Record<number, QueDescription> = { ... };
```

### 1.2 Component Contract

**File:** `apps/frontend/app/components/QueName.tsx`

This is the ONLY location where hexagram name rendering + tooltip logic lives. No other file may render a quẻ name or tooltip inline.

```typescript
import type { ReactNode } from "react";
import {
  Tooltip,
  TooltipContent,
  TooltipProvider,
  TooltipTrigger,
} from "~/components/ui/tooltip";
import { QUE_DESCRIPTIONS } from "~/lib/que-descriptions.generated";

interface QueNameProps {
  /** Hexagram id (1–64). Accepts either the numeric id or the string name as fallback. */
  hexagram: number;
  /** Vietnamese name string returned by the API (e.g. "Kiền"). */
  name: string;
  /** Optional CSS class for the trigger span. */
  className?: string;
}

export function QueName({ hexagram, name, className }: QueNameProps): ReactNode {
  const desc = QUE_DESCRIPTIONS[hexagram];
  const trigger = (
    <span className={className}>
      #{hexagram}{name ? ` — ${name}` : ""}
    </span>
  );
  if (!desc) return trigger; // graceful no-op if id out of range
  return (
    <TooltipProvider>
      <Tooltip>
        <TooltipTrigger asChild>
          {/* tabIndex={0} + aria-describedby wired by shadcn Tooltip automatically */}
          <span
            className={`cursor-help underline decoration-dotted decoration-slate-500 ${className ?? ""}`}
            tabIndex={0}
          >
            #{hexagram} — {name}
          </span>
        </TooltipTrigger>
        <TooltipContent
          side="top"
          className="max-w-xs text-xs leading-relaxed"
          aria-label={`Quẻ ${name} — ý nghĩa`}
        >
          <p className="font-semibold text-slate-100 mb-1">{name}</p>
          <p className="text-slate-300">{desc.coreMeaning}</p>
          {desc.state_trend && (
            <p className="mt-1 text-slate-400 italic">{desc.state_trend}</p>
          )}
        </TooltipContent>
      </Tooltip>
    </TooltipProvider>
  );
}
```

**Accessibility:**
- `tabIndex={0}` on the trigger span allows keyboard users to focus and activate the tooltip.
- shadcn `Tooltip` wires `aria-describedby` pointing to `TooltipContent` automatically via Radix primitives.
- Tooltip dismisses on Escape (Radix default).

**Truncation:** `max-w-xs` (20rem) on `TooltipContent` clips long `coreMeaning` lines. Vietnamese prose is typically 1–2 lines at this width. `leading-relaxed` prevents line cramping.

**shadcn/ui Tooltip dependency:** `@radix-ui/react-tooltip` is NOT yet in `apps/frontend/package.json` (only `react-collapsible` and `react-slot` are present). dev-frontend must run `bun add @radix-ui/react-tooltip` and create `apps/frontend/app/components/ui/tooltip.tsx` following the standard shadcn pattern (re-export of Radix primitives with cn() styling). This is a one-time install step in FOU-2-REQ1.

## REQUEST 2 — Service Health Page: 2-Axis mcp-online-truth Model

### 2.1 The Problem

`dashboard.services.tsx` renders a single-axis `ServiceStatus` (ok | degraded | down | not_deployed). The 7 intentionally-not-deployed standalone containers (stock-price, technical-analysis, kinh-dich-service, alert-engine, pdf-extractor, rag-service, news-fetch) show grey "NOT DEPLOYED" with no positive capability signal. These services' logic runs EMBEDDED in mcp-server and is verified LIVE via probe (see §2.3). The operator correctly wants a POSITIVE "LIVE via mcp-server" indicator — not silence.

### 2.2 Two-Axis Model

**Axis 1 — Container status** (infrastructure truth):
- `deployed` — container is in `host_runtime_set.services` and /health reports ok
- `not_deployed` — container is in `host_runtime_set.not_deployed_by_design`
- `down` — container is in `host_runtime_set.services` but /health reports down/degraded

**Axis 2 — Capability via mcp-server** (service capability truth):
- `live` — the designated probe tool returns a valid response from mcp-server
- `data_limited` — probe responds but data is partial/stale (e.g. ta: 30/35 candles)
- `dark` — capability not probed or probe returns no useful data
- `n/a` — not applicable (e.g. the mcp container itself has no separate capability probe)

**Composed display logic:**

| container | capability | Display badge | Color |
|-----------|-----------|---------------|-------|
| `deployed` | `n/a` | UP / DEGRADED / DOWN (existing) | green / yellow / red |
| `not_deployed` | `live` | LIVE via mcp-server | blue |
| `not_deployed` | `data_limited` | LIMITED via mcp-server | yellow |
| `not_deployed` | `dark` | NOT DEPLOYED (unchanged grey) | grey |
| `down` | any | DOWN | red (anti-false-green preserved) |

**Critical anti-false-green invariant:** A genuinely-deployed service (in `host_runtime_set.services`) that goes DOWN MUST render RED regardless of capability axis. The capability axis only applies to `not_deployed` services. A deployed service that goes down is never rescued by a "LIVE via mcp" label.

### 2.3 Capability Manifest SSOT

**Anchor location:** `docs/data/system-map.json` — add a new `capability_manifest` key inside `host_runtime_set` (sibling to `not_deployed_by_design` and `short_key_to_compose`). This is the single source of truth; the frontend reads it at build time (or via loader static import). The api-gateway's `/health` endpoint ALSO reads this manifest to run bounded probes server-side (see §2.4).

This manifest is the reference contract. The `capability` field is the STATIC baseline (what the manifest says capability is when probed as of last ground-truth date). The actual live capability is determined by the probe at runtime.

### 2.4 Probe Architecture — Bounded and Cached

**Where the probe runs: api-gateway `/health` enrichment (server-side, cached TTL 60s).**

Rationale for this placement over alternatives:
- The frontend loader already calls `fetchGatewayHealth()` → `GET /health`. Extending the response payload costs zero extra frontend calls.
- A frontend loader-side probe would fan out from the user's browser or Remix SSR, making the page load dependent on mcp-server tool latency. Rejected.
- A new `GET /mcp/capabilities` endpoint on mcp-server is possible but adds complexity with no benefit over api-gateway enrichment since api-gateway already proxies all service health.

**Probe execution rules (HARD — host-safety):**
1. The api-gateway runs at most ONE probe call per `not_deployed` service per `/health` request, but only if the cached result is stale (TTL 60s in-memory cache keyed by `short_key`).
2. Maximum 7 probe calls per 60s window (one per `not_deployed_short_key`). NOT 156.
3. Each probe is a single targeted mcp tool call with a lightweight argument (e.g. `get_market_snapshot` with no special params). Timeout: 3000ms per probe. On timeout → capability stays at manifest's static baseline.
4. The `/health` response gains two new fields per service entry: `capability: "live" | "data_limited" | "dark" | "n/a"` and `capability_note: string | null` (for DATA-LIMITED explanation text).

**GatewayHealthResponse extension (domain/health.ts):**
```typescript
export type CapabilityStatus = "live" | "data_limited" | "dark" | "n/a";

export interface ServiceRow {
  name: string;
  status: ServiceStatus;        // existing container axis
  latencyMs: number | null;
  capability: CapabilityStatus; // new axis
  capabilityNote?: string;      // e.g. "30/35 candles available"
}
```

**Frontend ServiceStatus badge upgrade (dashboard.services.tsx):**
- `StatusBadge` gains a second optional prop `capability?: CapabilityStatus`.
- For `not_deployed` services: renders the capability badge instead of "NOT DEPLOYED" when capability is `live` or `data_limited`.
- For deployed services: existing single-axis badge unchanged.
- A `CapabilityBadge` sub-component (private to services route, not a global shared component since it is specific to this page's domain logic) renders the blue/yellow/grey capability indicator.
