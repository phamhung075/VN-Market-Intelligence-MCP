## 1. Issue 1345a — Reuters + Trading Economics Source Outage

### 1.1 Problem Statement

Both Reuters RSS and Trading Economics have accumulated 50 consecutive failures
over a 7-hour window. The circuit breakers for `reuters` and `tradingEconomics`
(defined in `apps/mcp-server/src/infrastructure/circuitBreakerRegistry.ts`) use
default failure thresholds. When tripped, no fallback source is activated and
the news pipeline goes dark for the duration of the breaker's reset timeout.

Morning and evening briefing signal quality degrades silently: no error surfaces
to the user, the briefing simply runs on stale or missing macro data.

**Confirmed gap:** `pollNews.ts` (`SourceFetchers` interface, line 54–69) lists
`reuters` and `tradingeconomics` as optional fetcher slots, but there is no
fallback activation logic when either slot returns zero items or throws.

### 1.2 Root-Cause Hypothesis

Two possible causes — developer must confirm during implementation:

- **Hypothesis A (Credential/auth):** Reuters RSS endpoint requires no
  credentials but may have changed URL or added rate-limiting headers. TE may
  require an API key that has expired or hit quota.
- **Hypothesis B (Network/geo-block):** Both sources are fetched locally (not
  via VPS), so the France → server path is not geo-blocked. However, a proxy
  misconfiguration or CDN IP block on Reuters/TE side could cause sustained
  failure.

Developer must log the exact HTTP status code and error message from the
failing fetch before implementing a fallback, to confirm which hypothesis is
correct.

### 1.3 Functional Requirements

**FR-1345a-1 — Fallback source registration**
The `SourceFetchers` interface must support at minimum two fallback sources for
macro/global news when Reuters is unavailable. Candidate sources (developer
selects based on availability and license):

| Priority | Source | Type | Notes |
|----------|--------|------|-------|
| 1st fallback | NewsAPI.org (`newsapi`) | REST/JSON | Requires free API key |
| 2nd fallback | Finnhub News (`finnhub`) | REST/JSON | Requires free API key |
| Alt | MarketWatch RSS (`marketwatch`) | RSS | No key required |

At least one of these must be implemented for this sprint. The second can be
registered but left as a stub if key procurement is blocking.

**FR-1345a-2 — Fallback activation logic**
When `reuters` fetcher returns 0 items OR throws after circuit breaker trips,
the cycle must automatically attempt the first available fallback fetcher in
the registered fallback chain. The fallback must be logged at INFO level:
`[pollNews] reuters unavailable — falling back to <source>`.

**FR-1345a-3 — Breaker isolation**
Fallback source breakers must be registered in `circuitBreakerRegistry.ts` as
independent entries (e.g., `newsapi`, `finnhub`). A failure on the fallback must
not increment the primary source's failure counter and vice versa.

**FR-1345a-4 — Zero-fallback graceful degradation**
If ALL fallback sources are also unavailable (all circuit breakers open), the
pipeline must continue with the sources that ARE available (cafef, vnexpress,
vps-push sources). It must NOT throw or abort the poll cycle. A single warning
must be logged and a Telegram alert sent to the `bug` channel:
`[news-pipeline] all macro sources unavailable — briefing may lack global context`.

**FR-1345a-5 — Source health visibility**
`globalSourceTracker` (already used in `sourceHealthTools.ts`) must record
fallback activation events so the `/source-health` MCP tool shows which source
is currently acting as primary.

### 1.4 Non-Functional Requirements

- Fallback activation must add no more than 2 seconds of latency to the poll
  cycle (fetches are parallel — this is satisfied by Promise.allSettled pattern
  already in place).
- No new credentials may be hardcoded in source. Keys must go in
  `mcp.config.json` under `newsSources.<name>.apiKey` and be read via
  `loadMcpConfig()`.

### 1.5 Acceptance Criteria

- [ ] **AC-1345a-1:** When reuters circuit breaker is open, the configured

- [ ] **AC-1345a-2:** Fallback activation is logged at INFO with the source name.

- [ ] **AC-1345a-6:** All 7371 baseline tests pass. Zero regressions.

## 2. Issue 1345b — BCTC Extraction Confidence Audit (VNM / VEA Corruption)

### 2.1 Problem Statement

Two watchlist tickers exhibit impossible financial figures in extracted BCTC data:

| Ticker | Anomaly | Why Impossible |
|--------|---------|----------------|
| VNM | Assets (Tổng tài sản) = 957 tỷ, Equity (Vốn chủ sở hữu) = 18,829 tỷ | Assets must be >= Equity (Bảng cân đối kế toán identity: Assets = Liabilities + Equity) |
| VEA | Operating margin = 330%, Total Liabilities = 0 | Operating margin > 100% is physically impossible for a trading company; zero liabilities with non-zero equity is implausible |

These figures are being consumed by the value-investor analysis pipeline without
sanity-checking, producing misleading conviction signals for these tickers.

**Root-cause gap:** The `pdf-extractor` service (`apps/pdf-extractor/`) has an
`ocr_confidence` field on `ExtractedContent` (domain model, line 52–57 of
`domain/models.py`) but this confidence score is OCR-quality only (text legibility).
There is no layer that validates extracted numerical figures against accounting
identities (balance sheet equation, margin bounds, sign consistency).

The `ocr_confidence` field is defined (range 0.0–1.0) but there is no evidence
it is being propagated into the MCP server's BCTC storage or surfaced in logs.

### 2.2 Root-Cause Hypothesis

Three plausible causes — developer must determine which applies per ticker:

- **Hypothesis A (Unit mismatch):** PDF mixes tỷ (billion) and triệu (million)
  across tables. Parser reads all values as the same unit, producing a 1000x
  scale error (957 tỷ correctly read but equity read from a different-scale
  table as 18,829 tỷ when it should be 18,829 tỷ).
- **Hypothesis B (Column swap):** OCR misaligns table columns — equity column
  is read as assets column and vice versa.
- **Hypothesis C (OCR noise):** Low OCR confidence causes digit mis-recognition
  (e.g., "18.829" read from a partially rendered page where leading digits were
  cut off from "118.829").

### 2.3 Functional Requirements

**FR-1345b-1 — Propagate ocr_confidence to MCP server**
The `ocr_confidence` value from `ExtractedContent` must be stored alongside
the extracted BCTC figures in the MCP server's SQLite schema. The field must
appear in query results from `get_bctc_full()`.

**FR-1345b-2 — Financial figure validation rules**
A new domain-layer validation function must check extracted BCTC figures against
accounting identities before the data is stored or used for signal generation:

| Rule ID | Check | Threshold |
|---------|-------|-----------|
| BCTC-VAL-01 | Total Assets >= Total Equity | Hard constraint — always invalid if violated |
| BCTC-VAL-02 | Total Assets >= 0 | Hard constraint |
| BCTC-VAL-03 | Operating margin in range (-500%, +100%) | Soft constraint — flag if outside |
| BCTC-VAL-04 | Total Liabilities >= 0 | Hard constraint |
| BCTC-VAL-05 | Net revenue > 0 for non-holding companies | Soft constraint — flag if zero |
| BCTC-VAL-06 | Equity > 0 (not deeply negative) | Soft constraint — flag if negative equity |

Hard constraint violations immediately mark the extraction as
`confidence_financial = 0.0`. Soft constraint violations reduce
`confidence_financial` by 0.2 per violation, floor 0.1.

**FR-1345b-3 — Composite confidence score**
Introduce `confidence_financial` as a separate field distinct from
`ocr_confidence`. The final signal confidence for BCTC-sourced analysis must
be `min(ocr_confidence, confidence_financial)`.

**FR-1345b-4 — Low-confidence skip logic**
When `min(ocr_confidence, confidence_financial) <= 0.3`:
- Do NOT generate value-investor conviction signals for this ticker/period.
- Log at WARN: `[bctc-validation] <TICKER> Q<n> <year> skipped — composite confidence <score> (ocr=<x>, financial=<y>)`.
- Send Telegram alert to `bug` channel: `[BCTC] <TICKER>: données non fiables (confiance <score>) — signaux ignorés`.
- Store the raw extraction in the database with `status = 'low_confidence'` so
  it can be reviewed and re-extracted when PDF quality improves.

**FR-1345b-5 — Audit report**
A one-time audit must be run against all currently stored BCTC extractions for
the 30 watchlist tickers. The report must list:
- Ticker, period, ocr_confidence, identified validation failures, recommended action.

This report is the primary output of 1345b and informs whether a data migration
is needed in a follow-up sprint.

### 2.4 Non-Functional Requirements

- Validation logic belongs in `domain/services/` of the pdf-extractor service
  (or in the MCP server's domain layer if validation occurs post-extraction).
  It must NOT be placed in infrastructure or interface.
- Validation must be synchronous and pure (no I/O, no DB calls).

### 2.5 Acceptance Criteria

- [ ] **AC-1345b-1:** `ocr_confidence` value is stored in the MCP server BCTC
  table and returned by `get_bctc_full()`.
- [ ] **AC-1345b-2:** All 6 validation rules (BCTC-VAL-01 through VAL-06) are
  implemented and covered by unit tests.
- [ ] **AC-1345b-3:** VNM Q4 2024 and VEA Q4 2024 extractions are marked
  `low_confidence` after running the audit (their figures violate VAL-01 and
  VAL-03 respectively).
- [ ] **AC-1345b-4:** No value-investor conviction signal is generated for any
  ticker with composite confidence <= 0.3.
- [ ] **AC-1345b-5:** Audit report file written to
  `reports/BCTC_CONFIDENCE_AUDIT_1345b.md` listing all 30 tickers.
- [ ] **AC-1345b-6:** All 7371 baseline tests pass. Zero regressions.

### 2.6 DDD Layer Mapping

| Concern | Layer | File |
|---------|-------|------|
| Validation rules (pure logic) | Domain / services | `apps/pdf-extractor/domain/services.py` (new `validate_financial_figures()`) |
| `confidence_financial` field | Domain / models | `apps/pdf-extractor/domain/models.py` (`ExtractedContent`) |
| Confidence propagation to DB | Infrastructure | MCP server BCTC schema migration (add `ocr_confidence`, `confidence_financial` columns) |
| Low-conf skip logic | Application / usecases | Value-investor analysis use case (MCP server side) |
| Audit report generation | Application / usecases | New one-shot script or MCP tool |
| Unit tests | Test | `apps/pdf-extractor/__tests__/unit/test_financial_validation.py` |

### 2.7 Edge Cases

| Scenario | Expected Behaviour |
|----------|--------------------|
| Holding company with zero revenue | VAL-05 is soft — flag but do not zero out confidence |
| Negative equity (distressed company — e.g., after large accumulated losses) | VAL-06 is soft — flag as suspicious, let analyst override |
| PDF not yet extracted (status = pending) | Skip validation — not applicable |
| Multiple quarters for same ticker, some valid some not | Per-period confidence — valid periods produce signals normally |
| Vietnamese BCTC uses parentheses for negatives: (1.234) | Parser must strip parentheses and apply negative sign before validation; this is a parsing pre-condition, not a validation rule |
| Unit mix: tỷ vs triệu in same PDF | This is Hypothesis A — developer must detect and normalise units BEFORE validation runs |

### 2.8 Rollback Plan

1. Disable `confidence_financial` check in skip logic by setting threshold to
   `0.0` via config (effectively disabling the filter without code revert).
2. For schema migration: columns are additive (nullable) — existing queries
   unaffected.
3. `low_confidence` status is additive — no existing `success` rows are changed
   during audit; only future extractions are affected.

### 2.9 Blockers for PO

None. Developer can proceed with validation rule implementation and audit.
PDF re-extraction (if needed) is deferred to a follow-up sprint pending audit
results.

## 3. Issue 1345c — Polymarket API Staleness (26 Days)

### 3.1 Problem Statement

The `prediction_markets` SQLite table has `fetched_at = 2026-04-01` for all
rows — 26 days stale as of 2026-04-27. The `predictionMarketJob.ts` scheduler
is configured to run every 30 minutes (`CRONS.predictionMarketPoll = '*/30 * * * *'`).

The staleness implies one of two failure modes:

- **Mode A:** The scheduler is running but `enabled = false` in
  `mcp.config.json` — fetches are skipped silently (line 307–312 of
  `predictionMarketJob.ts`).
- **Mode B:** The scheduler is running and `enabled = true`, but
  `fetchPolymarkets()` is failing consistently and falling back to the cached
  snapshot (line 346–350) — silently returning the stale data on every cycle.

In Mode B, the Polymarket circuit breaker (`failureThreshold: 5,
resetTimeoutMs: 600_000`) may be permanently open after the CLOB geo-block
failures, and the Gamma fallback is also failing (network or API change).

**Confirmed gap:** There is no staleness guard. The job stores the snapshot
unconditionally and signals are generated from whatever data is in the DB,
regardless of age.

### 3.2 Functional Requirements

**FR-1345c-1 — Staleness guard**
Before generating prediction signals, `runPredictionMarketPoll` must check the
maximum `fetched_at` across all rows in `prediction_markets`. If the newest
row is older than `staleThresholdHours` (config, default 24), the job must:
- Log WARN: `[prediction-market-job] data stale by <N>h — skipping signal generation`.
- Skip `detectPredictionSignals()` and alert generation for this cycle.
- NOT send stale signals to Telegram.

**FR-1345c-2 — Staleness Telegram alert (once per 24h)**
When staleness is detected, send a single Telegram alert to `bug` channel:
`[POLYMARKET] données périmées depuis <N> jours — vérifier config/API`. This
alert must be rate-limited to once per 24 hours (use the existing
`prediction_signals` dedup pattern as reference).

**FR-1345c-3 — Confirm and fix enabled flag**
Developer must check `mcp.config.json` `predictionMarkets.enabled` value. If
`false`, set to `true`. This is a config fix, not a code change.

**FR-1345c-4 — Fetch frequency increase**
The cron schedule must be confirmed at `*/30 * * * *` (every 30 min = 48 fetches
per day), satisfying the ">= 2x daily" requirement. If `CRON_PREDICTION_MARKET_POLL`
env var has been set to a less frequent value in Docker config, it must be
corrected.

**FR-1345c-5 — Gamma API health check**
Developer must confirm the Gamma API endpoint
(`config.gammaApiUrl/markets?closed=false&active=true`) returns data by logging
raw response headers and status during one manual fetch. If the endpoint has
changed, update `mcp.config.json` `predictionMarkets.gammaApiUrl`.

### 3.3 Non-Functional Requirements

- Staleness check is a DB read (one SELECT MAX query) — negligible overhead.
- Config changes to `mcp.config.json` take effect on next Docker restart (no
  code compilation needed).

### 3.4 Acceptance Criteria

- [ ] **AC-1345c-1:** `predictionMarkets.enabled = true` confirmed in
  `mcp.config.json`.
- [ ] **AC-1345c-2:** After the fix, `prediction_markets.fetched_at` updates to
  within 30 minutes of current time on the next poll cycle.
- [ ] **AC-1345c-3:** When `fetched_at` is older than `staleThresholdHours`,
  `detectPredictionSignals()` is NOT called (unit test with mocked stale DB).
- [ ] **AC-1345c-4:** Staleness Telegram alert is sent once and not repeated
  within 24 hours.
- [ ] **AC-1345c-5:** All 7371 baseline tests pass. Zero regressions.

### 3.5 DDD Layer Mapping

| Concern | Layer | File |
|---------|-------|------|
| Staleness threshold config | Infrastructure / config | `infrastructure/config.ts` (`predictionMarkets.staleThresholdHours`) |
| Staleness guard logic | Interface / scheduler | `scheduler/macro/predictionMarketJob.ts` |
| Enabled flag | Infrastructure / config | `mcp.config.json` |
| Staleness alert dedup | Interface / scheduler | `predictionMarketJob.ts` (mirrors existing signal dedup pattern) |
| Unit test | Test | `__tests__/1345c-polymarket-staleness.test.ts` |

### 3.6 Edge Cases

| Scenario | Expected Behaviour |
|----------|--------------------|
| `prediction_markets` table is empty (first run) | MAX(fetched_at) returns NULL — treat as stale, skip signals, do NOT crash |
| Fetch succeeds but returns 0 markets (all filtered out) | `fetchedAt` is still updated to current time — not a staleness issue |
| Gamma returns data but CLOB is geo-blocked (normal Mode B with healthy Gamma) | `fetchedAt` updates normally — staleness guard passes |
| Docker container restarts mid-cycle | Concurrency guard (`_isRunning`) prevents duplicate cycles — no issue |

### 3.7 Rollback Plan

1. Revert `mcp.config.json` `predictionMarkets.enabled` to `false` if the
   fix causes unexpected alert volume.
2. Staleness guard code: remove the `fetchedAt` check block — job reverts to

## 4. Issue 1345d — VN-Index Cascade Incomplete (VIC-Only Broadcast)

### 4.1 Problem Statement

When a VN-Index market-wide event is detected, the cascade engine
(`cascadeEngine.ts`) is generating `watchlistImpacts` correctly for all sectors
via `buildCausalChain()` (confirmed by Task 162 test suite — all AC-9 tests
pass). However, downstream only VIC (Vingroup — real estate sector) is receiving
the broadcast alert in Telegram. Other sectors and tickers are silent.

**Root-cause localisation:** The `cascadeEngine.ts` domain logic is correct. The
bug is downstream of `buildCausalChain()` — either in the alert routing step
inside `intelligenceCycleJob.ts` or in the Telegram channel dispatch logic. The
cascade produces the correct `WatchlistImpact[]` array, but the Telegram send
path filters or routes only a subset of those impacts.

**Hypothesis:** The alert routing in `intelligenceCycleJob.ts` may contain a
condition that only dispatches alerts where `actionCode === 'VIC'` or
`domain === 'real_estate'`, possibly left from a targeted fix in a previous
sprint. Alternatively, the `broadcastMinImpact` threshold is being met but the
Telegram dispatch loop has an early-exit condition after the first matching
stock.

### 4.2 Functional Requirements

**FR-1345d-1 — Market-wide alerts reach all affected stocks**
When `buildCausalChain()` returns `watchlistImpacts` with N entries tagged
`reasoning: 'market-wide cascade: ...'`, all N entries must produce independent
Telegram messages (or be batched into a single market-wide summary), not just
the first or VIC-only.

**FR-1345d-2 — MARKET channel receives the summary**
Market-wide cascade events (VN-Index impactScore >= 6) must produce a summary
alert on the MARKET Telegram channel (`sendTelegramMarket`), distinct from
per-stock alerts on the WORK channel. This is in addition to any per-stock
routing, not a replacement.

**FR-1345d-3 — No duplication of per-stock alerts**
Stocks already receiving a sector-rule-based alert (i.e., their
`watchlistImpact.reasoning` does NOT start with `market-wide cascade:`) must
NOT receive a second market-wide alert for the same event. The de-duplication
already exists in the domain layer (Task 162 AC-11) — it must be preserved in
the routing fix.

### 4.3 Non-Functional Requirements

- Alert volume: a single VN-Index event should produce at most 1 MARKET channel
  message + 1 per-stock message for stocks NOT already covered by sector rules.
  Total Telegram messages per event must not exceed `watchlist_size + 1`.
- The fix must not alter `buildCausalChain()` — domain logic is correct and
  tested. Changes are confined to `intelligenceCycleJob.ts` and/or the alert
  dispatch layer.

### 4.4 Acceptance Criteria

- [ ] **AC-1345d-1:** When a simulated VN-Index bearish article (impactScore 8)
  is processed by `intelligenceCycleJob`, Telegram messages are sent for ALL
  watchlist stocks in the cascade result, not only VIC.
- [ ] **AC-1345d-2:** A MARKET channel summary message is sent for the
  VN-Index event.
- [ ] **AC-1345d-3:** No stock that already received a sector-rule alert
  receives a second market-wide alert for the same event.
- [ ] **AC-1345d-4:** Unit/integration test added in
  `__tests__/1345d-vnindex-cascade-broadcast.test.ts` covering the full
  dispatch path (not just `buildCausalChain`).
- [ ] **AC-1345d-5:** All 7371 baseline tests pass. Zero regressions.

### 4.5 DDD Layer Mapping

| Concern | Layer | File |
|---------|-------|------|
| Cascade broadcast logic | Domain / services | `domain/services/cascadeEngine.ts` — NO CHANGES (correct) |
| Alert dispatch routing | Interface / scheduler | `scheduler/news-analysis/intelligenceCycleJob.ts` — PRIMARY CHANGE |
