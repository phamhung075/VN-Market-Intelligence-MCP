**status:** DRAFT → READY_FOR_ARCHITECT
**sprint:** 229
**po_vision:** CRITICAL: market_prices.updated_at frozen 2026-03-27 (24 days stale) blocks all price-based intelligence (watchlist movers empty, TA signals null, evening briefings show no data). System appears dead to user. Root cause: VPS fetch-price pipeline not running or failing silently.

## User Story

As a Vietnamese stock investor using Claude,
I want the system to detect when market price data goes stale for >6 hours during VN market hours,
So that I can immediately know the data pipeline has failed and the briefing/movers are unreliable (not a quiet market).

---

## Functional Requirements

### FR-1: Price Staleness Watchdog (>6h stale detection)

- **Description:** Monitor `market_prices.updated_at` MAX timestamp during VN market hours (Mon-Fri 02:00-08:59 UTC). When it hasn't advanced in >6 hours, emit a WORK alert to dev team + human-friendly MARKET alert to user.

- **Input:**
  - `market_prices` table (current MAX timestamp)
  - Current UTC time (from scheduler)
  - VN market hours guard (Mon-Fri 02:00-08:59 UTC)

- **Output:**
  - WORK alert (Telegram WORK channel): diagnostic message with SSH commands for operator
  - MARKET alert (Telegram MARKET channel): human-friendly message for user ("Data pipeline issue detected")
  - Return value: one of `"ok" | "off-hours" | "alert-sent" | "cooldown" | "restored" | "notify-failed"`

- **Business rule:**
  - Fire alert only once per outage (30-min cooldown on repeated alerts during same outage)
  - When data restores after outage, send recovery message to MARKET channel
  - Do NOT fire if outside VN market hours (2-9 UTC)
  - Do NOT fire on brief lulls (<6h) — VPS pushes every ~5-10 min, so 6h = missed ~40 pushes

- **DDD layer:** application/scheduler (thin wrapper) + domain service (staleness logic + thresholds)

### FR-2: Stale Price Warning in Watchlist Context (bootstrap)

- **Description:** When assembling market context (used by Claude in /ask responses via cycle-bootstrap tool), detect if price data is >24h old and add a warning banner.

- **Input:**
  - watchlist with joined `market_prices` rows
  - current timestamp
  - price `updated_at` field

- **Output:**
  - Enhanced watchlist section in context text with `[STALE]` flag on each stale price
  - Contextual warning: "N price(s) are stale (>24h). Do NOT use for intraday signals or daily % calculations."

- **Business rule:**
  - Threshold: >24h without update = stale
  - Add per-price flag + bottom summary line
  - Pass to Claude so user sees that watchlist context is unreliable

- **DDD layer:** domain/services/marketContextBuilder.ts (~150-190)

### FR-3: Evening Summary Data Crisis Flag

- **Description:** When assembling evening summary and watchlist movers are empty OR no news items exist during supposedly normal market hours, detect if the reason is stale/missing data (not a quiet market) and flag it prominently in the user message.

- **Input:**
  - `watchlistMovers` array (from assembleEveningSummary)
  - `topStories` array (from assembleEveningSummary)
  - `newsCount` from pipeline
  - MAX(market_prices.updated_at), MAX(rag_analyses.created_at)

- **Output:**
  - Banner line in evening summary: `[⚠ Data pipeline crisis: prices stale X hours, last news Y hours ago]`
  - Helps user distinguish between "quiet market" (valid summary) and "broken pipeline" (summary is unreliable)

- **Business rule:**
  - Only fire if BOTH watchlistMovers AND topStories are empty
  - Check staleness thresholds (prices >6h, news >15min)
  - Append as diagnostic footer before sending

- **DDD layer:** scheduler/briefings/eveningSummaryJob.ts (~200-250)

### FR-4: Fallback Fetch Strategy (Investigation + Design)

- **Description:** Investigate whether a fallback price-fetch path exists for brief outages (e.g., CafeF banggia RSS as temporary replacement for HOSE when VPS down).

- **Input:**
  - Current data flow diagram (docs/ARCHITECTURE.md)
  - Fallback chain docs (Data Sources & Fallback Chain section)

- **Output:**
  - Decision document: "Fallback feasible for X sources, infeasible for Y due to Z"
  - Code skeleton (if feasible) or explicit "no fallback" declaration

- **Business rule:**
  - DO NOT implement full fallback in this sprint — only investigate
  - If fallback exists, make it opt-in flag (do not auto-activate during outage)
  - Fallback must respect rate limits + circuit breaker

- **DDD layer:** design/investigation only (no code change if infeasible)

## Non-Functional Requirements

- **Performance:** Watchdog runs every 10 min during market hours (existing cron schedule). Alert check <10ms.
- **Data freshness:** Detects staleness within the next scheduled run (max 10 min lag).
- **Language:** Bilingual — WORK alerts (English technical), MARKET alerts (Vietnamese user-friendly).
- **Reliability:** No false positives on brief lulls (6h threshold). No blind spots during weekends (off-hours guard).
- **Observability:** Log each watchdog cycle (including "ok" / "off-hours" results) for audit trail.

---

## Edge Cases & Data Quality

- **[EDGE]** Empty market_prices table after bootstrap: `readLatestPriceTimestamp()` returns null → age = Infinity → triggers alert (correct).
- **[EDGE]** market_prices.updated_at is malformed ISO string: `new Date()` fails → treated as null → age = Infinity → alert fires (correct, data is corrupted).
- **[EDGE]** Concurrent VPS crash + MCP server restart near 22:30 (evening summary cron): evening summary may send while watchdog silently alerts. No race condition (async independent channels).
- **[EDGE]** Timestamp in future (clock skew): `Date.now() - future < STALE_THRESHOLD` → will NOT trigger alert until threshold passed. Acceptable (rare, self-correcting).
- **[EDGE]** News table has items but price table stale: `watchlistMovers` empty (prices missing from movers algorithm) but `topStories` full. Evening summary shows crisis banner. Correct diagnosis.

## Acceptance Criteria

### AC-1: Watchdog detects price staleness >6h during market hours

**Given** it is 2026-04-21 05:00 UTC (inside VN market hours Mon-Fri)
**When** `MAX(market_prices.updated_at) = 2026-04-20 22:00 UTC` (7 hours old)
**Then**
- Watchdog returns `"alert-sent"`
- WORK Telegram alert sent with SSH diagnostic commands
- MARKET alert sent to user channel (human-friendly message)
- Alert timestamp recorded for cooldown check

### AC-2: Watchdog respects cooldown (no alert spam)

**Given** watchdog alert was sent at 05:00 UTC for stale prices
**When** watchdog runs again at 05:10 UTC and prices are still stale
**Then**
- Watchdog returns `"cooldown"` (not `"alert-sent"`)
- No new Telegram message sent
- lastAlertAt timer preserved

### AC-3: Watchdog off-hours guard prevents false alerts

**Given** it is 2026-04-20 10:00 UTC (outside VN market hours)
**When** `MAX(market_prices.updated_at) = 2026-04-19 05:00 UTC` (29 hours old)
**Then**
- Watchdog returns `"off-hours"`
- No alert sent (regardless of staleness)

### AC-4: Recovery message sent when data restores

**Given** watchdog previously detected stale data and sent alert
**When** watchdog runs and `MAX(market_prices.updated_at)` is now fresh (<6h)
**Then**
- Watchdog returns `"restored"`
- MARKET alert sent: "Data pipeline issue resolved — fresh data arriving again"

### AC-5: Watchlist context flags stale prices >24h

**Given** `buildWatchlistSection()` is called with a watchlist where FPT has price updated 25 hours ago

- User sees this in `/ask` bootstrap context and knows to discount stale prices

### AC-6: Evening summary flags data crisis

**Given** evening summary has:
  - `watchlistMovers = []` (empty, no movers today)
  - `topStories = []` (empty, no news)
  - `market_prices.updated_at = 2026-04-20 12:00 UTC` (stale >6h at evening time)
  - `rag_analyses.created_at = 2026-04-20 11:00 UTC` (stale >6h)

**When** `runEveningSummary()` executes
**Then**
- Evening summary includes banner: `[⚠ Data pipeline crisis: prices stale 8h, last news 9h ago]`
- User receives message and understands that empty summary is not a quiet market, but a system failure

### AC-7: Test isolation via dependency injection

**Given** unit tests for watchdog / context builder / evening summary
**When** tests provide mock `readPrice()`, `readNews()`, `readOhlcv()` functions
**Then**

## Technical Notes

### Threshold Strategy

| Source | Threshold | Rationale |
| --- | --- | --- |
| Price (FR-1 watchdog) | 6h | VPS pushes every ~5-10 min during market hours. 6h = 40+ missed pushes. Early enough to alert before evening summary runs. |
| Price (FR-2 context) | 24h | Older data (>1 day) is unreliable for same-day intraday/TA analysis. Conservative threshold so context warning doesn't spam. |
| News (FR-1 existing) | 15 min | News fetch runs every 15 min. Missing 1 cycle = 15 min stale. (Same as existing watchdog.) |
| OHLCV (FR-1 existing) | 26h | Daily bar, so next bar arrives after market close. 26h allows 1 day + rollover. |

## Implementation Notes for Architect

1. **FR-1 Watchdog location:** Should live in `src/scheduler/market-data/` (not in the root scheduler/) because it's market-data-specific. Naming: `priceUpdateWatchdogJob.ts` to match existing `ohlcvStalenessCheckJob.ts` pattern.

2. **Existing watchdog collision:** `vpsProxyWatchdogJob.ts` already monitors prices at 45-min threshold. FR-1 is a 6h *early warning* before the 45-min watchdog fires. No conflict — two separate detection windows. Both should coexist.

3. **MARKET alert routing:** Use `sendTelegramMarket()` for user alerts (FR-1 + FR-3). Use `sendTelegramWork()` for operator diagnostics (FR-1 WORK channel).

4. **Evening summary trigger:** FR-3 staleness detection should be lightweight (just two MAX() queries or check cached timestamps). Avoid expensive rescans during evening summary assembly.

5. **Fallback (FR-4):** Is out of scope for code, but architect should review `docs/ARCHITECTURE.md#Data Sources & Fallback Chain` and assess feasibility for a future sprint.
