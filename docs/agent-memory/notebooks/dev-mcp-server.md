## 2026-07-31 — FIX-PDFOCR-PAGECAP-COMPLETENESS-THRESHOLD-MISMATCH (BOUNDED-1 auto-pickup, P2/S) → REVIEW, next_agent=qa

**Session:** 64c7c677-0f0f-4cee-a3ce-dba79d70b7ae. `pdfOcrWorker.ts`'s completeness gate compared the OCR-capped (`maxPages = Math.min(totalPages, 80)`) row count against the UNCAPPED `expectedPages*0.5` threshold — any PDF >160 true pages could never satisfy its own gate, so a capped-80 extraction was judged perpetually incomplete and blanket-DELETEd + re-OCR'd (capped at 80 again) on every boot, forever. Architect live-confirmed 3 files pinned at exactly 80 rows across 2 boots (GVR_2026_Q1.pdf, GVR_2025_Q4.pdf, MSN annual report). Worse: the DELETE fired BEFORE re-extraction, so `read_bctc_pdf`/`getCachedPdfText` saw zero cached pages during the ~10-12min re-OCR window instead of the stale-but-present rows.

**Fix (`pdfOcrWorker.ts`):** new `OCR_MAX_PAGES=80` constant shared by both the threshold calc and the loop cap. Threshold now computed against `Math.min(expectedPages, OCR_MAX_PAGES)` — a full capped extraction reaches a terminal "already extracted" state. Removed the upfront blanket `DELETE` on the incomplete branch entirely — the loop's existing `INSERT OR REPLACE` (`UNIQUE(filename,page_number)`) already UPSERTs each page in place, so old rows stay visible until overwritten; added a defensive post-loop `DELETE ... AND page_number > maxPages` (write-before-delete) for the one edge case where a prior run's pdfinfo probe returned more pages than this run.
