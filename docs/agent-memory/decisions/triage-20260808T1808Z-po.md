## D-4 — orch-apply size ceiling: agreed on the gap, REJECTED as scoped

task_id: `FIX-ORCHAPPLY-NO-HOTFILE-SIZE-TELEMETRY-WARN`

**what-considered:** (a) implement the ~600KB hard ceiling as the 07-17 brief §7 specifies;
(b) WARN/telemetry only, hard gate deferred; (c) skip.

**why-change:** (a) rejected — **it would brick the file on the very next write**. The brief
proposed a ~600KB ceiling when `orch-state.json` was 844KB; it is **3.73MB today**. A hard gate at
600KB rejects 100% of writes. This is structurally the *same* naive-gate failure that the *same
brief* explicitly rejected in §2.5 for RC-VERIF ("would reject every single future write of the
hot file... immediately bricking the file"). Shipping it here would be repeating, in the sibling
leg, the exact mistake that brief is famous for catching.

(b) chosen: emit candidate + live byte size on every apply, non-fatal WARN above
`ORCH_HOT_CEILING_BYTES` (default 614400, env-tunable). No rejection path, no exit-code change —
pure observability, so it cannot deadlock the fleet. The hard gate is deferred until the file is
actually under ceiling, which is D-5's job. P2, **not** dispatched this tick (WIP budget).
