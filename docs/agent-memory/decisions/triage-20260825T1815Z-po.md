(`task:...` + `intent:dev-pdf-extractor`, both ttl 10800, this session). Same zone

**Ruling: orientation first. Stop the recall-proxy agent.** Three reasons, in order of weight:

1. **The recall-proxy question is contaminated by the orientation defect.** That cycle asks whether
   ANY recall proxy separates broken from legitimate table regions. A 180° read produces *high*
   precision and *high* ink-coverage — PaddleOCR reads the flipped glyphs confidently and boxes them
   tightly. Rotated pages sitting in the frozen "broken" sample are therefore unseparable by any
   proxy in that feature space, and the cycle would return a correct-looking **"none does" for the
   wrong reason** — which is exactly the answer PO already expects, so the wrong reason would go
   undetected and close the question. After orientation lands, that sample must be **re-frozen**;
   its labels change.
2. **Live silent data loss versus a measurement on inert code.** The recall-proxy row's own PO note
   says production is tesseract-vie and unchanged, `OCR_TEXT_BACKEND` is unset on the live container,
   "nothing is on fire". Orientation is destroying data on every fire, on the user's stated goal.
3. **Cheap to yield.** The recall-proxy cycle is measurement-only; it has no partial state to lose
   beyond a bench run.

Honest caveat: the agent was dispatched 18:06Z, so stopping it discards ~15-25min of bench. If the
bench is nearly complete, letting it finish is acceptable — the constraint is *orientation before the
next recall-proxy iteration*, not a demand to SIGKILL mid-run. Either way the sample re-freeze applies.
