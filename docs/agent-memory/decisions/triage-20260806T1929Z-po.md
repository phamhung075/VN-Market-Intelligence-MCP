## D1 — ba's notebook-prune report: accepted the symptom, REJECTED the stated root cause

**what-considered:** (a) mint against ba's premise as written; (b) fold onto one of the 3 open
`FIX-NOTEBOOK-AUTOPRUNE-*` rows; (c) read the script and mint against the real mechanism.

**why-decision:** Chose (c). ba reported the hook "counts ALL `## ` headings toward its 3-section
cap instead of scoping to DATED headings only per AC-2a". There is **no 3-section cap** in
`scripts/agents-flow/notebook-auto-prune.sh` — the drop loop is `while true` and breaks when both
the line and byte caps are satisfied; section count is consulted only for the `<=1` safe-fail.
Minting against that premise would have sent a developer hunting a constant that does not exist.

The real mechanism is the **inverse** of the report: rolling headings (`## Archive`,
`## Known patterns / preferences`) are assigned the MAX sentinel key, so they can never be the
MIN drop candidate — they are structurally **exempt from being dropped** while still being
**fully counted** in the whole-file byte total. Result: 100% of any byte overage is repaid by
deleting dated cycle history. On `ba.md` the byte axis binds at 45L/10252B against 200L/12000B —
it prunes at 22% of the line cap because 2 of its 4 headings are permanently retained. And it
ratchets: ba's own recovery action (re-documenting lost content into Known-patterns) grows the
undroppable share, so the next dated section dies sooner.

Rejected (b): all three open rows own adjacent-but-different planes — direction vote when all
sections are sentinel, tie ORDER within an already-chosen candidate set, and the heading regex.
None touches drop **eligibility** or the byte accounting.

**what-changed:** Minted `FIX-NOTEBOOK-AUTOPRUNE-ROLLING-SECTIONS-BYTE-COUNTED-BUT-UNDROPPABLE`
(P1, developer, cross-service/) with the corrected premise stated explicitly so the reporter's
version cannot be implemented by mistake.
