## Entry 3 — Query bug vs data gap: the split that decides routing

The router explicitly asked me to route data/backend gaps away from dev-frontend. So for each ghost I
counted the **backing table** before blaming any renderer. That single step reversed the routing twice:

- **what-considered:** (a) file the empty endpoints as frontend rendering bugs; (b) **CHOSEN** — count rows
  in the backing table first, via `docker exec … bun:sqlite` against the live `/app/data/market.db`.
- **why-change:** every one of the four ghosts has a **non-empty** backing table
  (`conviction_history` 3942, `cascade_rule_hits` 10976, `daily_foreign_flow` 6302, `vnstock_trading_stats`
  7449). Not one is a frontend fault, and not one is a plain "no data yet" gap either — which is the answer
  I expected to find and did not. Two are server-side **query** defects, two are **writer** defects.
- **conviction — proven, not inferred:** the endpoint's own reported `tradingDate` is `2026-06-17`. I ran
  `SELECT MAX(date) FROM (SELECT date FROM conviction_history ORDER BY date ASC, symbol ASC LIMIT 2000)`
  → `2026-06-17`. Exact match, so the `LIMIT 2000` is not *a* candidate cause, it is *the* cause. 1907 rows
  (48% of the table, all of it recent, healthy, ~33/day through 2026-08-21) are invisible. The store's
  docstring — *"766 rows … well within the default cap"* — was true when written on 2026-06-11; the table
  outgrew the cap and the cap became silent newest-data truncation. **Monotonic: it staled by one more day
  every day and would never self-heal.**
- **foreign-flow — implementation contradicts its own docstring:** handler line 8 states the contract
  *"Latest trading day = MAX(date) with foreign_volume IS NOT NULL"*; the SQL subquery omits that guard, so
  it selects `MAX(date)`=2026-08-22 (41 rows, **all 41 NULL**), then the outer `AND foreign_volume IS NOT
  NULL` deletes the entire result set. The last good day, 2026-08-18, has 99 non-null rows and is right
  there. No spec question to resolve — the spec is already written above the bug.
- **why this reads as intermittent to the user:** it only ghosts when a partial/NULL batch happens to sit
  at the top. Also seen 2026-08-16 (4 rows, 0 non-null) and 2026-08-15 (34 rows, 0 non-null).
