## STEP po-3 — A script that says "crash cliff" only when it has already proven there was no crash

12 A-30 alerts on rag-service in one day, several tagged CRITICAL "crash cliff", including `88.66% → 47.88%`. Rather than fold them onto the existing memory rows, I checked whether the container actually crashed:

```

3|2026-08-13T09:20:09.721086103Z|false        # docker ps: "Up 15 hours"
```

**No restart at any point in the 15h window that contains every one of those alerts.**

Then I read the verdict chain (`scripts/audits/verify-a30-mcp-memory-reclamation.sh:311-322`). It is an `if/elif`: branch 1 `STATE_CHANGED` (RestartCount/StartedAt delta), branch 2 `OOMKilled`, branch 3 `DEATH_SIGNATURE`, branch 4 `DISCONT>0 → "crash cliff"`. **Branch 4 is only reachable when branches 1-3 all evaluated false** — i.e. the script has already established from `docker inspect` that nothing died, and then labels the drop a crash. `tier1-probe.md:244` maps that substring to CRITICAL. The claim is unfalsifiable by construction.

Second, independent reason it is wrong on this container: `FIX-RAG-EMBEDDER-IDLE-UNLOAD-ALLOCATOR-PAGES-NOT-RETURNED-TO-OS` states a **full** model release should be ~35pp. The two drops branch 4 fired on are **40.78pp and 42.30pp**. `DISCONTINUITY_PP=40` sits just below the healthiest possible event on rag-service, so a complete, successful reclamation is *guaranteed* to raise a CRITICAL crash alert.

**Minted `FIX-AUDITOR-A30-CRASHCLIFF-BRANCH-CANNOT-BE-A-CRASH-BY-CONSTRUCTION`.** Not folded onto `FIX-AUDITOR-A30-SUSTAINED-WINDOW-SHORTER-THAN-TARGET-RECLAMATION-PERIOD` despite the shared file, because **the two are in tension**: that row lengthens the sample window so the 15-minute idle-unload becomes visible, which makes *more* healthy unloads land inside the window and trip branch 4. Shipping it alone converts a false ESCALATE into a false CRITICAL. Cross-linked both ways (`po_crosslink_20260814`) so whoever picks up either sizes both. Folding would have buried the branch-4 half — the exact partial-landing shape I caught on `FIX-DEVFLOW-MICROSERVICE-MAIN-NO-ERROR-BOUNDARY` yesterday.

**Same evidence corrected a P0.** `FIX-RAG-EMBEDDER-IDLE-UNLOAD-...`'s central quantitative claim is "only ~18-20pp vs the ~35pp expected" (measured 08-08). The 08-13 series shows 40.78pp / 42.30pp — at or above a full release.
