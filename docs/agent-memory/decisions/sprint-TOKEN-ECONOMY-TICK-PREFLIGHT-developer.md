**what-considered:**
- **R7 two-SKIP-path distinction:** implemented as two separate case branches keyed off `_step_sf1_claim`'s return code (1=peer holds it, release nothing) vs `_step_fire_election`'s return code (1=peer leads, release SF-1). Verified via T3 (asserts `task_claim` called exactly 2x, `task_release` never called) and T4 (asserts `task_release` IS called) — the two paths cannot be conflated because they are gated by different functions' return values, not a single shared "SKIP" branch.
- **R8 ERROR + malformed-JSON guard (new, beyond WU-1's precedent):** `mcp_call()` from `mcp-call.sh` only validates the SSE envelope's `.result...` JSON — it does NOT validate that the tool's own `content[0].text` string (e.g. the `task_claim` result body) is itself parseable JSON. Without an explicit `_is_json` check before `jq -r '.claimed // false' 2>/dev/null`, a malformed response would silently fall through to `claimed=""` → treated as `!= "true"` → misread as a clean "peer holds it" SKIP instead of an ERROR — masking a real transport/schema problem as a normal lock-contention outcome. Added `_is_json()` guard on every SF-1/fire-election/presence response before field extraction; T7/T8 assert this explicitly (malformed JSON on either claim call must produce `ERROR`, not `SKIP`).
- **New design decision, not in brief/handoff — fire-election ERROR releases SF-1:** `main.md`'s SF-1 claim step (kept verbatim in the fallback) has NO re-entrant self-hold check (unlike the fire-election step, which does check `current_holder.owner_client_session == $CLAUDE_CODE_SESSION_ID`). If the script left SF-1 held after a fire-election transport/malformed-JSON error and then emitted `ERROR` (triggering the LLM to re-run the full fallback from the top), the fallback's SF-1 claim would find SF-1 already held by *this same session*, read `sf_result.claimed == false`, and immediately SKIP + `JUMP TO end` — stranding SF-1 for the full 90-minute TTL and blocking this session's own next tick attempt. To avoid this self-inflicted deadlock, the script releases SF-1 (best-effort) before emitting `ERROR` on the fire-election step specifically (SF-1's OWN claim-step errors do not release anything, since nothing was claimed yet at that point). Documented in the script's own header comment; T6/T8 assert the release happens.
- **Presence step is best-effort, never a gate — deviates from WU-1's precedent:** WU-1's cowork script treats a presence `task_heartbeat` failure as `ERROR`. `main.md`'s dev-team PREFLIGHT explicitly states in-line, twice-emphasized: *"Presence result is NEVER a gate — always proceed to SF-1."* Honored that literally: any presence-claim failure (transport OR malformed JSON) is logged to stderr and swallowed; the script always proceeds to the SF-1 gate regardless. T9/T10 assert `RUN` is still reached despite simulated presence transport error / malformed JSON.
- **START telegram dropped from the script (token-economy tradeoff, not in brief):** `main.md`'s original pseudocode sends a `"[dev-team] cron START"` telegram as its very first action, before presence/SF-1/election. The PM spec's WU-2 DoD explicitly bounds the SKIP-path (a) cost at "<= 2 tool calls" — presence-claim (1) + SF-1-claim (2) already hits that ceiling; adding an unconditional START telegram would make it 3 on every tick (RUN, SKIP, and ERROR alike), violating the DoD. The script does not send it; it survives only inside the `jump:preflight-fallback` ERROR-recovery body (unchanged, verbatim). Net effect: routine ticks lose the "cron fired" heartbeat message — acceptable per the sprint's own token-savings goal, called out explicitly here so it isn't mistaken for an oversight.
- **Exit-code convention matches WU-1:** `0` = terminal, no further LLM read needed (`SKIP`, both paths); `1` = LLM must act (`RUN` continues at `gcc-preflight`; `ERROR` falls back to `preflight-fallback`). Verdict JSON field (not exit code alone) distinguishes `RUN` from `ERROR`.
- **`gcc-preflight` anchor split (jump-to SKILL constraint):** the jump-to SKILL requires every anchor to sit "immediately above its heading" — an anchor cannot live mid-fenced-code-block. The original single `Step 0-PREFLIGHT` code fence ran continuously from the START telegram through HEAD.lock/worktree-GC, so a plain "RUN jumps past presence/SF-1/election into the middle of the fence" was not expressible as a valid jump-to anchor. Resolved by splitting the fallback body into two headed sub-sections at the natural presence/SF-1/election → GCC-PREFLIGHT boundary (both verbatim, only re-headed) — this is the one structural (non-cosmetic) change to the flow doc beyond the deliverable's own description, necessary to satisfy the repo's own anchor-placement invariant.
- **cron-dev-team.md deliberately left untouched:** `cron-detect-loop/SKILL.md` documents its Job entries as "verbatim copies" of `.claude/commands/crons/cron-dev-team.md` ("re-sync if cadence changes there"). WU-2's Job 1 prompt now embeds self-arm+script-branching instructions that only make sense inside the auto-re-arm loop itself — copying that same blob into `cron-dev-team.md` (a simple one-off manual-setup reference) would bloat a file whose job is to state the cron's *conceptual* shape, not its internal script-branch logic. Documented the intentional one-Job exception to the "verbatim copy" rule directly above Job 1 in `cron-detect-loop/SKILL.md` instead of touching `cron-dev-team.md`. Flagging here in case QA/WU-3 expected the SSOT file to move too.
- Testing: same function-override-after-source mocking pattern as WU-1 (`mcp_call` stubbed post-`source`, dispatch keyed on `$args` substring since this script's SF-1/presence/fire-election all reuse `task_claim` under one tool name). Zero real `task_claim`/`task_heartbeat`/`task_release`/`send_telegram` calls against `dev-team-cron-singleton` or `cron:dev-team:*` at any point — confirmed by inspecting the mocked call log per test, never the live server. Live transport itself was re-verified read-only via `task_list_held(kind="sprint-task", owner_agent="dev-team")` only (confirmed no `dev-team-cron-singleton`/`cron:dev-team:*` locks were live-held at verification time, and no write call was made).

**why-decision:** All deviations preserve or strengthen the byte-identical lock-semantics requirement (R7) and the explicit "presence never gates" / "ERROR must exist" instructions already present in `main.md`/R8 — none change the design, all close gaps the brief's terse "RUN/SKIP" framing left implicit (malformed-JSON handling, SF-1-stranding-on-error, exact SKIP-path release obligations).
