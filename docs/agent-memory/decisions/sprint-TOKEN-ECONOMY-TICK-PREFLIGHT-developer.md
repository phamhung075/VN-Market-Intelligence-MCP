**what-considered:**
- **R7 two-SKIP-path distinction:** implemented as two separate case branches keyed off `_step_sf1_claim`'s return code (1=peer holds it, release nothing) vs `_step_fire_election`'s return code (1=peer leads, release SF-1). - **R8 ERROR + malformed-JSON guard (new, beyond WU-1's precedent):** `mcp_call()` from `mcp-call.sh` only validates the SSE envelope's `.result...` JSON — it does NOT validate that the tool's own `content[0].text` string (e.g. the `task_claim` result body) is itself parseable JSON. Without an explicit `_is_json` check before `jq -r '.claimed // false' 2>/dev/null`, a malformed response would silently fall through to `claimed=""` → treated as `!= "true"` → misread as a clean "peer holds it" SKIP instead of an ERROR — masking a real transport/schema problem as a normal lock-contention outcome. Added `_is_json()` guard on every SF-1/fire-election/presence response before field extraction; T7/T8 assert this explicitly (malformed JSON on either claim call must produce `ERROR`, not `SKIP`).
- **New design decision, not in brief/handoff — fire-election ERROR releases SF-1:** `main.md`'s SF-1 claim step (kept verbatim in the fallback) has NO re-entrant self-hold check (unlike the fire-election step, which does check `current_holder.owner_client_session == $CLAUDE_CODE_SESSION_ID`). If the script left SF-1 held after a fire-election transport/malformed-JSON error and then emitted `ERROR` (triggering the LLM to re-run the full fallback from the top), the fallback's SF-1 claim would find SF-1 already held by *this same session*, read `sf_result.claimed == false`, and immediately SKIP + `JUMP TO end` — stranding SF-1 for the full 90-minute TTL and blocking this session's own next tick attempt. To avoid this self-inflicted deadlock, the script releases SF-1 (best-effort) before emitting `ERROR` on the fire-election step specifically (SF-1's OWN claim-step errors do not release anything, since nothing was claimed yet at that point). Documented in the script's own header comment; T6/T8 assert the release happens.
- **Presence step is best-effort, never a gate — deviates from WU-1's precedent:** WU-1's cowork script treats a presence `task_heartbeat` failure as `ERROR`. `main.md`'s dev-team PREFLIGHT explicitly states in-line, twice-emphasized: *"Presence result is NEVER a gate — always proceed to SF-1."* Honored that literally: any presence-claim failure (transport OR malformed JSON) is logged to stderr and swallowed; the script always proceeds to the SF-1 gate regardless. T9/T10 assert `RUN` is still reached despite simulated presence transport error / malformed JSON.
- **START telegram dropped from the script (token-economy tradeoff, not in brief):** `main.md`'s original pseudocode sends a `"[dev-team] cron START"` telegram as its very first action, before presence/SF-1/election. The PM spec's WU-2 DoD explicitly bounds the SKIP-path (a) cost at "<= 2 tool calls" — presence-claim (1) + SF-1-claim (2) already hits that ceiling; adding an unconditional START telegram would make it 3 on every tick (RUN, SKIP, and ERROR alike), violating the DoD. Net effect: routine ticks lose the "cron fired" heartbeat message — acceptable per the sprint's own token-savings goal, called out explicitly here so it isn't mistaken for an oversight.

- **`gcc-preflight` anchor split (jump-to SKILL constraint):** the jump-to SKILL requires every anchor to sit "immediately above its heading" — an anchor cannot live mid-fenced-code-block. The original single `Step 0-PREFLIGHT` code fence ran continuously from the START telegram through HEAD.lock/worktree-GC, so a plain "RUN jumps past presence/SF-1/election into the middle of the fence" was not expressible as a valid jump-to anchor.
