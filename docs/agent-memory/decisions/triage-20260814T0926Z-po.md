## What was considered

1. **Dedup against existing rows.** Checked 3 near-neighbours and rejected all as distinct:
   - `FIX-CRON-RUNS-NULL-ERRORMSG` — same TABLE, different defect (NULL error_msg on the rows).
     It is the finding; this row is the detector that finds it. Left open and untouched.
   - `UC-ASL-P3` (READY) — freezes Tier-2/3 C-01..C-16 predicates into a NEW
     `scripts/auditor-db-checks.sh`. Different check family, different script, different tier.
     Deliberately NOT merged — folding a DATA-tier count into a Tier-2/3 script would put the
     count behind an unshipped dependency.
   - `FIX-AUDITOR-DATATIER-REINVOKES-STATEFUL-PREGATE-...` — same tier, unrelated mechanism.
   Recorded all three as `related`, none as `depends`.

2. **Root cause: located at source, not accepted from the report.** Read
   `.claude/commands/crons/cron-db-data-integrity.md`. The gap is explicit and licensed in the
   file's own text: line ~101 specifies cron_job_runs failure detection as prose only
   ("cron_job_runs last run errored"), and the NO HALLUCINATED COUNTS guard at line ~162 scopes
   itself to four counts, then says "use your own ad-hoc sidecar queries ... not for re-counting
   the known four". A recurring watched metric is therefore routed through the ad-hoc DISCOVERY
   path by design. Reporter's diagnosis confirmed at source.

3. **REJECTED the reporter's proposed predicate.** `status != 'success'` folds `running` — a legal
   in-flight state — into the failure count, manufacturing a phantom failure on any sweep landing
   mid-run. Traded one false negative for a recurring false positive.

4. **Ground-truthed independently** rather than trusting the report's numbers (both the report AND
   both auditor spawns could be wrong). Host-bind WAL-safe read via `scripts/lib/sqlite-wal-guard.sh`:
   `success|206023`, `crashed|205|max 2026-08-11 14:00:02`, `error|7|max 2026-07-19 12:40:08`.
   Reporter's ground truth confirmed.

5. **Found the fact nobody in the chain had.** The live schema carries
   `CHECK(status IN ('running','success','error','crashed'))`. `'failed'` is not a legal value —
   the second scan's `status='failed' or 'error'` had one disjunct that was **dead by construction**
   and could never match a row. This reframes the AC: the defect is not "the keyword list was too
   short", it is "there is a hand-authored keyword list at all when the enum is declared in the
   schema". AC-1 therefore mandates a `GROUP BY status` emitting every bucket, and explicitly
   REJECTS a hardcoded IN-list even if today's list is complete.
