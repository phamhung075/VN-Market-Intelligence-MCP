## Task 4: Architect — Root-Cause Analysis (Recurring Bug Escalation, Sprint 1289)

### Work
- Analyzed foreign flow parse error cascade (784 errors/24h, 3,739 total)
- Identified root cause: silent filter in `foreignFlowFetcher.ts` (lines 267)
- Diagnosed why ≥2 prior fixes (Sprint 228, 1288) failed to eliminate root cause

### Root Cause Finding

**Silent Filter Bug:**
- `isValidForeignFlowItem()` type guard uses `.filter()` to discard invalid items
- No error logging when items dropped → caller thinks success
- Domain validator (`foreignFlowValidator.ts`, Sprint 1566) never called by fetcher
- Different validation paths in POST endpoint vs fallback fetcher

**Why Prior Fixes Failed:**
- Sprint 228: Added parse hardening + validation to POST endpoint, but fallback fetcher uses different path
- Sprint 1288: Added fallback strategy (primary→cache→SSE), which masks the problem (cached data hides schema issue)
- Both treated symptoms; silent filter bug remained

**Cascading Effect:**
```
VPS sends 30 items with 3 schema violations
→ Filter discards 3, returns 27
→ Logs "changes: 27" (success)
→ Caller thinks "all items processed"
→ Missing 3 rows in daily_ohlcv accumulates over days
→ After 10 days: ~30 missing rows
→ No diagnostic to show why rows missing
```

### Solution Design

**Three changes:**
1. Replace `.filter()` with strict validator in `foreignFlowFetcher.ts`
2. Unify validation: call `validateForeignFlowPayload()` (domain layer) from both paths
3. Fail loudly: reject HTTP 400 on invalid schema, throw from fetcher
4. Log diagnostics: item index + field name + expected type (enable VPS debugging)

### Output
- **Status:** TECH doc written
- **File:** `docs/TECH_1289.md` (root-cause analysis, why prior fixes failed, proposed solution)
- **Issue doc:** `docs/agent-memory/issues/foreign-flow-parse-cascade.md` (prevention checklist)
- **TASKS.md updated:** Sprint 1289 added with 5 tasks (1 design, 2 dev, 1 qa)

### Prevention Pattern

For future foreign flow changes:
1. All entry points (POST endpoint, fetcher, tests) must use the same validator
2. Fail loudly on schema errors (reject with HTTP 400 or throw)
3. Log error diagnostics (item index + field name + expected type)
4. No custom type guards that filter silently
5. Test both valid and invalid payloads

### Status
- **Design complete:** TECH-1289 approved
- **Next:** Dev tasks 1289b–e (tests + implementation + QA)
- **Expected outcome:** parse errors <5/day after fix
