## Functional Requirements

### FR-1: New store helper — getMarketMessageDigest

- Description: Add a new query function `getMarketMessageDigest` to `src/infrastructure/db/marketMessageStore.ts`. The function groups unreviewed `market_messages` rows by date (UTC date of `sent_at`) and by `from_agent`, returning a structured summary with message counts and the first line of each message's content (a preview). This gives the user a scannable digest without exposing full message bodies until requested.
- Input: `db: Database`, `limit_days?: number` (max calendar days to look back, default 7, clamped 1–30)
- Output: `MarketMessageDigestEntry[]` — see type definition below

Type definitions (added to `marketMessageStore.ts`):

```ts
/** A single entry in the digest: one from_agent on one date. */
export interface MarketMessageDigestEntry {
  /** UTC calendar date, YYYY-MM-DD format (derived from sent_at) */
  date: string;
  /** Agent that sent the messages */
  from_agent: string;
  /** Total unreviewed messages from this agent on this date */
  count: number;
  /** Array of unreviewed message ids (for passing to batch_review_market_messages) */
  ids: number[];
  /** Preview of the first message: first 120 chars of content */
  preview: string;
}
```

Exact SQL for `getMarketMessageDigest`:

```sql
SELECT
  date(sent_at) AS date,
  from_agent,
  COUNT(*)      AS count,
  GROUP_CONCAT(id ORDER BY sent_at DESC) AS id_list,
  MIN(substr(content, 1, 120))           AS preview
FROM market_messages
WHERE verdict IS NULL
  AND sent_at >= date('now', '-' || ? || ' days')
GROUP BY date(sent_at), from_agent
ORDER BY date(sent_at) DESC, from_agent ASC
```

Post-query transformation: `id_list` (comma-separated string from `GROUP_CONCAT`) must be split into `number[]` for the `ids` field. Parse with `id_list.split(",").map(Number)`.

Note on `GROUP_CONCAT` ordering: SQLite supports `GROUP_CONCAT(expr ORDER BY ...)` from version 3.44.0 (2023-11-01). Bun bundles SQLite 3.46+. If in doubt, the Architect should add a runtime check. As a fallback, the order of `ids` within an entry does not need to match `sent_at` order — the user passes all IDs to `batch_review_market_messages` regardless.

- Business rule: the function is read-only. It never modifies rows. `limit_days` default of 7 covers one trading week — adequate for a user who reviews once per day. Clamping to 30 prevents accidental full-table scans when the table grows large.
- DDD layer: infrastructure (`src/infrastructure/db/marketMessageStore.ts`)

### FR-2: New store helper — batchReviewMarketMessages

- Description: Add a new mutation function `batchReviewMarketMessages` to `src/infrastructure/db/marketMessageStore.ts`. The function applies a single verdict to a list of message IDs in one SQLite transaction. This is the write partner of the digest tool.
- Input: `db: Database`, `ids: number[]`, `verdict: "signal" | "noise"`, `note?: string | null`
- Output: `{ updated: number; notFound: number[] }` — count of rows actually updated, plus IDs that did not exist

```ts
export interface BatchReviewResult {
  /** Number of rows successfully updated */
  updated: number;
  /** IDs from the input list that were not found in market_messages */
  notFound: number[];
}

export function batchReviewMarketMessages(
  db: Database,
  ids: number[],
  verdict: "signal" | "noise",
  note?: string | null,
): BatchReviewResult
```

Implementation contract:

1. Validate `verdict` at runtime — throw `Error("Invalid verdict")` for any value outside `"signal" | "noise"`.
2. If `ids` is empty, return `{ updated: 0, notFound: [] }` immediately.
3. Wrap all UPDATEs in a single SQLite transaction (`db.transaction()`).
4. For each id, run the same UPDATE SQL as `reviewMarketMessage`:

```sql
UPDATE market_messages
SET verdict = ?, verdict_note = ?, reviewed_at = datetime('now')
WHERE id = ?
```

5. Track which ids had `changes === 0` after their UPDATE — these are the `notFound` ids.
6. Commit the transaction. On any exception, rollback is automatic (Bun SQLite `db.transaction()` behaviour).

- Business rule: the function is idempotent per row — calling again on an already-reviewed row overwrites the previous verdict. This is consistent with `reviewMarketMessage` and allows corrections. Partial success is fine: some IDs may not exist while others are updated — both counts are reported to the caller.
- DDD layer: infrastructure (`src/infrastructure/db/marketMessageStore.ts`)

- Description: Register a new MCP tool that returns a grouped digest of unreviewed MARKET messages, enabling one-shot morning triage from Claude Desktop.
- Input: `limit_days` (optional integer, 1–30, default 7)
- Output: formatted digest text (not raw JSON) — human-readable, bilingual structure

```ts
server.tool(
  "get_market_message_digest",
  "Returns a grouped digest of unreviewed MARKET channel messages, grouped by date and sending agent. " +
  "Use this first thing in the morning to see what fired overnight. " +

  "Use the ids from each entry with batch_review_market_messages to label them all at once. " +
  "limit_days controls how many calendar days back to look (default 7).",
  {
    limit_days: z.coerce.number().int().min(1).max(30).default(7).optional()
      .describe("How many calendar days back to search (1-30, default 7)"),
  },
  async ({ limit_days }) => { ... }
)
```

Output format (when entries exist):

```
Digest chua review — 7 ngay gan nhat
=========================================

[2026-04-13]
  alert-commander   3 tin  ids: [42, 41, 40]
    Preview: "VCB — QUAN TRONG\nGia giam 3.2% ..."

  morning-briefing  1 tin  ids: [39]
    Preview: "Briefing 13/04: VNINDEX +0.3% ..."

[2026-04-12]
  alert-commander   1 tin  ids: [35]

```


Formatting rules:
- Date header uses `[YYYY-MM-DD]` format.
- Each agent line indented 2 spaces: `  {from_agent}  {count} tin  ids: [{id1}, {id2}, ...]`
- Preview line indented 4 spaces: `    Preview: "{first 120 chars}"`
- Footer line shows total unreviewed count across all entries.
- `limit_days` in the empty-state message uses the actual value passed.

### FR-4: MCP tool — batch_review_market_messages

- Description: Register a new MCP tool that applies a single verdict to a list of message IDs. Enables bulk labelling after reviewing the digest.
- Input: `ids` (required, array of integers, min 1 element, max 200 elements), `verdict` (required: `"signal"` or `"noise"`), `note` (optional string)
- Output: confirmation text with counts

Tool registration:

```ts
server.tool(
  "batch_review_market_messages",
  "Labels a list of MARKET channel messages with a single verdict in one call. " +
  "Pass the ids from get_market_message_digest. " +
  "Use verdict='noise' to clear low-value overnight messages, 'signal' for genuine alerts. " +
  "Returns a count of how many were updated and which ids were not found.",
  {
    ids: z.array(z.number().int().min(1)).min(1).max(200)
      .describe("Array of market_messages ids to review (from get_market_message_digest)"),
    verdict: z.enum(["signal", "noise"])
      .describe("'signal' = genuine useful alert. 'noise' = false positive or low-value."),
    note: z.string().optional()
      .describe("Optional free-text note applied to all messages in this batch"),
  },
  async ({ ids, verdict, note }) => { ... }
)
```

Output format (all IDs found and updated):

```
{updated} tin da duoc danh gia la '{verdict}'.{note_line}
```

Where `note_line` = `" Note saved."` if `note` was provided, else `""`.

Output format (some IDs not found):

```
{updated} tin da duoc danh gia la '{verdict}'. {notFound.length} ID khong tim thay: [{id1}, {id2}].{note_line}
```

Output format (zero IDs updated, all not found):

```
Khong tim thay bat ky tin nhan nao. IDs: [{id1}, ...].
```

Output format (error):

```
Error in batch review: {error.message}
```

- Business rule: the tool is idempotent per row (consistent with `review_market_message`). An empty `notFound` list is not reported in the success line — only included when at least one ID was not found. Max 200 IDs per call prevents accidental bulk writes during misuse. The limit is enforced by Zod before reaching the store.
- DDD layer: interface (`src/interface/mcp/tools/marketMessageTools.ts`)

## Non-Functional Requirements

- Performance: `getMarketMessageDigest` uses a single GROUP BY query with a date-range filter. With an index on `sent_at` (already created in Sprint 068: `idx_mm_sent_at`) and a 7-day window, expected < 5ms on a table with up to 10,000 rows. `batchReviewMarketMessages` wraps all UPDATEs in a single transaction — expected < 10ms for up to 200 IDs.
- Atomicity: `batchReviewMarketMessages` runs inside a single `db.transaction()` — all rows succeed or all roll back. Partial failure within the transaction is not possible; `notFound` tracking is post-hoc based on `changes === 0` per individual UPDATE within the transaction.
- Data freshness: both new tools read live rows — no caching, no TTL.
- Language: tool descriptions in English (consistent with existing tools). Formatted output uses Vietnamese phrasing for user-facing strings (consistent with Sprint 068: "tin nhan", "chua review", "danh gia") mixed with English for technical terms (IDs, verdict values, tool names).
- Backward compatibility: Sprint 068 tools (`get_unreviewed_market_messages`, `review_market_message`) are not modified. Existing call sites in `marketMessageTools.ts` are not changed.
- Max batch size: 200 IDs is ~10 days of messages at peak load (20 msg/day). This prevents accidental mass-writes while still covering practical use.

## Edge Cases and Data Quality

- [ ] Empty `ids` array: Zod schema `min(1)` rejects it before the handler runs. The user sees a Zod validation error.
- [ ] `ids` array with duplicates: two UPDATEs run on the same row — idempotent (second write overwrites with same verdict). `updated` count reflects the number of `changes > 0` UPDATEs; duplicates that hit an already-updated row in the same transaction report `changes === 0` and appear in `notFound`. This is acceptable — the outcome is correct.
- [ ] `limit_days = 0` or negative: Zod `min(1)` rejects it. User sees a Zod validation error.
- [ ] `limit_days` very large (> 30): Zod `max(30)` rejects it.
- [ ] `getMarketMessageDigest` when no unreviewed rows in range: returns empty array. Tool returns the "Khong co tin nhan" empty-state message.
- [ ] `GROUP_CONCAT` with a very large `content` field: `substr(content, 1, 120)` is applied before `MIN()` — limits the preview string. The full content is not transmitted in the digest response.
- [ ] `id_list` parsing: `GROUP_CONCAT` returns a `string` from SQLite. If only one row in the group, it returns a string without a comma. `"42".split(",").map(Number)` correctly produces `[42]`.
- [ ] Task 1139 already merged: the most likely scenario based on TASKS.md "Ready for review" status. The Architect must confirm via grep before taking any action.
- [ ] `batchReviewMarketMessages` called with 200 IDs all for non-existent rows: returns `{ updated: 0, notFound: [all 200 ids] }`. The tool renders the "Khong tim thay" error message. No exception.
- [ ] `verdict` outside `"signal" | "noise"`: Zod `z.enum(["signal", "noise"])` rejects it at the tool boundary before the store is called. The store also validates and throws as a second line of defence.
- [ ] Vietnamese number format in content: `market_messages.content` stores raw Telegram text as-is. No number parsing occurs in this sprint — content is display-only in the digest preview.
