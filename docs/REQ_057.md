## Problem Statement

The current system is purely reactive: an event happens, the system analyzes it, and fires an alert. There is no accumulation of evidence over time, no base-rate computation, and no structured prediction capability. The prediction market tools (`get_prediction_markets`, `record_signal_outcome`) exist as stubs but have no real engine behind them.

The result is that every analysis cycle starts from scratch. The system has no memory of whether its past signals were accurate, so it cannot improve.

---

## Business Goal

Build a prediction engine that:
1. Accumulates evidence fragments from existing agents (no new data sources needed)
2. Computes historical base rates from past outcomes
3. Generates structured probability claims with resolution criteria
4. Closes the feedback loop: compares outcomes to claims, computes Brier scores, updates likelihood ratios

The end state: the system knows which of its signal types are actually predictive, and weights future analysis accordingly.

---

## Architecture Decision (Locked by PO)

LLM (Claude scheduled agent) provides narrative synthesis and qualitative context. Numbers (probabilities, base rates, Brier scores) come exclusively from historical data computation. Neither alone is sufficient.

The Prediction Synthesizer runs as a **Claude scheduled agent** (Cowork team), NOT as an API call from a scheduler job. This is deliberate: the synthesis step requires reading multiple MCP tools, forming a coherent narrative, and writing structured claims. That is agent work, not function work.

## Phase Structure

### Phase A — Evidence Accumulation Store (Sprint 056)

**Goal:** Give the engine raw material to work with. Pure data engineering — no AI inference.

#### New Table: evidence_fragments

```sql
CREATE TABLE IF NOT EXISTS evidence_fragments (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  stock          TEXT NOT NULL,
  evidence_type  TEXT NOT NULL,
  direction      TEXT NOT NULL CHECK(direction IN ('bullish','bearish','neutral')),
  magnitude      REAL NOT NULL CHECK(magnitude BETWEEN 0.0 AND 1.0),
  confidence     REAL NOT NULL CHECK(confidence BETWEEN 0.0 AND 1.0),
  timestamp      TEXT NOT NULL,
  source_agent   TEXT NOT NULL,
  ttl_days       INTEGER NOT NULL DEFAULT 30,
  expires_at     TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_ef_stock_ts ON evidence_fragments(stock, timestamp DESC);
CREATE INDEX IF NOT EXISTS idx_ef_expires  ON evidence_fragments(expires_at);
```

`evidence_type` examples (non-exhaustive, BA to finalize):
- `news_sentiment_macro`, `news_sentiment_stock`, `bctc_revenue_growth`, `bctc_pe_ratio`, `bctc_debt_equity`, `price_momentum_5d`, `price_momentum_20d`, `foreign_net_flow`, `insider_transaction`, `kinh_dich_signal`

#### Agent Modifications

Each of the 5 main analysis agents writes evidence fragments at the end of each cycle via a new MCP tool `record_evidence_fragment(stock, evidence_type, direction, magnitude, confidence, source_agent, ttl_days)`. This is additive — no change to existing agent logic, just a new write at the end.

#### Nightly Accumulator Job

New scheduler job `evidenceAccumulatorJob.ts` (runs 23:00 VN):
1. Queries `evidence_fragments` for last 30 days grouped by stock
2. Produces per-stock JSON `evidence_score` object: weighted average of magnitude * confidence by direction
3. Writes result to a new `evidence_scores` table (upsert on stock + date)
4. Purges expired rows (`expires_at < NOW()`)

#### Foreign Net Flow Delta (HIGH PRIORITY GAP)

The most-watched signal in the VN retail market is foreign net buying/selling. Currently, the system tracks price and news but NOT foreign net flow delta. Phase A is the right time to add this.

New `foreign_flow_snapshots` table: `(stock, date, net_flow_vnd, direction, timestamp)`. The VPS proxy already pushes price data — adding net flow to the same push endpoint is low effort. Architect to confirm feasibility with current VPS proxy design.

### Phase B — Base Rate Computation (Sprint 056 or 057)

**Goal:** Compute historical likelihood ratios for each evidence type from past signal outcomes.

#### New Table: evidence_likelihood_ratios

```sql
CREATE TABLE IF NOT EXISTS evidence_likelihood_ratios (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  evidence_type   TEXT NOT NULL,
  direction       TEXT NOT NULL,
  horizon_days    INTEGER NOT NULL,
  likelihood_ratio REAL NOT NULL,
  sample_size     INTEGER NOT NULL,
  last_updated    TEXT NOT NULL,
  UNIQUE(evidence_type, direction, horizon_days)
);
```

#### Computation Logic

For each `(evidence_type, direction, horizon_days)` triple:
1. Join `evidence_fragments` with `record_signal_outcome` outcomes at the specified horizon
2. Compute: `likelihood_ratio = P(outcome correct | evidence) / P(outcome correct | base_rate)`
3. Minimum sample size = 10 before a likelihood ratio is considered reliable (below this, use 1.0)

#### Per-Stock Rolling Base Rate

From `get_price_history`, compute for each stock: what fraction of 5d, 10d, 20d windows exceeded ±3% move. This becomes the denominator for likelihood ratio computation.

### Phase C — Prediction Claim Generation (Sprint 057)

**Goal:** New Claude agent generates structured probability claims. New MCP tools support the workflow.

#### New Table: prediction_claims

```sql
CREATE TABLE IF NOT EXISTS prediction_claims (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  stock               TEXT NOT NULL,
  claim               TEXT NOT NULL,
  probability         REAL NOT NULL CHECK(probability BETWEEN 0.0 AND 1.0),
  horizon_days        INTEGER NOT NULL,
  resolution_date     TEXT NOT NULL,
  resolution_criteria TEXT NOT NULL,
  resolved            INTEGER DEFAULT 0,
  resolution_outcome  INTEGER,
  brier_score         REAL,
  created_at          TEXT NOT NULL,
  resolved_at         TEXT
);
```

#### New MCP Tools

| Tool | Description |
|------|-------------|
| `get_evidence_summary(stock)` | Returns current `evidence_score` + top 5 contributing fragments for a stock |
| `create_prediction_claim(stock, claim, probability, horizon_days, resolution_criteria)` | Inserts a prediction claim row |

Both tools: +2 to tool count.

#### Prediction Synthesizer Agent (Cowork Team)

New agent `08-prediction-synthesizer.md`. Runs weekly, Monday 07:30 VN (before market open).

Protocol:
1. Call `get_watchlist()` to get all monitored stocks
2. For each stock: call `get_evidence_summary(stock)` + `get_bctc_full(stock)` + `get_market_snapshot()`
3. For each stock where evidence_score indicates high-conviction direction: call `create_prediction_claim(...)`
4. Claim format: "FPT will close above VND 150k in 10 trading days" with explicit resolution criteria
5. Write summary to WORK channel via `send_telegram(channel:'work', ...)`

Resolution checker: new `predictionResolutionJob.ts` (runs nightly 23:30 VN):
1. Finds all unresolved claims with `resolution_date <= today`
2. Checks outcome against resolution criteria using price history
3. Computes Brier score: `(probability - outcome)^2` where outcome is 0 or 1
4. Updates `prediction_claims` row

### Phase D — Calibration Loop (Sprint 058)

**Goal:** System learns from its mistakes. Evidence types with poor Brier scores are flagged and their likelihood ratios are recalibrated.

#### Weekly Calibration Report

New scheduler job `calibrationReportJob.ts` (runs Sunday 03:00 VN):
1. Computes Brier score per evidence type (aggregate across all stocks and claims that used that type)
2. Evidence types with Brier score > 0.25 (poor calibration threshold) are flagged
3. Flagged types: likelihood_ratio reset toward 1.0 (neutral) pending more evidence
4. Report sent to WORK channel

## Key Architecture Constraints

1. Phase A must ship before Phase B (base rates require accumulated fragments)
2. Phase B must ship before Phase C (Synthesizer agent uses likelihood ratios)
3. Phase C must ship before Phase D (calibration requires resolved claims)
4. Foreign flow (Phase A, task 1114) is a decision point — Architect must confirm VPS proxy feasibility before it enters sprint scope
5. The Prediction Synthesizer (Phase C) is a Cowork agent — it must be authored by Cowork Refactory Expert agent, not Developer

## Open Questions for BA + Architect

1. Phase A: Is `foreign_flow_snapshots` feasible via the existing VPS proxy push endpoint? Or does it require a new data source?
2. Phase A: What is the canonical list of `evidence_type` values? Should this be enforced by a CHECK constraint or a lookup table?
3. Phase B: Minimum sample size of 10 for a reliable likelihood ratio — is this statistically defensible for VN market data, where some signals may be rare?
4. Phase C: Should `create_prediction_claim` be callable by agents other than the Prediction Synthesizer? Or restricted to that agent only?
5. Phase C: Resolution criteria format — free text or structured (e.g., `{metric: "price_close", operator: ">", value: 150000, currency: "VND"}`)?
6. Phase D: Brier score threshold of 0.25 — is this calibrated for VN market volatility? A perfectly calibrated predictor has Brier = 0.
