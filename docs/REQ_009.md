# REQ-009: Real-Time Intelligence Loop — Puppeteer SSC, Telegram Alerts, 15-Min Cycle

status: READY_FOR_ARCHITECT
sprint: 009
po_vision: Close the real-time intelligence loop: reliable SSC filing fetch, instant Telegram alerts, and a unified 15-minute cycle.

---

## User Story

As a Vietnamese stock investor using Claude,
I want the system to automatically scrape SSC filings via a headless browser, push HIGH/CRITICAL alerts to my Telegram chat, and run a coordinated 15-minute intelligence cycle during market hours,
So that I receive timely, actionable intelligence on my watchlist stocks without manually polling Claude or the SSC portal.

## Chain B — Telegram Bot Notifier

### FR-B1: Telegram notifier module (task 034)

- Description: New file `src/infrastructure/notifiers/telegram.ts`.
- Function signature:
  ```typescript
  export async function sendTelegramAlert(message: string): Promise<boolean>
  ```
- Transport: plain HTTPS POST to `https://api.telegram.org/bot${token}/sendMessage` with body `{ chat_id, text, parse_mode: "Markdown" }`.
- No third-party Telegram SDK — use Node `https` module or `fetch` (Bun native).
- Returns `true` on HTTP 200, `false` on any error (network failure, bad token, rate limit).
- Never throws — catches all errors, logs a warning, returns `false`.
- Env vars read from `config.ts`:
  - `TELEGRAM_BOT_TOKEN` — required; if absent, function logs warning and returns `false` immediately.
  - `TELEGRAM_CHAT_ID` — required; same fallback behaviour.
- DDD layer: infrastructure/notifiers

### FR-B2: Message format

- Parse mode: Markdown (Telegram v1 — single asterisks for bold, backticks for code).
- Template:
  ```
  *[SEVERITY] STOCK_CODE*
  Signal: SIGNAL_TYPES
  Summary: ONE_LINE_SUMMARY
  Time: DD/MM/YYYY HH:MM (GMT+7)
  ```
- `SEVERITY` = `HIGH` or `CRITICAL` (uppercase).
- `SIGNAL_TYPES` = comma-separated signal type list from `Alert.signals`.
- `ONE_LINE_SUMMARY` = first 120 characters of `Alert.message`.
- Time formatted in `Asia/Ho_Chi_Minh` timezone.
- Maximum message length: 4096 characters (Telegram limit). Truncate with `…` if exceeded.
- DDD layer: infrastructure/notifiers

### FR-B3: Hook into alertGenerator (task 034)

- The `generateAlerts` pure domain function must remain pure (no I/O). The Telegram call is made at the **application layer** after `generateAlerts` returns, not inside domain.
- Hook location: `src/application/usecases/pollNews.ts` (and `checkSscReports.ts` for SSC-discovered documents) — after alerts are generated and stored, iterate alerts and call `sendTelegramAlert` for those with severity `"high"` or `"critical"`.
- The notifier is called fire-and-forget: `sendTelegramAlert(msg).catch(() => {})` so it cannot block the pipeline.
- BCTC document discovery trigger: when `checkSscReports` finds a **new** document (not previously in `financial_reports.source_url`), send a Telegram message:
  ```
  *New BCTC Filing: STOCK_CODE*
  Title: DOCUMENT_TITLE
  Published: PUBLISHED_AT
  URL: DOC_URL
  ```
- Impact chain trigger: `runImpactChain` results with `confidence >= 0.7` send:
  ```
  *Macro Impact: STOCK_CODE*
  Chain: CAUSAL_SUMMARY (first 100 chars)
  Confidence: 0.XX
  ```
- DDD layer: application (hook in pollNews, checkSscReports, runImpactChain)

## Chain C — 15-Minute Intelligence Cycle

### FR-C1: `intelligenceCycleJob.ts` scheduler job (task 106)

- Description: New file `src/scheduler/intelligenceCycleJob.ts`.
- Export: `async function runIntelligenceCycle(): Promise<void>`
- Market hours: Monday–Friday, 09:00–15:30 `Asia/Ho_Chi_Minh`.
- During market hours: full cycle — news poll + SSC list + price fetch + impact chain + Telegram alerts.
- Outside market hours: reduced cycle — news poll only.
- Cycle sequence (market hours):
  1. `pollNews()` — fetch RSS feeds, embed, detect signals
  2. `listAllSscDocuments()` for each watchlist stock (lightweight: list only, no PDF download unless new URL found)
  3. `scanMarket()` — fetch current prices for watchlist
  4. `runImpactChain()` on new news entries from step 1
  5. Send Telegram alerts for any HIGH/CRITICAL alerts produced
- Each step is wrapped in individual try/catch — one failing step does not abort the cycle.
- DDD layer: scheduler

### FR-C2: Concurrency guard

- Module-level `let cycleRunning = false` flag.
- If `runIntelligenceCycle()` is called while a previous invocation has not completed: log `[intelligence-cycle] previous cycle still running — skipped` and return immediately.
- The flag is reset in a `finally` block so crashes do not permanently lock the cycle.
- DDD layer: scheduler

### FR-C3: Cycle duration tracking

- Record `Date.now()` at cycle start; compute elapsed on completion.
- Log: `[intelligence-cycle] cycle complete — elapsed: NNNms, steps completed: N/5`
- If elapsed > 720,000 ms (12 minutes): log a warning `[intelligence-cycle] WARN cycle exceeded 12 min threshold`.
- DDD layer: scheduler

### FR-C4: Cron registration

- Register two cron expressions in `src/scheduler/jobs.ts`:
  - Market hours: `*/15 9-15 * * 1-5` — every 15 minutes from 09:00–15:45 Mon–Fri (GMT+7).
  - Off-hours reduced: `0 * * * *` — top of every hour outside market window, news only.
- The market-hours job calls `runIntelligenceCycle()` which internally checks if it is market hours.
- The off-hours job calls a separate `runOffHoursCycle()` function (same file) that runs news poll only.
- Both jobs use the same concurrency guard.
- DDD layer: interface/scheduler (jobs.ts registration)

### FR-C5: Unit tests (task 129 TDD Red, task 106 Green)

- New file `src/__tests__/129-intelligence-cycle.test.ts`, minimum 15 cases.
- All sub-jobs mocked (no real network, DB, or Puppeteer).
- Cases must cover:
  1. Happy path market hours — all 5 steps called in order
  2. `cycleRunning = true` before call → returns immediately, no steps executed
  3. `cycleRunning` reset to `false` after successful cycle
  4. `cycleRunning` reset to `false` when step 1 throws
  5. `cycleRunning` reset to `false` when step 3 throws
  6. Step 2 failure (SSC error) — remaining steps still execute
  7. Step 3 failure (price fetch error) — remaining steps still execute
  8. Off-hours cycle — only step 1 (news poll) is called; steps 2–5 not called
  9. Cycle elapsed time is logged on completion
  10. Warning logged when cycle exceeds 12 minutes (mock timer)
  11. Saturday — `isMarketHours()` returns `false`
  12. Sunday — `isMarketHours()` returns `false`
  13. Weekday 08:59 — `isMarketHours()` returns `false`
  14. Weekday 09:00 — `isMarketHours()` returns `true`
  15. Weekday 15:30 — `isMarketHours()` returns `true` (inclusive upper bound)
  16. Weekday 15:31 — `isMarketHours()` returns `false`
- DDD layer: scheduler (test file)

## Non-Functional Requirements

- Performance: Each full intelligence cycle must complete within 12 minutes (5 steps; SSC Puppeteer is the slowest at up to 3 × 10s per stock = 30s for 4 stocks if parallelised).
- Data freshness: Prices and news no older than 15 minutes during market hours.
- Language: Log messages in English; Telegram alert messages in English with stock codes in uppercase.
- Reliability: No Chrome zombie processes. `browser.close()` verified via test assertions.
- Security: `TELEGRAM_BOT_TOKEN` never logged (redact in logger calls).
- Puppeteer: `headless: "new"` (string form required by puppeteer-core 24.x). Flags: `--no-sandbox`, `--disable-dev-shm-usage`, `--disable-gpu`.

## Edge Cases & Data Quality

- [ ] Chrome binary missing at `CHROME_PATH` → `defaultBrowserFactory` throws → `listSscDocuments` catches, logs error, returns `[]`. Production must verify Chrome is installed.
- [ ] SSC portal returns ADF error page (maintenance) → `waitForSelector` times out after 10s → up to 3 retries → returns `[]`.
- [ ] SSC portal returns results for a different stock code (ADF session bleed) → each row is filtered by `cells[2]` matching the requested `actionCode`.
- [ ] `tr[_afrRK]` selector matches 0 rows (new portal layout) → returns `[]`, logs warning with stock code.
- [ ] `cells.length < 8` (malformed row) → row skipped without throwing.
- [ ] Telegram Bot API rate limit (HTTP 429) → `sendTelegramAlert` returns `false`, does not retry (retry deferred to Sprint 010).
- [ ] `TELEGRAM_BOT_TOKEN` set but `TELEGRAM_CHAT_ID` not set → returns `false` with warning log.
- [ ] Intelligence cycle sub-step times out (e.g. VnDirect API slow) → individual step catches timeout, logs error, cycle continues to next step.
- [ ] Intelligence cycle called at 09:00 exactly on a public holiday (no holiday calendar) → cycle runs normally (holiday awareness deferred to Sprint 010).
- [ ] Concurrency guard: if `runIntelligenceCycle` is called concurrently from two cron triggers (system clock drift) → second call is rejected by guard.
- [ ] Off-hours cron fires at same second as market-open cron (unlikely but possible) → both use same `cycleRunning` flag; one is skipped.
