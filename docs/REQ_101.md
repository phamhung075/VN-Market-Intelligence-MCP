# REQ-101: DDD Boundary Fix — Move Shared Infra Types to domain/models

status: READY_FOR_ARCHITECT
sprint: 101
po_vision: Fix DDD boundary violation — domain layer has zero structural dependency on infrastructure

## User Story

As the VN Market Intelligence system maintainer,
I want all shared types used by domain services to live in `src/domain/models/shared-types.ts`,
So that the domain layer compiles and functions correctly even if infrastructure fetcher files are renamed, split, or removed.

---

## Functional Requirements

### FR-1: Create src/domain/models/shared-types.ts

- Description: New file containing 8 pure TypeScript interface/type definitions copied verbatim from their current infra locations. No imports from infrastructure. No runtime logic.
- Input: Type definitions sourced from 5 infrastructure files (see FR-3 for exact fields).
- Output: `src/domain/models/shared-types.ts` exporting all 8 types.
- Business rule: File must have zero imports from `infrastructure/`. Only primitive TypeScript types and literals allowed as dependencies.
- DDD layer: domain/models

### FR-2: Update 7 domain services to import from domain/models/shared-types

- Description: Each of the 7 domain services currently imports one or more types from `infrastructure/`. Those import lines are replaced to point to `../models/shared-types.js`.
- Input: Existing import lines in the 7 files listed in the DDD Layer Map.
- Output: Import lines updated; all other lines in each file unchanged.
- Business rule: Only the `import type` line changes. No logic, no signatures, no tests change.
- DDD layer: domain/services

- Input: 5 infra files that currently own the type definitions.
- Output: Each infra file exports the same type name(s) as before, sourced from the domain model.
- Business rule: No infra file may delete the export symbol — only re-source it. Any existing runtime code in the infra file is untouched.

## Edge Cases & Data Quality

- [ ] `SearchResult` is not defined directly in `retriever.ts` — it is re-exported from `vectorstore.ts` via `export type { SearchResult } from "./vectorstore.js"`. The new shim in `retriever.ts` must re-source from domain, not from vectorstore. Verify the chain does not create a circular dependency: `vectorstore.ts` must NOT import from domain (it is pure infra). The definition copy goes into `shared-types.ts`; `retriever.ts` shim points to domain; `vectorstore.ts` original definition stays in place (two definitions of same shape is acceptable, or vectorstore can re-export from domain too — Architect decides).
- [ ] `WeatherEvent.type` field name: the actual interface field is `type` (not `eventType`). Task 1321 TC-4 description references `eventType` — the test must assert the actual field name `type`, not `eventType`.
- [ ] `RssItem.url` and `RssItem.publishedAt`: task 1321 TC-3 description references `link` and `pubDate` — those are not the real field names. Test implementation must use `url` and `publishedAt` as defined in `rss.ts` line 21-35.
- [ ] `WeatherEvent.regions` is a `string[]` (plural). Task spec says `region` (singular) — test TC-4 must assert `regions`.
- [ ] Circular import guard: `shared-types.ts` must have zero imports. If any type transitively needs another type from the same file, define them in order within the file (WeatherEventType before WeatherSeverity before WeatherEvent).
- [ ] `domain/models/index.ts` already exists — check whether it barrel-exports existing models. If so, add `export type * from "./shared-types.js"` to keep the barrel complete. Do not break existing barrel consumers.
