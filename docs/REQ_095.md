# REQ-095: Bollinger Band Breakout Alert Scan Job

status: READY_FOR_ARCHITECT
sprint: 095
po_vision: Extend TA alert coverage to Bollinger Band breakouts — fire an intraday alert when a watchlist stock's price closes outside the BB20 band.

## User Story

As a Vietnamese stock investor using Claude,
I want to receive an intraday Telegram alert when a watchlist stock's latest close price breaks above the Bollinger Band upper band or below the lower band,
So that I can act on momentum breakout and panic-selling signals between morning briefings.

---

## Functional Requirements

### FR-1: BB breakout detection per ticker

- Description: For each watchlist ticker, fetch the last 60 days of daily candles from `market_prices_history`, compute BB20 via `computeAllIndicators`, compare the latest close price against `bb20.upper` and `bb20.lower`.
- Input: `DailyCandle[]` — rows from `market_prices_history` grouped `date(fetched_at)`, `AVG(price)`, ordered oldest to newest, last 60 days.
- Output: One of three outcomes — `ta_bb_breakout_up`, `ta_bb_breakout_down`, or no alert.
- Business rules:
  - `close > bb20.upper` → alert type `ta_bb_breakout_up`, message: `"VCB: giá 88000 vượt BB trên 86500 — bứt phá tăng"` (price and upper band formatted as integers, no decimal unless price has fractional part)
  - `close < bb20.lower` → alert type `ta_bb_breakout_down`, message: `"HPG: giá 22000 dưới BB dưới 23100 — bứt phá giảm"`
  - `bb20.lower <= close <= bb20.upper` → skip, no alert
  - `bb20 === null` (fewer than 20 candles) → skip silently
  - `candles.length === 0` → skip silently (no close price to compare)
  - Latest close = `candles[candles.length - 1]?.close ?? null`; if null → skip
- DDD layer: scheduler

### FR-2: 4-hour per-ticker cooldown

- Description: Before inserting, query the `alerts` table to check whether the same `(alertType, ticker)` pair fired within the last 4 hours. If yes, skip insert.
- Input: `alertType` (string), `code` (ticker string), current DB state.
- Output: Boolean gate — proceed to insert or continue to next ticker.
- Business rule: Cooldown uses SQLite `datetime('now', '-4 hours')` against `triggered_at` column. The cooldown check is type-specific: `ta_bb_breakout_up` cooldown does NOT block `ta_bb_breakout_down` and vice versa for the same ticker.
- DDD layer: scheduler (SQL query against `alerts` table)

### FR-3: Alert row insert

- Description: Write one row to the `alerts` table following the exact schema and JSON payload structure used by `taAlertScanJob`.
- Input: ticker code, alert type, close price, bb band value (upper or lower), timestamp from `nowFn()`.
- Output: One row inserted into `alerts` with the following field values:

| Column | Value |
|--------|-------|
| `id` | `crypto.randomUUID()` |
| `triggered_at` | `nowFn().toISOString()` |
| `severity` | `"warning"` |
| `signals_json` | `[{ type, actionCode, message, confidence: 0.65, detectedAt }]` |
| `affected_actions_json` | `[{ code }]` |
| `analysis_ids_json` | `NULL` |
| `message` | Vietnamese string (see FR-1 business rules) |
| `read` | `0` |
| `user_note` | `NULL` |

- Business rule: confidence is `0.65` (lower than RSI's `0.7` — BB breakout is a weaker directional signal). No `INSERT OR IGNORE` — cooldown is enforced by FR-2 before this step.
- DDD layer: scheduler

### FR-4: Scheduler registration

- Description: Register `bbAlertScanJob` in `src/scheduler/jobs.ts` as a periodic cron that runs every 15 minutes during VN market hours on weekdays.
- Input: cron expression `*/15 2-8 * * 1-5` (02:00–08:59 UTC = 09:00–15:59 GMT+7, Mon–Fri).
- Output: Job registered with name `bbAlertScanJob`, calling `runBbAlertScan()`.
- Business rule: Cron window covers VN market session (09:00–15:30 GMT+7). The cron runs until 08:59 UTC which maps to 15:59 GMT+7 — covers the full session including the 15:30 close.
- DDD layer: scheduler

### FR-5: Registry and stats file updates

- Description: Update `docs/data/cron-registry.json` with a new job entry and update `schedulerFileCount` in both `docs/data/cron-registry.json` and `docs/data/project-stats.json` from 30 → 31.
- Input: Current `schedulerFileCount = 30` in `cron-registry.json`, `schedulerFileCount = 29` in `project-stats.json` (note: `project-stats.json` currently lags at 29 — see Data Quality section).
- Output: Both files updated to `schedulerFileCount = 31`. New entry appended to `jobs[]` in `cron-registry.json`.
- Business rule: New cron-registry entry format:
  ```json
  { "schedule": "*/15 min market (2-8 UTC M-F)", "name": "bbAlertScanJob", "desc": "BB20 upper/lower breakout intraday scan — inserts ta_bb_breakout_up/ta_bb_breakout_down alerts, 4h cooldown" }
  ```
- DDD layer: infrastructure (config file)

## Non-Functional Requirements

- Performance: Each scan pass iterates the full watchlist (up to ~30 tickers). Each ticker triggers one candle SQL query + one cooldown SQL query + one optional insert. Total DB ops per pass: ≤ 90 at 30 tickers. No external HTTP.
- Data freshness: Uses `market_prices_history` written by `vn-price-fetch.service` on the VPS (60s cadence). Candles are AVG(price) per calendar day — same query as `taAlertScanJob`.
- Language: Alert messages in Vietnamese. Log messages in English.
- Error isolation: Per-ticker errors caught and logged at `warn` level. Scan continues. Errored ticker is counted in `scanned`.
- No Telegram direct send: `bbAlertScanJob` writes only to `alerts` table. Alert Commander (`05-alert-commander`) reads `readUnnotifiedAlerts()` and handles dispatch. This is the existing contract for all alert-generating jobs.

## Edge Cases & Data Quality

- [x] Empty candles array (no price history for ticker) → `candles[candles.length - 1]` is undefined → skip silently
- [x] `bb20 === null` (fewer than 20 candles) → `computeAllIndicators` returns `bb20: null` → skip silently
- [x] Price exactly equal to `bb20.upper` or `bb20.lower` → strict `>` / `<` comparison → no alert at exact boundary
- [x] `cron-registry.json` and `project-stats.json` count drift — `project-stats.json` shows `schedulerFileCount: 29` while `cron-registry.json` shows `30`. The sprint 094 `taAlertScanJob.ts` was added without updating `project-stats.json`. Both must be corrected to `31` in this sprint.
- [x] Vietnamese number format in message: use raw numeric value from `close` and the band value — no dot-thousands separator in the message string (e.g., `88000` not `88.000`). Consistent with RSI message format in `taAlertScanJob`.
- [x] Cooldown type independence: `ta_bb_breakout_up` and `ta_bb_breakout_down` have independent 4h windows per ticker. A stock can fire both types in the same scan if price somehow jumps across the full band (pathological, but must not be blocked by the wrong cooldown key).
- [x] `computeFn` injection: production uses `computeAllIndicators` from `domain/services/technicalIndicators.ts`. The injected `computeFn` signature is `(candles: DailyCandle[]) => TechnicalIndicatorResult` — identical to `taAlertScanJob`.

## Acceptance Criteria

### AC-1: Breakout-up alert fires

**Given** a watchlist ticker VCB with `close = 88000`, `bb20.upper = 86500`
**When** `runBbAlertScan()` executes
**Then**
- `result.fired === 1`, `result.scanned === 1`
- One row in `alerts` with `json_extract(signals_json, '$[0].type') = 'ta_bb_breakout_up'`
- `json_extract(signals_json, '$[0].actionCode') = 'VCB'`
- `json_extract(signals_json, '$[0].confidence') = 0.65`
- `json_extract(affected_actions_json, '$[0].code') = 'VCB'`
- `message` contains `"VCB"`, `"88000"`, `"86500"`, `"bứt phá tăng"`
- `severity = 'warning'`

### AC-2: Breakout-down alert fires

**Given** a watchlist ticker HPG with `close = 22000`, `bb20.lower = 23100`
**When** `runBbAlertScan()` executes
**Then**
- One row in `alerts` with `type = 'ta_bb_breakout_down'`
- `message` contains `"HPG"`, `"22000"`, `"23100"`, `"bứt phá giảm"`

### AC-3: No alert when price is inside band

**Given** `close = 84000`, `bb20 = { upper: 86000, mid: 84000, lower: 82000 }`
**When** `runBbAlertScan()` executes
**Then**
- `result.fired === 0`
- 0 rows in `alerts`

### AC-4: No alert when bb20 is null

**Given** `computeFn` returns `{ bb20: null, ... }` (fewer than 20 candles)
**When** `runBbAlertScan()` executes
**Then**
- `result.fired === 0`, 0 rows in `alerts`

### AC-5: No alert when candles array is empty

**Given** watchlist has ticker VCB but `market_prices_history` has no rows for VCB
**When** `runBbAlertScan()` executes
**Then**
- `result.fired === 0`, 0 rows in `alerts`

### AC-6: Cooldown suppresses within 4 hours

**Given** a first scan fires `ta_bb_breakout_up` for VCB
**When** a second scan runs 30 minutes later with the same conditions
**Then**
- Second scan `result.fired === 0`
- `alerts` table still has exactly 1 row

### AC-7: Cooldown lifts after 4 hours

**Given** a first scan fired `ta_bb_breakout_up` for VCB and the alert's `triggered_at` is more than 4 hours in the past
**When** a second scan runs with the same breakout condition
**Then**
- Second scan `result.fired === 1`
- `alerts` table has 2 rows total

### AC-8: Multi-ticker scan counts

**Given** 3 watchlist tickers where 2 have `close > bb20.upper` and 1 is inside band
**When** `runBbAlertScan()` executes
**Then**
- `result.scanned === 3`, `result.fired === 2`

### AC-9: Empty watchlist

**Given** `watchlist` table is empty
**When** `runBbAlertScan()` executes
**Then**
- `result === { scanned: 0, fired: 0 }`, 0 DB writes

### AC-10: TypeScript and registry

**Given** the implementation is complete
**Then**
- `bun tsc --noEmit` exits with 0 errors
- `jobs.ts` contains `bbAlertScanJob` entry with cron `*/15 2-8 * * 1-5`
- `cron-registry.json` `schedulerFileCount = 31`
- `project-stats.json` `schedulerFileCount = 31`
- No changes to `taAlertScanJob.ts`, Alert Commander, briefing formatter, cascade pipeline, or VPS proxies

## Implementation Notes for Architect

### Pattern mirror from taAlertScanJob

`bbAlertScanJob.ts` is a structural clone of `taAlertScanJob.ts` with these substitutions:

| taAlertScanJob | bbAlertScanJob |
|----------------|----------------|
| Reads `indicators.rsi14` | Reads `indicators.bb20` + `candles[last].close` |
| Thresholds: RSI > 70 / < 30 | Thresholds: close > bb20.upper / close < bb20.lower |
| Alert types: `ta_overbought` / `ta_oversold` | Alert types: `ta_bb_breakout_up` / `ta_bb_breakout_down` |
| Message suffix: "quá mua" / "quá bán" | Message contains price + band value + "bứt phá tăng" / "bứt phá giảm" |
| confidence: 0.7 | confidence: 0.65 |
| Skip on `rsi === null` | Skip on `bb20 === null` OR `candles.length === 0` |

### Injectable deps interface

```typescript
export interface BbAlertScanDeps {
  db?: Database;
  computeFn?: (candles: DailyCandle[]) => TechnicalIndicatorResult;
  nowFn?: () => Date;
}

export interface BbAlertScanResult {
  scanned: number;
  fired: number;
}
```

### SQL constants (identical to taAlertScanJob — copy verbatim)

- `CANDLE_SQL`: same `market_prices_history` query, parameterized on `code`
- `COOLDOWN_SQL`: same `alerts` query using `json_extract(signals_json, '$[0].type')` and `json_extract(affected_actions_json, '$[0].code')`
- `INSERT_ALERT_SQL`: same column list and `?` bindings

### Test file: 1309-bb-alert-scan-job.test.ts

9 test cases (see TASKS.md 1310 for full case list). Uses same in-memory SQLite pattern as `1307-ta-alert-scan-job.test.ts`:
- `buildTestDb()` creates `watchlist`, `market_prices_history`, `alerts` tables
- `makeComputeFn(bb20, close)` returns a `TechnicalIndicatorResult` with controlled `bb20` and the `candles` array provides the `close` value
- Cooldown lift test: manipulate `triggered_at` directly via `UPDATE alerts SET triggered_at = '...'` (same approach as AC-6 in test 1307)

Note on `makeComputeFn` for BB tests: unlike RSI tests (where `computeFn` returns a fixed rsi14 and the candle array is ignored), the BB job uses BOTH `computeFn` output (for `bb20`) AND the last element of the `candles` array (for `close`). The test must therefore either: (a) populate real candle rows in `market_prices_history` so the candle query returns a non-empty array, or (b) inject candles indirectly. Since `computeFn` is injected and replaces the real computation, the simplest approach is: populate at least one row in `market_prices_history` for the ticker so the candle query returns one row (providing a real `close` value), then inject `computeFn` to return the desired `bb20`.
