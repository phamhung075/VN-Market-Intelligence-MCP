# TECH-1307 — Single-Writer SQLite Architecture

## 1. Root Cause Analysis

### Confirmed Multi-Writer Services (from codebase scan)

`market.db` is mounted at `./data:/app/data` into **7 of 9 Docker services**. All 7 open the
file directly — not via the mcp-server HTTP API.

| Service | DB Access Type | Write Operations | Contention Risk |
|---------|---------------|-----------------|-----------------|
| `mcp-server` (3000) | `bun:sqlite` singleton (WAL) | ALL tables | **Designated writer** |
| `technical-analysis` (5003) | `bun:sqlite` readonly=true | READ ONLY | LOW (reader) |
| `macro-indicators` (5004) | `bun:sqlite` readonly=true | READ ONLY | LOW (reader) |
| `stock-price` (5010) | `bun:sqlite` — Tier3CacheFetcher | **WRITES market_prices** | HIGH |
| `alert-engine` (5006) | `bun:sqlite` write mode | **WRITES alert_engine_records** | HIGH |
| `kinh-dich-service` (5005) | `bun:sqlite` readonly=true | READ ONLY | LOW (reader) |
| `pdf-extractor` (5001) | `sqlite3` Python — `pdf_extractor.db` | Own DB only | NONE (different file) |
| `rag-service` (5002) | `sqlite3` Python — `rag_service.db` | Own DB only | NONE (different file) |

**Active writers to market.db:** 3 services simultaneously — `mcp-server`, `stock-price`, `alert-engine`.

WAL mode serialises SQLite _concurrent readers_ safely. It does NOT protect against concurrent
writers from separate OS processes. Multiple writers under WAL cause:
- `SQLITE_BUSY` (write lock contention)
- WAL frame ordering corruption across separate file descriptor handles
- Database file corruption when `wal_checkpoint(TRUNCATE)` runs during concurrent writes

The `docker-compose.yml` shows `DB_PATH=/app/data/market.db` set identically for
`technical-analysis`, `macro-indicators`, `stock-price`, `kinh-dich-service`, and `alert-engine`.

## 2. Chosen Solution: HTTP Push + Private DB Segregation

### Decision: Hybrid Approach

After evaluating three options:

**Option A — Pure HTTP push (services POST to mcp-server)**
- Pros: enforces single writer completely; matches existing VPS push pattern
- Cons: alert-engine and stock-price need new POST endpoints on mcp-server; adds latency

**Option B — ATTACH DATABASE (separate .db files per service)**
- Pros: no schema changes on mcp-server; Python PDF/RAG already use this pattern
- Cons: mcp-server must ATTACH on every query; cross-db JOINs break existing tooling

**Option C — Hybrid: private DBs for writers, readonly for readers**
- `stock-price` → `stock_price.db` (own file, own schema) + HTTP POST to mcp-server for persistence
- `alert-engine` → `alert_engine.db` (own file, own schema) + HTTP POST to mcp-server for persistence
- Readonly services (`technical-analysis`, `macro-indicators`, `kinh-dich-service`) keep reading `market.db` with `readonly: true`
- **Selected** — smallest blast radius, no mcp-server schema changes, no VPS changes

**Chosen: Option C** — aligns with constraint 4 (no VPS changes), constraint 5 (no schema breaking changes), and the existing pattern where `pdf-extractor` and `rag-service` already use isolated SQLite files.

## 3. Architecture After Fix

```
market.db (write)
    ONLY: mcp-server (port 3000) — bun:sqlite singleton

market.db (readonly)
    technical-analysis, macro-indicators, kinh-dich-service
    (readonly:true, no WAL writer contention)

stock_price.db (write)
    stock-price (port 5010) — own file, caches prices
    Tier3CacheFetcher writes here, NOT market.db
    After push: HTTP POST http://mcp-server:3000/api/push-prices (existing endpoint)

alert_engine.db (write)
    alert-engine (port 5006) — own file, caches alerts
    EvaluateAlertUseCase stores to alert_engine.db
    After evaluation: HTTP POST http://mcp-server:3000/api/internal/alerts (new endpoint)

pdf_extractor.db — unchanged (already isolated)
rag_service.db — unchanged (already isolated)
```

### Write Path After Fix

```
VPS → POST /api/push-prices → mcp-server writes market_prices table
stock-price Tier3 → writes stock_price.db (local cache only)
alert-engine → writes alert_engine.db → POST /api/internal/alerts → mcp-server writes alerts table
```

## 4. File-Level Injection Points

### 4a. stock-price service

**File:** `apps/stock-price/src/infrastructure/fetchers.ts`

`Tier3CacheFetcher.saveQuote()` — line 142–155:
- Change `DB_PATH` reference from `market.db` to env var `STOCK_PRICE_DB_PATH` (defaults to `./data/stock_price.db`)
- This is a best-effort local cache; writes go to the private file only
- Remove the `{ create: false }` open that would fail if market.db is write-locked

`SQLitePriceHistoryRepository.saveQuote()` — line 142–155:
- Same change: target `STOCK_PRICE_DB_PATH`
- Initialize private schema on startup (CREATE TABLE IF NOT EXISTS market_prices_cache)

**File:** `apps/stock-price/src/index.ts`
- Add `DB_PATH_OWN` env variable pointing to `./data/stock_price.db`
- Initialize own schema at startup

**File:** `docker-compose.yml` — `stock-price` service:
- Change `DB_PATH=/app/data/market.db` → `DB_PATH=/app/data/market.db` (keep for readonly reads of history)
- Add `STOCK_PRICE_DB_PATH=/app/data/stock_price.db` (for write operations)

### 4b. alert-engine service

**File:** `apps/alert-engine/src/infrastructure/config.ts`
- Add `ownDbPath` field: `process.env['ALERT_ENGINE_DB_PATH'] ?? './data/alert_engine.db'`
- Keep `dbPath` (= market.db) for readonly reads needed by mcp-server client calls

**File:** `apps/alert-engine/src/infrastructure/repositories.ts`
- `initAlertTables()` — accept `ownDb: Database` parameter, run DDL on own DB
- `SQLiteAlertRepository` — write to `ownDb` (alert_engine.db)
- `SQLiteMuteRepository` — read from `ownDb`

**File:** `apps/alert-engine/src/index.ts` (line 16–22):
- Open two DB handles: `ownDb = new Database(config.ownDbPath, { create: true })` for writes
- Remove `DB_PATH=/app/data/market.db` write usage entirely

**File:** `docker-compose.yml` — `alert-engine` service:
- Add `ALERT_ENGINE_DB_PATH=/app/data/alert_engine.db`
- Keep `DB_PATH=/app/data/market.db` only if alert-engine needs to read market data (currently: NO — remove it)

### 4c. docker-compose.yml readonly enforcement

For services that remain reading market.db, add a new env flag `DB_READONLY=true` and confirm
their `bun:sqlite` open already uses `{ readonly: true }`. Confirmed current state:
- `kinh-dich-service/src/index.ts` line 16: `readonly: true, create: false` — already safe
- `macro-indicators/src/infrastructure/repositories.ts` line 59: `readonly: true` — already safe
- `technical-analysis/src/infrastructure/repositories.ts`: passes `db: Database` injected from `index.ts`

**File:** `apps/technical-analysis/src/index.ts`
- Verify DB opened with `readonly: true` (check in task 1307b)

### 4d. Single-writer guard on mcp-server

**File:** `apps/mcp-server/src/infrastructure/db/schema.ts`
- Add startup check: verify no other process has write lock (PRAGMA locking_mode)
- Log warning to WORK channel if lock is contested at startup

**New file:** `apps/mcp-server/src/infrastructure/db/writerGuard.ts`
- `assertSingleWriter()`: runs `PRAGMA locking_mode = EXCLUSIVE` attempt, catches SQLITE_BUSY, sends WORK alert and throws
- Called in `initDatabase()` in development mode; logs only in production (non-fatal) to avoid blocking startup

## 5. New HTTP Endpoint Required

### POST /api/internal/alerts

mcp-server needs one new internal endpoint to accept alert records from alert-engine.

**DDD Layer:** `interface/` (new handler in `apps/mcp-server/src/index.ts` or dedicated router)
**Application layer:** new use case `storeExternalAlert.ts` under `application/usecases/`
**Domain:** existing `alertStore.ts` in `infrastructure/db/`

Payload (matches `StoredAlert` in alert-engine domain):
```json
{
  "stocks": "VCB",
  "signalTypes": "price_drop",
  "message": "...",
  "fingerprint": "sha256...",
  "severity": "high",
  "triggeredAt": "2026-04-25T10:00:00Z",
  "sentToTelegram": 1
}
```

Response: `{ "id": 42, "ok": true }` or `{ "ok": false, "error": "..." }`

This endpoint must be protected: only internal Docker network calls accepted (no external exposure via api-gateway). Add to `docker-compose.yml` — api-gateway does NOT route `/api/internal/*`.

## 7. Risk Assessment

| Risk | Likelihood | Severity | Mitigation |
|------|-----------|---------|-----------|
| alert-engine loses alerts during HTTP POST failure to mcp-server | LOW | MED | Retry with 3 attempts + exponential backoff; local alert_engine.db serves as queue |
| stock-price local cache diverges from market.db market_prices | LOW | LOW | stock_price.db is read-only cache for Tier3 fallback; VPS pushes are authoritative |
| technical-analysis reads stale market.db during mcp-server write | LOW | LOW | WAL mode allows concurrent readers safely — readers never blocked |
| writerGuard blocks mcp-server startup in test | NONE | NONE | Guard skipped when `DB_PATH=:memory:` |
| Corruption recurs if alert-engine DB_PATH accidentally set to market.db | LOW | HIGH | CI check: alert-engine env must NOT contain `market.db` path |
