## 1. Problem Statement

### Root Cause of 90% UNKNOWN

`get_alert_accuracy` scores alerts on-demand at query time using `market_prices_history`.
UNKNOWN is returned in four cases (code: `alertAccuracy.ts`):

| Cause | Frequency |
|-------|-----------|
| `predictedDir === "neutral"` — signal type not `price_drop`/`price_surge`/`volume_spike` | HIGH — most alerts are `news_mention`, `report_new`, `chain_catalyst`, `watchlist-opportunity`, `position-danger` composite types — all map to "neutral" |
| No price record at or after alert time | MEDIUM — composite alerts from Alert Commander carry no single ticker price signal |
| No price record in 1–3 day window (and intraday fallback fails) | MEDIUM — VN market closed weekends, data gaps |
| Price change < 0.1% (noise threshold) | LOW |

**Core gap:** The current scorer only handles raw price-signal alerts (`price_drop`, `price_surge`, `volume_spike`). The two policy-defined alert types (`position-danger`, `watchlist-opportunity`) and all composite/Commander alerts have no outcome model at all. They always score UNKNOWN. These represent the majority of fired alerts.

### Secondary Gap: No Persistent Outcome

Scoring is computed at query time — never written back to the DB. There is no `outcome` column on the `alerts` table. The existing `resolved_at` / `resolution_notes` columns are for manual user resolution, not automated accuracy tracking.

Contrast: `agent_signals` table has `outcome`, `outcome_at`, `outcome_detail` (added Task 244). `cascade_rule_hits` has `outcome_correct`, `price_impact_3d`, `price_impact_7d`. The `alerts` table has neither.

## 2. What "Alert Accuracy" Means Per Alert Type

### 2a. `position-danger` (3-condition rule: stopLossHit + singleDayDrop + newsSentiment < -0.5)
- Prediction: "this position is at risk of further loss in the near term"
- Evaluation window: **3 trading days** post-alert
- HIT: price continues ≤ 0% from alert price over 3d (loss not reversed)
- MISS: price recovers +2% or more from alert price within 3d
- AMBIGUOUS: price moves between -2% and +2% → UNKNOWN

### 2b. `watchlist-opportunity` (4-condition rule: kinhDich BUY + sentiment ≥ 0.3 + majority BUY)
- Prediction: "upside opportunity within short-to-medium term"
- Evaluation window: **5 trading days** post-alert
- HIT: price rises ≥ 1% from alert price within 5d
- MISS: price drops ≥ 1% from alert price at end of 5d window
- AMBIGUOUS: price change < 1% → UNKNOWN

### 2c. Raw price-signal alerts (`price_drop`, `price_surge`, `volume_spike`)
- Already handled by existing scorer (alertAccuracy.ts)
- Keep existing logic, extend to write outcome back to DB

### 2d. Multi-signal composite alerts (severity escalation: 2+ signals)
- Use primary signal direction (existing `alertPredictedDirection` logic)
- Same evaluation window as the primary signal type

## 3. Functional Requirements

### FR-1: `outcome` column on `alerts` table
Add 3 columns to `alerts` table (idempotent migration):
```
outcome        TEXT  — NULL | 'hit' | 'miss' | 'unknown'
outcome_at     TEXT  — ISO 8601 when outcome was written
outcome_detail TEXT  — e.g. "price +2.3% in 3d" or "neutral signal"
```

### FR-2: Alert type classifier
Pure domain function that maps an `alerts` row to its evaluation parameters:
```
alertType: 'position-danger' | 'watchlist-opportunity' | 'price-signal' | 'composite' | 'unscoreable'
evalWindowDays: number
hitThresholdPct: number (signed — negative for position-danger)
direction: 'up' | 'down' | 'neutral'
```

Mapping is driven by `signals_json` content and `message` text (Commander alerts may not have structured signals).

### FR-3: `alertOutcomeJob` — daily cron
Scheduler job. Runs daily post-market-close (same time slot as `signalOutcomeJob` — post 08:00 UTC).

Logic:
1. Query `alerts` WHERE `outcome IS NULL` AND `triggered_at <= NOW - evalWindowDays`
2. For each alert: classify alert type → compute eval window → query price history
3. Score → write `outcome`, `outcome_at`, `outcome_detail`
4. Return `{ evaluated, hit, miss, unknown, skipped }`

### FR-4: `get_alert_accuracy` tool upgrade
Extend existing tool to:
- Read `outcome` column when present (fast path — no real-time price lookup)
- Fall back to current on-demand scoring for rows where `outcome IS NULL` (within eval window, not yet resolved)
- Add `summary_by_type` breakdown in output (position-danger vs watchlist-opportunity vs price-signal)

### FR-5: MCP tool `mark_alert_outcome` (manual override)
Tool for user/Commander to manually mark outcome:
- Input: `alertId: string`, `outcome: 'hit' | 'miss'`, `notes?: string`
- Writes `outcome`, `outcome_at`, `outcome_detail`
- Guards: reject if `outcome` already set (unless `force: true`)

## 4. Non-Functional Requirements

| NFR | Requirement |
|-----|-------------|
| NFR-1 Performance | `alertOutcomeJob` must complete < 5s for 500 alerts |
| NFR-2 Idempotency | Job re-run must not overwrite existing outcomes (WHERE outcome IS NULL) |
| NFR-3 Data integrity | Outcome write in SQLite transaction per batch |
| NFR-4 Market hours | Eval only when `triggered_at + evalWindow` < `NOW` — no premature scoring |
| NFR-5 Weekend gaps | VN market closed Sat/Sun — `evalWindowDays` counts trading days, not calendar days (or use 7 calendar days for 5 trading days equivalent) |
| NFR-6 Price data dependency | If `market_prices_history` has no data for the eval window → `outcome = 'unknown'`, do not retry indefinitely. Cap at 14 calendar days then write 'unknown'. |

## 5. Edge Cases

| Case | Handling |
|------|----------|
| Alert fired for non-HOSE stock (UPCOM with thin data) | Price lookup fails → `outcome = 'unknown'` + detail "no price data" |
| Alert fired outside trading hours (e.g. overnight Commander alert) | `triggered_at` baseline price = first price after alert → OK |
| `signals_json` is NULL (Commander narrative alerts) | Classifier returns `unscoreable` → `outcome = 'unknown'` |
| `affected_actions_json` has multiple tickers | Use first ticker only (existing pattern from alertAccuracy.ts) |
| Ticker delisted / halted during eval window | Price lookup fails → `outcome = 'unknown'` |
| Alert resolved by user before job runs | `resolved_at` set → still score accuracy separately (resolution != accuracy) |
| `position-danger` alert for watchlist stock (not held) | Still scoreable — direction inference is stock-agnostic |

## 8. Blockers — PO Decision Required

### BLK-1: HIT threshold for `watchlist-opportunity` — is 1% gain in 5d meaningful?
VN stocks move 5–7% on a good day. 1% may be too low (noise). PO to decide: **1% or 3%?**
> Blocks: FR-2, FR-3, AC-7

### BLK-2: Manual override scope — can Alert Commander call `mark_alert_outcome`?
Tool FR-5 is designed for user + Commander. If Commander auto-marks based on its own chain verification, that changes the feedback loop design (Commander outcome = ground truth vs price = ground truth).
> Blocks: FR-5, AC-5

### BLK-3: Treat `position-danger` HIT as bad news (user lost money) — should it Telegram-notify?
If position-danger is confirmed HIT (price kept falling), should the system send a follow-up alert "your stop-loss call was correct — position still at risk"? Or silent?
> Blocks: alertOutcomeJob notification step

### BLK-4: `unscoreable` alerts — are Commander narrative alerts (no signals_json) worth tracking?
Currently ~30-40% of fired alerts come from Alert Commander with rich narrative but no structured `signals_json`. These will always be `unknown`. PO to decide: (A) accept unknown, (B) have Commander set a signal type on all fired alerts, (C) build NLP direction extractor from message text.
> Blocks: FR-2 classifier, UNKNOWN rate target in AC-4
