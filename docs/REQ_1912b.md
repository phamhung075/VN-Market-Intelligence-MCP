## §1 Goal & Scope

Rewrite `apps/alert-engine/` from TS/Bun to Go 1.22. The crash vector is `bun:sqlite`
(synchronous `Database` opened at process startup in `index.ts:8` and all repository
CRUD ops). Replacing with `database/sql` + `mattn/go-sqlite3` eliminates the JSC GC
teardown SIGABRT/SIGSEGV that has recurred across 21 days of QA cycles.

**DDD layer map (TS source → Go package):**

| TS source | Go package |
|-----------|-----------|
| `domain/models.ts` — StoredAlert, AlertRequest, AlertSeverity, CooldownConfig, EvaluateAlertResult | `pkg/domain/models.go` — plain structs, no deps |
| `domain/errors.ts` — AlertEngineError, AlertSuppressedError | `pkg/domain/errors.go` — sentinel errors |
| `domain/services.ts` — computeFingerprint (djb2), shouldSuppressAlert, isDuplicate | `pkg/domain/services.go` — pure logic, no I/O |
| `domain/repositories.ts` — AlertRepositoryPort, MutePort, TelegramPort | `pkg/domain/ports.go` — Go interfaces |
| `infrastructure/repositories.ts` — SQLiteAlertRepository, SQLiteMuteRepository, initAlertTables | `pkg/infrastructure/sqlite.go` — `database/sql` + `mattn/go-sqlite3`, WAL mode |
| `infrastructure/telegram.ts` — TelegramClient | `pkg/infrastructure/telegram.go` — `net/http` POST |
| `infrastructure/config.ts` — loadConfig, ServiceConfig | `pkg/infrastructure/config.go` — `os.Getenv` |
| `application/usecases.ts` — EvaluateAlertUseCase | `pkg/application/evaluate.go` |
| `application/dtos.ts` — EvaluateAlertRequest, EvaluateAlertResponse | `pkg/application/dtos.go` |
| `interface/handlers.ts` — createRouter (POST /evaluate, GET /health) | `pkg/interface/http/router.go` — `net/http` or `chi` |

**Module path:** `github.com/vn-market-intelligence/alert-engine`

**Port:** 5006 (unchanged). Env var `PORT` respected.

**DB invariant:** `alert_engine.db` is the sole write target. Schema is
`CREATE TABLE IF NOT EXISTS alert_engine_records` + `alert_mutes` (idempotent DDL, run
at startup). No shared writer conflict.

## §2 Acceptance Criteria

**AC-1 — Dockerfile builds cleanly.**
Multi-stage: `golang:1.22-alpine` + `apk add gcc musl-dev` (CGO required) → final
`alpine:3.19`. `docker build` exits 0 with no warnings about CGO.

**AC-2 — GET /health returns byte-identical JSON.**
Response: `{"status":"ok","service":"alert-engine","port":5006}`.
HTTP 200, `Content-Type: application/json`. Matches TS handler verbatim.

**AC-3 — POST /evaluate request validation parity.**
Missing `stock` → 400 `{"error":"stock is required"}`.
Missing `message` → 400 `{"error":"message is required"}`.
Invalid severity → 400 `{"error":"severity must be low|medium|high|critical"}`.
Malformed JSON body → 400 `{"error":"Invalid JSON body"}`.
All four cases sourced from `interface/handlers.ts` integration tests (TS fixture parity).

**AC-4 — POST /evaluate stock normalisation.**
Handler trims + uppercases `stock` field before passing to use case (matching TS
`body.stock.trim().toUpperCase()`). Test: POST `{"stock":"vcb",...}` → use case receives `"VCB"`.

**AC-5 — POST /evaluate response shape byte-identical.**
Fired response: `{"fired":true,"cooldown_sec":1800,"reason":"alert fired","fingerprint":"<8-hex>"}`.
Suppressed response: `{"fired":false,"cooldown_sec":1800,"reason":"<reason>","fingerprint":"<8-hex>"}`.
All four fields present on every 200 response. `fingerprint` is 8 lower-hex chars.
Caller interface in `clients.ts` (`AlertEvaluateResponse`) must parse without change.

**AC-6 — computeFingerprint produces Go-identical output to TS djb2.**
Test table: reproduce the three TS unit test cases in Go `testing.T`:
- deterministic 8-hex string for same input;
- order-independent for `signalTypes` (`["a","b"]` == `["b","a"]`);
- differs for different stocks.
Go output must be numerically identical to TS output for the same inputs (djb2 hash
algorithm ported exactly: seed 5381, `hash = ((hash << 5) + hash) ^ charCode`, unsigned
32-bit mask, lowercase hex with zero-padding to 8 chars).

**AC-7 — shouldSuppressAlert parity via shared fixture values.**
Five TS test cases ported to Go table-driven tests:
1. No suppress for first alert (empty recentAlerts).
2. Suppress when same signal type within cooldown window (10min ago, cooldown=30min).
3. No suppress for `severity=critical` non-MACRO.
4. Suppress for `severity=critical` + `actionCode=MACRO`.
5. Suppress when daily cap reached (3/3 today, cooldown window short enough to skip rule 1).

**AC-8 — isDuplicate parity.**
Two cases: false for empty list; true when fingerprint present.

**AC-9 — EvaluateAlertUseCase orchestration parity.**
Three use-case unit tests with mocked ports (Go interfaces injected):
1. Fires + stores alert when no suppression (mute=false, dedup=false, cooldown=false).
2. Does not fire when stock is muted.
3. Does not fire when fingerprint is duplicate within 60min window.

**AC-10 — SQLite infrastructure parity.**
`initAlertTables` runs idempotently (twice) on fresh DB without error.
`getRecentAlerts`, `countTodayAlerts`, `storeAlert`, `hasDuplicateFingerprint`,
`isStockMuted` behave identically to their TS counterparts for the same SQL inputs.
WAL mode DSN: `?_journal=WAL&_busy_timeout=5000`.
DB opened at process startup (not per-request).

**AC-11 — Alert outcome schema migration parity.**
`alert_engine_records` schema includes `outcome`, `outcome_at`, `outcome_detail` columns
(sourced from `1847d-A-schema-store.test.ts`). Migration is idempotent; index
`idx_alerts_outcome_pending` created. `readPendingOutcomeAlerts` (90-day lookback,
NULL-outcome only, limit option) and `writeAlertOutcome` (idempotent, returns false
on second call) ported to Go with full test coverage.

**AC-12 — mcp-server Vitest suite unchanged.**
`apps/mcp-server` Vitest count remains 8804/8804 (or current passing baseline) after
Go image is deployed. No change to `clients.ts`, `bbAlertScanJob.ts`, or
`alertScanParallelJob.ts`.

**AC-13 — Telegram client silent-skip on missing config.**
When `TELEGRAM_BOT_TOKEN` or channel ID is empty, `Send()` returns false without error.
Matches TS `TelegramClient.send()` silent-skip behaviour.

**AC-14 — log/slog JSON structured logging.**
All log output uses `log/slog` JSON handler. Field schema: `level`, `msg`, `time` +
context fields. No `fmt.Println` or unstructured output in production paths.

**AC-15 — API gateway aggregator shows 9/9 healthy.**
After Go image deployed, `GET http://localhost:4000/health` shows `alert-engine` as
healthy. Gateway Vitest suite (Phase 1) remains green.

**AC-16 — Go tests authored BEFORE implementation (R5 mitigation).**
All Go `testing.T` files committed with `// TODO: implement` stubs before any domain or
infrastructure code is written. CI must show red-then-green progression in commit history.

`maxAlertsPerStockPerDay=3`, fingerprint of `{stock:"VCB", signalTypes:["price_surge"],
message:"test"}` must equal `computeFingerprint` Go output for same input.

## §4 Non-Functional Requirements

**NFR-1 — CGO Dockerfile.**
`golang:1.22-alpine` build stage: `apk add --no-cache gcc musl-dev`. `CGO_ENABLED=1`.
Final stage: `alpine:3.19` + `ca-certificates`. Binary statically linked where possible.

**NFR-2 — WAL mode DSN.**
Alert engine DB DSN: `file:<path>?_journal=WAL&_busy_timeout=5000&_foreign_keys=on`.
DB connection opened once at startup, closed on OS signal (SIGINT/SIGTERM).

**NFR-3 — Structured logging.**
`log/slog` JSON handler, defaulting to `INFO` level. Level overrideable via `LOG_LEVEL`
env var. All error paths log at `ERROR`, HTTP request summaries at `INFO`.

**NFR-4 — Port 5006.**
`PORT` env var respected. Default 5006. Matches TS `config.ts` loadConfig.

**NFR-5 — ENV vars.**
Exact names from TS `config.ts`: `PORT`, `DB_PATH`, `ALERT_ENGINE_DB_PATH`,
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_INFO_MARKET_GROUP_ID`, `TELEGRAM_INFO_WORK_CHANNEL_ID`,
`TELEGRAM_REPORT_BUG_CHANNEL_ID`. No new env vars introduced.

**NFR-6 — Graceful shutdown.**
HTTP server closes with `Shutdown(ctx)` on SIGINT/SIGTERM. In-flight requests drain
within 5s. DB connection closed after server shutdown.

## §7 Risks

**R5 (brief §8) — Dedup/cooldown drift during migration. Likelihood: MEDIUM. Impact: HIGH.**
Mitigation already encoded in AC-16 and §3: Go tests authored from TS fixtures BEFORE
implementation. Developer must produce red CI run (tests compile, tests fail) before
writing any domain logic.

**D-1 — Response shape mismatch between internal DTO and clients.ts consumer.**
`EvaluateAlertResponse` (internal DTO, source of test fixtures) has fields
`{fired, cooldown_sec, reason, fingerprint}`. `AlertEvaluateResponse` in `clients.ts`
(the actual consumer) expects `{alert_id, code, fired, reason, telegram_sent}`.
The TS handler returns the internal DTO and `clients.ts` currently reads only `fired`
and `reason` from the response (other fields are typed but may be empty). Go handler must
satisfy both shapes or the developer must confirm which fields clients.ts actually
consumes at runtime. PO does not need to resolve — architect or developer resolves during
implementation. BA flags here to prevent a silent contract break.

**D-2 — `bbAlertScanJob.ts` and `taAlertScanJob.ts` do NOT call `POST /evaluate`.**
Inspection of `bbAlertScanJob.ts` and `alertScanParallelJob.ts` shows these jobs write
directly to the local `alerts` table in `market.db` via `bun:sqlite`, and call
`computeTAIndicators` (TA service), NOT `evaluateAlert` (alert-engine service).
The alert-engine's `POST /evaluate` is the dedup/cooldown/Telegram path for a different
caller. Developer must confirm which scheduler jobs actually call alert-engine before
assuming scheduler integration test scope. This does not block the Go migration itself —
the HTTP API is unchanged regardless.
