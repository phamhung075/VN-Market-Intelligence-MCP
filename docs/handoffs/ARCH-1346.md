## 1346c — Alert Quality Bugs

### Bug 1320: Volume Spike Calibration (avgVolume includes current session)

**Root cause confirmed:**

Two separate code paths compute `avgVolume`. The push-prices path in `server.ts` is already correct. The `scanMarket` path is broken.

**File to fix:**
- `apps/mcp-server/src/application/usecases/scanMarket.ts`
  - Function `getAvgVolumeSync`, lines 103–128
  - Bug: `ORDER BY fetched_at DESC LIMIT 20` pulls the last 20 rows regardless of date. During an open session this includes today's intraday rows, inflating the rolling average. The ratio then approaches `(N+1)/N` for uniform intraday volume, producing the observed 5.909090 cluster (65/11 = (10+1)/10 ≈ 1/N at N=11 rows of today + 10 prior).
  - The `server.ts` push-prices path (lines 677–686) already uses `WHERE ... AND substr(fetched_at, 1, 10) < ?` to exclude today. `scanMarket.ts` must match this pattern.

**Fix (domain — pure SQL change, no DDD violation):**

Replace the query in `getAvgVolumeSync` to exclude the current UTC date:

```sql
-- BEFORE (line 111-116):
SELECT volume
FROM market_prices_history
WHERE code = ?
ORDER BY fetched_at DESC
LIMIT ?

-- AFTER:
SELECT AVG(day_vol) as avg_vol FROM (
  SELECT MAX(volume) as day_vol
  FROM market_prices_history
  WHERE code = ? AND substr(fetched_at, 1, 10) < ?
  GROUP BY substr(fetched_at, 1, 10)
  ORDER BY substr(fetched_at, 1, 10) DESC
  LIMIT 20
)
```

The function signature changes to accept `todayUtc: string` (injectable for tests) or computes it internally.

**Test:**
- `apps/mcp-server/src/__tests__/1320-volume-avg-excludes-today.test.ts`
- Seed `market_prices_history` with 10 rows for today + 10 rows for T-1. Assert `getAvgVolumeSync` equals avg of T-1 rows only. Assert no 5.909090 ratio fires.

### Bug 1321: Sentiment Negation — "lỗ" not in bearish keyword list

**Root cause confirmed:**

`apps/mcp-server/src/domain/services/sentimentClassifier.ts`

Scanning `VN_BEARISH` (lines 125–252): standalone `"lỗ"` (loss, as in operating loss) is NOT present. The compound phrases `"thua lỗ"` (weight 2) and `"khoản lỗ"` (weight 2) exist but `"lỗ"` alone does not fire.

For headline `"VIX Q1 lợi nhuận lỗ 63% giảm"`:
- Bullish matches: none that dominate — `"tăng"` could be absent, OR matched via partial word in other context. (Actual issue: "lợi nhuận" is not in bullish list, but "tăng" (w1) may be absent. The real gap is that "lỗ" alone w2 + "giảm" w1 = 3 bearish, which should already win unless there is a cross-match issue.)
- The `findOccurrences` function uses word-boundary check (`/\s/.test(...)` or punctuation). If the word boundary logic allows "lỗ" to match inside "lợi" via Unicode handling, this is the deeper bug.

**Investigation note:** `normalizeText` in `stockAliases.ts` strips diacritics, but `sentimentClassifier.ts` uses `text.toLowerCase()` without diacritic stripping. Vietnamese diacritics remain in the lowercased text. "lỗ" with diacritics will only match the literal diacriticed form. Possible root: in some RSS feeds, "lỗ" arrives with different Unicode normalization (NFD vs NFC) — `"lỗ"` (NFC) vs `"lơ\u0303"` (NFD). If the RSS delivers NFD and the keyword table has NFC, no match occurs.

**Fix:**
1. Add `{ word: "lỗ", weight: 2 }` to `VN_BEARISH` list (standalone loss, covers "lỗ 63%", "lỗ ròng", etc.).
2. Add `{ word: "lợi nhuận âm", weight: 3 }` to `VN_BEARISH` (negative profit = loss explicitly stated).
3. Normalize text to NFC before matching: in `classifySentiment`, change `const lower = text.toLowerCase()` to `const lower = text.normalize("NFC").toLowerCase()`.

**File:** `apps/mcp-server/src/domain/services/sentimentClassifier.ts`
- Line 514: add `.normalize("NFC")` before `.toLowerCase()`
- Lines 125–252: insert new bearish keywords

**Test:**
- `apps/mcp-server/src/__tests__/1321-sentiment-negation-loss.test.ts`
- Assert: `classifySentiment("VIX Q1 lợi nhuận lỗ 63% giảm")` → `direction: "bearish"`
- Assert: `classifySentiment("lợi nhuận tăng 20%")` → `direction: "bullish"` (no regression)
- Assert: `classifySentiment("giảm 30% so với")` → `direction: "bearish"`

## 1346d — Infrastructure Reliability Bugs

### Bug 1316: PDF Download Circuit Breaker (5 concurrent timeouts, no CB trip)

**Root cause confirmed:**

The CB is correctly wired in `fetchParseAndStoreBctc.ts` (lines 234–248) via `breakers.ssc.execute()`. The CB does increment on `ECONNABORTED`/`ETIMEDOUT` failures (pdf.ts lines 310–311 re-throw them, and `breakers.ssc.execute()` calls `_onFailure()` in the catch branch).

**Actual bug:** The 5 simultaneous timeouts occur because `bctcQueueEnricherJob.ts` or `bctcReparseJob.ts` triggers multiple concurrent `fetchParseAndStoreBctc` calls in `Promise.all()` or a fast loop. All 5 calls hit the SSC URL simultaneously, all timeout at the same wall-clock second, and all 5 increment the CB counter. However, `breakers.ssc.failureThreshold = 3` — so the CB **should** open on the 3rd failure. The symptom "no CB trip" suggests either:
  - The 5 calls are launched before any `_onFailure()` completes (race between concurrent promises and `_consecutiveFailures`)
  - OR the default HTTP client (`makeDefaultHttpClient()`) is calling the SSC URL directly instead of the VPS endpoint

**Check needed:** Examine `bctcQueueEnricherJob.ts` to see if concurrent fetches are launched.

The CB `execute()` is NOT thread-safe for concurrent calls — `_consecutiveFailures++` is synchronous but if 5 promises are all in flight before any resolves/rejects, all 5 will read `_consecutiveFailures=0` at start, and only increment sequentially as each awaits. The CB may open after the 3rd reject resolves, but calls 4 and 5 are already in `fn()` (not in the `execute()` guard path). This is a race condition.

**Fix:**
1. In `bctcQueueEnricherJob.ts`: replace `Promise.all(codes.map(fetchParseAndStoreBctc))` with a sequential loop or `Promise.allSettled` with CB-state pre-check before each item.
2. Add a `beforeExecute` guard in `CircuitBreaker.execute()`: check `this._state` AFTER `_checkTimeout()` and reject early if `open`.
3. Add observability: log `[circuitBreaker] state changed CLOSED→OPEN` whenever `_openCircuit()` is called.

**Files to fix:**
- `apps/mcp-server/src/infrastructure/circuitBreaker.ts` — add state-change logging in `_openCircuit()`, `_onSuccess()` transition to closed
- `apps/mcp-server/src/scheduler/financial-reports/bctcQueueEnricherJob.ts` — serialize or CB-gate concurrent PDF fetches

**Test:**
- `apps/mcp-server/src/__tests__/1316-pdf-cb-concurrent.test.ts`
- Simulate 5 concurrent `breakers.ssc.execute()` calls all rejecting with ETIMEDOUT
- Assert: CB opens after 3rd failure
- Assert: 4th and 5th calls throw `CircuitOpenError` immediately (not network calls)

### Bug 1317: submit_feedback BUG Channel Retry

**Root cause confirmed:**

`apps/mcp-server/src/interface/mcp/tools/system/feedbackTools.ts`, lines 62–82.

The Telegram send is wrapped in `try { ... } catch { /* best-effort */ }` (line 82). Any transient error (429, 503, ECONNRESET) is silently swallowed. `msgId` stays 0 and the caller sees `"BUG channel: failed"` in the response but no retry occurs and no queue fallback exists.

**Fix:**
Add a retry wrapper around `sendTelegramBug(msg)` with exponential backoff. The handoff specifies 1 retry with 2s delay for the minimal fix. The fuller approach (3 retries + DB queue) is deferred to a follow-up sprint.

Minimal fix for this sprint:
```typescript
// Replace line 81:
msgId = await sendTelegramBug(msg);

// With:
msgId = await retryOnTransient(() => sendTelegramBug(msg), 1, 2000);
```

Where `retryOnTransient` is a small local helper (or imported from `infrastructure/resilience.ts` if it exists).

**DDD layer:** `feedbackTools.ts` is `interface/mcp` — calling a retry helper from `infrastructure/` is permitted.

**Files to fix:**
- `apps/mcp-server/src/interface/mcp/tools/system/feedbackTools.ts`
  - Lines 62–82: add retry wrapper around `sendTelegramBug(msg)`
  - Log retry attempts: `logger.warn("[feedback] Telegram send failed, retrying...", { attempt })`

**Test:**
- `apps/mcp-server/src/__tests__/1317-feedback-retry.test.ts`
- Mock `sendTelegramBug` to throw once then succeed
- Assert: second attempt succeeds, `msgId > 0`
- Mock `sendTelegramBug` to always throw

| Risk | Severity | Mitigation |

| Volume avg SQL change alters behavior for stocks with <5 closed days history | LOW | Preserve `MIN_HISTORY_ROWS = 5` guard — returns 0 (suppresses spike) when insufficient history |
