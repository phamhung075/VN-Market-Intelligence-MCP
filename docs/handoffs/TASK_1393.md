# TASK_1393 — volume_spike dedup fix: VRE 21 identical alerts in 23 min

## Status
IMPL DONE — commit `8e3feff8` on branch `task/1393-volume-spike-dedup-fix`

## Root Cause

**Push-prices handler in `server.ts` re-sent every generated alert to Telegram on every VPS push (~65 s cadence) regardless of `notified_telegram` state.**

The `storeAlerts` call uses `INSERT OR IGNORE`, so the DB row is correctly deduplicated via the deterministic 4h-bucket ID (`alert-VRE-volume_spike-2026-04-28T04`). However, `generateAlerts` still returns a fresh in-memory Alert object from the newly-detected signals. The push-prices loop iterated over all generated alerts and called `sendTelegramWork` + `markAlertNotified` for each — without first checking whether the row already had `notified_telegram=1`.

Timeline: VPS pushes every ~65 s → 21 sends in 23 min, all with identical message and values.

The intelligence cycle step E was NOT the source: its `shouldSuppressAlert` + `readUnnotifiedAlerts` chain is correct. The bug was entirely in the inline push-prices send path.

## Fix

### New function — `alertStore.ts`

```ts
export function shouldSkipAlreadyNotifiedAlert(alertId: string, db: Database = getDb()): boolean
```

Single `SELECT notified_telegram FROM alerts WHERE id = ? LIMIT 1`. Returns `true` (skip) when the row exists and `notified_telegram = 1`. Returns `false` in all other cases (new alert, unnotified alert → proceed with send).

### Guard in `server.ts` push-prices handler

```ts
if (shouldSkipAlreadyNotifiedAlert(alert.id, db)) {
  log.debug("[push-prices] alert already notified — skipped", { id: alert.id });
  continue;
}
```

Added before the `sendTelegramWork` call. If the alert was already sent on a prior push, the send is silently skipped. The existing `markAlertNotified` call after a successful send is unchanged.
