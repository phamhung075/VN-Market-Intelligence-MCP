### 3. Evening Report Generation Timing — ROOT CAUSE A (Startup Catchup Race)

**2026-04-28-evening.json** was generated at `2026-04-28T00:38:22.126Z` by the **startup-catchup job**, which fires 30s after boot if `15:30 UTC` passed on the previous day. At 00:38 UTC, VNINDEX in `market_prices` was still the 2026-04-18 value (market hadn't opened yet — open is 02:00 UTC). The report was stamped with stale VNINDEX and zero news/alerts because no trading-day data existed yet.

**2026-04-29-evening.json** was generated at `2026-04-28T20:57:46.144Z` (container restarted ~16:06 UTC; startup-catchup re-ran eveningSummaryJob 30s after boot because 15:30 UTC had already passed). At that point market_prices already had fresh 2026-04-28 VNINDEX — but the report still shows `fetchedAt: 2026-04-18`. This is suspicious and suggests the startup-catchup may have used a DB snapshot taken before the current container's market_prices was populated, OR the report filename `2026-04-29` was the date computed for "tomorrow's" evening summary by a bug in date calculation when run at 20:57 UTC VN+7 = 03:57 UTC+7 next day.

## Developer Fix — Root Cause A (task 1408)

**Branch:** `fix/1408-startup-catchup`
**Commit:** `36c9db26`
**Date:** 2026-04-28

### What was changed

**`apps/mcp-server/src/scheduler/jobs.ts`**

1. Added `eveningReportIsValid(reportsDir, nowMs)` — reads `YYYY-MM-DD-evening.json`
   for today's VN date, returns `true` only when `vnIndex.fetchedAt` is within 25h
   AND `newsCount > 0`.

2. Extended `shouldRunCatchup()` with an optional 7th parameter:
   `reportCheckFn?: () => boolean`. When provided and returns `true`, the catchup
   is skipped with log message `valid report already exists — skipping`.

3. In the production `setTimeout` (30s after boot), `eveningSummaryJob` catchup now
   passes `() => eveningReportIsValid()` as `reportCheckFn`. The race condition
   (container boots at 23:50 UTC day N, `15:30` window passed on day N, but VN date
   is day N+1 with no market data yet) is now blocked when a valid report for the
   VN date already exists on disk.

**`apps/mcp-server/src/__tests__/1408-startup-catchup-report-guard.test.ts`**

5 tests covering:
- AC-1a: valid report → skips (new behaviour, was failing RED)
- AC-1b: stale/missing report → runs
- AC-2: pre-market window (00:38 UTC < 15:30) → skips via window check (pre-existing)
- AC-3: no reportCheckFn → backward compatible (returns true)
- AC-4: cron row already exists → skips regardless of reportCheckFn
- AC-5: weekend + weekdayOnly → skips regardless

All 43 evening-summary / startup-catchup tests pass.

### What is NOT fixed here

- **Root Cause B** (2026-04-29 report still shows `fetchedAt: 2026-04-18` despite
  fresh DB) — needs further investigation of `assembleEveningSummary` date logic when
  called at 20:57 UTC (04:57 VN+7 next day).
- **Root Cause C** (foreign-flow circuit breaker OPEN, 43 failures) — separate task.
