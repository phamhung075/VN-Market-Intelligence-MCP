**FR-1 — DDD: domain**
Refactor `extractCashFlow()` to use `extractSplitBlockAll` (same helper used by `balanceSheetExtractor.ts`) for all 3 OCF sections (operating/investing/financing), replacing the current line-by-line `findValue` loop. Prerequisite for positional-drift detection.

**FR-2 — DDD: domain**
Implement positional-drift override guard on `operatingCF`, `investingCF`, `financingCF` grand totals, mirroring the 1908c pattern (`b6db5ef3`, `balanceSheetExtractor.ts:718-725`): if `sum(sub-items) / stated_total > 5` AND sub-items > 0, override with sub-item sum + emit `console.warn("[cashFlowExtractor] BCTC-1909a: <section> positional drift detected; overriding.")`. Threshold = 5 (same ratio as 1908c).

**FR-3 — DDD: domain**
Unit-multiplier detection via shared `JANITOR-014` helpers (`detectUnitMultiplier`, `extractNumber`). Cash flow PDFs may use tỷ (billion) or triệu (million) header — same detection pattern as balance sheet extractor.

**FR-4 — DDD: domain**
Confidence scoring aligned to `BCTC-1345b` schema: `confidence < 0.2` → `low_confidence` flag inserted; `confidence = 0` → skip insert (per `reference_low_confidence_handling.md`).

**FR-5 — DDD: domain (tests)**
New test file `apps/mcp-server/src/__tests__/1909a-cashflow-extractor-expansion.test.ts` with inline OCR mock fixtures (no PDF binary in repo):
- VNM Q4-2025 OCF block — multi-layout, page-spanning, must trigger drift override
- DIG Q4-2025 OCF block — same drift pattern (different scale)
- VCB Q4-2025 OCF block (bank layout, operating/investing/financing sections distinct) — regression guard, override must NOT fire
- All 38 baseline BCTC tests still pass (existing `044-bctc-cashflow.test.ts` + `1878a-ocf-column-migration.test.ts` + `1890a-get-cash-flow.test.ts`)

**NFR-1**
No new I/O dependencies. `extractCashFlow()` remains a pure domain function (zero I/O, domain layer).

**NFR-2**
`tsc 0` errors. Baseline 38 BCTC tests pass.

**Edge cases:**
- E-1: 3 OCF sections page-split across PDF pages — `extractSplitBlockAll` must handle merged text stream correctly (known risk per spec §6; same handling as balance sheet multi-page layout)
- E-2: Bank BCTC layout: operating CF section uses different VN label convention (`lưu chuyển tiền từ hoạt động kinh doanh` vs some banks use `hoạt động ngân hàng`) — regex patterns must accommodate both; fixture must include one bank ticker (VCB suggested per spec)
- E-3: Negative values (cash outflows) represented as parenthesised numbers `(800.000)` — `parseVnNumber` handles this; verify no regression in `extractNumber` helper after refactor
- E-4: `operatingCF = 0` legitimately (rare) — must NOT trigger drift override; guard condition requires both stated_total > 0 AND sub-item sum > 0

## Spec-time discoveries (4 items — architect/PO attention)

**SD-1 (architect note — rubber-stamp eligible):** `cashFlowExtractor.ts` current implementation is a flat `findValue` keyword-scanner (129 LOC). Migrating to `extractSplitBlockAll` (line-code positional mapping) requires the OCF PDF to have numeric codes on each line (e.g. code "20", "30", "40" for operating/investing/financing totals in VN BCTC format). Architect must confirm that VN cash flow PDFs consistently carry these numeric codes OR specify fallback strategy if some PDFs lack them (keyword-only fallback acceptable per existing pattern). Existing analog `balanceSheetExtractor.ts` uses code-based extraction as primary + keyword as secondary. **Recommendation: same dual strategy for cashFlowExtractor.**

**SD-2 (architect question — DB schema):** `get_bctc_ocf` spec includes `extraction_method` field in output. `cashFlowTool.ts` `CashFlowRow` interface does not include `extraction_method` column — it is not in the DB row type. Architect must confirm: (a) column exists in `financial_reports` table and was omitted from `CashFlowRow`, OR (b) `extraction_method` is a derived constant `"ocr_parsed"` for this tool. This must be resolved before 1909b-tool implementation.

**SD-3 (sequencing conflict — PM action):** `1909b-tool` FR-9 touches `agentBootstrap.ts` + `SKILL_MANIFEST.md` + `financial-analyst.md`, which are the same files modified by in-flight `1890a-B`. PM must ensure `1909b-tool` is sequenced AFTER `1890a-B` is merged (or combine into a single branch). Merge conflict risk is high if both execute concurrently.

**SD-4 (TASKS.md capacity — PM action):** TASKS.md is currently 79 lines (cap = 80L per WIP context). Adding 3 sub-task rows (1909a + 1909b + 1909c) will breach the 80L cap. PM must compact/archive at least 2-3 Done rows before inserting 1909 sub-tasks, or compact the Done section further. Flag: TASKS.md compaction required before 1909 PM entry.
