## 1. Blocker Resolutions

### BLK-1 — Equity curve not in resultJson: Decision = Option C (recompute on demand)

**Decision: Option C — recompute equity curve from trades[] on demand inside the tool handler.**

Rationale:

- Option A (add `equityCurve: number[]` to `BacktestReport` and serialise) requires a schema migration concern: all existing stored runs lack the field. Any export tool reading old records would receive `null` for the equity curve and still need a fallback recomputation path. Two code paths for one feature is not justified.
- Option B (always return "not available" error) satisfies zero AC criteria and ships broken behaviour. Rejected.
- Option C is pure domain logic: `trades` already contains `exitDate`, `positionWeight`, and `returnPct` — the exact three fields the engine uses at lines 301–307 of `backtestEngine.ts`. The recomputation is a deterministic fold with no DB access, no side effects, and no new types. It works equally for old and new runs. CPU cost for a large run (200 trades cap) is negligible.

**No changes to `BacktestReport`, `backtestEngine.ts`, or `BacktestRunRecord`.**

**Equity curve recomputation algorithm (pure, no DB):**

Input: `trades: TradeRecord[]` (from `BacktestReport` parsed out of `resultJson`)

```
1. Sort trades by exitDate ASC (same order the engine uses — localeCompare on ISO strings is correct)
2. equity = 1.0
3. equityCurve = [1.0]          // index 0 = starting value
4. for each trade t in sortedTrades:
     equity = equity * (1 + t.positionWeight * t.returnPct)
     equityCurve.push(equity)   // index i = equity after trade i
5. return equityCurve           // length = trades.length + 1
```

This is identical to lines 302–307 in `backtestEngine.ts`. The output is a `number[]` with `trades.length + 1` elements. For an empty trades array, the result is `[1.0]` (one element — the starting value, no changes).

CSV equity curve section format (when `includeEquityCurve=true`):
```
<blank line>
equity_curve
index,equityValue
0,1.000000
1,<value rounded to 6dp>
...
```

BLK-1 is fully unblocked. AC-2-7 is satisfied: when `includeEquityCurve=true`, the tool recomputes and appends the section rather than returning an error.

A new file matches the existing pattern of splitting by functional concern (compare `registerBacktestTools` vs `registerBacktestQueryTools` in the same file — already two functions for two concerns).

- The barrel `index.ts` is the only wiring point that needs both old and new exports. `registry.ts` adds one import line.

This function registers all three lifecycle tools (#123, #124, #125) in one call, consistent with how `registerBacktestQueryTools` registers two tools (#121, #122) in a single call.

### BLK-3 — UUID validation consistency: Decision = leave `get_backtest_run` as-is

**Decision: Do not change `get_backtest_run`'s `z.string().min(1)` to `.uuid()` in Sprint 1846.**

Rationale:

- Changing the Zod schema for an existing tool is a behaviour change: any caller passing a non-UUID string that currently reaches the DB (and gets a not-found response) would now receive a Zod validation error instead. That is a breaking change in error shape.
- The new tools (#123, #124, #125) are greenfield — using `.uuid()` from the start is correct and does not imply retroactive standardisation.
- Mixing the fix into this PR expands scope and introduces test maintenance for AC-122-3 (currently written to tolerate both Zod rejection and handler-level error).
- If standardisation is desired, it belongs in a dedicated housekeeping task with its own AC.

Sprint 1846 new tools use `z.string().uuid()` for all `id` parameters.

## 3. Interface Diffs

### `IBacktestResultRepository.ts` — additive change only

Add one method to the existing interface. All four existing methods are unchanged.

```typescript
export interface IBacktestResultRepository {
  saveRun(record: BacktestRunRecord): void;
  getRunsByStrategy(strategy: string, limit: number): BacktestRunRecord[];
  getRunById(id: string): BacktestRunRecord | null;
  getAllRuns(limit: number): BacktestRunRecord[];
  /** Delete a run by ID. Returns true if deleted, false if not found or on error. */
  deleteRun(id: string): boolean;
}
```

### `SqliteBacktestResultRepository` — new method

```typescript
deleteRun(id: string): boolean {
  try {
    const result = this.db
      .prepare(`DELETE FROM backtest_runs WHERE id = ?`)
      .run(id);
    return result.changes >= 1;
  } catch {
    return false;
  }
}
```

Key notes:
- `stmt.run(id).changes` is the Bun SQLite API for rows affected. Zero changes = not found. One change = deleted.
- `try/catch` returns `false` on any SQLite error, consistent with `getRunById` returning `null` on error (NFR-1-3).
- No logging inside the repo — error isolation only. The tool layer surfaces the user-facing message.

## 4. CSV Schema

### Tool: `export_backtest_run_csv` (#124)

**Trades section — always present:**

```
date,ticker,direction,entryPrice,exitPrice,returnPct,positionWeight,holdDays
```

| Column | Source | Rounding | Notes |
|--------|--------|----------|-------|
| `date` | `trade.exitDate` | none (ISO date string) | Settlement date, mirrors engine equity accumulation order |
| `ticker` | `trade.ticker` | none (string) | Uppercase ASCII, e.g. `VCB` |
| `direction` | `trade.direction` | none (`"BUY"` or `"SELL"`) | |
| `entryPrice` | `trade.entryPrice` | `.toFixed(2)` | 2 decimal places |
| `exitPrice` | `trade.exitPrice` | `.toFixed(2)` | 2 decimal places |
| `returnPct` | `trade.returnPct` | `.toFixed(6)` | 6 decimal places |
| `positionWeight` | `trade.positionWeight` | `.toFixed(6)` | 6 decimal places |
| `holdDays` | derived | floor at 0 | `Math.max(0, Math.round((new Date(trade.exitDate).getTime() - new Date(trade.entryDate).getTime()) / 86_400_000))` |

**Sort order:** `exitDate` ASC before emitting rows (same `localeCompare` sort used by the engine).

**Null handling:** No nullable fields exist in `TradeRecord` — no null handling required in the trades section.

**Empty trades:** Header row only, no data rows, no error.

**Equity curve section — conditional on `includeEquityCurve=true`:**

```
\n
equity_curve\n
index,equityValue\n
0,1.000000\n
1,<equityCurve[1].toFixed(6)>\n
...
```

The blank separator line is a single `\n` — one empty line between the trades section and the equity header. The section header `equity_curve` is a single-column label line. Index 0 is always `1.000000` (starting equity). Values use `.toFixed(6)`.

**Output content block:**

```typescript
return { content: [{ type: "text" as const, text: csvString }] };
```

Note: the CSV output block does NOT wrap in `JSON.stringify`. It returns the raw CSV string as `text`. This is the correct deviation from the standard JSON response pattern — the tool is explicitly a CSV exporter.

**CSV quoting:** No quoting required. All field values are numeric, ISO dates, or uppercase ASCII ticker/direction codes. No commas or embedded quotes are possible in the current data model. Quoting is not added preemptively.

## 5. Tool Specifications

### `delete_backtest_run` (#123)

**Zod schema:**
```typescript
{ id: z.string().uuid().describe("UUID of the backtest run to delete.") }
```

**Handler logic:**
```
1. getDb() inside handler (U-4 pattern)
2. new SqliteBacktestResultRepository(db)
3. repo.deleteRun(id) → boolean
4. if false → return { error: `Backtest run not found: ${id}` }
5. if true  → return { deleted: true, id }
```

**Response shapes:**
- Success: `{ "deleted": true, "id": "<uuid>" }`
- Not found: `{ "error": "Backtest run not found: <id>" }`
- Zod rejection (non-UUID): Zod validation error at framework level, never reaches handler

### `export_backtest_run_csv` (#124)

**Zod schema:**
```typescript
{
  id: z.string().uuid().describe("UUID of the backtest run to export."),
  includeEquityCurve: z.boolean().default(false).describe(
    "When true, appends an equity_curve section after the trades CSV."
  ),
}
```

**Handler logic:**
```
1. getDb() inside handler
2. new SqliteBacktestResultRepository(db)
3. run = repo.getRunById(id)
4. if !run → return { error: `Backtest run not found: ${id}` }
5. try { report = JSON.parse(run.resultJson) as BacktestReport }
   catch → return { error: `resultJson parse failed for run ${id}` }
6. trades = report.trades ?? []
7. sortedTrades = [...trades].sort((a, b) => a.exitDate.localeCompare(b.exitDate))
8. Build CSV header line
9. For each trade: build data row with holdDays derivation + rounding
10. if includeEquityCurve:
      recompute equityCurve from sortedTrades (Option C algorithm)
      append blank line + "equity_curve" + "index,equityValue" + data rows
11. return { content: [{ type: "text" as const, text: csvString }] }
```

### `compare_backtest_runs` (#125)

**Zod schema:**
```typescript
{
  ids: z.array(z.string().uuid()).min(2).max(5).describe(
    "Array of 2–5 backtest run UUIDs to compare side by side."
  ),
}
```

**Handler logic:**
```
1. getDb() inside handler
2. new SqliteBacktestResultRepository(db)
3. uniqueIds = [...new Set(ids)]  // dedup, preserve first-occurrence order
4. For each id in uniqueIds: run = repo.getRunById(id)
5. Collect all ids where run === null → missingIds[]
6. if missingIds.length > 0 → return { error: `Backtest runs not found: [${missingIds.join(", ")}]` }
7. Build comparison array: for each run, project the 11 fields
   - Ensure benchmarkReturn and sharpeRatio are serialised as null (not undefined) when absent
8. return { content: [{ type: "text" as const, text: JSON.stringify(comparisonArray, null, 2) }] }
```

**Null serialisation guard:** Use `run.benchmarkReturn ?? null` and `run.sharpeRatio ?? null` explicitly when building each comparison object. `JSON.stringify` drops `undefined` values but preserves `null` — the explicit coercion is required.

**Comparison object shape (per run):**
```typescript
{
  id: string;
  strategy: string;
  startDate: string;
  endDate: string;
  runAt: string;
  totalReturn: number;
  benchmarkReturn: number | null;
  maxDrawdown: number;
  sharpeRatio: number | null;
  winRate: number;
  tradeCount: number;
}
```

`resultJson` is excluded from all comparison objects (too large).

## 9. Risk Register

| Risk | Severity | Mitigation |
|------|----------|-----------|
| `stmt.run().changes` undefined in Bun SQLite — API differs from better-sqlite3 | Medium | Confirmed: Bun SQLite `Database.prepare().run()` returns `{ changes: number, lastInsertRowid: ... }`. Pattern already used in codebase (see other repos). |
| `JSON.parse(resultJson)` for large runs (200–500 KB) — blocking main thread | Low | MCP server is local stdio, single-user. No async path needed. `JSON.parse` is synchronous and fast for this size. |
| `compare_backtest_runs` N+1 reads (up to 5 `getRunById` calls) | Low | Max 5 IDs, each a primary-key lookup. SQLite PK lookups are sub-millisecond. No batching required. NFR-3-1 explicitly accepts this. |
| `new Set(ids)` order preservation | Low | `Set` iteration order is insertion order in JS/V8. First-occurrence order is guaranteed. |
| Equity curve recomputation divergence from original engine output | Low | Algorithm is a direct copy of lines 302–307 of `backtestEngine.ts`. Floating-point order is identical (same sort, same formula). No divergence possible unless `trades` are stored truncated to 200 by the engine cap. Truncation applies equally to both paths. |
| CSV raw string output (not JSON) differs from standard MCP tool response | Low | Deliberate and documented. The tool description must state the output is a CSV string. No downstream tool parses this as JSON. The `type: "text"` block is correct per MCP spec. |
| `holdDays` floor at 0 for `entryDate > exitDate` | Low | `Math.max(0, ...)` guard required. Data corruption guard, not a normal path. |
