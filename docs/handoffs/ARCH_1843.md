## Deliverable 1 — Real `combined-high-confidence` Strategy

### Design Decision: Option A chosen

**Chosen:** Option A — Pre-compute `Map<ticker, TADirection>` in `runBacktest` use case (application layer); close over it in the strategy's `signalFilter` via a factory function.

**Rejected:**
- Option B: Adds an optional hook (`enrichSignals?`) to `StrategyDefinition`, widening the domain interface unnecessarily. All three existing strategies would carry a hook they never use. The interface grows for one consumer.
- Option C: Computes EMA/RSI inside `SqliteBacktestSignalRepository.getSignals()`, which is an infrastructure layer performing business-rule computation (TA direction derivation). That inverts the DDD golden rule — infrastructure must not own domain logic. It also joins `daily_ohlcv` inside a signal repo that is documented as reading only from `kinhdich_readings`. Changing that contract affects all callers.

**Why Option A is correct:**
- The `StrategyDefinition` interface in `domain/backtesting/` stays narrow and unchanged. Zero domain interface churn.
- TA pre-computation is I/O and belongs in the application layer (`runBacktest.ts`) — precisely where other I/O (signal fetch, benchmark candle fetch, persistence) already lives.
- `runBacktestEngine()` stays synchronous and pure — it receives the fully-filtered signal array and never sees a DB handle.
- The closure pattern (`buildCombinedHighConfidenceStrategy(taMap)`) is a standard factory idiom: the registry becomes a map of factory functions for strategies that need context, and plain `StrategyDefinition` objects for strategies that don't. Both shapes implement the same `StrategyDefinition` interface — no callers change.
- The `Map<ticker, TADirection>` is cheap to build (one pass over candles per ticker) and fits easily in the application layer's existing pre-fetch block.

### TA Computation Rules (confirmed from REQ)

- **EMA-12 / EMA-26 crossover:** EMA-12 > EMA-26 → BULLISH; EMA-12 < EMA-26 → BEARISH; equal → NEUTRAL.
- **RSI-14:** value > 50 → BULLISH bias; value < 50 → BEARISH bias; exactly 50 → NEUTRAL.
- **Combined TA direction:** BULLISH when both EMA crossover AND RSI agree BULLISH; BEARISH when both agree BEARISH; NEUTRAL in all other cases (disagreement, or insufficient candles).
- **Insufficient data:** fewer than 26 candles for a ticker → `TADirection = "NEUTRAL"` for that ticker. Appends a warning to `BacktestReport.warnings`.
- **Date format:** use `daily_ohlcv.date` as `YYYY-MM-DD` strings (string-sortable, no `Date` object parsing needed for candle ordering — candles arrive pre-sorted ASC from the repo).

### Agreement Gate (from FR-3)

| Kinh Dich direction | TA direction | Position opened? |
|---------------------|--------------|------------------|
| BUY                 | BULLISH      | YES              |
| SELL                | BEARISH      | YES              |
| BUY                 | BEARISH      | NO               |
| SELL                | BULLISH      | NO               |
| BUY or SELL         | NEUTRAL      | NO               |

### Interface Changes

None to existing interfaces. One additive change only: a new type exported from `strategyRegistry.ts`.

```typescript
// New export in strategyRegistry.ts — domain layer
export type TADirection = "BULLISH" | "BEARISH" | "NEUTRAL";

// New factory function exported from strategyRegistry.ts
export function buildCombinedHighConfidenceStrategy(
  taMap: Map<string, TADirection>,
): StrategyDefinition;
```

`strategyRegistry` remains a `Record<string, StrategyDefinition>` but `combined-high-confidence` is no longer statically registered in it. Instead, `runBacktest.ts` builds the strategy at use-case time when the strategy ID is `"combined-high-confidence"`:

```typescript
// In runBacktest.ts — application layer only
let strategy: StrategyDefinition;
if (params.strategy === "combined-high-confidence") {
  const taMap = await computeTADirectionMap(deps.priceRepo, params);
  strategy = buildCombinedHighConfidenceStrategy(taMap);
} else {
  strategy = strategyRegistry[params.strategy];
  if (!strategy) throw new BacktestStrategyNotFoundError(params.strategy);
}
```

`BacktestStrategyNotFoundError` must also accept `"combined-high-confidence"` in its available list — update the error constructor to include it.

### New File: `taComputation.ts`

**Location:** `apps/mcp-server/src/domain/backtesting/taComputation.ts`
**Layer:** `domain/backtesting` — pure computation, zero I/O, zero infrastructure imports.

Exports:
- `computeEMA(closes: number[], period: number): number[]` — returns EMA array, same length as input (initial values filled using SMA seed for the first `period` values).
- `computeRSI(closes: number[], period: number): number | null` — returns the final RSI value (last bar only), or `null` if insufficient data.
- `deriveTADirection(candles: DailyCandle[]): TADirection` — calls EMA-12, EMA-26, RSI-14; applies agreement rule; returns `TADirection`. Returns `"NEUTRAL"` if fewer than 26 candles.

This file is pure domain logic — no imports from infrastructure, no DB access.

### New Helper in `runBacktest.ts`

**Location:** `apps/mcp-server/src/application/usecases/runBacktest.ts`
**Layer:** application — I/O allowed, uses injected `priceRepo`.

```typescript
// Private helper inside runBacktest.ts
async function computeTADirectionMap(
  priceRepo: IBacktestPriceRepository,
  params: BacktestParams,
): Promise<Map<string, TADirection>>
```

This function:
1. Fetches candles for all tickers via `priceRepo.getCandles(ticker, extendedStartDate, params.endDate)`. The `extendedStartDate` must look back at least 26 additional trading days before `params.startDate` to seed EMA-26. Use `addCalendarDays(params.startDate, -40)` (40 calendar days ≈ 28+ trading days — safe margin).
2. Calls `deriveTADirection(candles)` from `taComputation.ts` for each ticker.
3. Returns the result map.
4. Collects tickers that resolved to `"NEUTRAL"` due to insufficient data and returns them separately so warnings can be added to the report.

The ticker set is derived from the already-fetched `rawSignals` (all unique `stockCode` values after the signal repo returns). This means `computeTADirectionMap` is called after `signalRepo.getSignals()` and iterates the unique tickers from that result set — not a static watchlist.

### Warning Propagation

When `combined-high-confidence` is run and any ticker has insufficient candles (< 26), append to `warnings`:
```
"combined-high-confidence: {TICKER} resolved to NEUTRAL TA direction (< 26 OHLCV candles available) — signal blocked"
```

The existing `"No trades executed"` warning path in `backtestEngine.ts` already handles the zero-trade case; no special handling needed there.

## Deliverable 2 — Fix Task 265 Test Failures (x3)

### Root Cause (confirmed via live test run)

The 3 failing tests all use the hardcoded hour string `"2026-04-03T10:00:00.000Z"`. The `recordMention()` function in `mentionVelocityStore.ts` runs a prune query after every insert:

```sql
DELETE FROM mention_velocity WHERE hour < ?
```

where the cutoff is `Date.now() - 30 * 24 * 60 * 60 * 1000`. On 2026-05-03, this cutoff is `2026-04-03T18:xx:xx.xxxZ`. The hardcoded `10:00:00` hour is earlier than the cutoff, so the row is inserted and immediately deleted. `getVelocity` returns null.

The test expects the row to survive — it was written when `"2026-04-03"` was in the future (or at most a few days old). The date has now drifted 30 days into the past.

### Fix (test-only change — production code is correct)

Replace the three hardcoded hour literals `"2026-04-03T10:00:00.000Z"` with relative offsets that are always within the 30-day window:

```typescript
// Replace this pattern (3 occurrences across the 3 failing tests):
const hour = "2026-04-03T10:00:00.000Z";

// With this pattern:
const hour = new Date(Date.now() - 1 * 60 * 60 * 1000).toISOString(); // 1 hour ago
```

Use distinct offsets per test to avoid cross-test collisions if tests run in the same Bun worker:

| Test | Replacement |
|------|-------------|
| "records a mention and retrieves velocity" | `Date.now() - 1h` |
| "upserts: second insert for same code+hour increments counts" | `Date.now() - 2h` |
| "stores different codes independently" | `Date.now() - 3h` |

The reputation store tests in the same file use a `"2026-04-03"` date too, but those tests pass because `reputationStore` has no prune-on-insert behavior. No change needed for the reputation tests.

**File changed:** `apps/mcp-server/src/__tests__/265-velocity-store.test.ts` only.
**Production code changed:** none.

Test file only — no layer assignment.

## Deliverable 4 — `computeBenchmarkReturn` DRY Cleanup

### Design

Extract the duplicated block into a module-level function in `backtestEngine.ts`:

```typescript
function computeBenchmarkReturn(candles: DailyCandle[]): number | null {
  if (candles.length < 2) return null;
  const first = candles[0]!.close;
  const last = candles[candles.length - 1]!.close;
  return (last - first) / first;
}
```

Both `runBacktestEngine()` (line 324) and `buildEmptyReport()` (line 372) replace their inline blocks with a single call to `computeBenchmarkReturn(benchmarkCandles)`.

**File changed:** `apps/mcp-server/src/domain/backtesting/backtestEngine.ts` only.

## Risks and Constraints

**RISK-1 (resolved):** Chosen Option A. `signalFilter` stays synchronous. TA data enters via closure — no signature change.

**RISK-2: EMA seed strategy.** EMA computation for the first `period` bars must use SMA as seed (standard practice). Using `close[0]` as seed produces incorrect early EMA values. Developer must implement the SMA-seed variant in `computeEMA`.

**RISK-3: Registry entry removal.** If the developer removes the `"combined-high-confidence"` literal from `strategyRegistry`, the `BacktestStrategyNotFoundError` message built from `Object.keys(strategyRegistry)` will omit it. Fix: either keep the entry as a metadata-only object (with `signalFilter` returning the kinh-dich-high-confidence behaviour as before, unused), or maintain a separate `KNOWN_STRATEGY_IDS` constant that includes all known IDs for error display.

**RISK-4: `computeTADirectionMap` ticker set.** The TA map must cover all tickers present in `rawSignals` — not just the `params.tickers` filter. The ticker filter is applied later inside the engine. If `computeTADirectionMap` only fetches for `params.tickers`, tickers present in signals but not in the explicit filter list will miss their TA lookup. Solution: derive the ticker set from `rawSignals.map(s => s.stockCode)` after the signal fetch.

**RISK-5: Extended date range for EMA warmup.** The `priceRepo.getCandles` call for TA pre-computation must extend `startDate` backwards by ~40 calendar days to provide enough candles to seed EMA-26. This extra fetch is only for TA computation — the engine's own `getCandles` calls (using `params.startDate`) are unaffected. The extended fetch is local to `computeTADirectionMap`.

**RISK-6 (out of scope, flagged): Phase 0 symlink failure.** `bun test` currently shows a 5th failure: `Phase 0 — Monorepo Scaffold > docs/ resolves from apps/mcp-server/ (symlink)`. This is a missing symlink at `apps/mcp-server/docs`. It is NOT in the Sprint 1843 scope (the task lists only Task 265 x3 and Task 1332 x1). PM should create a separate micro-task to restore the symlink. It will prevent `bun test` from ever returning 0 failures unless addressed.
