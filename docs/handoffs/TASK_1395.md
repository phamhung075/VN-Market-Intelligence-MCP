# TASK 1395 — BA Spec: Sector-Drop Alert Digest Grouping

**Status:** Architect design complete — ready for Developer
**Date:** 2026-04-28
**Author:** BA agent

---

## 1. Problem Statement

When VPS pushes a price batch containing 8 banking-sector tickers that all breach
the `price_drop` threshold simultaneously, the `push-prices` handler in
`apps/mcp-server/src/interface/mcp/server.ts` (lines 774–795) iterates `for
(const alert of alerts)` and calls `sendTelegramWork` once per alert. The result
is 8 separate Telegram messages with near-identical text fired within the same
second.

`alertGrouper.ts` (`groupRelatedAlerts`) already contains grouping logic but is
**never called** in the real-time push-prices path. It is only available as an
unused utility.

---

## 2. Root Cause Mapping (DDD Layers)

| Layer | Component | Current behaviour | Gap |
|-------|-----------|-------------------|-----|
| Domain | `alertGenerator.ts` | Generates one `Alert` per ticker per signal group | Correct — no change needed |
| Domain | `alertGrouper.ts` | Groups by overlapping signal types within time window | Exists but unused in real-time path |
| Application | `assembleAlertDigest.ts` | Groups by stock code for 21:00 digest | End-of-day only — no real-time grouping |
| Interface / Scheduler | `server.ts` push-prices loop | Sends one `sendTelegramWork` call per alert | Missing grouping step before send |

---

## 3. Grouping Key Specification

Two real-time alerts must be grouped into one digest message when **all three** of
the following conditions are true:

| Condition | Rule |
|-----------|------|
| **Signal type match** | The primary signal type is identical (e.g. both are `price_drop`, or both are `volume_spike`). Primary = `signals[0].type` after the alert is generated. |
| **Severity match** | Both alerts share the same severity level (`high` or `critical`). A `high` price_drop must not be merged with a `critical` price_drop — they represent materially different risk levels. |
| **Time window** | Both alerts are generated within the same **push-prices invocation** (same synchronous batch). This is the natural grouping boundary because VPS sends all tickers in one push payload. |

The existing `alertGrouper.ts` signal-overlap + 15-minute window approach is
**too broad** for the real-time path: it can merge alerts from different batches
and different signal types. The real-time grouper must use a narrower same-batch
key.

No sector metadata exists in the current schema. Grouping must be derived from
signal type + severity, not from a sector field.

---

## 4. Dedup Window

| Context | Window | Rationale |
|---------|--------|-----------|
| Real-time push-prices digest | Per-batch (single invocation) | All alerts in one `generateAlerts()` call are co-temporal by definition |
| Existing `alertGrouper.ts` | 15 minutes | Retained for its current use case (if any); not changed |
| End-of-day digest | 24 hours | Existing behaviour in `assembleAlertDigest.ts`; not changed |

## 5. Required Output Format

### 5a. Single-ticker case (no grouping needed, current behaviour preserved)

```
[QUAN TRỌNG] VCB alert: price_drop — VCB giảm 5.2%
```

### 5b. Multi-ticker grouped digest (new behaviour)

When N >= 2 tickers share the same signal type + severity in one batch:

```
[QUAN TRỌNG] price_drop — 8 mã cùng giảm mạnh
  • VCB, BID, CTG, VPB, TCB, MBB, ACB, HDB
```

Rules for the grouped message:
- Header line: `[{SEV_LABEL}] {signal_type} — {N} mã cùng {verb}`
- Verb mapping (Vietnamese):
  - `price_drop` → `giảm mạnh`
  - `price_surge` → `tăng mạnh`
  - `volume_spike` → `khối lượng đột biến`
  - `ta_overbought` → `quá mua`
  - `ta_oversold` → `quá bán`
  - Other / unknown → `kích hoạt cảnh báo`
- Ticker line: bullet list, all tickers on one line, space-separated with `,`
- If N > 10: show first 10, append `(+{N-10} mã khác)`
- No individual alert messages in the grouped output — only tickers

### 5c. Severity label mapping (existing, unchanged)

| Severity | Label |
|----------|-------|
| `critical` | `NGHIÊM TRỌNG` |
| `high` | `QUAN TRỌNG` |

## 6. Edge Cases

### EC-1: Mixed signal types in one batch

Tickers with `price_drop` are grouped separately from tickers with `volume_spike`
even if they arrive in the same VPS push. Each (signal_type, severity) pair
produces its own digest line or message.

Example batch: VCB=price_drop/high, SSI=volume_spike/high, BID=price_drop/high
Result: two separate Telegram messages — one for price_drop (VCB, BID), one for
volume_spike (SSI).

### EC-2: Mixed severities for the same signal type

VCB=price_drop/critical, BID=price_drop/high must NOT be merged. They produce
two separate messages — one critical, one high.

### EC-3: Single ticker for a given (signal_type, severity) pair

If only one ticker fires `volume_spike/high` in a batch, the existing single-ticker
message format is used (no grouping header). The grouped format only activates
when N >= 2.

### EC-4: Prices differ significantly across grouped tickers

The grouped message intentionally omits individual price values. The user can
query individual tickers via MCP tools (`get_stock_price`, etc.) after receiving
the grouped alert. Individual detailed messages must not be suppressed — they are
still stored in the `alerts` table via `storeAlerts`; only the Telegram send is
batched.

### EC-5: `notified_telegram` dedup guard still applies

The existing `shouldSkipAlreadyNotifiedAlert(alert.id, db)` guard must be applied
to each alert in the group before grouping. Alerts already marked
`notified_telegram = 1` are excluded from the group. The grouped Telegram send
marks all included alert IDs as `notified_telegram = 1` after a successful send.
If the Telegram send fails, no IDs are marked (consistent with current behaviour).

### EC-6: Empty group after dedup filter

If all alerts in a (signal_type, severity) group are already notified, no Telegram
message is sent for that group (silent skip, same as current per-alert behaviour).

### EC-7: Vietnamese special characters

Message text must pass through the existing `sendTelegramWork` call unchanged.
No HTML stripping or Markdown escaping changes are in scope for this task. The
diacritics rules from sprint 1412 apply as-is.

## 8. Blockers — PO Decisions (2026-04-28)

| # | Question | PO Decision |
|---|----------|-------------|
| B1 | Should the grouped message be sent to the **WORK** channel or a different channel? | **WORK channel** (`sendTelegramWork`). Grouped digests are real-time risk alerts, not market broadcasts. Channel routing is unchanged. `sendTelegramMarket` is not used for alert signals. |
| B2 | One Telegram message total per batch, or one per (signal_type, severity) pair? | **One per (signal_type, severity) pair.** A batch with `price_drop/high` x 3 and `volume_spike/high` x 2 produces exactly 2 messages. Each pair is a distinct risk event; merging them into one blob would destroy signal clarity. The spec assumption is confirmed as correct. |
| B3 | Is per-batch synchronous grouping acceptable, or is a delay-collect buffer queue needed? | **Per-batch synchronous — no buffer queue.** `generateAlerts()` already completes before the send loop begins, so grouping within the same push invocation adds zero wall-clock latency. Cross-batch buffering is explicitly out of scope and would introduce unnecessary state complexity. |

## 11. Architect Design

**Date:** 2026-04-28

### 11.1 Layer Assignment

The grouping logic is a pure transformation over an in-memory array of `Alert`
objects. It has no I/O and no DB dependency. Per dev-standards it belongs in
**domain/services**.

The formatted Telegram string is a presentation concern — it lives inside the
new helper as a private formatter, not exposed separately.

`server.ts` (interface layer) calls the new helper inline, replacing the current
`for` loop.

### 11.2 New File: `apps/mcp-server/src/domain/services/alertBatchGrouper.ts`

**Why a new file, not a change to `alertGrouper.ts`:** The BA spec explicitly
prohibits touching `alertGrouper.ts`. The existing function uses a 15-minute
time-window + signal-overlap model that is incompatible with the same-batch,
exact-key semantics required here. Extending it would break its current
contract. A new, narrowly scoped file keeps concerns separate.

#### Public API

```typescript
/**
 * Groups a flat list of high/critical Alert objects by (signal_type, severity)
 * within a single push-prices invocation (same-batch grouping).
 *
 * Pure function — no I/O.
 *
 * @param alerts - Pre-filtered list (high or critical severity only).
 * @returns      - Array of AlertBatchGroup, one per (signal_type, severity) pair.
 */
export function groupAlertsBySignalSeverity(alerts: Alert[]): AlertBatchGroup[];

/**
 * Formats one AlertBatchGroup into the Vietnamese Telegram string defined in
 * BA spec §5.
 *
 * Pure function — no I/O.
 */
export function formatBatchGroupMessage(group: AlertBatchGroup): string;

export interface AlertBatchGroup {
  /** Primary signal type — derived from alert.signals[0].type */
  signalType: string;
  severity: "high" | "critical";
  /** Ticker codes for all alerts in this group, in insertion order */
  tickers: string[];
  /** Original alert IDs — needed to mark notified_telegram = 1 */
  alertIds: string[];
}
```

#### Grouping Logic (`groupAlertsBySignalSeverity`)

```
key = `${alert.signals[0].type}::${alert.severity}`

For each alert in the input array:
  1. Derive key. If alert.signals is empty, use "unknown" as signal type.
  2. Look up key in a Map<string, AlertBatchGroup>.
  3. If found: push alert.actionCode to tickers, push alert.id to alertIds.
  4. If not found: create a new AlertBatchGroup entry.

Return Array.from(map.values()).
```

The Map preserves insertion order, so groups are emitted in the order the first
alert of each type was encountered — deterministic for tests.

#### Verb Table (`formatBatchGroupMessage`)

```typescript
const SIGNAL_VERB: Record<string, string> = {
  price_drop:    "giảm mạnh",
  price_surge:   "tăng mạnh",
  volume_spike:  "khối lượng đột biến",
  ta_overbought: "quá mua",
  ta_oversold:   "quá bán",
};
// fallback: "kích hoạt cảnh báo"
```

Severity label:
```typescript
const SEV_LABEL: Record<string, string> = {
  critical: "NGHIÊM TRỌNG",
  high:     "QUAN TRỌNG",
};
```

Message assembly:
```
const verb  = SIGNAL_VERB[group.signalType] ?? "kích hoạt cảnh báo";
const label = SEV_LABEL[group.severity] ?? group.severity.toUpperCase();
const n     = group.tickers.length;

if (n === 1) {
  // Single ticker — preserve existing format, BA spec §5a
  return `[${label}] ${group.tickers[0]} alert: ${group.signalType}`;
}

// Multi-ticker — BA spec §5b
const visibleTickers = group.tickers.slice(0, 10);
const tickerLine = visibleTickers.join(", ")
                 + (n > 10 ? ` (+${n - 10} mã khác)` : "");
return `[${label}] ${group.signalType} — ${n} mã cùng ${verb}\n  • ${tickerLine}`;
```

Note: the single-ticker branch in `formatBatchGroupMessage` replicates the
existing `server.ts` format exactly. This lets `server.ts` unconditionally call
`formatBatchGroupMessage` — no branching at call site.

### 11.3 Changes to `server.ts` (push-prices handler, lines 774–795)

Replace the current `for (const alert of alerts)` loop with:

```typescript
// Step 1 — filter to notifiable alerts (dedup guard applied per-alert)
const { groupAlertsBySignalSeverity, formatBatchGroupMessage } =
  await import("../../domain/services/alertBatchGrouper.js");

const notifiable = alerts.filter(
  (a) =>
    (a.severity === "high" || a.severity === "critical") &&
    !shouldSkipAlreadyNotifiedAlert(a.id, db),
);

// Step 2 — group by (signal_type, severity)
const groups = groupAlertsBySignalSeverity(notifiable);

// Step 3 — one Telegram send per group
for (const group of groups) {
  try {
    const msg = formatBatchGroupMessage(group);
    await sendTelegramWork(msg, {
      persist: { from_agent: "push-prices", message_type: "system_alert" },
    });
    // Mark all alerts in the group as notified
    for (const id of group.alertIds) {
      db.prepare("UPDATE alerts SET notified_telegram = 1 WHERE id = ?").run(id);
    }
    log.info("[push-prices] batch alert sent", {
      signalType: group.signalType,
      severity:   group.severity,
      count:      group.tickers.length,
    });
  } catch (tgErr) {
    // No IDs are marked — consistent with existing per-alert error policy (EC-4)
    log.warn("[push-prices] Telegram batch send failed", {
      error: tgErr instanceof Error ? tgErr.message : String(tgErr),
    });
  }
}
```

Touch surface in `server.ts`: the 22-line `for` loop (lines 774–795) is
replaced by ~25 lines. The dynamic import for `alertBatchGrouper.js` is added
alongside the existing imports at line 688 (same `await import` pattern already
used for `signalDetector`, `alertGenerator`, `alertStore`). No other lines in
`server.ts` are touched.

### 11.5 Risk Flags

**R1 — `signals` array empty on an Alert.**
`generateAlerts` always produces at least one signal per alert (it groups by
stock code and only creates an alert when `signals.length > 0`). However,
defensive code must handle `alert.signals[0]` being undefined; the grouper
must fall back to `"unknown"` as signal type rather than throw.

**R2 — `notified_telegram` mark loop on Telegram failure.**
The current code marks IDs in a second loop only after a successful `await`.
If the `sendTelegramWork` rejects, the `catch` must not mark any IDs (EC-4).
The proposed design satisfies this: the `for (const id of group.alertIds)`
mark loop is inside the `try` block, after the `await`.

**R3 — Dynamic import path.**
`alertBatchGrouper.js` is a new file. The import must use `.js` extension
(ESM rule in dev-standards). Developer must confirm the file lands in
`apps/mcp-server/src/domain/services/` and the import path from
`apps/mcp-server/src/interface/mcp/server.ts` is
`../../domain/services/alertBatchGrouper.js`.

**R4 — Single-ticker format parity.**
The single-ticker branch in `formatBatchGroupMessage` must produce output
byte-identical to the old `[${sevLabel}] ${alert.message}` line. The old
`alert.message` is not the ticker symbol — it is the full message string
generated by `alertGenerator`. Architect decision: preserve the old message
string for N=1 groups by storing it in `AlertBatchGroup`.

This changes the `AlertBatchGroup` interface: for single-ticker groups the
formatter returns `[${label}] ${group.singleMessage}` not the reconstructed
format. For multi-ticker groups `singleMessage` is irrelevant.

**Revised `AlertBatchGroup` interface to handle R4:**

```typescript
export interface AlertBatchGroup {
  signalType: string;
  severity: "high" | "critical";
  tickers: string[];
  alertIds: string[];
  /** Full alert.message of the first (and only) alert when tickers.length === 1 */
  singleMessage: string;
}
```

In `groupAlertsBySignalSeverity`, store `alert.message` when creating a new
group (it is only used when the group stays at count 1 — if a second ticker
joins, the multi-ticker format takes over and `singleMessage` is ignored).
