## 1. Three-Decision Resolution

### BLK-1 — Tool Slot Numbers: #121 and #122

**Decision:** The two new tools use slots **#121** and **#122**, not #124 and #125.

**Rationale:**

The BA spec assigned #124 and #125 based on an expectation that 121-123 are reserved for in-flight tasks. Code inspection finds no evidence of any reservation:

- `registry.ts` ends at `run_backtest (+1 → 120)` with no follow-on slot comments.
- Grepping the entire codebase for `#121`, `#122`, `#123` returns zero matches in any tool file, handoff, or task spec.
- `TASKS.md` Backlog, Todo, and In-Progress sections are empty — no task claims those slots.
- `docs/agent-memory/notebooks/po.md` records `toolCount=123` at the 1844 baseline. This means three tools were added after `run_backtest` was registered but without updating slot comments in `registry.ts`. The gap between the comment watermark (#120) and the actual toolCount (123) is a documentation debt, not a slot reservation. Those three tools already exist at the infrastructure level; they have no bearing on the next available comment slot.

The registry slot comments are a sequential documentation convention, not a functional mechanism. Slots 121-123 are vacant in the comment sequence. Using #121 and #122 is correct, maintains sequential ordering, and avoids creating a permanent gap in the comment history that would mislead future readers.

`get_backtest_runs` → **#121**
`get_backtest_run` → **#122**

### BLK-2 — getAllRuns() Interface: Option A

**Decision:** Add an explicit `getAllRuns(limit: number): BacktestRunRecord[]` method to `IBacktestResultRepository` and `SqliteBacktestResultRepository`.

**Rationale:**

Option B (making `strategy` optional on `getRunsByStrategy`) muddies the method's contract — a method named "by strategy" that accepts no strategy is semantically incoherent. Option C (sentinel value in the tool layer) is a DDD violation per the spec. Option A is clean, explicit, follows the existing `getRunsByStrategy`/`getRunById` naming pattern, and leaves each method with a single unambiguous purpose.

**Exact interface declaration to add to `IBacktestResultRepository`:**

```typescript
/** Retrieve runs across all strategies, most-recent-first. */
getAllRuns(limit: number): BacktestRunRecord[];
```

**SQLite implementation body for `SqliteBacktestResultRepository`:**

```typescript
getAllRuns(limit: number): BacktestRunRecord[] {
  try {
    const rows = this.db
      .prepare(
        `SELECT id, strategy, start_date, end_date, run_at,
                total_return, benchmark_return, max_drawdown, sharpe_ratio,
                win_rate, trade_count, result_json
         FROM backtest_runs
         ORDER BY run_at DESC
         LIMIT ?`,
      )
      .all(limit) as BacktestRunRow[];

    return rows.map(rowToRecord);
  } catch {
    return [];
  }
}
```

The query mirrors `getRunsByStrategy` exactly, minus the `WHERE strategy = ?` clause. It reuses the existing `BacktestRunRow` interface and `rowToRecord` helper already present in the file — no new types needed.

### BLK-3 — File Organisation: Extend backtestTools.ts

**Decision:** Add both new tools to the existing `backtestTools.ts` file. Do **not** create `backtestQueryTools.ts`.

**Rationale:**

`backtestTools.ts` is 114 lines with one tool. Adding two small read-only handlers will bring it to approximately 200 lines — well within the project's implicit per-file ceiling (e.g. `marketContextTools.ts` was trimmed from 502 to 105 lines as a DRY task, not from 200). Both new tools belong to the same domain (backtesting) and share the same infrastructure import (`SqliteBacktestResultRepository`). Splitting into a second file at this size would add an indirection layer with no benefit. The barrel `index.ts` export will be updated to also export the new registration function.

## 3. Zod Schema Specifications

### 3.1 get_backtest_runs — input schema

```typescript
{
  strategy: z
    .enum([
      "kinh-dich-high-confidence",
      "kinh-dich-all",
      "combined-high-confidence",
    ])
    .optional()
    .describe(
      "Filter by strategy ID. Omit to list runs across all strategies.",
    ),
  limit: z
    .number()
    .int()
    .min(1, "limit must be >= 1")
    .max(50)
    .default(10)
    .optional()
    .describe("Maximum number of results to return (1–50, default 10)."),
}
```

**Clamping note:** `z.number().max(50)` rejects values above 50 with a Zod validation error. This satisfies AC-1-4 (values above 50 are clamped) — the spec says "clamped to 50" in FR-1-3 but the AC says "returns at most 50 results." Using `max(50)` with a validation error is the simpler and safer approach; it avoids silent mutation of the caller's intent and is consistent with how `min(1)` rejects values below 1 (AC-1-3). The tool description must document the 1-50 range to set caller expectations.

### 3.2 get_backtest_run — input schema

```typescript
{
  id: z
    .string()
    .uuid()
    .describe("UUID of the backtest run to retrieve."),
}
```

## 4. Tool Handler Patterns

### 4.1 get_backtest_runs handler

```typescript
async ({ strategy, limit = 10 }) => {
  try {
    const db = getDb();
    const resultRepo = new SqliteBacktestResultRepository(db);

    const runs = strategy !== undefined
      ? resultRepo.getRunsByStrategy(strategy, limit)
      : resultRepo.getAllRuns(limit);

    // Strip resultJson — summary list only (FR-1-4)
    const summary = runs.map(({ resultJson: _omit, ...rest }) => rest);

    return {
      content: [{ type: "text" as const, text: JSON.stringify(summary, null, 2) }],
    };
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    return {
      content: [
        { type: "text" as const, text: JSON.stringify({ error: message }, null, 2) },
      ],
    };
  }
}
```

Key design points:
- `getDb()` is called inside the handler (U-4 pattern), not at module scope.
- `resultJson` is destructured out and not included in the response (FR-1-4).
- The `strategy` branch is explicit — no sentinel values passed to the repo.
- Empty array from repo returns `[]` as valid JSON (AC-1-5 / FR-1-5).

### 4.2 get_backtest_run handler

```typescript
async ({ id }) => {
  try {
    const db = getDb();
    const resultRepo = new SqliteBacktestResultRepository(db);

    const run = resultRepo.getRunById(id);

    if (run === null) {
      return {
        content: [
          {
            type: "text" as const,
            text: JSON.stringify({ error: `Backtest run ${id} not found.` }, null, 2),
          },
        ],
      };
    }

    return {
      content: [{ type: "text" as const, text: JSON.stringify(run, null, 2) }],
    };
  } catch (err) {
    const message = err instanceof Error ? err.message : String(err);
    return {
      content: [
        { type: "text" as const, text: JSON.stringify({ error: message }, null, 2) },
      ],
    };
  }
}
```

Key design points:
- `getRunById` already catches SQLite errors internally and returns `null`. The outer `try/catch` covers any future error paths (e.g. `getDb()` failure).
- `resultJson` is included (FR-2-3) — no stripping.
- The not-found message matches AC-2-2 exactly: `"Backtest run <id> not found."`.

## 7. Risk Register

### RISK-1 — AC-1-4 clamping vs. rejection ambiguity (LOW)

**Description:** FR-1-3 says "values above 50 are clamped to 50" while AC-1-4 says "returns at most 50 results." These are consistent outcomes but different mechanisms: silent clamping vs. Zod validation error. The design chooses the validation error (consistent with `min(1)` rejection). If the intended UX is silent clamping, the schema needs `.transform()`.

**Mitigation:** Developer confirms with PO before merging. Test T-4 is written for the validation-error path. If PO chooses clamping, T-4 must be rewritten to assert `array.length <= 50` instead.

### RISK-2 — resultJson size in get_backtest_run (LOW)

**Description:** REQ acknowledges 200-500 KB `resultJson` blobs are possible. Local stdio MCP transport has no practical size limit, but very large payloads will slow `JSON.stringify` in the tool handler.

**Mitigation:** No action required. REQ explicitly states "No truncation — callers are responsible for handling large payloads." Document in tool description that payload size grows with backtest scope.

### RISK-3 — toolCount drift in project-stats.json (LOW)

**Description:** The slot comment watermark in `registry.ts` is already behind actual toolCount (watermark shows #120, PO notebook records toolCount=123). This sprint adds 2 more, bringing toolCount to 125. The developer must count actual `server.tool(` calls before updating `project-stats.json` to avoid perpetuating the drift.

**Mitigation:** Developer runs `grep -c 'server.tool(' apps/mcp-server/src/interface/mcp/tools/**/*.ts` (recursive) before updating stats. The correct value is ground truth, not the comment watermark.

### RISK-4 — No DDD violation introduced (CLEARED)

The tool handlers import `SqliteBacktestResultRepository` only to instantiate it for injection into the method call. They contain no domain logic. `IBacktestResultRepository` (domain port) has zero infrastructure imports. `backtestResultRepo.ts` imports only from `domain/` (the interface). The DDD golden rule is satisfied throughout.

### RISK-5 — tsc compatibility of resultJson omission pattern (LOW)

**Description:** The destructuring `const { resultJson: _omit, ...rest } = run` depends on TypeScript knowing `BacktestRunRecord` has a `resultJson` field. This is guaranteed by the existing interface. However, if `tsc` has `noUnusedLocals: true`, the `_omit` variable may trigger a warning.

**Mitigation:** Use the underscore-prefixed convention (`_omit`) which TypeScript treats as intentionally unused. If the project's `tsconfig.json` still rejects it, use `delete (run as Record<string, unknown>)["resultJson"]` — but the destructuring approach is cleaner and preferred.

## 8. Output Shape Contracts

```typescript
{
  id: string;
  strategy: string;
  startDate: string;
  endDate: string;
  runAt: string;
  totalReturn: number;
  benchmarkReturn: number | null;
  maxDrawdown: number;
  sharpeRatio: number | null;
  winRate: number;
  tradeCount: number;
  // resultJson intentionally absent
}
```

### get_backtest_run — full record

```typescript
{
  id: string;
  strategy: string;
  startDate: string;
  endDate: string;
  runAt: string;
  totalReturn: number;
  benchmarkReturn: number | null;
  maxDrawdown: number;
  sharpeRatio: number | null;
  winRate: number;
  tradeCount: number;
  resultJson: string;  // verbatim DB string, not re-parsed
}
```

Both `benchmarkReturn` and `sharpeRatio` serialise as `null` in JSON output when the DB column is NULL (TypeScript `null` serialises to JSON `null`; `undefined` would be omitted — the domain model uses `number | null`, which is correct).
