---

## 1. Step Boundaries

| Event | Where in chef.md | Condition |
|---|---|---|
| ENTRY | Immediately after Bootstrap (Step 0 header, before GATHER reads) | Always — every dish type |
| CLOSE success | End of Step 8 LOG, after notebook append + `cowork-end-cycle` | Morning/EOD/Evening dish sent to MARKET |
| CLOSE silent | End of Step 1 CLUSTER intraday gate, after existing `send_telegram(work, "Intraday scan: 0 clusters — silent exit")` | Intraday + 0 clusters only |
| FAILED | `cowork-boundary` catch block wrapping Steps 0–7 | Any unhandled exception before Step 8 completes |

The existing intraday silent-exit line in Step 1 already sends a WORK message — the CLOSE silent message replaces/augments that line (same send call, standardised format per §3 below).

---

## 2. FAILED Wrapper Boundary

`cowork-boundary` skill wraps the entire execution body: Steps 0 through 7 inclusive (GATHER → WRITE DISH). Step 8 LOG is outside the try block — it is housekeeping that must not suppress a FAILED signal. If Step 8 itself errors, the `cowork-boundary` error rule (1 retry → BUG Telegram → EXIT) applies as-is.

Failure path:
1. `send_telegram(channel="work", <FAILED message, §3>)`
2. `send_telegram(channel="bug", "<one-line error>")` — per cowork-boundary on_error rule
3. EXIT non-zero. No partial MARKET dish. No Step 8 notebook append.

---

## 3. Telemetry Message Format

All messages use `send_telegram(channel="work", ...)`. Tone: terse, machine-parseable prefix, no emoji.

### 3a — ENTRY

```
[chef] START {dish_type} | slot={slot_utc} | cycle={cycle_id}
```

Example:
```
[chef] START morning | slot=2026-05-19T05:23Z | cycle=chef-morning-20260519T0523Z
```

### 3b — CLOSE (success, dish sent to MARKET)

```
[chef] SENT {dish_type} | slot={slot_utc} | cycle={cycle_id} | clusters={N} | convergence={true|false}
```

Example:
```
[chef] SENT morning | slot=2026-05-19T05:23Z | cycle=chef-morning-20260519T0523Z | clusters=3 | convergence=true
```

### 3c — CLOSE (silent, intraday 0 clusters)

```
[chef] SILENT intraday | slot={slot_utc} | cycle={cycle_id} | clusters=0
```

This replaces the current free-form `"Intraday scan: 0 clusters — silent exit"` string with the standardised format. The existing `send_telegram` call location in Step 1 is preserved — only the message string changes.

### 3d — FAILED

```
[chef] FAILED {dish_type} | slot={slot_utc} | cycle={cycle_id} | reason={failure_reason}
```

Example:
```
[chef] FAILED morning | slot=2026-05-19T05:23Z | cycle=chef-morning-20260519T0523Z | reason=get_market_hexagram timeout
```

---

## 4. Schema Contract (message fields)

| Field | Type | Values | Source |
|---|---|---|---|
| `cycle_id` | string | `chef-{dish_type}-{YYYYMMDDTHHmmZ}` | Constructed at ENTRY from `$DISH_TYPE` + slot UTC |
| `dish_type` | enum | `morning` \| `intraday` \| `eod` \| `evening` | `$DISH_TYPE` env/input variable |
| `slot_utc` | ISO-8601 | e.g. `2026-05-19T05:23Z` | Slot fire time (not wall-clock at execution) |
| `status` | enum | `start` \| `sent` \| `silent` \| `failed` | Derived from execution path |
| `convergence_detected` | bool | `true` \| `false` | Present on SENT only — true if ≥1 cluster qualified in Step 1 |
| `clusters` | int | ≥0 | Present on SENT and SILENT |
| `failure_reason` | string | Free text, one line, no newlines | Present on FAILED only — exception message or tool name |

`cycle_id` is constructed once at ENTRY and reused verbatim in CLOSE and FAILED messages — enables grep-based pairing by T2.

# REQ_1950 §T4 — TNB Cron Schedule Hotfix

**BA:** ba | **Sprint:** 1950 | **Size:** XS | **Date:** 2026-05-18
**Type:** HOTFIX | **Owner:** agent-father | **Zone:** `.claude/commands/crons/`
**DEADLINE: ship before 2026-05-18T20:17Z** (next stale-cron fire; false-positive BUG storm begins at that tick)

---

## T4.1 — Root Cause (verified)

Sprint 1949-T9 rescheduled `tran-ngoc-bau` from `0 13 * * *` to `13 20 * * *` (daily 20:13 UTC). That change was applied to:

- `.claude/agents/tran-ngoc-bau.md` (line 24: "Daily audit… 20:13 UTC") — CORRECT
- `docs/standards/cron-jobs.md` L128 (`13 20 * * *`, note "(moved from `0 13 * * *` by Sprint 1949-T9)") — CORRECT

It was NOT applied to the cron command file. Audit finding CRITICAL #2 confirms:
- `.claude/commands/crons/cron-tran-ngoc-bau.md` L3 still reads `17 */4 * * *` (every 4h at :17 UTC — fires 00:17, 04:17, 08:17, 12:17, 16:17, 20:17 UTC)

The live cron registered from this file therefore fires 6x/day. Sprint 1950-T2 (commit `ad68cf5c`) checks that `[chef] START` count ≥3 in last 24h — when TNB fires at a 4h slot well before chef's morning dish (05:23 UTC), it sees <3 START events and emits a false-positive `chef-coverage-low` BUG.

---

## T4.2 — Requirement

**FR-T4-1 (DDD: infrastructure/scheduling)** — Update `.claude/commands/crons/cron-tran-ngoc-bau.md` L3: replace `17 */4 * * *` with `13 20 * * *`. All other lines in the file (recurring, durable, prompt block) are unchanged.

**FR-T4-2 (DDD: infrastructure/scheduling)** — After the file edit, ops must delete the stale live cron and re-register via CronCreate using the updated file. Agent-father is responsible for triggering this ops step or doing it directly via CronCreate in the same session.

**NFR-T4-1** — No in-flight TNB session is harmed by this edit. If a TNB cycle is running at the moment of file change, it continues to completion on its old cadence. The new schedule takes effect on the next CronCreate registration. Document this in the commit message.

**NFR-T4-2** — No other file references `17 */4 * * *` as TNB's schedule. Verify with a grep across `.claude/` and `docs/` before commit.

---

|---|---|
| AC-T4-1 | `.claude/commands/crons/cron-tran-ngoc-bau.md` L3 reads exactly `17 */4 * * *` BEFORE → `13 20 * * *` AFTER |

## T4.6 — Risk Note

If a TNB session is active when agent-father edits the file and calls CronDelete, the running session completes on its own cadence — it is not interrupted. CronCreate then arms the new daily slot. Ship by 20:17Z to prevent that fire.
