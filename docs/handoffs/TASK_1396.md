# TASK_1396 — GAS Digest: Double Price-Drop Label UX

**Layer:** application/usecases
**File in scope:** `apps/mcp-server/src/application/usecases/assembleAlertDigest.ts`
**Function in scope:** `formatAlertDigest` (lines 137-171)
**Status:** Spec — awaiting architect review

---

## 1. Problem Statement

When a ticker triggers multiple `price_drop` alerts within the same 24-hour window,
`assembleAlertDigest` places their raw `message` strings consecutively inside the
same stock block with no label distinguishing whether each value is an independent
intraday drop or a running cumulative move.

### Example of current (broken) digest output

```
[2026-04-28] Tóm tắt cảnh báo (24 giờ qua)
Tổng: 3 cảnh báo | Nghiêm trọng: 0 | Quan trọng: 3

GAS — 3 cảnh báo:
  - Giá giảm ↓1.2% (45.500 → 44.954 VND)
  - Giá giảm ↓2.4% (44.954 → 43.866 VND)
  - Giá giảm ↓3.6% (45.500 → 43.866 VND)
```

A user reading this sees three "Giá giảm" entries without knowing:
- Are `-1.2%` and `-2.4%` two separate intraday drops (additive) or the same move measured twice?
- Is `-3.6%` the day-total (cumulative from open) or a third independent event?
- Which message is the most recent?

The ambiguity is worst when one message carries a cumulative percentage (measured
from the session open or the first alert baseline) and a later message carries the
marginal drop since the prior alert — both look identical in format.

### Root cause (in `assembleAlertDigest.ts`)

`topMessages` is built from `a.message` verbatim (line 242). The formatter
`formatAlertDigest` renders each message with the prefix `- ` and no contextual
qualifier (lines 161-163). There is no distinction between:

- An **incremental drop** — the price moved an additional X% since the last alert.
- A **cumulative drop** — the price is now X% below the reference price (open or
  first-alert baseline).

## 2. Acceptance Criteria

The following must all be true for the task to be considered done.

### AC-1: Single price_drop alert — no label change needed

When only one `price_drop` alert exists for a ticker in the 24h window, the
message is rendered exactly as today (no qualifier appended). No regression.

```
GAS — 1 cảnh báo:
  - Giá giảm ↓1.2% (45.500 → 44.954 VND)
```

### AC-2: Multiple incremental price_drop alerts — "them" qualifier

When two or more consecutive `price_drop` messages exist for the same ticker AND
their percentage values differ AND none is flagged as cumulative in the message
text, each entry after the first is prefixed with `(+thêm)` to signal an
additional intraday move.

```
GAS — 2 cảnh báo:
  - Giá giảm ↓1.2% (45.500 → 44.954 VND)
  - (+thêm) Giá giảm ↓2.4% (44.954 → 43.866 VND)
```

The first entry is the most-recent alert (existing sort order: severity DESC then
`triggered_at` DESC is preserved). Only subsequent entries in the rendered block
receive the `(+thêm)` prefix.

### AC-3: Cumulative price_drop present — "luy ke" qualifier

When a message string contains the substring `lũy kế` or `cumulative` (case-
insensitive), it is rendered with the prefix `(lũy kế)` regardless of its position
in the block.

```
GAS — 2 cảnh báo:
  - (lũy kế) Giá giảm ↓3.6% từ mở cửa (45.500 → 43.866 VND)
  - Giá giảm ↓1.2% (45.500 → 44.954 VND)
```

### AC-4: Non-price_drop alert types — no qualifier

`volume_spike`, `price_surge`, `report_new`, `news_mention` messages must not
receive any qualifier. The change is strictly scoped to consecutive `price_drop`
entries within the same stock block.

### AC-5: Overflow line unaffected

The `(và N cảnh báo khác)` overflow line is not changed and must still appear when
`block.overflow > 0`.

### AC-6: No data-model changes

`StockAlertBlock`, `AlertDigest`, `AssembleAlertDigestOptions` interfaces are
unchanged. The fix lives entirely in `formatAlertDigest`'s per-block rendering
loop.

## 5. Non-Goals

The following are explicitly out of scope for TASK_1396.

1. **Do not change alert message generation.** The alert engine that writes to
   the `alerts.message` column is not touched. The qualifier is display-only.

2. **Do not add a `type` field to `StockAlertBlock`.** The fix must derive intent
   from the existing `message` string using substring detection, not a new schema
   field.

3. **Do not change the sort order of `topMessages`.** Severity DESC, then
   `triggered_at` DESC remains as-is. The qualifier is applied post-sort.

4. **Do not fix `telegram.ts` or `formatSignalVi`.** Those produce per-alert
   real-time push messages, which are a separate UX surface. This task concerns
   only the daily digest.

5. **Do not add internationalisation infrastructure.** The qualifier strings
   (`(+thêm)`, `(lũy kế)`) are Vietnamese literals hard-coded directly in
   `formatAlertDigest`. No i18n layer.

6. **Do not add a `signal_type` column to the `alerts` table.** Schema changes
   require a migration task and are out of scope here.

## Architect Notes

### Blocker Resolutions

**B1 — Scope of `(+thêm)` qualifier: price_drop only**

Decision: apply `(+thêm)` strictly to consecutive `price_drop` messages within the same stock block. Other alert types (`volume_spike`, `price_surge`, `report_new`, `news_mention`) must never receive the qualifier.

Rationale: the ambiguity problem is specific to price_drop because that type generates both incremental and cumulative percentage values that look identical. Applying the label to all repeated types would be semantically wrong (two `volume_spike` entries are not "additional" moves of the same kind — they are independent events). The BA-provided default is correct and aligns with AC-4 and Non-Goal 1.

Detection: a message is a `price_drop` entry when it contains the substring `Giá giảm` (case-sensitive, Vietnamese). This matches all existing alert-engine outputs without a schema field. A private helper `isPriceDrop(msg: string): boolean` returns `msg.includes("Giá giảm")`.

**B2 — ASCII transliteration: detect both `lũy kế` and `luy ke`**

Decision: detect both forms, case-insensitive.

Rationale: older alert rows may have been generated before the alert engine used diacritics consistently. Substring matching `lũy kế` alone would silently miss those rows and render them as unlabelled third entries, which is the exact ambiguity the spec wants to resolve. Cost is a single additional `||` branch in a private helper — zero risk.

Implementation: a private helper `isCumulative(msg: string): boolean` returns `msg.toLowerCase().includes("lũy kế") || msg.toLowerCase().includes("luy ke")`.

**B3 — Reference price for "cumulative": message text only, no price lookups**

Decision: the qualifier label is display-only, derived purely from the message string. No price-lookup or arithmetic is performed. The label `(lũy kế)` signals to the reader that this entry is a cumulative figure; it does not attempt to compute or verify the reference price.

Rationale: the BA's default is the correct call. Adding a price lookup would cross the layer boundary — `formatAlertDigest` is a pure text-formatting function (no DB, no I/O). Any reference-price calculation belongs in the domain layer and is out of scope for this task (Non-Goal 6).

### Implementation Design

**Where to insert the logic**

`formatAlertDigest` in `/apps/mcp-server/src/application/usecases/assembleAlertDigest.ts`, inside the per-stock block loop (lines 158-168). The existing loop is:

```
for (const block of stockBlocks) {
  lines.push(`${label} — ${block.count} cảnh báo:`);
  for (const msg of block.topMessages) {
    lines.push(`  - ${msg}`);     // ← qualifier inserted here
  }
  ...
}
```

The change replaces the inner `for` loop body. Before iterating, we:
1. Identify which messages in `block.topMessages` are `price_drop` entries.
2. Among those, determine their position in the rendered order (first vs. subsequent).
3. For each message, compute the qualifier prefix:
   - `isCumulative(msg)` → prefix `(lũy kế) `
   - `isPriceDrop(msg)` AND not the first price_drop entry seen → prefix `(+thêm) `
   - Otherwise → no prefix

The "first price_drop seen" counter resets for each stock block.

**High-level diff**

Two private helpers added above `formatAlertDigest` (no exports, no new files):

```typescript
function isPriceDrop(msg: string): boolean {
  return msg.includes("Giá giảm");
}

function isCumulative(msg: string): boolean {
  const lower = msg.toLowerCase();
  return lower.includes("lũy kế") || lower.includes("luy ke");
}
```

Inner loop inside `formatAlertDigest` changes from:

```typescript
for (const msg of block.topMessages) {
  lines.push(`  - ${msg}`);
}
```

to:

```typescript
let priceDropSeen = false;
for (const msg of block.topMessages) {
  let prefix = "";
  if (isCumulative(msg)) {
    prefix = "(lũy kế) ";
  } else if (isPriceDrop(msg)) {
    if (priceDropSeen) {
      prefix = "(+thêm) ";
    } else {
      priceDropSeen = true;
    }
  }
  lines.push(`  - ${prefix}${msg}`);
}
```

The `isCumulative` branch intentionally does NOT set `priceDropSeen = true`, so a cumulative message does not consume the "first drop" slot. This is correct: if a cumulative entry appears before an incremental one, the incremental entry is still the first unqualified drop.

**AC coverage mapping**

| AC | Handled by |
|----|-----------|
| AC-1 (single price_drop, no label) | `priceDropSeen` starts false; only one drop sets it true, no prefix applied |
| AC-2 (multiple incremental, second gets `(+thêm)`) | `priceDropSeen` true on second iteration |
| AC-3 (cumulative gets `(lũy kế)`) | `isCumulative` branch fires independently of `priceDropSeen` |
| AC-4 (non-price_drop types unaffected) | `isPriceDrop` returns false; neither branch fires |
| AC-5 (overflow line unaffected) | overflow block is outside the inner loop, unchanged |
| AC-6 (no data-model changes) | only `formatAlertDigest` function body changes |
