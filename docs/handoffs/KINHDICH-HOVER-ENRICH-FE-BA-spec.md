## Decision Journal

**Task:** BA-KINHDICH-HOVER-ENRICH-FE  
**Date:** 2026-06-14  
**What considered:**  
- Option A: Hardcode 64 hoverSummary strings directly in `que-descriptions.generated.ts` — violates DRY (second data source, breaks single-SSOT invariant).  
- Option B: Extend `QueName.tsx` to directly import and read `que-reference.js` — violates codegen layer (que-reference.js is not a TypeScript module; the codegen exists precisely to mirror it into TypeScript).  
- Option C (chosen): Extend the EXISTING codegen (`gen-que-descriptions.ts`) to also emit `hoverSummary` from `que-reference.js` into `que-descriptions.generated.ts`, then update `QueName.tsx` to render `desc.hoverSummary ?? desc.coreMeaning`. Preserves QUE-TOOLTIP-DRY mechanism exactly.  

**Why C chosen:** Only Option C adds `hoverSummary` through the existing single-SSOT→codegen→generated-file→component pipeline. A and B both introduce a second data path, directly violating the `dry_constraint` field of the task and the QUE-TOOLTIP-DRY sprint outcome.  

**coreMeaning fallback rationale:** `hoverSummary` typed optional in interface so future entries can omit it without breaking the component. Existing `QUE_DESCRIPTIONS[hexagram]` undefined guard already handles full-entry absence.  

**EN field exclusion from QueDescription:** The tooltip renders VI only (language-boundary rule). EN is in `que-reference.js` but not needed in the frontend contract. Keeps QueDescription minimal and avoids confusion with future i18n work.  

**Why change:** User-reported UX defect — coreMeaning is a 17–40 char terse clause, not comprehensible to a non-technical Vietnamese reader tracking stock market positions. hoverSummary (80–220 chars, plain VN) directly addresses the complaint.

### Brownfield Risk Review (3-file change surface)

**R1 — TypeScript type-safety of optional `hoverSummary` field** (RISK: LOW, MITIGATED)

- `hoverSummary?: string` in `QueDescription` is an additive optional field. All existing callers that destructure only `coreMeaning` and `marketTrendLabel` are not affected — TypeScript does not break when a new optional field is added to an exported interface.
- `desc.hoverSummary ?? desc.coreMeaning`: both sides are `string | undefined` → `string` (since `coreMeaning: string` is non-optional). TypeScript infers the expression type as `string`. No type error. No cast required.
- The `QueRefEntry` interface addition (`hoverSummary: { vi: string; en: string }`) restores static typing for the codegen-internal parse path. Currently `[key: string]: unknown` index signature covers it silently. Making it explicit is a strict improvement — removes the `unknown` cast path for this field.
- **Mitigation:** Run `tsc --noEmit` from `apps/frontend/` after codegen re-run before commit (include in dev-frontend acceptance checklist).

**R2 — Backtick injection in hoverSummary.vi strings** (RISK: LOW, MITIGATED)

- The BA spec and the pre-authored 64 strings do not contain raw backticks. However the codegen for `coreMeaning` already uses `.replace(/\`/g, "\\`")` as a safety measure. The same escape MUST be applied to `hoverSummary.vi` in the entry builder (see implementation below). This is not a new escape mechanism — it is a copy of the existing pattern.
- **Mitigation:** Implementation blueprint below mandates the escape. QA zero-short-residue check also detects malformed entries.

**R3 — No regression to `marketTrendLabel` consumer** (RISK: NONE)

- `marketTrendLabel` is emitted by BLOCK 1 and rendered at QueName.tsx L76-78. Neither BLOCK 1's `marketTrendLabel` extraction nor L76-78 is touched. Confirmed by reading both files. No regression path.

**R4 — No regression to `withDetailLink` deep-link** (RISK: NONE)

- `withDetailLink` anchor (L79-86 of QueName.tsx) is conditional on the `withDetailLink` prop, not on any description field. Unaffected by the L75 render change.

**R5 — `que-descriptions.generated.ts` file header preservation** (RISK: LOW, MITIGATED)
