## TLDR

`get_agent_signals` filters exclusively on `to_agent`, so self-sent signals (where `from_agent = to_agent = "news-scout"`) are never returned unless news-scout also sets `to_agent = "news-scout"` when posting. The inter-cycle dedup gate in `stage-signals.md` calls `get_agent_signals(agent="news-scout")` hoping to see its own prior posts — but news-scout posts to `"alert-commander"` or `"all"`, not to itself. The fix is a one-param extension: add an optional `from_agent` filter to `get_agent_signals` (both the MCP tool schema and the underlying `getSignals` store function), so the dedup gate can query `agent="news-scout", from_agent="news-scout"`.

### Root cause (exact)

`getSignals()` in `agentSignalStore.ts` L751–760 queries:

```sql
WHERE (s.to_agent = ? OR s.to_agent = 'all')
  AND s.expires_at > datetime('now')
  -- optional: AND s.status = 'unread'
```

When news-scout calls `get_agent_signals(agent="news-scout")`, the query binds `"news-scout"` as the `to_agent` filter. News-scout's own prior signals have `to_agent = "alert-commander"` or `to_agent = "all"` — the `"all"` case IS matched. However, the practical failure is that urgent_news / chain_catalyst signals are posted `to_agent = "alert-commander"` (not `"all"`), so they are invisible on the to_agent axis from news-scout's perspective.

Even for signals posted `to_agent = "all"`, the `status = "unread"` default filter marks them as read on first retrieval by alert-commander — so by the time news-scout polls, they have already been marked read and are excluded if the default `status="unread"` is used.

**Root cause summary:** The tool was designed for inbox retrieval (what was sent TO me). The dedup gate needs sender history (what did I post). These are orthogonal queries over the same table. The simpler fix is extending the existing tool with a `from_agent` filter rather than exposing a separate tool.

### Design decision: extend vs alias

Options evaluated:
- **Option A:** Add `from_agent` optional filter to `get_agent_signals` — extends the existing contract, backward compatible, zero new tool entry in registry, no new test file required (only extensions to existing tests).
- **Option B:** Expose `get_my_signals` alias — a new tool with identical logic but pre-wired to `from_agent`. Adds a tool-registry entry, a new Zod schema block, and a new agent-manifest entry. Unnecessary surface.

**Decision: Option A.** Extend `get_agent_signals` with an optional `from_agent` param. When `from_agent` is provided, the WHERE clause additionally filters `AND s.from_agent = ?`. The `agent` (to_agent) param remains required for backward compatibility but becomes the "who do I address" axis — the caller can pass any value (or their own name). For the dedup use-case, news-scout passes `agent="news-scout"` with `from_agent="news-scout"`, making the query return only rows where `from_agent = "news-scout"` regardless of `to_agent`.

DDD layer assignment: both touched files live in `infrastructure/db/` (store) and `interface/mcp/tools/` (tool). No domain layer changes. SDD-1 invariant unaffected.

## Implementation Notes

### Store layer (`agentSignalStore.ts`)

Extend `GetSignalsOptions`:

```typescript
export interface GetSignalsOptions {
  status?: "unread" | "all";
  fromAgent?: string;        // NEW: filter by sender, not recipient
}
```

In `getSignals()`, append to the WHERE clause when `fromAgent` is set:

```sql
-- append:
AND s.from_agent = ?
```

Bind the extra parameter in the query. Keep the `to_agent` filter as-is (required, backward compatible). The `agent` parameter still anchors the query — this is intentional; the caller always identifies themselves as the context agent.

**Side-effect concern (AC-3):** When `fromAgent` is provided, the query is a sender-history lookup, not an inbox read. Do NOT mark rows as read in this path. Guard the mark-read block with `if (statusFilter === "unread" && opts.fromAgent === undefined)`.

### Tool layer (`agentSignalTools.ts`)

Add to the `get_agent_signals` schema:

```typescript
from_agent: z
  .string()
  .optional()
  .describe("If provided, return only signals sent BY this agent (sender history). Useful for dedup checks."),
```

Forward in the handler:

```typescript
const signals = getSignals(db, args.agent, {
  status: args.status,
  ...(args.from_agent !== undefined ? { fromAgent: args.from_agent } : {}),
});
```

No change to `formatSignalLines` — the output format is identical.

### Flow update (`stage-signals.md`)

Replace the dedup gate call block:

```
recent = call_tool(server="vn-market", tool="get_agent_signals", arguments={
  "agent": "news-scout",
  "from_agent": "news-scout",
  "status": "all"
})
```

The `status: "all"` is required so already-read rows (read by other agents) are visible. The 180-min window check uses `created_at` which is already in the returned payload.

### Test plan

New tests in `242-agent-signals.test.ts` (extend existing `describe` block):

1. `getSignals with fromAgent returns self-sent rows regardless of to_agent` — post 2 signals: one `from=news-scout, to=alert-commander` and one `from=alert-commander, to=news-scout`. Call `getSignals(db, "news-scout", { fromAgent: "news-scout", status: "all" })`. Assert only the first row is returned.

2. `getSignals without fromAgent does not leak cross-agent rows` — same setup; call `getSignals(db, "news-scout", { status: "all" })`. Assert only the second row is returned (the one addressed to news-scout).

3. `getSignals with fromAgent + status=all returns read rows` — post 1 signal `from=news-scout, to=all`; mark it read via `UPDATE`; call with `fromAgent="news-scout", status="all"`. Assert row is returned.

### Implementation divergence from handoff

The handoff spec (Implementation Notes section) said to keep the `to_agent` filter and add `from_agent` as an additional AND clause. That approach would never return rows where `to_agent = "alert-commander"` when querying from news-scout's perspective. AC-1 ("regardless of to_agent") required switching the WHERE clause to `from_agent = ?` exclusively when `fromAgent` is set. The `agent` parameter is still accepted at the call site but not used as a bind parameter in this mode (sender-history queries are self-contained).
