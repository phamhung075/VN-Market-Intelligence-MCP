## JOB 2 — Data Reachability Verdict

### Question
Can the frontend already reach hexagram description data (coreMeaning.vi, stateInterpretation.vi, marketTrendLabel.vi, favorable.vi, warning.vi) via an existing API/contract, or is a thin server-side expose endpoint needed?

### Finding — Two parallel description pipelines exist today

**Pipeline A — mcp-server hexagramLibrary.ts → codegen script → frontend static file (LIVE)**

- SSOT: `apps/mcp-server/src/domain/services/kinhDich/hexagramLibrary.ts` — 64 hexagrams with full Vietnamese descriptions including `coreMeaning`, `state.trend`, `judgment.interpretation`, `image.action`
- Codegen: `scripts/gen-que-descriptions.ts` — reads `QUE_DATA` + `QUE_META` from hexagramLibrary.ts and emits `apps/frontend/app/lib/que-descriptions.generated.ts`
- Frontend consumer: `apps/frontend/app/components/QueName.tsx` imports `QUE_DESCRIPTIONS` from that generated file — already complete for all 4 text fields (`coreMeaning`, `judgment_interpretation`, `image_action`, `state_trend`)
- Generation trigger: `bun run gen:que` in `apps/frontend/package.json`
- This pipeline is **LIVE** — the generated file is present and consumed by QueName today

**Pipeline B — kinh-dich-service que-reference.js (SSOT per PO ruling)**

- The actual PO-designated SSOT is `apps/kinh-dich-service/dashboard/que-reference.js` (auto-generated by `go run ./cmd/sandbox -emit-reference`) — contains richer fields: `coreMeaning.vi`, `stateInterpretation.vi`, `marketTrendLabel.vi`, `favorable.vi`, `warning.vi`
- The Go package `reading_composer` contains `hexagram_reference.go` with `GetAllQueReferences()` and `GetQueReference(id int)` functions returning the full `queReference` struct
- The kinh-dich-service router (`pkg/interface/http/router.go`) has `/hexagram/{number}/explain` which returns `ExplainResponse{CoreMeaning, TradingContext}` — partial fields only, **no dedicated `/reference` bulk endpoint**
- The mcp-server proxies `/hexagram/{number}/explain` via `clients.ts:616` `explainHexagram()` but this is per-hexagram (64 calls) not a bulk fetch — no bulk `/que-reference` API route exists

### Reachability verdict

**zone: multi** — the data lives in two separate zones (mcp-server domain + kinh-dich-service Go service) and no single HTTP endpoint currently serves the full 64-hexagram description map that the frontend needs.

**Current state of QueName.tsx**: uses `QUE_DESCRIPTIONS` from the codegen pipeline (Pipeline A = mcp-server source). This is functional but violates the PO ruling that the SSOT is the kinh-dich-service emit-reference.

**Gap identified:**
- FR-1 (kinh-dich-signals SnapshotRow unguarded): migrate `<span>` to `<QueName>` — uses existing `QUE_DESCRIPTIONS` generated file, no new endpoint needed
- FR-2 (SSOT alignment): the generated file's source must be aligned to kinh-dich-service SSOT (`que-reference.js`) per PO ruling. Currently codegen reads mcp-server hexagramLibrary.ts (a different file). Two options: (A) add a `GET /que-reference` bulk endpoint to kinh-dich-service and regenerate from it, or (B) align hexagramLibrary.ts to be a downstream of que-reference.js. Architect decides.

**For FR-1 (immediate fix to SnapshotRow):** no new endpoint is needed — `QUE_DESCRIPTIONS` already covers all 64 hexagrams. The `hexagram` field is already available on `KinhDichSnapshotItem` as `hexagramNumber: number`.

## Edge Cases

- **Missing hexagramNumber (0 or undefined):** `KinhDichSnapshotItem.hexagramNumber` should be validated before passing to `QueName`. If 0 or falsy, fallback to plain display (QueName's existing no-op handles this).
- **Vietnamese diacritics in tooltip text:** already correct in QUE_DESCRIPTIONS generated file — no encoding issue observed.
- **Long coreMeaning text:** current max in QUE_DESCRIPTIONS is ~100 chars. `max-w-xs` in TooltipContent handles wrapping. No truncation needed.
- **Snapshot table on mobile:** the snapshot table already has horizontal scroll via `overflow-x-auto`; touch tooltip must not conflict with row-click or scroll gestures.
- **FlipRow in kinh-dich-signals:** FlipRow (L452) renders `flip.fromHexagramName` and `flip.toHexagramName` as text but not as a tooltip-bearing quẻ name. Architect must decide if FlipRow also needs QueName migration (see BLOCKER-2).

## Blockers

No PO blockers — all PO rulings already in sprint_goal.

**Architect blockers:**

- **BLOCKER-1 (SSOT alignment path):** Two sources exist: mcp-server `hexagramLibrary.ts` (currently used by codegen) vs kinh-dich-service `que-reference.js` (PO-designated SSOT). Architect must decide: (A) add `GET /que-reference` bulk endpoint to kinh-dich-service + update codegen to fetch from it, OR (B) declare hexagramLibrary.ts as downstream mirror of que-reference.js and gate gen:que on que-reference.js. Option A has network call at build time; Option B keeps codegen entirely local. Decision gating FR-2.
- **BLOCKER-2 (FlipRow scope):** `FlipRow` renders `flip.fromHexagramName` and `flip.toHexagramName` as plain text. These are hexagram names but may not carry a numeric id in the `KinhDichFlip` DTO. Architect must confirm: (a) does `KinhDichFlip` carry `fromHexagramNumber` / `toHexagramNumber` fields? (b) if not, is adding them in scope for this sprint? If both ids are available, QueName migration of FlipRow is in scope. If not, FlipRow stays plain text — explicitly deferred.
- **BLOCKER-3 (Tooltip fields to surface):** que-reference.js has 5 VI fields: `coreMeaning.vi`, `stateInterpretation.vi`, `marketTrendLabel.vi`, `favorable.vi`, `warning.vi`. The tooltip should not dump all 5 (too verbose for hover). Architect must specify the 1–2 fields to show in the tooltip: recommended is `coreMeaning.vi` (primary) + `marketTrendLabel.vi` (label badge). BA recommends against showing `stateInterpretation.vi` inline (3 sentences = too long for hover).
