### 2c. Dependency injection contract (confirmed)

All three route handlers must use this signature pattern:

```typescript
import type { IncomingMessage, ServerResponse } from "node:http"
import type { Database } from "bun:sqlite"
import type { Logger } from "../../infrastructure/logger.js"  // or ReturnType<typeof createLogger>

export async function handlePushPrices(
  req: IncomingMessage,
  res: ServerResponse,
  db: Database,
  log: ReturnType<typeof createLogger>,
): Promise<void>
```

- No `getDb()` calls inside handler files. `db` is always injected by `handleRequest()`.
- No module-level singletons inside handler files.
- `server.ts` calls each handler as: `await handlePushPrices(req, res, getDb(), log)`.

**Why DI and not singleton:** `getDb()` returns a module-level singleton, which makes isolated unit tests impossible without `mock.module`. Injecting `db` lets tests pass a `new Database(":memory:")` directly.

### 2e. `_staleTickers_lastNotifiedDate` — write-back risk

`pushPricesHandler.ts` writes to `_staleTickers_lastNotifiedDate` (line 674 of server.ts). After extraction, the handler file must import it from `./server-startup.js` and mutate the same module reference:

```typescript
// pushPricesHandler.ts
import { _staleTickers_lastNotifiedDate as _lastNotified } from "./server-startup.js"
// ... inside handler:
// WRONG — local alias does not propagate back
// CORRECT — access the live binding via the module:
import * as startup from "./server-startup.js"
startup._staleTickers_lastNotifiedDate = todayUtc
```

Because ESM live bindings for `let` exports are read-only from the importer side in strict ESM, the cleanest solution is to expose a setter from `server-startup.ts`:

```typescript
// server-startup.ts
export let _staleTickers_lastNotifiedDate = ""
export function _setStaleTickers_lastNotifiedDate(v: string): void {
  _staleTickers_lastNotifiedDate = v
}
export function _resetStaleTickers_lastNotifiedDate(): void {
  _staleTickers_lastNotifiedDate = ""
}
```

`pushPricesHandler.ts` calls `_setStaleTickers_lastNotifiedDate(todayUtc)`. Tests call `_resetStaleTickers_lastNotifiedDate()`. This is the correct pattern — do not use `import * as` module namespace mutation.

## 4. Risk Flags

### Risk 1 — `_staleTickers_lastNotifiedDate` ESM live binding (HIGH)
Described in §2e. If developer uses a re-import alias instead of a setter function, the stale-ticker cooldown will silently break (the `if (_staleTickers_lastNotifiedDate !== todayUtc)` guard will never be true after the first push). **Mitigation:** use the `_setStaleTickers_lastNotifiedDate()` setter pattern.

### Risk 2 — `parseMultipartFields` scope boundary
`parseMultipartFields` is called only inside `/api/push-bctc-pdf` which stays in `server.ts`. It must NOT be moved to a handler file. It is fine to leave it as a private module-level function in `server.ts`.

### Risk 3 — `ensureForeignFlowMigration` coupling
`ensureForeignFlowMigration()` is called inside the push-foreign-flow route block (line 1026), not at the top level. After extraction, `pushForeignFlowHandler.ts` must import `ensureForeignFlowMigration` from `./server-startup.js`. Do not import it from `server.ts` (circular).

### Risk 4 — `startScheduler.ts` import chain length
`startScheduler.ts` will carry all 40+ job runner imports that currently live at the top of `jobs.ts`. This is intentional — those imports belong to the scheduler wire-up, not to the cron config or helpers. Do not redistribute them.

### Risk 5 — `cronConfig.ts` must have zero side-effects
`CRONS` uses `Bun.env` reads at module evaluation time. This is safe — `Bun.env` reads are synchronous and have no I/O. The file must not import from scheduler jobs or infrastructure.

### Risk 6 — bctcQueueEnricherJob.ts is modified in working tree
The git status shows `apps/mcp-server/src/scheduler/financial-reports/bctcQueueEnricherJob.ts` has unstaged changes. Developer must not conflict with those changes. Task 1406e only touches `jobs.ts`, `cronConfig.ts`, `startupHelpers.ts`, and `startScheduler.ts` — no job files.
