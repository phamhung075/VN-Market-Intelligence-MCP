# TASK_1398 — pollNews all-sources-dark DB-backed cooldown

## Status
IMPL DONE

## Problem
`pollNews` all-sources-dark alert fired on every poll cycle when all sources returned 0 items.
The module-level `_lastAllDarkAlertAt` guard worked within one process lifetime but reset on every
server restart. Reports 2664 (14:15) and 2666 (16:30) were the same error 135 min apart.

## Root Cause
`_lastAllDarkAlertAt = 0` on every process start → first post-restart poll cycle always
triggered a Telegram bug alert, regardless of when the last alert was sent before the restart.

## Fix

### `apps/mcp-server/src/application/usecases/pollNews.ts`

- Added `nowMs?: () => number` to `PollNewsOptions` (clock override for test isolation).
- In the `if (allItems.length === 0)` block, replaced the simple `_lastAllDarkAlertAt` check
  with a combined module-var + DB-backed check:
  1. Query `MAX(started_at)` from `cron_job_runs WHERE job_name = 'pollNews_all_sources_dark'`
  2. Use `Math.max(_lastAllDarkAlertAt, dbLastMs)` as the effective last-sent time
  3. On send: insert a row into `cron_job_runs` with `job_name='pollNews_all_sources_dark'`
     using `strftime('%Y-%m-%dT%H:%M:%SZ','now')` for UTC ISO 8601 format
- The `_resetAllDarkAlert()` export is unchanged (resets module var; tests use fresh `:memory:` DB
  so no explicit DB reset is needed in `beforeEach`).

### `apps/mcp-server/src/__tests__/1398-pollnews-all-dark-cooldown.test.ts`

Two new tests:
- **(a)** Second invocation within 4h cooldown (after module-var reset simulating process restart)
  → alert suppressed by DB cooldown guard
- **(b)** Second invocation after 4h cooldown (after module-var reset)
  → alert fires again
