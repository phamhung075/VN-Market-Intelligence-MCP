## Open Questions — Architect Answers

### Q1: Are 6 statuses sufficient?

**Answer: Yes — approved as specified, with one naming clarification.**

The 6 values cover the full resolution lifecycle:

| Value | Layer | Verdict |
|-------|-------|---------|
| `none` | Default, pre-resolution | Keep — necessary for backward compat + NULL-avoidance |
| `fixed` | Terminal positive | Keep |
| `wontfix` | Terminal negative | Keep |
| `duplicate` | Terminal redirect | Keep |
| `monitoring` | Non-terminal, stays visible | Keep |
| `claimed` | Transitional | **Remove from ResolutionStatus** (see constraint C-1 below) |

`claimed` must NOT appear in the `resolution` column. Claim state is already tracked by the `claimed_by` / `claimed_at` columns added in Task 231. Putting `claimed` in resolution would duplicate that state and create sync risk (what if claimed_by is set but resolution != 'claimed', or vice versa?).

**Final ResolutionStatus enum (5 values):**
```typescript
export type ResolutionStatus = "none" | "fixed" | "wontfix" | "duplicate" | "monitoring";
```

The BATCH spec AC-2 lists 6 values including `claimed` in ResolutionStatus — this is a spec error. Developer must implement 5 values only.

### Q2: Manual-only lifecycle for monitoring — approved?

**Answer: Yes — manual only for this sprint.**

Auto-expiration is out of scope (SPRINT-S budget). The 3-strike deadlock mitigation from the risk register (force wontfix after 3 claims) is also deferred — it requires a claim_count column that does not exist yet.

Future sprint trigger: if `monitoring` reports accumulate >5 in the loop, PM should initiate Sprint 1850 with auto-expiration logic.

### Q3: Separate-column design acceptable?

**Answer: Yes — approved. The two-column design is correct.**

`status` (new/processed) = pipeline state — "is this report in the processing queue?"
`resolution` (none/fixed/wontfix/duplicate/monitoring) = issue outcome — "how was the underlying issue handled?"

These are orthogonal dimensions. Merging them would require a breaking migration and introduce ambiguity ("processed" currently means "archived from loop", not "issue fixed"). The separate-column approach preserves all existing queries unchanged.

## Constraints and Modifications

### C-1: Remove `claimed` from ResolutionStatus

BATCH spec AC-2 includes `"claimed"` in `ResolutionStatus`. This is a DDD violation — claim state belongs to the ownership lock (`claimed_by`/`claimed_at`), not to resolution outcome.

**Mandatory change:** `ResolutionStatus` = `"none" | "fixed" | "wontfix" | "duplicate" | "monitoring"` (5 values, not 6).

The `ReportStatus` type extension in AC-2 that adds `"claimed"` to `ReportStatus` is also incorrect — `status` column must stay `"new" | "processed"` only. `claimed` is not a status value in this schema; it is implicit when `claimed_by IS NOT NULL`.

### C-2: Fix SELECT column coverage gap

The existing `listNewReports()`, `listAllReports()`, and `getReport()` functions SELECT only 7 columns and omit `claimed_by` and `claimed_at`. The new `resolution` and `resolved_at` columns must NOT repeat this omission.

**Mandatory:** All SELECT statements in the store that return `TelegramReport` must project all columns:
```sql
SELECT id, message_id, text, from_agent, priority, status,
       created_at, claimed_by, claimed_at, resolution, resolved_at
FROM telegram_reports
```

Also update `serializeReport()` in `telegramReportTools.ts` to include `resolution` and `resolved_at` in the JSON output (currently omits claimed_by/claimed_at — fix both at once in this sprint).

### C-3: created_at is INTEGER, not TEXT

The BATCH spec references `resolved_at TEXT` — correct for resolved_at (ISO string is fine). But note that `created_at` in this table is `INTEGER` (unixepoch), not TEXT, as confirmed in the existing DDL. Developer must not confuse the two columns.

`resolved_at` as TEXT (ISO 8601) is acceptable — matches `claimed_at TEXT` pattern already in use.

### C-4: Schema migration pattern

Use the established try/catch pattern (lines 266-267 in schema-system.ts), not `ALTER TABLE ... IF NOT EXISTS` (SQLite does not support that syntax):

```typescript
// Task 1849 — resolution tracking
try { db.exec(`ALTER TABLE telegram_reports ADD COLUMN resolution TEXT NOT NULL DEFAULT 'none'`); } catch {}
try { db.exec(`ALTER TABLE telegram_reports ADD COLUMN resolved_at TEXT`); } catch {}
```

Note: `resolution` should be `NOT NULL DEFAULT 'none'` (not nullable) to avoid three-value logic in WHERE clauses. The BATCH spec has this correct.

### C-5: listUnresolvedReports — query correctness

The BATCH spec Step 4 pseudocode conflates "unresolved" with "claimed+monitoring". The correct predicate is:

```sql
SELECT ... FROM telegram_reports
WHERE resolution NOT IN ('fixed', 'wontfix', 'duplicate')
  AND status != 'processed'
ORDER BY created_at ASC
```

This includes `none` (old reports) and `monitoring` — both should remain visible. Do NOT filter out `none` in `listUnresolvedReports` as old reports that predate resolution tracking deserve review too.

### C-6: Dev-team flow — Step 4 loop-safety guard

The risk register flags a potential infinite loop: `monitoring` reports stay visible forever, so Step 4 will perpetually retrigger Step 1.

**Mandatory flow guard:** When `listUnresolvedReports()` returns ONLY monitoring reports (no `new` reports), the dev-team cron must NOT re-enter Step 1. It must log the monitoring count to WORK and proceed to idle:

```
Step 4 logic:
  new = read_telegram_reports(status="new")
  if new.length > 0 → Step 1

  unresolved = listUnresolvedReports() filtered to non-monitoring
  if unresolved.length > 0 → Step 1

  monitoring_only = listUnresolvedReports() filtered to monitoring
  if monitoring_only.length > 0:
    send_telegram(work, "N report(s) in monitoring — no action needed.")

  archive all fixed|wontfix|duplicate → process_telegram_report(id)
  send_telegram(work, "Dev loop idle.") → EXIT
```

This prevents the monitoring state from becoming a perpetual loop trigger.

### C-7: Index — compound preferred over single-column

Single-column index on `resolution` is acceptable for current scale. However, the dominant query pattern (`WHERE resolution NOT IN (...) AND status != 'processed'`) would benefit from a compound index:

```sql
CREATE INDEX IF NOT EXISTS idx_telegram_reports_resolution
  ON telegram_reports(status, resolution)
```

This is a recommendation, not a blocker. Developer may use the single-column index proposed in the ARCH_BRIEF if compound index testing is out of SPRINT-S scope.
