# TASK_1383 — Fix: CRITICAL macro alerts not dispatched (notified_telegram=0)

## Status: IMPL COMPLETE — pending QA

## Root Cause

Step A2.5 of `intelligenceCycleJob.ts` inserts the macro alert into the DB.
Step E of the **same cycle** builds `recentAlertHistory` from the DB using a 7-hour
look-back window — which already includes the just-inserted alert. `shouldSuppressAlert`
Rule 1 then finds the same indicator/signal in history, fires suppression, and calls
`markAlertNotifiedFn(alert.id)` — marking `notified_telegram=1` WITHOUT sending.

On the **next cycle**, step A2.5's `INSERT OR IGNORE` dedup query (keyed on
`macro-{today}-{name}-{level}`) finds the existing row and skips re-insertion.
`readUnnotifiedAlerts` returns nothing for that alert (already marked notified=1).
The user never receives the alert.

The 2 stuck alerts (`notified_telegram=0` not `=1`) are from cases where this exact
suppression path was not reached — meaning the history query failed silently or the
timing was slightly different, leaving them permanently unreachable by Step E because
A2.5 prevents re-insertion.

## Fix

**File changed**: `apps/mcp-server/src/scheduler/news-analysis/intelligenceCycleJob.ts`

Line ~949 — MACRO alerts now bypass `shouldSuppressAlert` entirely in Step E:

```typescript
const suppress = isMacroAlert ? false : shouldSuppressAlert(...)
```

**Rationale**: Step A2.5's `INSERT OR IGNORE` (keyed on `macro-{today}-{name}-{level}`)
already provides once-per-indicator-per-day dedup. Cooldown suppression in Step E was
redundant and caused first-send failures to permanently drop the alert.
