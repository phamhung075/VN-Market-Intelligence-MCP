## TLDR

Wire a daily cron job (`accuracyDigestJob`) that computes system accuracy over the past 30 days by querying `signal_outcomes` table, formats a Telegram digest message per AC-11 spec, and sends to WORK channel at 07:00 UTC daily. Job includes DB-backed dedup guard, graceful-skip on empty outcomes, and AC-8 all-neutral edge case handling. Task spans 6 files (3 new, 3 modify) across DDD layers per architect spec.

## Acceptance Criteria

| ID | Criterion |
|---|---|
| AC-1 | `accuracyDigest` cron registered in `cronConfig.ts` with expression `0 7 * * *` (env override `CRON_ACCURACY_DIGEST`) |
| AC-2 | Job queries `cron_job_runs` dedup guard; exits without send if already run today |
| AC-3 | When `signal_outcomes` empty or zero resolved rows, job logs info + exits without error or Telegram send |
| AC-4 | Overall accuracy = (total correct) / (total correct + incorrect) across all 30-day rows; null when < 10 total resolved rows; displayed as percentage 1 decimal (e.g. `63.4%`) |
| AC-5 | Top 3 signal types by accuracy rate, min 3 samples per type, aggregated across all stocks (no per-stock grouping) |
| AC-6 | Bottom 3 signal types by accuracy rate (same sample minimum); can overlap with top 3 if < 6 total eligible types |
| AC-7 | "New" stocks = stock_code with < 3 resolved rows across all signal types. Report count: `X stocks with <3 samples (New)` |
| AC-8 | When all resolved rows have `outcome_24h = 'neutral'` (zero correct/incorrect rows), send short digest: `Sistema accuracy: n/a (all outcomes neutral — no directional resolution possible today)` + "New" count |
| AC-9 | Telegram sent via `sendTelegramWork(text)` to `TELEGRAM_INFO_WORK_CHANNEL_ID` |
| AC-10 | DB queries complete in ≤200 ms on 50k-row table; reuse existing indices (`idx_signal_outcomes_created_at`, `idx_signal_outcomes_stock_code`) |
| AC-11 | Telegram body format per spec (date, system accuracy line, top 3 section, bottom 3 section, new stocks line, no emoji, space-separated numbers) |
| AC-12 | 3 smoke tests: (1) empty outcomes → exits without send (spy on `sendTelegramWork`), (2) all-neutral outcomes → sends short digest, (3) normal case ≥6 eligible types → verifies top-3 and bottom-3 in message |

## Implementation Notes

**SQL query shape** (architect spec § Design Decisions, FR-2):

Three synchronous queries via `bun:sqlite`:

```sql
-- Part 1: Per-signal-type aggregation (GROUP BY signal_type)
SELECT
  signal_type,
  COUNT(CASE WHEN outcome_24h IN ('correct','incorrect') THEN 1 END) AS total,
  COUNT(CASE WHEN outcome_24h = 'correct' THEN 1 END)                AS correct
FROM signal_outcomes
WHERE predicted_direction != 'NEUTRAL'
  AND created_at >= datetime('now', '-<days> days')
GROUP BY signal_type
HAVING total >= 3
ORDER BY signal_type;

-- Part 2: System-level totals
SELECT
  COUNT(CASE WHEN outcome_24h IN ('correct','incorrect') THEN 1 END) AS totalResolved,
  COUNT(CASE WHEN outcome_24h = 'correct' THEN 1 END)                AS totalCorrect
FROM signal_outcomes
WHERE predicted_direction != 'NEUTRAL'
  AND created_at >= datetime('now', '-<days> days');

-- Part 3: New stocks count (< 3 resolved rows)
SELECT COUNT(*) AS newStocksCount
FROM (
  SELECT stock_code
  FROM signal_outcomes
  WHERE predicted_direction != 'NEUTRAL'
    AND created_at >= datetime('now', '-<days> days')
  GROUP BY stock_code
  HAVING COUNT(CASE WHEN outcome_24h IN ('correct','incorrect') THEN 1 END) < 3
);
```

Then add a 4th query for AC-8 discrimination:

```sql
-- Part 4: Count all-neutral rows (for neutralOnlyRows field)
SELECT COUNT(*) AS neutralOnlyRows
FROM signal_outcomes
WHERE outcome_24h = 'neutral'
  AND predicted_direction != 'NEUTRAL'
  AND created_at >= datetime('now', '-<days> days');
```

All queries hit existing indices. No new indices needed. ≤200 ms on 50k-row table (architect verified).

**`buildAccuracyDigestText()` logic:**
- Input: `SystemAccuracyDigestStats` + date string (YYYY-MM-DD)
- Output: Telegram body string per AC-11 format
- Special case: `totalResolved === 0 && neutralOnlyRows > 0` → return short digest (AC-8)
- Otherwise: full digest with system accuracy % + top 3 + bottom 3 + new stocks line

**Cron registration pattern** (matching `alertDigestJob.ts`):
- `isRunning` guard prevents concurrent job execution
- `alreadySentToday()` prevents duplicate sends on day boundary (DB-backed, not in-memory)
- Dynamic import of telegram module inside try/catch
- Failure: log.warn, no crash to cron process

## Q&A / Clarifications

**Q: Why 4 queries instead of 1 complex CTE?**  
A: Architect design decision (FR-2 spec). Three separate queries allow SQLite planner to optimize each independently. Single complex CTE may confuse planner. All 4 complete within 200 ms budget on 50k-row table.

**Q: What if `signal_outcomes` table doesn't exist?**  
A: Wrap queries in try/catch, return zero-valued stats, job exits gracefully (AC-3). No error to BUG channel.

**Q: Can same signal type appear in both top-3 and bottom-3?**  
A: Yes, only when fewer than 6 total eligible types exist (architect spec). Not a bug — report as-is.

**Q: When does Cron expression `0 7 * * *` fire?**  
A: 07:00 UTC every day (= 14:00 GMT+7 Vietnam time). After VN morning session closes (09:00 VN = 02:00 UTC), before evening cowork cycle. Collision check: minute=0 hour=7 UTC is free (cronHealthAlert fires 00:00 UTC).
