## Diagnosis

### Root Cause Chain

1. **Container restart after TASK_1399 bind-mount fix.**  
   TASK_1399 merged the `./apps/mcp-server/reports:/app/reports` bind-mount into `docker-compose.yml` and killed a zombie bun process. The mcp-server container was restarted at approximately 17:00 UTC.

2. **eveningSummaryJob fired at 16:47 UTC (22:47 Vietnam) in the OLD container.**  
   At that time, the old container's `market_prices` table had a stale VNINDEX row: `price=1300, updated_at=2026-04-18`. The VPS price-fetch had not yet populated fresh data after the restart. The `rag_analyses` table also had zero rows (news indexing was still catching up). The job ran successfully with stale inputs and wrote bad data to the reports file.

3. **Same-day dedup guard blocked re-runs.**  
   `eveningSummaryJob` writes a `market_messages` row with `from_agent='evening-summary'` after each run. The `alreadySentToday()` check (`sent_at >= date('now')`) found this row and silently skipped all subsequent invocations for the rest of the day — even after fresh data arrived.

4. **Fresh data arrived but was never used.**  
   After restart: VNINDEX pushed to DB at `2026-04-28T08:59:04` (price=1875.84). News: 154 articles indexed by 18:04. Alerts: 73 in last 24h. None of this was captured in the report because the dedup guard had already fired.

5. **2026-04-29 report shows empty data.**  
   This is correct behavior — it is currently 02:05 Vietnam time on April 29. The market has not opened yet. The April 29 report will be populated when eveningSummaryJob runs at 22:30 VN time on April 29.

---

## Structural Bug Identified

The dedup guard is too aggressive. It prevents re-generation even when:
- The previous run used demonstrably stale VNINDEX data (>25h old at time of report generation)
- The `isVnIndexFresh` guard in the job body already handles this case for Telegram suppression

**The dedup guard should be conditioned on whether the previous run produced valid (fresh) data,** not just whether it ran at all. If `vnIndex.fetchedAt` was stale when written, the report slot should remain open for a retry.

## Remaining Issue (New Task Required)

**Structural bug:** `eveningSummaryJob` dedup guard does not check whether the previous run used fresh data. If the job fires during a VPS downtime window and records a stale report, no retry is possible for the rest of the day.

**Recommended fix:** Add a staleness check to `alreadySentToday()`: if the last `market_messages` row for `evening-summary` today was generated with stale VNINDEX data (check `vnIndex.fetchedAt` in the persisted report JSON, or add a `data_quality` flag), allow a re-run.

**Priority:** Medium — affects any day where VPS is down during the 22:30 cron window and recovers later the same day.

## Fix Implementation (TASK_1401-fix)

**Branch:** `fix/1401-dedup-guard`

**Change:** `alreadySentToday()` in `eveningSummaryJob.ts` now fetches the `content`
of the most recent today's `evening-summary` row (instead of a `COUNT(*)`).
If the content contains ` (cũ)` — the stale-data marker written by
`formatEveningSummaryLines` when `isVnIndexFresh()` is false — the function
returns `false`, re-opening the dedup slot for a retry.

If no row exists today, or the row does not contain ` (cũ)`, behaviour is
unchanged from before.

**Test file:** `apps/mcp-server/src/__tests__/1401-dedup-guard-stale-retry.test.ts`
- stale row → returns false (retry allowed)
- fresh row → returns true (retry blocked)
- no row → returns false (first run)
- different agent row → returns false (not counted)
