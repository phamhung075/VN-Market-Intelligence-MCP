`/api/push-reuters` and `/api/push-tradingeconomics`. However there are NO
systemd `.service` files for either script in `vps-scripts/`. The VPS only runs

`vn-foreign-flow.service`, `vn-sbv-fetch.service`, and `vn-bctc-fetch.service`.

The push scripts for Reuters and TE are never invoked automatically on the VPS.

`readLatestNewsTimestamp()` which queries `MAX(created_at) FROM rag_analyses`.

but Reuters/TE is dead, the watchdog passes silently.

### 2.3 Approach

The staleness guard in `vpsProxyWatchdogJob.ts` must distinguish Reuters/TE
from the general news stream. The `rag_analyses` table has a `source` column.
The new readers query `MAX(created_at) FROM rag_analyses WHERE source = 'reuters'`
and `source = 'tradingeconomics'` respectively.

For the fallback chain in `pollNews.ts`, the pattern is:

```
1. Attempt reuters fetcher (VPS push path — already stubbed to [] in defaultPollNews)
   NOTE: The scheduled cycle stubs reuters to []; the real push comes from
   POST /api/push-reuters. Fallback only activates when VPS push is absent.
2. After Step A completes, check: did any reuters items arrive via push in last 90 min?
   (query rag_analyses WHERE source='reuters' AND created_at > now - 90min)
3. If count == 0 AND newsapi.enabled → call newsapi fetcher → process items
4. If all macro sources dark → sendTelegramBug once per 4h (use module-level lastAlertAt)
```

The VPS systemd service files must follow the exact same pattern as
`vn-news-fetch.service`: `Type=simple`, `Restart=always`, `RestartSec=10`,
`MemoryMax=512M`, `StandardOutput=append:/var/log/vn-reuters.log`.

### 3.3 Approach

`validate_financial_figures()` is a pure function (no I/O):

```python
def validate_financial_figures(
    total_assets: float | None,
    total_equity: float | None,
    total_liabilities: float | None,
    operating_margin: float | None,
    net_revenue: float | None,
) -> float:
    """
    Returns confidence_financial in [0.0, 1.0].
    Hard violations → 0.0 immediately.
    Soft violations → subtract 0.2 per violation, floor 0.1.
    """
```

Rules (from BA spec REQ_1345 § 2.3):

| Rule | Type | Action |
|------|------|--------|
| total_assets < total_equity (both non-None, non-zero) | Hard | return 0.0 |
| total_assets < 0 | Hard | return 0.0 |
| total_liabilities < 0 | Hard | return 0.0 |
| operating_margin outside (-5.0, +1.0) — note: stored as ratio not pct | Soft | -0.2 |
| net_revenue <= 0 (non-holding company — source_type == 'bctc') | Soft | -0.2 |
| equity < 0 | Soft | -0.2 |

The function is called AFTER tables are parsed into structured figures. The call
site in `process_pdf()` extracts the key figures from `tables` before calling the
function — this extraction logic stays in domain (no infra knowledge needed, just
string parsing of table cell values already extracted by the engine port).

**Vietnamese number format pre-condition:** Before validation, cell values must
have parentheses stripped and negatives applied: `"(1.234)"` → `-1234.0`. This
normalization happens in the extraction pipeline before `validate_financial_figures`
is called. Developer must confirm this is already handled in `extraction_engine.py`
or add it there (infrastructure layer — correct placement).

## 4. Task 1345c — Polymarket Staleness Guard

### 4.1 Problem (confirmed from codebase)

`mcp.config.json` already shows `"predictionMarkets": { "enabled": true, ... }`.
This rules out Mode A (disabled flag). The root cause is Mode B: `fetchPolymarkets()`
is failing and the fallback silently reuses the cached snapshot (line 346–350 of
`predictionMarketJob.ts`). The `storeSnapshot()` is called with the cached rows,
which does NOT update `fetched_at` — INSERT OR REPLACE only updates `updated_at`.
So `fetched_at` stays at 2026-04-01. There is no staleness check before
`detectPredictionSignals()`.

### 4.2 Files to Change

| File | Action | Change |
|------|--------|--------|
| `apps/mcp-server/src/scheduler/macro/predictionMarketJob.ts` | MODIFY | Add `checkStaleness(db, thresholdHours)` helper; call it after `storeSnapshot()` and before `detectPredictionSignals()`; if stale → skip signals + send bug alert (once per 24h via module-level `_lastStalenessAlertAt`) |
| `mcp.config.json` | MODIFY | Add `"staleThresholdHours": 24` under `predictionMarkets` block |
| `apps/mcp-server/src/infrastructure/config.ts` | MODIFY | Add `staleThresholdHours: number` to `PredictionMarketsConfig` type |
| `apps/mcp-server/src/__tests__/1345c-polymarket-staleness.test.ts` | CREATE | Unit tests (see 4.4) |

**Note:** `mcp.config.json` `predictionMarkets.enabled` is already `true` — no
change needed there. The config change is adding the `staleThresholdHours` field.

### 4.3 Approach

```typescript
function checkStaleness(db: Database, thresholdHours: number): { isStale: boolean; ageHours: number } {
  const row = db.prepare(
    "SELECT MAX(fetched_at) AS max_fetched FROM prediction_markets"
  ).get() as { max_fetched: string | null } | null;

  if (!row?.max_fetched) return { isStale: true, ageHours: Infinity };
  const ageMs = Date.now() - new Date(row.max_fetched).getTime();
  const ageHours = ageMs / 3_600_000;
  return { isStale: ageHours > thresholdHours, ageHours };
}
```

The staleness alert dedup uses a module-level `let _lastStalenessAlertAt = 0`
and a 24h cooldown — identical pattern to `lastAlertAt` in `vpsProxyWatchdogJob.ts`.

The `PredictionMarketPollOptions` interface must expose `staleThresholdHours?`
for test injection so the unit test can set a threshold of 0 to force stale.

## 5. Task 1345d — VN-Index Cascade Broadcast Fix

### 5.1 Problem (confirmed from codebase)

The `intelligenceCycleJob.ts` step E sends alerts via `notifyTelegramAlert(alert)`
which is defined in `telegram.ts` lines 505–555. Reading that implementation:
`notifyTelegramAlert` routes to the **BUG channel** (`coreSend("bug", ...)`) —
NOT MARKET, NOT WORK. The comment on line 500 says: "Per CLAUDE.md Alert
Commander exclusivity rule, only Alert Commander sends user-facing alerts to MARKET."

This means every stock alert from the intelligence cycle goes to BUG. There is
no separate `sendTelegramMarket` call for market-wide cascade events anywhere in
`intelligenceCycleJob.ts`.

The BA spec hypothesis is partially correct: the routing does not filter by VIC
specifically. The gap is different — a market-wide summary `sendTelegramMarket`
call is simply absent. All cascade alerts (VIC and others) go to BUG. The user
only sees VIC because VIC is the first or only alert that fires consistently
enough to be noticed.

The fix requires adding a market-wide summary dispatch to MARKET channel when
the alerts being processed have `market-wide cascade` reasoning. This is additive
— it does NOT change how individual per-stock alerts are routed (they stay on BUG
per the Alert Commander rule). The MARKET message is a summary, not per-stock.

### 5.2 Files to Change

| File | Action | Change |
|------|--------|--------|
| `apps/mcp-server/src/scheduler/news-analysis/intelligenceCycleJob.ts` | MODIFY | In step E, after reading `unnotifiedAlerts`, detect market-wide cascade batch (alerts where `signals[].type = 'news_mention'` AND `message` includes `'market-wide cascade'`). If the batch contains >= 2 distinct `actionCode` values, compose a summary and call `sendTelegramMarket`. This is ONE send per cycle, not one per stock |
| `apps/mcp-server/src/__tests__/1345d-vnindex-cascade-broadcast.test.ts` | CREATE | Unit tests (see 5.4) |

`telegram.ts` and `cascadeEngine.ts` receive no changes.

### 5.3 Approach

The step E loop in `_runCycle()` already iterates `unnotifiedAlerts`. Before
the per-alert loop, add a pre-pass:

```typescript
// Market-wide summary — detect if this batch contains VN-Index cascade impacts
const marketWideAlerts = unnotifiedAlerts.filter(a =>
  a.signals.some(s => s.message?.includes("market-wide cascade"))
);

if (marketWideAlerts.length >= 2) {
  const stockList = marketWideAlerts.map(a => a.actionCode).join(", ");
  const maxSeverity = marketWideAlerts.some(a => a.severity === "critical")
    ? "critical" : "high";
  const summaryMsg =
    `[VN-Index] Tác động toàn thị trường — ${maxSeverity.toUpperCase()}\n` +
    `Cổ phiếu bị ảnh hưởng: ${stockList}\n` +
    `Nguồn: market-wide cascade event`;
  try {
    await sendTelegramMarket(summaryMsg, {
      persist: { from_agent: "intelligence-cycle", message_type: "market_wide_cascade" }
    });
  } catch { /* non-fatal */ }
}
```

This change is strictly additive. The existing per-stock loop (which routes to
BUG via `notifyTelegramAlert`) is unchanged. The minimum count of 2 prevents
a single-stock cascade from triggering a market-wide broadcast (avoids noise).

**CycleDeps interface addition:**
Add `sendMarketFn?: (text: string) => Promise<boolean>` to `CycleDeps` so the
test can inject a spy and verify the MARKET send occurs without hitting Telegram.
