# TASK 1789 Handoff — earningsCalendar Q4-2025 overdue shows 16 days instead of 30

## Status: IMPL_DONE — ready for QA

## Root Cause

`getDeadlineForQuarter()` in `apps/mcp-server/src/domain/services/financial-reports/earningsCalendar.ts` used local-time Date arithmetic:

```typescript
const qEnd = new Date(`${year}-12-31`);  // UTC midnight
qEnd.setDate(qEnd.getDate() + 105);      // setDate = LOCAL time
```

`new Date('2025-12-31')` parses as UTC midnight (correct), but `setDate()` operates in the server's local timezone. In Europe/Paris (UTC+1 in winter, UTC+2 after the Mar 29 2026 DST change), adding 105 days crosses the DST boundary and lands 1 hour short of UTC midnight:

- Result: `2026-04-14T23:00:00Z` (ISO slice = `2026-04-14`)
- Correct: `2026-04-15T00:00:00Z` (ISO slice = `2026-04-15`)

`classifyFilingStatus` then computed `Date.UTC(2026,3,14) - Date.UTC(2026,3,30) = -16` days, not the correct `-15`.

For the standard path (90 days), the same bug produced `2026-03-30` instead of `2026-03-31`, giving `-31` days overdue instead of the correct `-30`.

## Fix

Replaced `new Date(ISO_STRING) + setDate(local)` with `Date.UTC(y,m,d) + setUTCDate(UTC)` in `getDeadlineForQuarter()`:

```typescript
// Q4 standard: Dec 31 UTC + 90 days
const qEnd = new Date(Date.UTC(year, 11, 31));
qEnd.setUTCDate(qEnd.getUTCDate() + 90);
// → always 2026-03-31, regardless of server TZ

// Q4 extended (banking/insurance): Dec 31 UTC + 105 days
qEnd.setUTCDate(qEnd.getUTCDate() + 105);
// → always 2026-04-15, regardless of server TZ
```

Q1–Q3 use the same pattern with `Date.UTC(year, month, day)` anchors.
