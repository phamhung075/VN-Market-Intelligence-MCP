- **Description:** `cron-registry.json` has `schedulerFileCount: 29` since sprint 085 (task 1290 added `franceSummaryJob`). Test 1190 line 281 still asserts `toBe(28)`. The `it(...)` description on line 280 also states `"=== 28"`. Both must be updated to `29`.
- **Input:** `docs/data/cron-registry.json` — `schedulerFileCount: 29` (SSOT)
- **Output:** Test reads the actual JSON value and asserts it equals `29`
- **Business rule:** `schedulerFileCount` assertion must always track the SSOT file value; never hardcode a stale number.
- **DDD layer:** test

**Exact changes — `src/__tests__/1190-pipeline-watchdog.test.ts`**

| Line | Before | After |
|------|--------|-------|
| 280 | `it("schedulerFileCount === 28", () => {` | `it("schedulerFileCount === 29", () => {` |
| 281 | `expect(json.schedulerFileCount).toBe(28);` | `expect(json.schedulerFileCount).toBe(29);` |

### FR-3: Fix test 137 — Step E unconditional behavior drift

- **Description:** Task 1255 moved Step E (`readUnnotifiedAlerts` → `sendAlertsFn`) outside the `if (marketHours)` block. Step E now runs on every cycle regardless of market hours (confirmed: `intelligenceCycleJob.ts` line 795 comment: "Step E: Send HIGH/CRITICAL alerts to Telegram — unconditional (Task 1255)"). The test case labelled `"Step E is skipped outside market hours"` asserts `readCalled === false` — that expectation is now wrong.
- **Input:** `isMarketHoursFn: () => false` passed to `runIntelligenceCycle`
- **Output after fix:** `readUnnotifiedAlertsFn` IS called; `readCalled === true`; `telegramAlertsSent === 0` (mock returns empty array — unchanged)
- **Business rule:** Off-hours sigma alerts (USD/VND, gold, macro) from step A2.5 (runs 24/7) must reach Telegram without waiting for market hours.
- **DDD layer:** test

**Exact changes — `src/__tests__/137-fix-alert-pipeline.test.ts`**

| Line | Before | After |
|------|--------|-------|
| 430 | `it("Step E is skipped outside market hours", async () => {` | `it("Step E runs unconditionally (even outside market hours)", async () => {` |
| 453 | `expect(readCalled).toBe(false);` | `expect(readCalled).toBe(true);` |
| 454 | `expect(result!.telegramAlertsSent).toBe(0);` | unchanged — mock returns `[]`, so `telegramAlertsSent` stays `0` |

**Timeout investigation (two 30 s CYCLE_TIMEOUT spans in the same describe block):**

- `CYCLE_TIMEOUT = 30_000` is defined at line 267 and applied to every case in the `"Task 137 — Step E"` describe block (lines 304, 337, 372, 407, 428, 455).
- The timeout is not caused by the drift — it was set deliberately because `runIntelligenceCycle` has internal `withTimeout` guards designed for the real 2-minute cycle window.
- The previously-failing "Step E is skipped" case does not time out; it fails immediately on the wrong `toBe(false)` assertion. No timeout fix is needed.
- Verdict: leave all `CYCLE_TIMEOUT` values unchanged; only the description string and one assertion need updating.
