# PO — `.signal_queue.rows[]` long-tail types (lazy-load sibling)

**Parent:** `docs/agents/po/flow/triage-signals.md` § Live `.signal_queue.rows[]` inbox
**Load trigger:** a Pipeline-B (`.signal_queue.rows[]`, `to==po`) signal's `type` is one of the 17 below — these are individually low-volume (≤1-4 live fires each as of 2026-08-01, except `bctc_image_fetch_degraded` added 2026-08-23 and the five system-auditor capacity/WARN types added 2026-08-28) so they are split out of the hot-path doc per the waterfall/lazy-load size-cap convention.

Same dedup discipline as the parent doc: "dedup-check" = scan `.task_board.backlog[]` + `.ready[]` + `.in_progress[]` + `.review[]` + `.qa[]` (NON-TERMINAL LANES — never a status-token enum).

| `type` | From | Action | Routing |
|---|---|---|---|
| `routing-gap` | `cowork-team` | Claim that a signal/type has no handler. **VERIFY THE CLAIM FIRST** against the live routing table + task_board before acting — the only live example was itself a false positive (claimant's jq queried a nonexistent `.task_board.rows` path; the defect it flagged was already tracked). If the gap is real and untracked → mint FIX row (shape per `repair_task_request` in the parent doc). If verified false → `status: "RETRACTED"` + one-line reason, no mint. | FIX (verified real) OR RETRACTED (false positive) |
| `orch-health-finding` | `orch-sentinel` | Finding from `docs/data/orch-sentinel-scorecard.md` (read `payload_ref`). Live rows often ALREADY cite a tracked row in their own `summary` (e.g. `"Tracked: CLEAN-COWORK-DISPATCHER-TELEMETRY-DRAIN-DIR (REVIEW)"`) — if so, log ack (`status: "triaged"`, `disposition` = the cited row id), no mint. Else dedup-check, mint FIX/CLEAN if untracked. | ACK (already tracked, cited in summary) OR FIX/CLEAN (untracked) |
| `tool_contract_gap` | `cowork-team` | An MCP tool's contract violates a caller's implicit assumption (ordering, missing filter, etc). Dedup-check is HIGH-STAKES here — a live "no prior art" claim was proven wrong (a covering row existed but wasn't grep'd); do a full-text board grep on the ROOT CAUSE description, not just `check_id`/title. If a covering row exists → ENRICH it (priority bump if this occurrence raises severity, `origin_signal_id` back-ref), do NOT re-mint; flip signal → RESOLVED only when the covering row reaches `done_verified`. If genuinely new → mint FIX, `zone: apps/mcp-server/` (or the owning service). | ENRICH existing (dedup) OR FIX (new) |
| `bctc-data-quality-anomaly` | `dev-team` (forwarding bctc-analyst) | BCTC extraction data-quality defect on one ticker+period (`guard-key` in `summary` = `data-quality-anomaly:{TICKER}:{period}`). Dedup vs any in-flight generic batch-corruption FIX (e.g. `FIX-BCTC-REPARSE-BATCH-CORRUPTION` family) — if the batch row already covers this ticker/period class, fold (no mint). Else mint a ticker+period-specific FIX, `zone: apps/pdf-extractor/` or `apps/bctc-analyst/` per the failing stage named in `summary`. | FOLD (batch row covers it) OR FIX (ticker-specific, new) |
| `config_drift` | `cowork-team` | A documented/known config landmine has detonated (drift from an intended value). Dedup-check FIRST — live pattern shows these are usually ALREADY prior-art-tracked (`"evidence-attached-no-new-row"`); if a matching open row exists, attach this occurrence as corroborating evidence, no new mint. Else mint FIX. | ATTACH-EVIDENCE (prior art) OR FIX (new) |
| `context_bloat_breach` | `context-bloat-backstop-hook` | A notebook breached its context-bloat budget (`payload_ref` = `docs/signals/processed/context-bloat-*.json`). NOT a PO-owned fix — route to `claude-manager-helper` for prune: mint a lightweight `.task_board.backlog[]` CHORE, `owner: claude-manager-helper`, `zone: docs/agent-memory/notebooks/`. Log + `status: "triaged"`. | Hand off — CHORE to claude-manager-helper (prune) |
| `methodology-flag` | `cowork-team` (or `financial-analyst` per `.claude/skills/signal-dashboard/SKILL.md` § Receivers) | Agent-reported methodology/logic gap (TNB violation, OR — per the live example — an alert-commander gate design gap). PO JUDGMENT CALL, not an auto-route: read the payload, decide (a) rewire the flagged logic — mint FIX row targeting the owning agent/flow, (b) confirm current behavior is correct-by-design — log + `pendingObservations[]`, no mint, or (c) WONTFIX — log with reason, no mint. Never auto-mint without reading the argument; never silently drop either. | FIX (rewire) OR pendingObservations (confirmed correct) OR WONTFIX (logged) |
| `notebook_unparseable_breach` | `notebook-auto-prune-hook` | A notebook file failed to parse (`payload_ref` = `docs/signals/processed/notebook-unparseable-*.json`). Same hand-off pattern as `context_bloat_breach` — route to `claude-manager-helper` for repair, `zone: docs/agent-memory/notebooks/`. | Hand off — CHORE to claude-manager-helper (repair) |
| `ops_followup_request` | `dev-team` | Follow-up asks from a COMPLETED ops remediation (`payload_ref` = the recon doc, e.g. `docs/vps-sources/.../recon.md`, enumerating N numbered follow-ups). Read `payload_ref`, mint ONE FIX/CHORE row PER distinct numbered follow-up (do not collapse unrelated follow-ups into one row — matches the `ci_red` file-scoped-row precedent in the parent doc), `owner: ops`, `zone` per the follow-up's own target (VPS service / deploy script / freshness check). | `.task_board.backlog[]` — one FIX/CHORE per follow-up, owner:ops |
| `recurring_churn_escalation` | `dev-team` | A Tier-1/Tier-2 probe is churning — re-firing every tick on an already-known-dead check with no open fix, burning cycles without new signal. Read `summary` for the named dead component(s). (1) If the underlying dead component has NO open FIX row yet → mint one (the actionable root cause). (2) Separately, if the probe itself lacks an "acknowledged-failure" suppression (so it keeps re-escalating despite an open fix already tracking the root cause) → mint a SECOND, distinct FIX row for the suppression-guard gap (dedup-checked against any existing `*-PROBE-SUPPRESSION-*`/`*-ACK-FAILURE-*` row first) — do not conflate the two asks into one row. | up to 2 FIX rows: (1) dead-component root cause, (2) probe suppression-guard gap |
| `triage-persist-request` | `dev-team` | dev-team's own Step-1 triage produced a BATCH but could not persist it (WIP-saturation or lock contention) — `payload_ref` names the decision-journal doc carrying the EXACT rows dev-team wants minted. Read `payload_ref`, mint each named row into `.task_board.backlog[]` at `status: "BACKLOG"` VERBATIM per the ask (dedup-check each against NON-TERMINAL LANES first — dev-team's own dedup pass may be stale by the time PO reads it). Priority order = the order named in the request. | `.task_board.backlog[]` — N rows verbatim per payload_ref, dedup-checked |
| `bctc_image_fetch_degraded` | `mcp-server` (`push_bctc_refined_unit`, `bctcImageFetchDegradedSignalWriter.ts` — rising-edge fire on ≥2 `image_unavailable`-flagged refine units for the same report) | BCTC refine batch degradation, symptom-only at signal time (root cause NOT pre-diagnosed — do not assume which layer failed) — `payload.report_id` + `payload.affected_unit_ids[]`, `dedup_key` = `bctc_image_fetch_degraded:{report_id}` (already stamped). Dedup-check on `dedup_key` first — if an open row already covers this `report_id` → fold, append occurrence. If new → mint FIX naming `get_bctc_page_image`/pdf-extractor/stored-PDF as candidate layers to investigate, `zone: cross-service/`, `next_agent: developer`, priority from `severity`. | FOLD (`dedup_key`) OR FIX (new) |
| `container_capacity_pressure` | `system-auditor` | A named container is near/at its memory cap (`payload.container`, `payload.peak_percentage`, `payload.headroom_mib`, `payload.cap`, `dedup_key` already stamped, live example `auditor-capacity-pdf-extractor-thin-headroom-76mib`; `to=po`). **Verify the premise before acting** — live precedent: a "transient pressure, healthy GC sawtooth" verdict was REFUTED because kernel dmesg showed two real CONSTRAINT_MEMCG OOM kills of child workers the container-level `OOMKilled` flag cannot see (child kills leave `OOMKilled=false`, `ExitCode=0`). Dedup-check NON-TERMINAL LANES on the named container first — capacity is a recurring WARN class, ONE open row per container, never one per fire. If new: `severity` WARN with no incident lineage → `pendingObservations[]` + re-check next tick; CRITICAL/HIGH or corroborated by a kill record → mint FIX `zone: apps/{service}/`, priority from `severity`. | FOLD (same container) OR pendingObservations (single WARN) OR FIX (CRITICAL/kill-corroborated) |
| `launchd_tracking_gap` | `system-auditor` | A launchd job's tracking state has a gap (missing/never-written marker file, stale `last_fired` — the auditor cannot see a launchd job's live state). Dedup-check on the named job/marker first. If new → mint FIX targeting the tracking gap (`zone: apps/mcp-server/` auditor runner, or the job's own launchd plist zone), priority from `severity`. | FOLD (same job) OR FIX (new) |
| `memory_loop_breach` | `system-auditor` | A memory-growth loop breached a cap or threshold (`payload` names the container/process, `dedup_key` already stamped). **Verify the premise before acting** — memory signals are the class where a benign-verdict trap was measured live (see `container_capacity_pressure` row above: child-process OOM kills are invisible to container-level flags). Dedup-check NON-TERMINAL LANES on the named container/process first; fold repeats onto the open row. If new and CRITICAL/HIGH, or corroborated → mint FIX `zone: apps/{service}/`; single WARN blip with no history → `pendingObservations[]`. | FOLD (same container) OR FIX (CRITICAL/corroborated) OR pendingObservations (single WARN) |
| `memory_pressure_transient` | `system-auditor` | A transient memory-pressure reading (usually WARN, `payload` names container + peak/cap). By its own name this class is self-limiting — do NOT mint on a single tick (`feedback_auditor_mcpserver_a21_a30_memory_fp_reemit_churn` discipline): log + `pendingObservations[]`, re-check next tick. Mint only on recurrence or CRITICAL severity, `zone: apps/{service}/`. | `pendingObservations[]` (single fire) OR FIX (recurring/CRITICAL) |
| `observability_defect` | `system-auditor` | A component emits no logs/metrics in production — the observability layer itself is blind for that component (`summary` names the module, `dedup_key` = `observability_defect:{module}:{finding}`, already stamped — live example: `ocrworker_module_emits_no_logs_in_production`). Dedup-check on `dedup_key` first (fold repeats). If new → mint FIX targeting the named module's logging/telemetry (`zone` from the module's owning service), priority from `severity`. | FOLD (`dedup_key`) OR FIX (new) |

**Coverage guard:** these 17 `type` values are picked up automatically by `scripts/audits/guard-signal-type-coverage.sh` (wired into `.github/workflows/ci.yml`'s `signal-type-coverage-guard` job — see `docs/agents/po/flow/triage-signals.md` § Regression verifier — signal-type coverage guard), which parses the `type` column straight out of THIS table (plus the parent doc's Pipeline-B table) rather than hand-maintaining a separate allowlist (FIX-SIGNAL-ROUTING-ROWS-COVERAGE-GAP-DEEPDIVE, 2026-08-22 — the prior hand-synced array is exactly what let 5 new live types go unrouted for 3 weeks unnoticed). Adding/removing a `| \`type\` |` row here is now sufficient by itself; no second array to keep in lockstep.
