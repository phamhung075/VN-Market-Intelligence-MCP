# REQ-018: Scheduled Database Audit & Cleanup Job

status: READY_FOR_ARCHITECT
sprint: 018
po_vision: "Add a dataAuditJob.ts scheduler that auto-cleans safe bad data, flags issues via agent_feedback, and sends a single Telegram summary so the operator knows DB health without querying it manually."

---

## User Story

As a Vietnamese stock investor using Claude,
I want the system to automatically audit its own database every night and report any data
quality issues in one Telegram message,
So that I can trust the pipeline's inputs (prices, news, BCTC) without manually inspecting
SQLite tables and without stale or corrupted data silently distorting alerts or briefings.

---

## Functional Requirements

### FR-1: AuditFinding data contract

- Description: A shared TypeScript interface used as the accumulator unit throughout both audit
  modes. Every check appends one `AuditFinding` entry per table/check combination.
- Input: Result of a SQL query or LanceDB count call.
- Output: Structured finding object.
- Business rule:

```typescript
interface AuditFinding {
  table: string;          // SQLite table name or "lancedb" or "db_overall"
  check: string;          // Short slug: e.g. "zero_price_rows", "stale_alerts_unread"
  severity: "info" | "warning" | "critical";
  rowsAffected: number;   // Rows deleted, updated, or counted as problematic
  action: "auto_cleaned" | "flagged" | "escalated" | "none";
  detail: string;         // Human-readable explanation ≤200 chars
}
```

- DDD layer: domain (pure type — no I/O)

---

### FR-2: runDailyAudit() — lightweight nightly checks

- Description: Exported async function `runDailyAudit(): Promise<AuditFinding[]>` inside
  `src/scheduler/dataAuditJob.ts`. Runs all daily-mode checks listed in FR-4. Target
  wall-clock runtime: < 5 seconds. Returns the full array of findings.
- Input: None (reads from `getDb()` singleton).
- Output: `Promise<AuditFinding[]>`; side-effects: DB writes (deletes/updates), `agent_feedback`
  inserts for warning/critical findings, `system_logs` inserts, Telegram message if issues found.
- Business rule: All SQL runs synchronously inside the Bun SQLite API. The only async
  operations are the Telegram send and the `system_logs` insert at the end.
- DDD layer: infrastructure/scheduler (direct DB access, same pattern as `intelligenceCycleJob.ts`)

---

### FR-3: runWeeklyAudit() — deep checks

- Description: Exported async function `runWeeklyAudit(): Promise<AuditFinding[]>`. Runs all
  daily checks FIRST, then appends the weekly-only checks in FR-5. Target wall-clock
  runtime: < 30 seconds.
- Input: None.
- Output: `Promise<AuditFinding[]>`
- Business rule: Weekly audit calls `runDailyAudit()` internally and merges its findings
  array before continuing with weekly-specific checks. This ensures the nightly state is
  always a subset of the weekly state.
- DDD layer: infrastructure/scheduler

### FR-4: Daily audit check catalogue

All checks run inside `runDailyAudit()`. Each produces exactly one `AuditFinding` unless
the check category has zero rows, in which case it produces a finding with `rowsAffected: 0`
and `action: "none"` — this is the "row count snapshot" mechanism.

| # | Table | Check slug | SQL condition | Auto-clean action | Severity |
|---|-------|-----------|---------------|-------------------|----------|
| D-1 | `market_prices` | `zero_price_rows` | `price = 0 OR price IS NULL` | DELETE rows | warning |
| D-2 | `market_prices` | `stale_price_rows` | `updated_at < date('now','-3 days')` | DELETE rows | info |
| D-3 | `alerts` | `stale_unread_alerts` | `read = 0 AND triggered_at < datetime('now','-30 days')` | UPDATE `read = 1` | info |
| D-4 | `alerts` | `auto_expire_unresolved` | `resolved_at IS NULL AND triggered_at < datetime('now','-60 days')` | UPDATE `resolved_at = datetime('now'), resolution_notes = 'auto-expired by audit'` | info |
| D-5 | `rag_analyses` | `missing_sentiment_or_impact` | `sentiment IS NULL OR impact_score = 0 OR impact_score IS NULL` | Flag only (no delete) | warning |
| D-6 | `rag_analyses` | `null_source_url_old` | `source_url IS NULL AND created_at < datetime('now','-7 days')` | Flag only | info |
| D-7 | `financial_reports` | `failed_validation_unfixed` | `validation_status = 'failed'` | Flag only | warning |
| D-8 | `agent_feedback` | `stale_new_feedback` | `status = 'new' AND created_at < datetime('now','-14 days') AND priority IN ('low','medium')` | UPDATE `priority = 'high'` | warning |
| D-9 | `system_logs` | `old_log_purge` | `timestamp < datetime('now','-60 days')` | DELETE rows | info |
| D-10 | `db_overall` | `row_count_snapshot` | COUNT(*) per major table: `watchlist`, `market_prices`, `alerts`, `rag_analyses`, `financial_reports`, `agent_feedback`, `system_logs` | Log info | info |

Business rules:
- D-1 and D-2 use `DELETE` — zero-price and stale prices are data garbage with no recovery value.
- D-3 and D-4 use `UPDATE` — alerts retain audit history; they are never deleted, only marked.
- D-5 through D-7 use `INSERT INTO agent_feedback` (see FR-7) — a human decision is needed.
- D-8 escalates priority but does not change status — escalated items still appear in `get_feedback`.
- D-9 is a hard delete — system_logs older than 60 days have no operational value.
- D-10 produces one `AuditFinding` per table with `rowsAffected = COUNT(*)` and `action = "none"`.
  This forms the DB health snapshot visible in Telegram and `system_logs`.

### FR-5: Weekly audit check catalogue (additions to daily)

All checks run inside `runWeeklyAudit()` after the daily checks complete.

| # | Table | Check slug | SQL condition | Auto-clean action | Severity |
|---|-------|-----------|---------------|-------------------|----------|
| W-1 | `commodity_prices_history` | `old_commodity_history` | `fetched_at < datetime('now','-180 days')` | DELETE rows | info |
| W-2 | `sbv_rates_history` | `old_sbv_history` | `fetched_at < datetime('now','-180 days')` | DELETE rows | info |
| W-3 | `market_prices_history` | `duplicate_price_history` | Same `(code, DATE(fetched_at))` with multiple rows — see note below | DELETE older rows, keep the one with latest `fetched_at` per `(code, DATE(fetched_at))` | warning |
| W-4 | `rag_analyses` | `duplicate_null_source_url` | `source_url IS NULL AND created_at < datetime('now','-30 days')` — duplicate `source_title` within same `(level, DATE(created_at))` bucket | DELETE all but the newest per bucket | warning |
| W-5 | `tracked_indicators` | `outlier_indicator_values` | `value` outside plausible range per indicator type — see FR-6 for thresholds | Insert `agent_feedback` with `category = 'data_extraction_error'` | critical (oil/gold) or warning (others) |
| W-6 | `alerts` | `orphan_alerts` | `analysis_ids_json` contains IDs not in `rag_analyses` | Flag count only | warning |
| W-7 | `lancedb` | `lancedb_rag_count_drift` | `vectorstore.getCount()` vs `SELECT COUNT(*) FROM rag_analyses` — flag if delta > 100 | Flag only | warning |

Implementation note for W-3: `market_prices_history` has `PRIMARY KEY (code, fetched_at)`, so
exact (code, fetched_at) duplicates cannot occur at the SQLite level. The meaningful duplicate
is multiple entries for the same stock on the same calendar day (e.g., two scans within the
same minute might differ by sub-second timestamps). The dedup query is:

```sql
DELETE FROM market_prices_history
WHERE rowid NOT IN (
  SELECT MIN(rowid)
  FROM market_prices_history
  GROUP BY code, DATE(fetched_at)
  HAVING COUNT(*) > 1
)
AND (code, DATE(fetched_at)) IN (
  SELECT code, DATE(fetched_at)
  FROM market_prices_history
  GROUP BY code, DATE(fetched_at)
  HAVING COUNT(*) > 1
);
```

Wait — the intent is to keep the LATEST, not earliest, per day. Use:
```sql
DELETE FROM market_prices_history
WHERE rowid NOT IN (
  SELECT MAX(rowid)
  FROM market_prices_history
  GROUP BY code, DATE(fetched_at)
)
AND (code, DATE(fetched_at)) IN (
  SELECT code, DATE(fetched_at)
  FROM market_prices_history
  GROUP BY code, DATE(fetched_at)
  HAVING COUNT(*) > 1
);
```

Implementation note for W-6: Parse `analysis_ids_json` with `JSON_EACH()` and LEFT JOIN to
`rag_analyses`. Flag the count but do not delete — orphan alerts could indicate a separate
LanceDB sync issue that needs investigation.

Implementation note for W-7: Wrap the `vectorstore.getCount()` call in try/catch. If LanceDB
is unavailable, emit a finding with `severity: "warning"`, `detail: "LanceDB count check
skipped: <error message>"`, `action: "none"`. The weekly audit must never throw.

### FR-6: Plausible-range constants for tracked_indicators (W-5)

These are physical validity constraints, not policy. They are hardcoded as named constants
inside `dataAuditJob.ts` with JSDoc explaining the rationale.

```typescript
/** Commodity plausible-range constants — physical validity bounds, not policy thresholds.
 *  Oil: WTI/Brent never below $10 or above $300 in modern markets (pre-war record ~$147).
 *  Gold: Has never traded below $500/oz since 2005; above $5000 would be unprecedented.
 *  CPI: Annual CPI change outside -5% to +30% indicates extraction error for VN context.
 *  USD/VND: Rate should be between 20,000 and 30,000 for any plausible VN scenario.
 */
const INDICATOR_RANGES: Record<string, { min: number; max: number; severity: "critical" | "warning" }> = {
  brent_crude_usd:  { min: 10,     max: 300,    severity: "critical" },
  wti_crude_usd:    { min: 10,     max: 300,    severity: "critical" },
  gold_usd_per_oz:  { min: 500,    max: 5000,   severity: "critical" },
  cpi_vietnam:      { min: -5,     max: 30,     severity: "warning"  },
  usd_vnd_rate:     { min: 20000,  max: 30000,  severity: "warning"  },
  // Indicators not listed here are skipped — no false positives for new indicators
};
```

The check iterates only over indicators whose names match a key in `INDICATOR_RANGES`. Unknown
indicators produce no finding. This prevents the audit from flagging legitimately new
indicators added by `commodityTracker.ts`.

- DDD layer: infrastructure/scheduler (constants in the same file — no domain service needed)

### FR-7: agent_feedback insert contract

Findings with `severity IN ("warning", "critical")` and `action IN ("flagged", "escalated")`
are persisted to `agent_feedback` using a direct `db.prepare(...).run(...)` call — NOT via
the `submit_feedback` MCP tool (that is a public endpoint, not an internal function).

Insert statement:
```sql
INSERT INTO agent_feedback (agent, category, title, detail, priority, status, created_at)
VALUES ('data-auditor', ?, ?, ?, ?, 'new', datetime('now'))
```

Mapping from `AuditFinding` to `agent_feedback` columns:
- `agent`: always `"data-auditor"`
- `category`: map `check` slug to the nearest `agent_feedback` category enum:
  - `zero_price_rows`, `stale_price_rows` → `"data_extraction_error"`
  - `missing_sentiment_or_impact` → `"data_extraction_error"`
  - `failed_validation_unfixed` → `"data_extraction_error"`
  - `outlier_indicator_values` → `"data_extraction_error"`
  - `orphan_alerts` → `"alert_quality"`
  - `lancedb_rag_count_drift` → `"performance_issue"`
  - `stale_new_feedback` → `"other"`
  - everything else → `"other"`
- `title`: `"[AUDIT] <check_slug> — <table> (<rowsAffected> rows)"`
- `detail`: `AuditFinding.detail` truncated to 500 chars
- `priority`: map severity: `"critical"` → `"critical"`, `"warning"` → `"medium"`, `"info"` → `"low"`
- `status`: always `"new"`

Business rule: Do not insert a duplicate `agent_feedback` entry if the same `(agent, title)`
combination was already inserted today. Guard with:
```sql
SELECT COUNT(*) FROM agent_feedback
WHERE agent = 'data-auditor'
  AND title = ?
  AND created_at >= date('now')
```
If count > 0, skip the insert. This prevents repeated audit runs on the same day from
flooding the feedback table.

### FR-8: system_logs write for each audit run

After all checks complete, write one summary row to `system_logs`:

```sql
INSERT INTO system_logs (timestamp, level, source, message, details_json)
VALUES (datetime('now'), ?, 'data-auditor', ?, ?)
```

- `level`: `"error"` if any finding is `severity = "critical"`, `"warn"` if any is `"warning"`,
  otherwise `"info"`.
- `message`: `"Daily audit complete: <N> cleaned, <M> warnings, <K> criticals"` or
  `"Weekly audit complete: ..."`.
- `details_json`: JSON array of all `AuditFinding` objects as a compact string.

### FR-9: Telegram summary message

After persisting findings, send a single Telegram message using the existing
`sendTelegramMessage()` notifier from `src/infrastructure/notifiers/telegram.ts`.

Send conditions:
- If `telegram.enabled = false` in `mcp.config.json`: skip silently.
- If all findings have `rowsAffected = 0` AND no `action IN ("flagged", "escalated")`:
  do NOT send (stay silent on clean runs — PO answer b).
- Otherwise: send exactly one message.

Message format (plain text, no Markdown):
```
DB audit (daily) — 2026-04-01 23:00 GMT+7
Cleaned: 5 rows (zero-price: 2, stale-alerts: 1, old-logs: 2)
Flagged: 3 warnings, 0 criticals
Feedback queue: 7 new items (2 high priority)
```

For weekly audit:
```
DB audit (weekly) — 2026-04-06 01:00 GMT+7
Cleaned: 12 rows (commodity-history: 8, rag-dupes: 4)
Flagged: 1 warning (lancedb drift: +47 rows), 1 critical (brent_crude_usd = 5.0)
Feedback queue: 9 new items (3 high priority)
```

Rules:
- Timestamp in GMT+7 display format: `YYYY-MM-DD HH:mm GMT+7`
- "Cleaned" line: list only categories where `rowsAffected > 0` and `action = "auto_cleaned"`.
  If nothing was cleaned, write "Cleaned: 0 rows".
- "Flagged" line: count of findings where `action IN ("flagged", "escalated")`,
  grouped by severity.
- "Feedback queue" line: always include — query `agent_feedback` for current counts.

### FR-11: audit_state table for get_system_health integration

After each audit run (both daily and weekly), upsert one row into the `audit_state` table:

```sql
CREATE TABLE IF NOT EXISTS audit_state (
  id                    INTEGER PRIMARY KEY CHECK (id = 1),  -- singleton row
  last_daily_audit_at   TEXT,
  last_weekly_audit_at  TEXT,
```

## Non-Functional Requirements

- Performance: daily audit < 5 seconds wall-clock; weekly audit < 30 seconds. All SQLite
  operations synchronous (Bun SQLite API). LanceDB count is the only async DB call.
- Idempotency: running the same audit twice on the same day must not create duplicate
  `agent_feedback` rows (FR-7 dedup guard).
- Resilience: each check is wrapped in its own try/catch. A failing check logs the error to
  `system_logs` and continues — the entire audit run does not abort.
- Language: Telegram messages in Vietnamese-friendly format (dates/numbers human-readable).
  Internal logs and `agent_feedback` titles in English.
- Data freshness: audit uses `datetime('now')` for all time comparisons — always relative to
  execution time, never hardcoded dates.
- No external libraries: all SQL via `bun:sqlite`; Telegram via existing notifier;
  LanceDB via existing `vectorstore.ts` exports.

## Edge Cases & Data Quality

- [ ] `market_prices_history` PRIMARY KEY is `(code, fetched_at)` — no `id` column exists.
  The weekly dedup (W-3) uses `rowid` (SQLite implicit rowid) and `DATE(fetched_at)` bucketing.
  The Developer must verify `rowid` access works on a table with an explicit composite PK
  (SQLite always has a rowid unless `WITHOUT ROWID` is used — this table does not use it).

- [ ] `agent_feedback` table is created lazily by `feedbackTools.ts` (not in `schema.ts`).
  `dataAuditJob.ts` must call `ensureFeedbackTable()` (or duplicate its DDL) before inserting.
  Recommended approach: extract `ensureFeedbackTable()` into a shared helper in
  `src/infrastructure/db/schema.ts` or duplicate the `CREATE TABLE IF NOT EXISTS` inline.
  The simplest correct approach: inline the DDL in `dataAuditJob.ts` since it is
  infrastructure-level code with no circular import risk.

- [ ] `tracked_indicators` table is also created lazily by `commodityTracker.ts` (not in
  `schema.ts`). W-5 check must guard against table-not-found with a try/catch around the
  SELECT, emitting a `severity: "info"`, `action: "none"` finding if the table does not exist.

- [ ] `analysis_ids_json` in `alerts` is a JSON array string. The orphan check (W-6) uses
  `json_each(analysis_ids_json)` which requires SQLite JSON1 extension — available in
  Bun's bundled SQLite. If `analysis_ids_json` is NULL or empty, skip that row.
  Use: `WHERE analysis_ids_json IS NOT NULL AND analysis_ids_json != '[]'`.

- [ ] LanceDB `getCount()` does not currently exist in `vectorstore.ts`. The Developer must
  add it as a new export: `export async function getCount(): Promise<number>`. It uses
  `(await getTable()).countRows()` or equivalent LanceDB API. If the table does not exist
  (first startup), return 0.

- [ ] Vietnamese number format in Telegram: row counts may be large (e.g. 1234567 rows in
  `rag_analyses`). Format with locale-aware separator: `rowsAffected.toLocaleString('vi-VN')`.

- [ ] Clock skew: `datetime('now')` in SQLite uses UTC. The `created_at` columns in existing
  tables may be stored in ISO format (UTC) or local time. Verify against `schema.ts` — all
  existing timestamps use `datetime('now')` which returns UTC. The `-30 days`, `-60 days`
  offsets are correct for UTC-stored timestamps.

- [ ] Empty `audit_state` table on first run: `get_system_health` must handle `null` row
  gracefully and display "never" for both audit timestamps.

- [ ] Weekly audit calling `runDailyAudit()` internally: if the daily audit was already
  triggered by its own cron at 23:00 Sunday, and the weekly audit fires at 01:00 Monday,
  the dedup guard in FR-7 ensures no duplicate `agent_feedback` rows are created (they are
  in different calendar days — 23:00 Sunday vs 01:00 Monday). No additional guard is needed.

- [ ] Concurrency: if `intelligenceCycleJob.ts` is running during the audit, both will
  call `getDb()` concurrently. SQLite WAL mode handles concurrent readers safely. The audit
  runs short DELETE/UPDATE transactions that will not block the cycle's reads significantly.

## Acceptance Criteria

### AC-1: Daily audit cleans zero-price rows

**Given** a `market_prices` row with `price = 0` exists in the database
**When** `runDailyAudit()` is called
**Then**
- The row with `price = 0` is deleted from `market_prices`
- The returned `AuditFinding[]` contains one finding with `table = "market_prices"`,
  `check = "zero_price_rows"`, `action = "auto_cleaned"`, `rowsAffected >= 1`
- A `system_logs` row with `source = "data-auditor"` is inserted

### AC-2: Stale unread alert is marked read

**Given** an alert with `read = 0` and `triggered_at = 35 days ago` exists
**When** `runDailyAudit()` is called
**Then**
- The alert's `read` column is updated to `1`
- A finding with `check = "stale_unread_alerts"`, `action = "auto_cleaned"` is returned

### AC-3: Old agent_feedback priority is escalated

**Given** an `agent_feedback` row with `status = 'new'`, `priority = 'medium'`,
`created_at = 15 days ago` exists
**When** `runDailyAudit()` is called
**Then**
- The row's `priority` is updated to `'high'`
- A finding with `check = "stale_new_feedback"`, `action = "escalated"` is returned
- An `agent_feedback` row with `agent = 'data-auditor'` and `title` containing
  `"stale_new_feedback"` is inserted

### AC-4: Outlier commodity value triggers critical finding

**Given** a `tracked_indicators` row with `indicator = 'brent_crude_usd'`, `value = 5.0` exists
**When** `runWeeklyAudit()` is called
**Then**
- An `agent_feedback` row is inserted with `agent = 'data-auditor'`,
  `category = 'data_extraction_error'`, `priority = 'critical'`
- The finding has `severity = "critical"`, `check = "outlier_indicator_values"`
- The original `tracked_indicators` row is NOT deleted (flag only)

### AC-5: Old history rows are pruned in weekly audit

**Given** `commodity_prices_history` rows with `fetched_at = 200 days ago` exist
**When** `runWeeklyAudit()` is called
**Then**
- Those rows are deleted from `commodity_prices_history`
- A finding with `check = "old_commodity_history"`, `action = "auto_cleaned"`,
  `rowsAffected >= 1` is returned

### AC-6: Telegram is silent on clean run

**Given** all tables are clean (no zero prices, no stale alerts, no outliers, etc.)
  AND `telegram.enabled = true` in config
**When** `runDailyAudit()` is called
**Then**
- No Telegram message is sent
- The function still returns an array of `AuditFinding` objects (row count snapshots)

### AC-7: Telegram sends one message when issues found

**Given** at least one `rowsAffected > 0` or `action = "flagged"` finding exists
  AND `telegram.enabled = true`
**When** `runDailyAudit()` or `runWeeklyAudit()` completes
**Then**
- Exactly one Telegram message is sent per audit run
- The message contains "Cleaned:", "Flagged:", and "Feedback queue:" lines

### AC-8: LanceDB count drift is flagged, not thrown

**Given** `vectorstore.getCount()` throws an error (LanceDB unavailable)
**When** `runWeeklyAudit()` is called
**Then**
- The audit run completes without throwing
- A finding with `check = "lancedb_rag_count_drift"`, `severity = "warning"`,
  `action = "none"` is returned
- The error message is included in `detail`

### AC-9: get_system_health shows db_audit section

**Given** at least one daily audit has run
**When** `get_system_health` MCP tool is called
**Then**
- The response contains a `--- DB Audit ---` section
- `last_daily_audit` shows a valid ISO timestamp
- `pending_feedback` shows the current count from `agent_feedback WHERE status = 'new'`

### AC-10: Scheduler registers both audit crons

**Given** `startScheduler()` is called
**Then**
- `CRONS.dataAuditDaily` is defined (default `'0 23 * * *'`)
- `CRONS.dataAuditWeekly` is defined (default `'0 1 * * 0'`)
- Both are overridable via `CRON_DATA_AUDIT_DAILY` and `CRON_DATA_AUDIT_WEEKLY` env vars

### AC-11: No duplicate agent_feedback on same-day re-run

**Given** `runDailyAudit()` is called twice on the same calendar day with the same findings
