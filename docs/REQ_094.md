# REQ-094: RSI Overbought/Oversold Intraday Alert Job

status: READY_FOR_ARCHITECT
sprint: 094
po_vision: Close the TA lifecycle gap — fire actionable RSI alerts intraday, not just once per day in the morning briefing.

## User Story

As a Vietnamese stock investor using Claude,
I want to receive a Telegram alert when a watchlist stock crosses RSI 70 (overbought) or RSI 30 (oversold) during market hours,
So that I can act on momentum extremes as they happen, not 12+ hours later at the next morning briefing.

---

## Functional Requirements

### FR-1: taAlertScanJob — periodic RSI scan

- **Description:** New scheduler job `src/scheduler/taAlertScanJob.ts` that scans every watchlist ticker for RSI extremes and writes alert rows so the existing Alert Commander pipeline dispatches them to the user.
- **Input:**
  - `watchlist` table — `SELECT code FROM watchlist`
  - `market_prices_history` table — daily candle query (same SQL as `get_technical_indicators` MCP tool): `SELECT date(fetched_at) AS day, AVG(price) AS close_price FROM market_prices_history WHERE code = ? AND fetched_at >= datetime('now', '-60 days') GROUP BY date(fetched_at) ORDER BY day ASC`
  - `alerts` table — cooldown query (see FR-3)
- **Output:** `{ scanned: number, fired: number }` for `recordJobRun` logging
- **Business rules:**
  - RSI > 70 → alert type `ta_overbought`, message `"{CODE}: RSI(14) = {value} — quá mua"`
  - RSI < 30 → alert type `ta_oversold`, message `"{CODE}: RSI(14) = {value} — quá bán"`
  - RSI null (insufficient history) → skip, no alert
  - RSI 30–70 → no alert
  - Per-ticker cooldown: skip if same `(code, alert_type)` alert was inserted in the last 4 hours (see FR-3)
  - Per-ticker error isolation: if `computeAllIndicators` or the DB candle query throws for a single ticker, log the error and continue to the next ticker — do not abort the scan
- **DDD layer:** scheduler — may import from `domain/` and `infrastructure/`. Must NOT import from `application/` or `interface/`.

### FR-2: Alert row insert — production alerts table schema

Insert into the existing `alerts` table using the same pattern as `bctcOverdueCheckJob.ts`. Column mapping:

| alerts column        | Value for TA alerts                                                                 |
|----------------------|-------------------------------------------------------------------------------------|
| `id`                 | `crypto.randomUUID()` — not deterministic (cooldown is time-based, not id-based)    |
| `triggered_at`       | `new Date().toISOString()`                                                           |
| `severity`           | `'warning'`                                                                          |
| `signals_json`       | `JSON.stringify([{ type: alertType, actionCode: code, message, confidence: 0.7, detectedAt: triggeredAt }])` |
| `affected_actions_json` | `JSON.stringify([{ code }])`                                                     |
| `analysis_ids_json`  | `NULL`                                                                               |
| `message`            | Vietnamese string, e.g. `"VCB: RSI(14) = 74.2 — quá mua"`                          |
| `read`               | `0`                                                                                  |
| `user_note`          | `NULL`                                                                               |

**No INSERT OR IGNORE** — each firing generates a unique UUID. Cooldown is enforced by FR-3 before insert, not by DB dedup.

> NOTE: TASKS.md described columns `ticker`, `alert_type`, `is_read`, `created_at` — these do NOT exist in the production `alerts` table. The columns above are the correct production schema as defined in `src/infrastructure/db/schema.ts` lines 169–188.

### FR-3: 4-hour per-ticker cooldown

- **Description:** Before inserting, query whether the same ticker + alert type already fired within the last 4 hours.
- **Query:**
  ```sql
  SELECT COUNT(*) AS cnt
  FROM alerts
  WHERE json_extract(signals_json, '$[0].type') = ?
    AND json_extract(affected_actions_json, '$[0].code') = ?
    AND triggered_at >= datetime('now', '-4 hours')
  ```
- **Parameters:** `[alertType, code]`
- **Rule:** if `cnt > 0` → skip insert for that ticker+type. Otherwise → insert.
- **Rationale:** `signals_json` and `affected_actions_json` are the canonical lookup columns for this alert type because the `alerts` table has no `ticker` or `alert_type` columns.

### FR-4: Cron registration in jobs.ts

- **Cron key:** `taAlertScan` in the `CRONS` map
- **Default schedule:** `*/15 2-8 * * 1-5`
  - Every 15 minutes, 02:00–08:59 UTC, Monday–Friday
  - UTC equivalent of VN market hours 09:00–15:59 GMT+7
  - Matches the same window as `vpsProxyWatchdog` (already using this UTC band)
- **Env override:** `CRON_TA_ALERT_SCAN`
- **Timezone option:** `UTC` (like `vpsProxyWatchdog`) — the cron range directly encodes the UTC window
- **Wrapper pattern:** use `recordJobRun(getDb(), 'taAlertScanJob', async () => { ... return { rowsWritten: result.fired } })`
- **Comment in header:** `taAlertScan — every 15min VN market hours (task 1307)`

### FR-5: Injectable dependencies for TDD

All external I/O must be injectable so tests use in-memory SQLite with no real network or disk access:

| Param | Type | Default |
|-------|------|---------|
| `db` | `Database \| undefined` | `getDb()` |
| `computeFn` | `(candles: DailyCandle[]) => TechnicalIndicatorResult` | `computeAllIndicators` |
| `nowFn` | `() => Date` | `() => new Date()` |

The `computeFn` injectable replaces `computeAllIndicators` only — the candle SQL query always runs on the injected `db`. This lets tests control RSI output without needing to populate `market_prices_history`.

## Non-Functional Requirements

- **Performance:** Each scan processes at most 30 watchlist tickers. At 15-minute intervals, total DB round-trips per cycle = (1 watchlist read) + (N candle queries) + (N cooldown checks) + (M inserts). Acceptable for SQLite.
- **Frequency:** Every 15 minutes during VN market hours only (`*/15 2-8 * * 1-5` UTC). Zero executions outside this window — no off-hours wakeup.
- **Scheduler file count:** Adding `taAlertScanJob.ts` raises `schedulerFileCount` from 29 to 30 in `docs/data/project-stats.json`. The Dev agent must update this after merging.
- **Language:** Alert messages in Vietnamese (`quá mua`, `quá bán`). RSI value formatted to 1 decimal place.
- **No direct Telegram send:** This job writes to `alerts` table only. Alert Commander (`05-alert-commander.md`) reads `readUnnotifiedAlerts()` and handles Telegram dispatch. No Telegram import in this file.

## Edge Cases & Data Quality

- [x] Empty watchlist → `{ scanned: 0, fired: 0 }`, no error
- [x] RSI null (< 15 candles in history) → skip ticker, no alert, no log noise
- [x] Per-ticker DB or compute error → catch, log warning, continue to next ticker
- [x] Cooldown active (same ticker+type within 4h) → skip insert, not counted in `fired`
- [x] Same ticker overbought + oversold simultaneously → impossible (RSI is a scalar); only one type fires per scan
- [x] VN market holidays (weekends, Tet) → cron does not fire on weekends (`1-5`); VN public holidays are not encoded in cron — the job will run but may find no updated prices if the VPS did not push new data; RSI will be stale but won't fire spuriously because prices haven't changed
- [x] `market_prices_history` empty for a ticker → candle query returns 0 rows → `computeAllIndicators([])` returns `rsi14: null` → skip, no alert
- [x] 60-day lookback returns < 15 candles → RSI null → skip
- [x] DB write failure (disk full, locked) → catch + log, do not crash the entire scan; other tickers continue

## Acceptance Criteria

### AC-1: Alert fires for overbought RSI

**Given** a watchlist with ticker VCB and `computeFn` returning `{ rsi14: 74.2, ... }`
**When** `runTaAlertScan()` is called
**Then**
- 1 row inserted into `alerts` with `message` containing "VCB" and "quá mua"
- `signals_json` contains an object with `type = "ta_overbought"`
- `affected_actions_json` contains `[{ "code": "VCB" }]`
- Return value is `{ scanned: 1, fired: 1 }`

### AC-2: Alert fires for oversold RSI

**Given** `computeFn` returning `{ rsi14: 27.8, ... }`
**When** `runTaAlertScan()` is called
**Then**
- `signals_json` contains `type = "ta_oversold"`
- `message` contains "quá bán"
- Return value `{ scanned: 1, fired: 1 }`

### AC-3: No alert for neutral RSI

**Given** `computeFn` returning `{ rsi14: 50.0, ... }`
**When** `runTaAlertScan()` is called
**Then**
- 0 rows inserted into `alerts`
- Return value `{ scanned: 1, fired: 0 }`

### AC-4: No alert when RSI is null

**Given** `computeFn` returning `{ rsi14: null, ... }`
**When** `runTaAlertScan()` is called
**Then**
- 0 rows inserted into `alerts`
- Return value `{ scanned: 1, fired: 0 }`

### AC-5: Cooldown suppresses second fire within 4 hours

**Given** first scan fires ta_overbought for VCB at T=0
**When** `runTaAlertScan()` is called again at T=30min (via `nowFn` returning T+30min)
**Then**
- 0 additional rows inserted
- Return value `{ scanned: 1, fired: 0 }`

### AC-6: Cooldown does not suppress after 4 hours

**Given** first scan fires ta_overbought for VCB at T=0
**When** `runTaAlertScan()` is called at T=5h (via `nowFn`)
**Then**
- 1 additional row inserted
- Return value `{ scanned: 1, fired: 1 }`

### AC-7: Multi-ticker scan counts correctly

**Given** watchlist with 3 tickers, 2 returning RSI > 70, 1 returning RSI 50
**When** `runTaAlertScan()` is called
**Then**
- Return value `{ scanned: 3, fired: 2 }`
- Exactly 2 rows inserted into `alerts`

### AC-8: Empty watchlist returns zero counts

**Given** empty watchlist table
**When** `runTaAlertScan()` is called
**Then**
- Return value `{ scanned: 0, fired: 0 }`
- No DB writes

### AC-9: Per-ticker error does not abort scan

**Given** watchlist with 3 tickers, computeFn throws on ticker 2, ticker 3 is overbought
**When** `runTaAlertScan()` is called
**Then**
- Error for ticker 2 is caught and logged
- Alert fires for ticker 3
- Return value `{ scanned: 3, fired: 1 }` (or `scanned: 2` if errored tickers are excluded — Dev decides, must document)

### AC-10: Job registered in jobs.ts

**Given** the scheduler starts
**When** `startScheduler()` runs
**Then**
- `CRONS.taAlertScan` key exists with default `*/15 2-8 * * 1-5`
- `runTaAlertScan` is imported and wired into the cron callback
- `recordJobRun` wraps the call with job name `'taAlertScanJob'`

### AC-11: TypeScript clean

**Given** the full source tree
**When** `bun tsc --noEmit` runs
**Then** 0 errors
