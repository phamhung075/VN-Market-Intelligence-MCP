## Functional Requirements

### FR-1: Evidence Likelihood Ratios Table (Phase B — DDL + Store)

- **Description:** Create the `evidence_likelihood_ratios` table and its CRUD store. This table holds one row per `(evidence_type, direction, horizon_days)` triple, recording the statistical lift that evidence type provides over the unconditional base rate.
- **Input:** Computed by `baseRateComputationJob` (FR-2), never written by agents directly.
- **Output:** Read by `get_evidence_summary` tool (FR-5) and by the Prediction Synthesizer agent (FR-7).
- **Business rule:** A `likelihood_ratio` of 1.0 means the evidence type has no lift over the base rate. Values > 1.0 mean the evidence is positively predictive; < 1.0 means it predicts the opposite direction. Ratios are only trusted when `sample_size >= 10`; below that threshold, the store returns 1.0 (neutral — no claim of predictive power).
- **DDL:**

```sql
CREATE TABLE IF NOT EXISTS evidence_likelihood_ratios (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  evidence_type    TEXT NOT NULL,
  direction        TEXT NOT NULL CHECK(direction IN ('bullish','bearish','neutral')),
  horizon_days     INTEGER NOT NULL CHECK(horizon_days IN (5, 10, 20)),
  likelihood_ratio REAL NOT NULL DEFAULT 1.0,
  sample_size      INTEGER NOT NULL DEFAULT 0,
  last_updated     TEXT NOT NULL,
  UNIQUE(evidence_type, direction, horizon_days)
);
CREATE INDEX IF NOT EXISTS idx_elr_type_dir ON evidence_likelihood_ratios(evidence_type, direction);
```

- **DDD layer:** infrastructure — `src/infrastructure/db/likelihoodRatioStore.ts`

### FR-2: Base Rate Computation Job (Phase B — Weekly Scheduler)

- **Description:** A new scheduler job `baseRateComputationJob.ts` runs every Sunday at 02:00 VN time (19:00 UTC Saturday). It recomputes likelihood ratios for all `(evidence_type, direction, horizon_days)` triples by joining evidence fragment history against price outcome history.
- **Input:** `evidence_fragments` table (raw evidence) + `market_prices` table (price history via `priceQueries.ts`)
- **Output:** Upserted rows in `evidence_likelihood_ratios`
- **Computation logic — step by step:**

  1. For each distinct `(evidence_type, direction)` pair in `evidence_fragments`, and for each horizon in `[5, 10, 20]` days:
  2. Find all `evidence_fragments` rows where a price outcome is resolvable — i.e. a price exists at `timestamp + horizon_days` trading days. Only rows older than `horizon_days` days are used (cannot resolve future outcomes).
  3. For each such fragment row: determine the outcome — did the stock close higher (for bullish direction) or lower (for bearish direction) by at least 3% at the horizon date? This 3% threshold is the VN market noise floor (see edge cases).
  4. Compute: `hit_rate = count(correct outcomes) / count(resolvable fragments for this triple)`
  5. Compute the per-stock unconditional base rate: `base_rate = fraction of all horizon windows where stock moved ±3%` from `market_prices` rolling history.
  6. `likelihood_ratio = hit_rate / base_rate` (clamped to range `[0.1, 5.0]` to prevent extreme values from data gaps)
  7. `sample_size = count(resolvable fragments)`. If `sample_size < 10`: upsert `likelihood_ratio = 1.0`, `sample_size = actual count`.
  8. Upsert into `evidence_likelihood_ratios`.

- **Cron schedule:** `0 19 * * 0` (Sunday 19:00 UTC = 02:00 VN Monday morning)
- **recordJobRun:** must call `recordJobRun` wrapper (Task 1101 pattern) for cron health observability
- **DDD layer:** scheduler — `src/scheduler/baseRateComputationJob.ts`

### FR-3: Per-Stock Rolling Base Rate Computation (Phase B — Domain Service)

- **Description:** A domain service function `computeRollingBaseRate(stock, horizonDays, db)` that computes the unconditional probability of a ±3% move for a given stock over a given horizon. Used as the denominator in FR-2's likelihood ratio computation.
- **Input:** `stock: string`, `horizonDays: 5 | 10 | 20`, `db: Database`
- **Output:** `number` in `[0.0, 1.0]` — fraction of historical windows where the absolute price change exceeded 3%. Minimum window count to return a non-default value: 10. If fewer than 10 windows are available, returns `0.5` (neutral prior).
- **Data source:** `market_prices` table via existing `priceQueries.ts` helpers. No new fetcher needed.
- **Business rule:** The 3% threshold aligns with HOSE intraday circuit-breaker sensitivity (±7% daily limit). A 3% move over 5d/10d/20d is a meaningful directional signal for VN blue-chips.
- **DDD layer:** domain — `src/domain/services/baseRateComputer.ts`

### FR-4: Prediction Claims Table (Phase C — DDL + Store)

- **Description:** Create the `prediction_claims` table and its CRUD store. Each row is a single structured, falsifiable claim generated by the Prediction Synthesizer agent.
- **Input:** Written by `create_prediction_claim` MCP tool (FR-6), resolved by `predictionResolutionJob` (FR-8).
- **DDL:**

```sql
CREATE TABLE IF NOT EXISTS prediction_claims (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  stock                TEXT NOT NULL,
  claim_text           TEXT NOT NULL,
  probability          REAL NOT NULL CHECK(probability BETWEEN 0.0 AND 1.0),
  horizon_days         INTEGER NOT NULL CHECK(horizon_days IN (5, 10, 20)),
  resolution_date      TEXT NOT NULL,
  resolution_criteria  TEXT NOT NULL,
  resolved             INTEGER NOT NULL DEFAULT 0,
  resolution_outcome   INTEGER CHECK(resolution_outcome IN (NULL, 0, 1)),
  brier_score          REAL CHECK(brier_score BETWEEN 0.0 AND 1.0),
  created_at           TEXT NOT NULL,
  resolved_at          TEXT,
  synthesizer_version  TEXT NOT NULL DEFAULT '08-prediction-synthesizer'
);
CREATE INDEX IF NOT EXISTS idx_pc_stock_resolved ON prediction_claims(stock, resolved);
CREATE INDEX IF NOT EXISTS idx_pc_resolution_date ON prediction_claims(resolution_date);
```

- **`resolution_criteria` format:** Structured JSON string — not free text. Format:

```json
{
  "metric": "price_close",
  "operator": ">",
  "value": 150000,
  "currency": "VND",
  "description": "FPT closing price above VND 150,000"
}
```

  Allowed `metric` values: `price_close`, `price_change_pct`. Allowed `operator` values: `>`, `<`, `>=`, `<=`. The `description` field is human-readable and appears in Telegram messages.

- **`brier_score` formula:** `(probability - outcome)^2` where `outcome` is 0 or 1. A perfectly calibrated predictor has Brier = 0.0; random guessing at 0.5 gives 0.25; always-wrong at 1.0 gives 1.0.
- **DDD layer:** infrastructure — `src/infrastructure/db/predictionClaimStore.ts`

### FR-6: `create_prediction_claim` MCP Tool (Phase C — Tool +1)

- **Description:** Inserts a new row into `prediction_claims`. Intended to be called exclusively by the `08-prediction-synthesizer` Cowork agent, but not technically restricted at the MCP layer (any agent can call it).
- **Input:**
  - `stock: string` — ticker, will be `.toUpperCase().trim()`
  - `claim_text: string` — human-readable claim, e.g. "VNM sẽ đóng cửa trên 80,000 VND trong 10 phiên giao dịch"
  - `probability: number` — `[0.01, 0.99]` (clamped away from 0 and 1 to avoid degenerate Brier scores)
  - `horizon_days: 5 | 10 | 20` — trading-day horizon
  - `resolution_criteria: string` — must be valid JSON matching the schema in FR-4; tool validates JSON parse only, not schema depth
- **Computed by the tool:**
  - `resolution_date` = today + `horizon_days` calendar days (not trading days — simpler, conservative)
  - `created_at` = now ISO 8601
- **Output:** Confirmation text with inserted `id` and resolution date.
- **Business rule:** If `resolution_criteria` is not valid JSON, return an error string (do not throw). Do not allow duplicate identical `(stock, claim_text, resolution_date)` — use INSERT OR IGNORE and report "Duplicate claim skipped" if no row was inserted.
- **DDD layer:** interface — `src/interface/mcp/tools/evidenceTools.ts` (extend existing file)
- **Tool count delta:** +1

### FR-7: `08-prediction-synthesizer` Cowork Agent (Phase C — New Agent File)

- **Description:** A new Cowork agent `08-prediction-synthesizer.md` that runs every Monday at 07:30 VN time (00:30 UTC). It synthesizes evidence into structured prediction claims before market open.
- **Authored by:** Cowork Refactory Expert agent — this is Cowork territory, not developer territory.
- **Protocol (7 steps):**
  1. Call `get_watchlist()` — get all monitored tickers.
  2. For each ticker: call `get_evidence_summary(stock)`. Skip if "No evidence accumulated yet".
  3. For stocks where `bullish_score > 0.6` or `bearish_score > 0.6` (high-conviction): call `get_bctc_full(stock)` + `get_market_snapshot()` for macro context.
  4. For each high-conviction stock, call `create_prediction_claim(...)` with:
     - `claim_text` in Vietnamese ("VNM sẽ đóng cửa trên X VND trong N phiên")
     - `probability` = `min(0.95, max(0.05, bullish_score * top_likelihood_ratio))` — agent computes this inline
     - `horizon_days` = 10 (default; use 5 for very high conviction stocks, 20 for low-conviction)
     - `resolution_criteria` = structured JSON per FR-4 schema
  5. Maximum 5 claims per run (avoid flooding). If more than 5 stocks qualify, take the 5 with highest `|bullish_score - bearish_score|` delta.
  6. Call `log_agent_work(agent_name, summary)` to record the cycle.
  7. Call `send_telegram(channel="work", message)` with a summary of claims created.
- **File location:** `.claude/agents/08-prediction-synthesizer.md` (NOT in `src/`)
- **DDD layer:** interface (Cowork agents are interface-layer orchestrators)

### FR-8: `predictionResolutionJob` Scheduler (Phase C — Nightly Cron)

- **Description:** A nightly scheduler job that resolves expired prediction claims by checking actual price outcomes against resolution criteria.
- **Schedule:** `30 16 * * *` (23:30 VN = 16:30 UTC)
- **Logic — step by step:**
  1. Query `prediction_claims WHERE resolved = 0 AND resolution_date <= date('now')`.
  2. For each unresolved claim: parse `resolution_criteria` JSON.
  3. Look up closing price for `stock` at `resolution_date` from `market_prices` (use latest available price on or before `resolution_date` if exact date is missing — VN market may be closed).
  4. Evaluate the resolution criteria against the closing price: `outcome = 1` if criteria met, `outcome = 0` if not met, `outcome = NULL` if no price data available (leave `resolved = 0`, retry next night for up to 5 days past `resolution_date`).
  5. Compute `brier_score = (probability - outcome)^2` when `outcome` is 0 or 1.
  6. UPDATE: `resolved = 1, resolution_outcome = outcome, brier_score = score, resolved_at = now`.
  7. Log count of resolved and unresolvable claims.
  8. Call `recordJobRun` wrapper for observability.
- **Retry logic:** Claims where `outcome = NULL` (no price data) are retried on subsequent nights. After `resolution_date + 5 calendar days`, if still no price data, mark `resolved = 1, resolution_outcome = NULL, brier_score = NULL` (unresolvable — excluded from calibration).
- **DDD layer:** scheduler — `src/scheduler/predictionResolutionJob.ts`

## Non-Functional Requirements

- **Performance:** `baseRateComputationJob` may be slow (full table scan over `evidence_fragments` + `market_prices`). Acceptable — runs weekly at 02:00 VN when no other jobs compete. Target: complete in < 60 seconds for 30 watchlist stocks.
- **Data freshness:** `get_evidence_summary` reads from `evidence_scores` (last nightly aggregate). It does not query `evidence_fragments` live on every call — this is intentional for performance. The summary is at most 23 hours stale.
- **Language:** `claim_text` in Vietnamese. Tool output and job logs in English. Telegram WORK message may be bilingual (English subject, Vietnamese claim texts).
- **Idempotency:** `baseRateComputationJob` uses INSERT OR REPLACE on the UNIQUE constraint — safe to re-run.
- **Tool budget:** +2 tools total this sprint (`get_evidence_summary` + `create_prediction_claim`). Tool count goes from 84 to 86. No tool removals.

## Edge Cases and Data Quality

- [ ] **Empty evidence_scores for stock:** `get_evidence_summary` returns "No evidence accumulated yet for {stock}" — not an error. The Synthesizer agent skips these stocks.
- [ ] **No price history for horizon resolution:** `predictionResolutionJob` retries for 5 days before marking unresolvable. These rows have `brier_score = NULL` and are excluded from Phase D calibration.
- [ ] **Insufficient sample size (n < 10):** `baseRateComputationJob` upserts `likelihood_ratio = 1.0` and the real `sample_size`. `get_evidence_summary` must display "UNTRUSTED (n<10)" next to these ratios so the Synthesizer agent sees the caveat.
- [ ] **VN market closed on resolution_date:** HOSE/HNX is closed weekends and Vietnamese public holidays. The resolution job uses `latest available price on or before resolution_date` — not exact-date only.
- [ ] **VN number format in claim_text:** All VND amounts in `claim_text` use format `80,000 VND` (comma thousand separator, no dots) to avoid confusion with decimal notation. The Synthesizer agent is instructed to use this format.
- [ ] **Likelihood ratio denominator = 0:** If base_rate is 0 (stock never moved ±3% in the historical window — extremely unlikely for VN stocks), set `likelihood_ratio = 1.0` and log a warning. Do not divide by zero.
- [ ] **Likelihood ratio clamping:** Ratios are clamped to `[0.1, 5.0]`. A ratio of 5.0 means the evidence is 5x more predictive than the base rate — extremely strong. Without clamping, small samples produce absurd values.
- [ ] **Claim text duplicates:** Same claim re-created on a new Monday run. `create_prediction_claim` uses INSERT OR IGNORE on `(stock, claim_text, resolution_date)` — the tool reports "Duplicate claim skipped" rather than inserting a second row.
- [ ] **kinh_dich_signal base rate:** Kinh Dich signals are rare and structurally different (hexagram-based, not statistical). Sample size will be < 10 for months. This is correct behavior — the system will use `likelihood_ratio = 1.0` for this type until it earns trust. Do not special-case it.
- [ ] **horizon_days calendar vs. trading days:** `resolution_date = created_at + horizon_days calendar days` (not trading days). This simplification means some 10-day claims resolve over weekends. The resolution job handles this via the "latest price on or before resolution_date" rule.
- [ ] **baseRateComputationJob on first Sunday after deploy:** `evidence_fragments` will have only ~7 days of data (Sprint 057 shipped 2026-04-12). Sample sizes will all be < 10. All likelihood ratios will be `1.0`. This is correct and expected — the table populates over time.
