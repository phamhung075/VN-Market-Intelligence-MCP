## Problem Statement

28 cron jobs are running in production with zero observability. `pollNews` and SSC fetch jobs are failing every cycle and no one knows. There is no way to determine which jobs ran, what status they completed with, how many rows they produced, or whether performance is degrading over time. The system is operationally blind.

This is the highest-priority gap in the current system.

---

## Business Goal

Provide a lightweight health layer that lets any operator (or the QA Responder agent) answer: "Are my scheduled jobs healthy right now?" with a single tool call. Trigger a Telegram WORK channel alert the moment any job degrades below 80% success rate in a 24-hour window.

---

## Scope

### In

- `cron_job_runs` SQLite table (new)
- `recordJobRun(name, fn)` wrapper function usable by any existing scheduler job
- `get_cron_health()` MCP tool (new, +1 tool)
- Daily Telegram alert to WORK channel when any job 24h success rate < 80%
- Wrapper applied to at minimum: `pollNewsJob`, `sscFetchJob`, `marketScanJob`, `askQueueCheckJob`, `dailyAuditJob`

### Out

- Dashboard UI (not a web project)
- Per-job configuration of thresholds (fixed 80% for now)
- Historical retention beyond 30 days (purge older rows automatically)
- Alerting to MARKET channel (WORK channel only — operator concern, not investor concern)

## Functional Requirements

### FR-1: cron_job_runs table

Schema:

```sql
CREATE TABLE IF NOT EXISTS cron_job_runs (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  job_name    TEXT NOT NULL,
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  status      TEXT NOT NULL CHECK(status IN ('running','success','error')),
  rows_written INTEGER,
  error_msg   TEXT,
  duration_ms  INTEGER
);
CREATE INDEX IF NOT EXISTS idx_cron_job_runs_job_started
  ON cron_job_runs(job_name, started_at DESC);
```

Row lifecycle:
1. Insert on job start: `status='running'`, `started_at=now`, all other fields NULL
2. Update on job end: `status='success'|'error'`, `finished_at`, `rows_written`, `error_msg`, `duration_ms`

### FR-2: recordJobRun wrapper

Signature: `async function recordJobRun<T>(db: Database, name: string, fn: () => Promise<{ rowsWritten?: number }>): Promise<void>`

Behaviour:
- Inserts start row, calls `fn()`, updates end row
- If `fn()` throws: captures error message, sets `status='error'`, does NOT rethrow (job must not crash the cron process)
- `rowsWritten` is optional — jobs that do not produce rows (e.g. audit jobs) may omit it

### FR-3: get_cron_health() MCP tool

Returns per-job summary for all jobs that have run in the last 7 days:

```typescript
{
  job_name: string,
  last_run: string,          // ISO timestamp
  last_status: string,       // 'success' | 'error' | 'running'
  last_error: string | null,
  success_rate_7d: number,   // 0.0–1.0
  avg_duration_ms: number,
  total_runs_7d: number
}[]
```

Sorted by `job_name` ASC.

### FR-4: Daily degradation alert

A new scheduler job (`cronHealthAlertJob`) runs once daily at 07:00 VN time (00:00 UTC).

Logic:
1. For each distinct `job_name` in `cron_job_runs`, compute 24h success rate (runs in last 24h only)
2. If any job has `>= 3 runs in 24h AND success_rate < 0.80`: fire `send_telegram(channel:"work", ...)`
3. Alert format: `[CRON HEALTH] {job_name}: {success_rate*100}% success rate over last 24h ({error_count} errors). Last error: {last_error_msg}`
4. One message per failing job (not batched into one message — each is independent for easy scanning)
5. Minimum 3 runs threshold prevents false positives from jobs that ran only once and errored during a restart

### FR-5: Auto-purge

`recordJobRun` (or a companion function called during each job run) deletes rows older than 30 days for that job_name. Keeps the table bounded.

## Non-Functional Requirements

- `recordJobRun` adds < 2ms overhead per job (two SQLite writes, synchronous, WAL mode)
- `get_cron_health()` executes in < 50ms (indexed query, 7-day window)
- Zero change to existing job logic except wrapping the function body in `recordJobRun`
- DDD compliance: `recordJobRun` lives in `src/infrastructure/db/cronJobRunStore.ts`. `get_cron_health` lives in `src/interface/mcp/tools/systemTools.ts` (or a new file — Architect decides)

## Acceptance Criteria

| # | Scenario | Expected |
|---|----------|----------|
| AC-1 | `recordJobRun(db, 'pollNews', async () => { return { rowsWritten: 5 } })` | Row inserted with status='success', rows_written=5, duration_ms > 0 |
| AC-2 | `recordJobRun(db, 'sscFetch', async () => { throw new Error('timeout') })` | Row inserted with status='error', error_msg='timeout', process does not crash |
| AC-3 | 5 success + 1 error in 7d for 'marketScan' | `get_cron_health()` returns success_rate_7d=0.833 for that job |
| AC-4 | 'pollNews' has 4 runs in 24h, 1 success, 3 errors | `cronHealthAlertJob` fires 1 Telegram WORK message for pollNews |
| AC-5 | 'sscFetch' has 2 runs in 24h, both errors | No Telegram fired (below 3-run minimum threshold) |
| AC-6 | Row from 31 days ago exists for 'pollNews' | After next `recordJobRun('pollNews', ...)`, that row is deleted |
| AC-7 | `get_cron_health()` called with 0 runs in DB | Returns empty array, no error |

## Open Questions — RESOLVED (PO decision 2026-04-11)

1. `get_cron_health()` accepts optional `job_name` filter parameter. When provided, returns only that job. When omitted, returns all jobs.
2. No "all green" heartbeat. Alert fires ONLY on degradation (success_rate < 80%).
3. 80% threshold is fixed. Not configurable via mcp.config.json in this sprint.
