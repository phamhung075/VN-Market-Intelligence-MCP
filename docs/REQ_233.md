## Executive Summary

**Problem**: Sprint 232 implemented resilient fallback chains (primary→secondary→tertiary) with escalation callbacks, but the implementation has NOT been validated in production conditions. Without end-to-end verification, fallback signals may reach the MARKET channel without proper labeling (source_fallback=true), confidence penalties may not be applied, and alert escalation may silently fail when all sources are exhausted.

**Impact**:
- Silent confidence overstatement on fallback signals → false alerts from stale prices
- Missing `source_fallback` metadata → users unaware signal came from cache, not live VPS
- Escalation callback failures → agents continue processing with degraded data without notifying user

**Solution**: Implement comprehensive end-to-end validation suite with:
1. **E2E test suite** (233-cowork-resilience-e2e.test.ts) with 15+ assertions covering all fallback paths
2. **Signal quality audit logging** (marketAnalysisJob.ts signal_quality_audit table) to capture source, confidence, staleness metadata
3. **Extended signalValidator** to apply confidence penalty for fallback signals (multiplier 0.8075)
4. **Market-hours manual smoke tests** during Vietnam 09:00–15:00 +07:00 window with live VPS circuit breaker injection

**Success metric**:
- All E2E assertions pass ✓
- Signal quality audit shows 100% of fallback signals labeled with source_fallback=true ✓
- Confidence penalties applied correctly (0.8075× for cached prices) ✓
- Alert escalation fires for >2 exhausted services during test window ✓

### FR-3: Extended Signal Validator with Confidence Penalty for Fallback Signals

**Description**: Enhance signalValidator.ts (currently prices only) to accept fallback context and apply confidence penalty.

**Input**:
```typescript
{
  signal_price: number,
  snapshot_price: number,
  ticker: string,
  source_fallback: boolean,           // NEW
  fallback_source?: "cache" | "yahoo" | "domestic_rss" | "congbao",
  price_age_minutes?: number,         // NEW: staleness for cached prices
}
```

**Output**:
```typescript
{
  valid: boolean,
  divergence_percent?: number,
  confidence_score: number,           // 0–100, BEFORE penalty
  confidence_score_final: number,     // AFTER penalty (0.8075× if fallback)
  confidence_penalty: number,         // 1.0 or 0.8075
  issue?: string,
  staleness_warning?: boolean,        // true if price >4h old
  validated_at: string,
  source_fallback: boolean,           // ECHOED back for audit logging
  fallback_source?: string,           // ECHOED back for audit logging
}
```

**Business rule**:
- Base confidence = 100 - divergence, clamped [95, 100] (existing logic)
- If source_fallback=true: `confidence_score_final = base_confidence × 0.8075`
- If price_age_minutes > 240 (4h): set `staleness_warning: true`, log warning
- Staleness reduces confidence further: `confidence_score_final *= (1 - age_hours / 24)` (temporal decay, capped at 0.5 minimum)
- Examples:
  - Fresh VPS price, divergence 2%: confidence_final = 98 × 1.0 = **98**
  - Cached price (2h old), divergence 2%: confidence_final = 98 × 0.8075 × (1 - 2/24) = **98 × 0.8075 × 0.917 = 72.8** ≈ **73**
  - Cached price (6h old), divergence 2%: confidence_final = 98 × 0.8075 × max(0.5, 1 - 6/24) = **98 × 0.8075 × 0.5 = 39.6** ≈ **40**

**DDD layer**: domain/services

**File**: `src/domain/services/signalValidator.ts:120` (extend existing function)

## Edge Cases & Data Quality

| Case | Handling |
|------|----------|
| **Fallback price from cache, 8h old** | Apply temporal decay: confidence_final = base × 0.8075 × max(0.5, 1 - 8/24) = base × 0.8075 × 0.5 = **0.404× base**. Log staleness_warning=1. |
| **HNX ticker, fallback has only HOSE** | Mark signal with `coverage_gap: "HNX unavailable from Yahoo fallback"`. Accept if cache available; otherwise escalate. |
| **Fallback signal diverts from ±5% threshold** | If cached price diverges >5% from current snapshot (e.g., major gap event overnight), mark valid=false but still post with source_fallback=1. User must inspect staleness. |
| **Confidence score 0 (invalid snapshot)** | If snapshot_price ≤ 0, set confidence_score=0, confidence_penalty=1.0 (no fallback penalty; signal invalid regardless). Do NOT apply 0.8075 to invalid signals. |
| **Audit table grows unbounded during multi-day test** | Index on (created_at, signal_type, ticker) for performance. Run `VACUUM` after test window if needed. |
| **Temporal decay formula precision** | Use 64-bit floats; round confidence_score_final to nearest integer after penalty. |
| **Multiple signals per ticker same minute** | Audit logs all; no deduplication (each signal gets separate entry). Query tool can aggregate if needed. |

## Appendix: Confidence Penalty Formula Derivation

**Rationale for 0.8075**:
- Fallback introduces two sources of uncertainty:
  1. Age uncertainty (cache may be stale 0–6h)
  2. Source uncertainty (cache, Yahoo, or domestic RSS may diverge from live VPS)
- Geometric mean of confidence reduction:
  - Age effect: ~0.9 (fresh cache within 1h is nearly as good as live)
  - Source effect: ~0.9 (alternative source typically within ±2% of live)
  - Combined: 0.9 × 0.9 = 0.81 ≈ **0.8075** (rounded to 4 decimals for consistency)
- Temporal decay formula: `confidence_final *= (1 - age_hours / 24)` capped at 0.5 minimum
  - At 2h: 1 - 2/24 = 0.917 (slight decay)
  - At 6h: 1 - 6/24 = 0.75 (moderate decay)
  - At 12h: 1 - 12/24 = 0.5 (max decay, then capped)
  - At 24h+: 0.5 (cache too old; recommend escalation if stale >6h)

**Example**: Cached price 3h old, divergence 1% from snapshot, fallback router
- Base confidence: 100 - 1 = 99
- Temporal decay: 1 - (3/24) = 0.875
- Fallback penalty: 0.8075
- Final: 99 × 0.8075 × 0.875 = **69.6** ≈ **70**

This conservative approach ensures users are aware of fallback signal limitations while maintaining practical usability (confidence still >70 for fresh cached data).
