## Deliverable 1 — Real `combined-high-confidence` Strategy

### Business intent

A position is only opened when **both** signal sources independently agree on direction:

- Kinh Dich hexagram reading is BUY (or SELL) with confidence >= 0.7
- EMA/RSI technical confirmation also indicates the same direction

Neither signal source alone is sufficient. This is the distinguishing behaviour from
`kinh-dich-high-confidence`, which uses only the hexagram reading.

### Functional Requirements

**FR-1: Dual-signal gate — DDD layer: domain/backtesting**

The `combined-high-confidence` entry in `strategyRegistry.ts` must replace its current
stub `signalFilter` with logic that enforces agreement between Kinh Dich confidence and a
TA-derived direction. A signal row passes the filter only when the Kinh Dich direction
(BUY or SELL) is confirmed by TA.

**FR-2: EMA/RSI computation from `daily_ohlcv` — DDD layer: infrastructure/db**

TA confirmation must be derived purely from price data already in the mcp-server SQLite
`daily_ohlcv` table (columns: code, date, open, high, low, close, volume). No HTTP call
to the `technical-analysis` microservice at backtest time. Rationale: the backtest engine
is synchronous, pure, and runs over historical date ranges; the TA microservice is
stateless and real-time, not history-aware.

Minimum TA rule (implementation-agnostic definition):
- **EMA crossover:** short-period EMA (e.g. 12-day) crosses above long-period EMA (e.g.
  26-day) → BULLISH; below → BEARISH.
- **RSI:** value > 50 → BULLISH bias; value < 50 → BEARISH bias. (Exact thresholds are
  Architect's choice — the AC tests only require consistent self-consistency, not a
  specific value.)
- Combined TA direction: BULLISH when both EMA crossover and RSI agree; BEARISH when
  both agree; NEUTRAL otherwise.

**FR-3: Agreement rule — DDD layer: domain/backtesting**

| Kinh Dich direction | TA direction | Position opened? |
|---------------------|--------------|------------------|
| BUY                 | BULLISH      | YES              |
| SELL                | BEARISH      | YES              |
| BUY                 | BEARISH      | NO               |
| SELL                | BULLISH      | NO               |
| BUY or SELL         | NEUTRAL      | NO               |

**FR-4: Confidence threshold unchanged — DDD layer: domain/backtesting**

`minConfidence` stays at 0.7. TA confirmation is an additional gate, not a replacement
for the confidence filter.

**FR-5: Hold period unchanged — DDD layer: domain/backtesting**

`holdDays` stays at 5. Exit logic in `backtestEngine.ts` is unaffected.

**FR-6: `IBacktestSignalRepository.getSignals()` contract unchanged — DDD layer: domain/repositories**

The repository interface and its SQLite implementation must not change. TA computation
happens inside `strategyRegistry.ts` `signalFilter` or in a helper the filter calls.
The filter receives a `RawSignalRow` (same shape as `BacktestSignal`) plus whatever
additional context the Architect decides to inject.

**FR-7: Signal set must differ from `kinh-dich-high-confidence` — DDD layer: domain/backtesting**

When run against the same date range and tickers, `combined-high-confidence` must produce
a `tradeCount` that is less than or equal to (never greater than) the `tradeCount` from
`kinh-dich-high-confidence`. The combined strategy is strictly a subset — it adds a
filter, it never adds new trades.

### Non-Functional Requirements

**NFR-1: Zero I/O in `backtestEngine.ts`**

The pure computation function `runBacktestEngine()` must remain free of any DB access,
HTTP calls, or async operations. TA data, if needed at engine time, must be pre-fetched
and passed in via the `BacktestEngineInput` interface or via the strategy's `signalFilter`
closure.

**NFR-2: `tsc` clean**

No TypeScript errors after the change.

**NFR-3: `bun test` baseline preserved**

Test pass count must remain >= 8775. No pre-existing passing test may be broken.

### Acceptance Criteria

**AC-CHC-1:** `run_backtest("combined-high-confidence", startDate, endDate)` returns a
`BacktestReport` without throwing.

**AC-CHC-2:** `run_backtest("combined-high-confidence", ...)` returns `tradeCount <=`
the `tradeCount` from `run_backtest("kinh-dich-high-confidence", ...)` for the same
inputs. (The two results are numerically distinct unless OHLCV data is too sparse to
compute TA for any ticker.)

**AC-CHC-3:** A unit test for `strategyRegistry["combined-high-confidence"].signalFilter`
with a mocked BUY row + BULLISH TA context returns the row (trade opened).

**AC-CHC-4:** A unit test for `strategyRegistry["combined-high-confidence"].signalFilter`
with a mocked BUY row + BEARISH TA context returns `null` (trade blocked).

**AC-CHC-5:** A unit test for `strategyRegistry["combined-high-confidence"].signalFilter`
with a mocked BUY row + NEUTRAL TA context returns `null` (trade blocked).

**AC-CHC-6:** The `combined-high-confidence` entry in `backtestTools.ts` tool description
is updated to remove the phrase "currently alias for high-confidence" (or equivalent stub
language).

**AC-CHC-7:** `tsc --noEmit` exits 0.

### DDD Layer Map

| Change | Layer |
|--------|-------|
| `strategyRegistry.ts` — replace stub signalFilter | domain/backtesting |
| EMA/RSI computation helper | domain/backtesting (pure fn) or infrastructure/db (data fetch) |
| Pre-fetch of OHLCV candles for TA derivation | infrastructure/db |
| Injection of TA context into signalFilter | application/usecases (runBacktest.ts) |
| Tool description update | interface/mcp/tools |

### Architectural Risk (blocker category: design decision for Architect)

**RISK-1: `signalFilter` is a synchronous function receiving only one `RawSignalRow`.**

The current `StrategyDefinition.signalFilter(row: RawSignalRow): BacktestSignal | null`
signature has no access to price history. EMA/RSI computation requires N candles per
ticker. The Architect must choose one of the following approaches before implementation:

- Option A: Pre-compute a `Map<ticker, TADirection>` in `runBacktest` use case (application
  layer) and close over it in the strategy's `signalFilter` at instantiation time. The
  registry becomes a factory function rather than a plain object literal. No interface
  change required.
- Option B: Extend `StrategyDefinition` with an optional
  `enrichSignals?(signals, priceRepo): BacktestSignal[]` hook that runs before the engine,
  letting the strategy mutate or pre-filter its full signal list with full price access.
- Option C: Add a `taDirection?: string` field to `BacktestSignal` / `RawSignalRow` and
  populate it in `SqliteBacktestSignalRepository.getSignals()` by joining `daily_ohlcv`.

Each option has different layer-purity tradeoffs. This is the primary design question for
Sprint 1843. **BA does not prescribe the option — Architect decides.**

## Deliverable 3 — `benchmarkReturnPct` Duplication Cleanup

### Context

QA noted in Sprint 1842e that `benchmarkReturnPct` computation appears in two places in
`backtestEngine.ts`:

1. Lines 324–329 inside `runBacktestEngine()` (main happy path)
2. Lines 372–376 inside `buildEmptyReport()` (zero-trades fallback)

Both blocks are identical:
```
let benchmarkReturnPct: number | null = null;
if (benchmarkCandles.length >= 2) {
  const first = benchmarkCandles[0]!.close;
  const last = benchmarkCandles[benchmarkCandles.length - 1]!.close;
  benchmarkReturnPct = (last - first) / first;
}
```

This is a cosmetic DRY violation. It is non-blocking (QA explicitly marked it
non-blocking) but creates a maintenance hazard if the benchmark formula ever changes.

### Functional Requirements

**FR-11: Extract `computeBenchmarkReturn` helper — DDD layer: domain/backtesting**

Extract the duplicated block into a private helper function
`computeBenchmarkReturn(candles: DailyCandle[]): number | null` inside
`backtestEngine.ts`. Both `runBacktestEngine()` and `buildEmptyReport()` call this helper.

### Acceptance Criteria — Cleanup

**AC-DRY-1:** `backtestEngine.ts` contains exactly one implementation of the
benchmark-return formula.

**AC-DRY-2:** Both `runBacktestEngine()` and `buildEmptyReport()` produce identical
`benchmarkReturnPct` values for the same input as before the refactor.

**AC-DRY-3:** All existing backtest tests continue to pass.

**AC-DRY-4:** `tsc --noEmit` exits 0.

### DDD Layer Map — Cleanup

| Change | Layer |
|--------|-------|
| Extract `computeBenchmarkReturn` helper | domain/backtesting |

## Blockers — Questions Only PO Can Answer

**Q1:** For the `combined-high-confidence` TA confirmation rule, should the strategy use
**EMA crossover only**, **RSI only**, or **both must agree**? The spec above defaults to
"both must agree" (stricter filter = fewer trades). If PO wants a looser rule (either
indicator suffices), the AC-CHC-2 assertion direction stays the same but the trade count
reduction will be smaller.

**Q2:** Should the `holdDays` for `combined-high-confidence` differ from the 5-day
default? A higher-confidence strategy might justify a longer hold (e.g. 10 days). No
opinion from BA — this is a product decision.

**Q3:** Task 265 failures are listed as "Task 265 x3" but the test file has 6 tests.
Are exactly 3 specific tests failing, or is the entire describe block failing? PO or
developer should confirm via `bun test 2>&1 | grep "(fail)"` before Architect designs
the fix.

## Edge Cases

**Missing OHLCV data for TA computation:** If `daily_ohlcv` has fewer than 26 rows
for a ticker (not enough for EMA-26), TA direction must default to NEUTRAL. This blocks
the combined signal (per FR-3), and a warning should be appended to `BacktestReport.warnings`.

**All TA directions NEUTRAL:** If every ticker resolves to NEUTRAL (e.g. DB is empty or
backfill has not run), `combined-high-confidence` produces 0 trades. The engine already
handles this via the "No trades executed" warning path. No special case needed.

**VN date formatting:** `daily_ohlcv.date` is `TEXT` in `YYYY-MM-DD` format (confirmed
from schema). EMA computation must use this string-sortable format, not parse to
`Date` objects, to stay consistent with the rest of the codebase.

**Confidence = 0 signals:** Already filtered out by `minConfidence: 0.7`. No additional
handling needed for the combined strategy.
