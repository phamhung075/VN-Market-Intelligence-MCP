# REQ-192: cascade-backtest — daily cron fills outcome cols on cascade_rule_hits

status: READY_FOR_ARCHITECT
sprint: 192
po_vision: Close the signal quality feedback loop by populating price_impact_3d/7d/outcome_correct daily after market data settles.

## User Story

As a Vietnamese stock investor using Claude,
I want cascade rule hits older than 3 days to automatically receive D+3 and D+7 price outcome data,
So that I can track whether cascade rule predictions were correct and improve signal quality over time.

## Functional Requirements

### FR-1: Backtest job function

- Description: `runCascadeBacktest(deps?)` exported from `src/scheduler/cascadeBacktestJob.ts`
- Input: optional `deps` bag — `db`, `nowMsFn`, `sendWorkFn`; production uses `getDb()` + `sendTelegramWork`
- Output: `CascadeBacktestResult` — `{ processed: number; skipped: number; noData: number }`
- Business rule:
  - Query `cascade_rule_hits WHERE outcome_correct IS NULL AND price_impact_3d IS NULL AND hit_at <= datetime('now', '-3 days')`
  - For each hit row, parse `affected_stocks` (comma-separated codes, may be NULL → skip to `noData`)
  - For each code, look up `daily_ohlcv` for D+3 date relative to `hit_at` date → `close_d3`
  - Look up `daily_ohlcv` for D+7 date relative to `hit_at` date → `close_d7` (may be NULL if weekend/no data)
  - Look up base close: `daily_ohlcv WHERE code = ? AND date = date(hit_at)` → `close_d0`
  - Compute `price_impact_3d = (close_d3 - close_d0) / close_d0 * 100` (rounded to 4 decimal places)
  - Compute `price_impact_7d = (close_d7 - close_d0) / close_d0 * 100` when `close_d7` available, else NULL
  - Determine `outcome_correct`: `1` when `price_impact_3d > 1.0`, `0` when `price_impact_3d < -1.0`, `NULL` when no `close_d3` data
  - Call `updateOutcome(db, hit.id, { priceImpact3d, priceImpact7d, outcomeCorrect })` per hit row
  - A hit with `affected_stocks IS NULL` → skip, count as `noData`; do not call `updateOutcome`
  - A hit where `close_d0` is missing in `daily_ohlcv` → skip, count as `noData`
  - A hit where `close_d3` is missing → call `updateOutcome` with `priceImpact3d: null, outcomeCorrect: null` (prevents re-query next cycle once d7 also checked); actually leave row untouched (do NOT update) — row stays NULL so future cycles can retry when OHLCV arrives. Count as `noData`.
  - Send WORK summary on completion
- DDD layer: scheduler (orchestration) — calls infrastructure `cascadeHitStore.updateOutcome` + `getDb`

### FR-2: WORK channel summary message

- Description: send one WORK message after processing completes
- Format: `[cascade-backtest] processed=N skipped=M noData=K`
  - `processed` = rows where `updateOutcome` was called with non-null `priceImpact3d`
  - `skipped` = hits < 3 days old (filtered out by WHERE clause — not in query result; this counter stays 0 unless implementation queries all and filters in-process; simplest: report only processed + noData from query result, skipped = 0 from cron)
  - `noData` = rows where no `daily_ohlcv` data found for D+3 or affected_stocks NULL
- Send even when processed=0 (confirms cron fired)
- DDD layer: scheduler → infrastructure/notifiers/telegram

## Non-Functional Requirements

- Performance: batch query all pending hits in one SELECT; individual `updateOutcome` calls per row acceptable (low volume — typically < 50 rows/day)
- Data freshness: runs after `ohlcvDailyAggregatorJob` (20:00 UTC) so D+3/D+7 OHLCV rows are fully aggregated
- Language: WORK summary in English (dev channel)
- Error handling: errors in per-row processing must not abort entire batch — catch per-row, log warn, count as `noData`
- DB: all queries parameterized (no string interpolation)

## Edge Cases & Data Quality

- [ ] `affected_stocks IS NULL` → skip row, count `noData`; do not call `updateOutcome`
- [ ] `affected_stocks = ''` (empty string) → treat same as NULL; skip
- [ ] `close_d0` missing from `daily_ohlcv` (hit_at date is weekend or VPS outage) → skip row, `noData`
- [ ] `close_d3` missing (D+3 is weekend/holiday, VPS hadn't pushed yet) → leave row untouched, `noData`; retry on next daily cycle
- [ ] `close_d7` missing but `close_d3` present → write `priceImpact3d` + `outcomeCorrect`, write `priceImpact7d: null`
- [ ] Multiple tickers in `affected_stocks`: compute average `price_impact_3d` across all codes with data; if none have data → `noData`
- [ ] `price_impact_3d` exactly = 1.0 or -1.0 → boundary: `outcome_correct = NULL` (strictly greater/less)
- [ ] No pending rows (all already filled) → `processed=0 noData=0`, still send WORK summary
- [ ] `daily_ohlcv` date format: `YYYY-MM-DD` TEXT; `hit_at` format: `YYYY-MM-DD HH:MM:SS` — use `date(hit_at)` for base date
- [ ] D+3/D+7 computation: `date(hit_at, '+3 days')` in SQLite; this is calendar days, not trading days — acceptable per sprint scope

## Implementation Notes for Architect

### Query pattern for pending hits

```sql
SELECT id, rule_key, hit_at, affected_stocks
FROM cascade_rule_hits
WHERE outcome_correct IS NULL
  AND price_impact_3d IS NULL
  AND hit_at <= datetime('now', '-3 days')
```

### D+3 / D+7 close lookup

```sql
SELECT close FROM daily_ohlcv
WHERE code = ? AND date = date(?, '+3 days')
LIMIT 1
```

### Multi-ticker averaging

When `affected_stocks = 'VCB,FPT,HPG'`, compute impact per code, average across codes that have data. If none → `noData`.

### Deps injection pattern

Follow `ohlcvStalenessCheckJob.ts` exactly: dynamic import of `schema.js` and `telegram.js` when deps not injected. Export `CascadeBacktestDeps` + `CascadeBacktestResult` interfaces.

### updateOutcome import

```ts
import { updateOutcome } from "../infrastructure/db/cascadeHitStore.js"
```
