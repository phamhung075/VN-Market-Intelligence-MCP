## Structural Findings (beyond simple healed/broken)

### Finding A — Reuters RSS Ngưng row is a ghost: not a live regression

`pollNews` (the scheduled cron job that populates `rag_analyses`) permanently disabled the `reuters` (RSS) fetcher in Sprint 1833g (`pollNews.ts:625`): `...(options.fetchers?.reuters !== undefined && { reuters: options.fetchers.reuters })` — `reuters` only fires if the caller injects it explicitly. It is absent from `resolvedFetchers` defaults. The `Reuters RSS | Ngưng | 20` row in the source health table is a pre-Sprint-1833g accumulation, not a live failure. The `fetch_and_analyze` MCP tool calls `fetchReuters()` directly (bypassing `pollNews`) and still returns items via Google News RSS, but it does NOT update `globalSourceTracker`. The display row is misleading — it shows 20 consecutive errors but no fetcher is actually calling it in production.

### Finding B — 5 new VPS sources are healed at VPS push layer, not at fetch_and_analyze layer

TNB c46 noted "RSS sources RECOVERED + EXPANDED — nhandan, nld, vietnambiz, vietstock, vnbusiness". These sources are VPS-push-only (`pollNews.ts:638 vpsOnlyKeys`): they are fetched by the VPS `vn-news-fetch.service` every 15 min and pushed via `POST /api/push-news`. They do NOT appear in `fetch_and_analyze`'s `sources` enum (`analysis.ts:93`), which only accepts `["cafef", "vnexpress", "reuters", "vneconomy"]`. The source health table shows all 5 as `OK | 14 phút trước` — HEALED at the VPS push layer. However, there is no regression test that asserts items from these 5 sources appear in `rag_analyses` after a VPS push cycle.

### Finding C — fetch_and_analyze vnexpress/vneconomy: HEALED with no staleness

Both CafeF and VnExpress returned same-day articles (2026-05-13). VnEconomy circuit breaker clean, source health OK. The 41-day-old article in the reuters/vneconomy batch is from Google News RSS (which aggregates older permalinks) — this is expected behaviour for the Google News RSS feed, not a regression.

## Verdict: PARTIAL — targeted fixes + regression tests

Three issues remain after the main RSS recovery:

1. **Source health UI misleads on permanently-disabled sources** — `Reuters RSS | Ngưng | 20` and `Trading Economics (legacy) | Ngưng | 20` are displayed as active failures when both are permanently disabled. These rows should show `disabled` (like `newsapi`) not `Ngưng`. Fix: update `sourceHealthTools.ts` seed list or `pollNews.ts` to call `recordDisabled()` for permanently-disabled entries on process startup.

2. **No regression test covers the 5 new VPS sources** — nhandan, nld, vietnambiz, vietstock, vnbusiness were the c45 degradation targets. They are now healed per live source health but there is no test asserting their integration into `pollNews` via the VPS push path.

3. **No regression test covers healed main sources in the VPS push path** — CafeF/VnExpress/VnEconomy health is tracked by `globalSourceTracker` but the regression-shape contract (items must have correct `source_type`, `published_at` within 24h, non-empty `summary`) is not tested.

### Fix 1 — Mark permanently-disabled sources as `disabled` in source health (sourceHealthTools.ts)

`pollNews.ts` permanently removes `reuters` (RSS) and `tradingeconomics` (legacy stream) from `resolvedFetchers` defaults in Sprint 1833g. On process startup, these sources accumulate `Ngưng` ghost entries because `pollNews` never calls `recordSuccess` for them. The fix is to call `globalSourceTracker.recordDisabled("Reuters RSS")` and `globalSourceTracker.recordDisabled("Trading Economics")` (legacy legacy stream) in the same seed block where `seedKnownSources()` is called — or remove them from the seed list entirely (since they are not in active production use).

Preferred approach: add `recordDisabled` calls after `seedKnownSources()` in `sourceHealthTools.ts` for the two permanently-disabled sources. This matches the existing `newsapi | disabled` display pattern and is a 2-line addition.
