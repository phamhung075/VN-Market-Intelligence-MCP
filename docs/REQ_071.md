# REQ-071: Per-Ticker Intelligence Summary

status: READY_FOR_ARCHITECT
sprint: 071
po_vision: Collapse 5-7 separate MCP tool calls into a single get_ticker_intelligence(code) invocation that returns a complete Vietnamese-language pre-trade intelligence brief for one stock.

---

## User Story

As a Vietnamese stock investor in France using Claude,
I want to call one tool with a stock ticker and get the full current intelligence picture,
So that I can make informed pre-trade decisions without manually orchestrating 5-7 separate tool calls and assembling the results myself.

---

## Functional Requirements

### FR-1: New MCP tool — get_ticker_intelligence

- Description: Register a new MCP tool `get_ticker_intelligence` in a new file `src/interface/mcp/tools/tickerIntelligenceTools.ts`. The tool accepts a single stock `code` and aggregates data from six existing data sources into a formatted Vietnamese-language brief. It is a pure read-and-format aggregator — it calls no new store functions, adds no new tables, and introduces no new write paths.
- Input: `code` (string, required) — stock ticker, e.g. `"VCB"`, `"FPT"`, `"VNM"`. Uppercased and trimmed inside the tool.
- Output: formatted multi-section plain-text brief in Vietnamese (see FR-7 for output format).
- Business rule: the tool is best-effort across all six sections. Each section is wrapped in its own try/catch. If any section fails (query error, missing table, null result), that section renders as `(khong co du lieu)` and the tool returns a complete brief regardless. The tool never throws to the MCP layer.
- DDD layer: interface (`src/interface/mcp/tools/tickerIntelligenceTools.ts`)

### FR-2: Section 1 — Latest price

- Description: Query `market_prices_history` for the most recent price row for the ticker. Return the latest close price, volume, and date.
- Query: direct SQL on `market_prices_history` — same table used by `get_price_history` in `priceHistoryTools.ts`. Do NOT import `registerPriceHistoryTools`; issue the query inline.
- SQL:
  ```sql
  SELECT price, volume, fetched_at
  FROM market_prices_history
  WHERE code = ?
  ORDER BY fetched_at DESC
  LIMIT 1
  ```
- Output when data present: `Gia hien tai: {price} VND | KL: {volume} | Ngay: {date}`
- Output when no row: `(khong co du lieu)`
- Business rule: price is formatted as an integer with comma separators (e.g. `85,000`). Volume uses abbreviated form: `1.50M` / `500.0K` / raw integer. Date uses `YYYY-MM-DD` slice of `fetched_at`.
- DDD layer: interface (inline query in `tickerIntelligenceTools.ts`)

---

### FR-3: Section 2 — Evidence score

- Description: Call the existing exported function `getLatestEvidenceScore(db, ticker)` from `src/infrastructure/db/evidenceFragmentStore.ts`. This returns the most recent `evidence_scores` row for the ticker.
- Reuse: import `getLatestEvidenceScore` from `evidenceFragmentStore.ts` — do not duplicate the SQL.
- Output when data present:
  ```
  Evidence score ({score_date}): Bullish {bullish:.4f} | Bearish {bearish:.4f} | Neutral {neutral:.4f} | {fragmentCount} fragments
  ```
- Output when null: `(khong co du lieu)`
- Business rule: `score_date` is the ISO date string from the `evidence_scores` row. Values formatted to 4 decimal places. Fragment count is the integer from `fragmentCount`.
- DDD layer: interface (imports infrastructure function)

---

### FR-4: Section 3 — Recent insider activity

- Description: Call the existing exported function `getInsiderTransactionsFiltered(db, { codes: [ticker], sinceDate })` from `src/infrastructure/db/insiderStore.ts`. Look back 7 days (consistent with the "recent" framing in this brief).
- Reuse: import `getInsiderTransactionsFiltered` from `insiderStore.ts` — do not duplicate the SQL.
- Output when transactions found: one line per transaction, maximum 3 shown (most recent first by `fromDate` DESC):
  ```
  Insider ({fromDate}): {insiderName} [{position}] — {type} {executedVolume} cp
  ```
  If more than 3 transactions exist, append: `(+{N} giao dich khac trong 7 ngay)`
- Output when no transactions in 7-day window: `(khong co giao dich insider trong 7 ngay qua)`
- Business rule: `sinceDate` = today minus 7 calendar days, ISO `YYYY-MM-DD` format. `executedVolume` formatted with comma separators. `type` = `"mua"` when `type === "buy"`, `"ban"` when `type === "sell"`. Rows with `executedVolume === 0` are included (registered but not yet executed — shown with volume `0`).
- DDD layer: interface (imports infrastructure function)

### FR-5: Section 4 — Previous-day foreign flow

- Description: Query `vnstock_trading_stats` for the most recent row for the ticker. Return `foreign_volume`, `foreign_room`, and `current_holding_ratio` from that row.
- Query: direct SQL on `vnstock_trading_stats` — same table used by `get_foreign_flow` in `foreignFlowTools.ts`. Do NOT import `registerForeignFlowTools`; issue the query inline.
- SQL:
  ```sql
  SELECT foreign_volume, foreign_room, current_holding_ratio,
         substr(fetched_at, 1, 10) AS date
  FROM vnstock_trading_stats
  WHERE code = ?
  ORDER BY fetched_at DESC
  LIMIT 1
  ```
- Output when data present:
  ```
  Khoi ngoai ({date}): KL {foreign_volume} | Room con lai: {foreign_room} | Ty le so huu: {holding_ratio}%
  ```
  Where `foreign_volume` and `foreign_room` use abbreviated form (M/K), and `holding_ratio` = `(current_holding_ratio * 100).toFixed(2)`.
- Output when no row or `foreign_volume === 0`: `(khong co du lieu khoi ngoai)`
- Business rule: a zero `foreign_volume` in the only row is treated as no data (same guard as `foreignFlowTools.ts`).
- DDD layer: interface (inline query in `tickerIntelligenceTools.ts`)

### FR-6: Section 5 — Latest BCTC AI outlook

- Description: Query `financial_reports` for the most recent row for the ticker that has a non-null `ai_analysis` column. Parse the JSON stored in `ai_analysis` and extract `outlook`, `summary`, and `signals` fields from the `AIAnalysis` shape defined in `bctc-schema.ts`.
- Query: direct SQL on `financial_reports`.
- SQL:
  ```sql
  SELECT action_code, sort_key, period_year, period_quarter, ai_analysis
  FROM financial_reports
  WHERE action_code = ?
    AND ai_analysis IS NOT NULL
  ORDER BY sort_key DESC
  LIMIT 1
  ```
- Output when data present:
  ```
  BCTC ({sort_key}): Nhan dinh {outlook_vi} | {summary_truncated}
  ```
  Where `outlook_vi` is:
  - `"positive"` → `"TICH CUC"`
  - `"neutral"` → `"TRUNG TINH"`
  - `"negative"` → `"TIEU CUC"`
  - `"mixed"` → `"HO HOP"`
  And `summary_truncated` = first 120 characters of `ai_analysis.summary`, appended with `"..."` if truncated.
- Output when no row with non-null `ai_analysis`: `(chua co phan tich BCTC)`
- Business rule: `ai_analysis` is stored as a JSON string in the DB (written by `updateFinancialReportAiAnalysis` in `generateAiSummary.ts`). The tool calls `JSON.parse(ai_analysis)` inside a try/catch — if parsing fails, that section shows `(loi phan tich BCTC)`.
- DDD layer: interface (inline query in `tickerIntelligenceTools.ts`)

### FR-7: Section 6 — Prediction calibration accuracy

- Description: Call the existing exported function `getResolvedClaims(db, ticker, 20)` from `src/infrastructure/db/predictionClaimStore.ts`. From the returned resolved claims, compute: total resolved count, correct count (where `resolution_outcome === "correct"`), and average `brier_score` across all resolved rows. Only claims with non-null `brier_score` contribute to the average.
- Reuse: import `getResolvedClaims` from `predictionClaimStore.ts` — do not duplicate the SQL.
- Output when resolved claims exist:
  ```
  Du doan ({N} resolved): Chinh xac {correct}/{N} ({pct}%) | Brier TB: {avg_brier:.4f}
  ```
  Where `pct = (correct / N * 100).toFixed(1)` and `avg_brier` = mean of non-null brier_scores formatted to 4 decimal places.
- Output when no resolved claims for this ticker: `(chua co du doan da giai quyet)`
- Business rule: `getResolvedClaims` is called with `limit = 20` so the calibration view covers the 20 most recent resolved claims for this ticker. `resolution_outcome === "correct"` is the correctness check (matching the existing resolution logic). Pending claims (null `resolution_outcome`) are not returned by `getResolvedClaims` — no filtering needed.
- DDD layer: interface (imports infrastructure function)

### FR-8: Formatted output — complete brief structure

- Description: Assemble all six sections into a structured Vietnamese brief header + section blocks.
- Output format:

```
=== INTELLIGENCE BRIEF: {CODE} ===
Thoi gian: {ISO timestamp UTC}

[1] GIA
{section_1_content}

[2] EVIDENCE SCORE
{section_2_content}

[3] INSIDER (7 NGAY)
{section_3_content}

[4] KHOI NGOAI
{section_4_content}

[5] BCTC AI
{section_5_content}

[6] DU DOAN
{section_6_content}

===================================
```

- Business rule: `{ISO timestamp UTC}` = `new Date().toISOString()` at the moment the tool executes. The separator lines use exactly 35 `=` characters. Section labels (`[1] GIA`, etc.) are uppercase and fixed — not localised per data state. Each `{section_N_content}` is the single-line output described in FR-2 through FR-7, or `(khong co du lieu)` if the section try/catch catches an error.
- DDD layer: interface (`tickerIntelligenceTools.ts`)

## Non-Functional Requirements

- Performance: the tool issues 4 inline SQL queries (Sections 1, 4, 5) plus 3 store function calls (Sections 2, 3, 6) in sequence. All queries hit indexed columns (`code`, `action_code`, `stock`). Expected total latency < 30ms on local SQLite with a populated production database. No caching — results are always fresh.
- Error isolation: each of the 6 data sections is wrapped in its own try/catch. A failure in Section 3 does not prevent Sections 4–6 from executing. The tool always returns a complete 6-section brief.
- Data freshness: the brief reflects whatever data is currently in the local SQLite database. No TTL, no cache invalidation. Staleness of individual sections depends on their respective feed pipelines (price: VPS push pipeline; insider: daily insiderCheckJob; foreign flow: VPS push pipeline; evidence: nightly evidenceAccumulatorJob; BCTC: on-demand parse; calibration: predictionResolutionJob).
- Language: section labels and structure in Vietnamese. Data values may contain English technical terms (e.g. `"Bullish"`, `"Bearish"`) consistent with the existing evidence tools output. Outlook labels translated to Vietnamese uppercase per FR-6.
- Scope: one tool, one file (`tickerIntelligenceTools.ts`). No new DB tables, no new store functions, no schema migrations, no new cron jobs.
- Backward compatibility: no existing tools are modified. The new tool is purely additive.

## Edge Cases and Data Quality

- [ ] Ticker not in DB at all: all 6 sections return their respective no-data strings. The brief renders cleanly with `(khong co du lieu)` in every section.
- [ ] `code` passed in lowercase or with spaces: tool uppercases and trims inside the handler before all queries — `"vcb "` → `"VCB"`.
- [ ] `market_prices_history` has rows but all are older than 30 days: the `LIMIT 1 ORDER BY fetched_at DESC` query still returns the most recent row — the tool does not apply a freshness cutoff in this aggregation layer (freshness is the responsibility of the feed pipelines). Price freshness is visible from the `{date}` field in the output.
- [ ] `ai_analysis` column does not exist on `financial_reports` (pre-Sprint 066 DB): the inline SQL query will throw. The Section 5 try/catch catches this and renders `(khong co du lieu)` — no crash.
- [ ] `ai_analysis` JSON is malformed or missing fields: `JSON.parse` succeeds but `aiAnalysis.outlook` or `aiAnalysis.summary` is undefined — render `(loi phan tich BCTC)` from the inner catch.
- [ ] `vnstock_trading_stats` table does not exist (pre-Sprint 061 DB): inline SQL query throws. Section 4 catch renders `(khong co du lieu khoi ngoai)`.
- [ ] All brier_scores in getResolvedClaims result are null: `avg_brier` is computed over an empty set → display `N/A` for `Brier TB`.
- [ ] Vietnamese number format: prices and volumes in `market_prices_history` are stored as numbers by the VPS push pipeline — no Vietnamese dot-separator ambiguity at the DB level. Display formatting uses `toLocaleString("en-US")` for commas.
- [ ] `getInsiderTransactionsFiltered` returns rows with `executedVolume = 0` (registered but not yet traded): these are shown with volume `0` — not filtered out, because the registration itself is informative.
- [ ] More than 3 insider transactions in 7 days: cap at 3 rows shown, append the `(+N giao dich khac)` footer line.
- [ ] `getResolvedClaims` returns claims for a different ticker due to a bug: cannot occur — the function accepts `stock` as a filter parameter and the SQL includes `WHERE stock = ?`.
