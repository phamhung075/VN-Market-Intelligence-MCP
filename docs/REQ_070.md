## Functional Requirements

### FR-1: New store helper — getLabelAccuracyReport

- Description: Add a new read-only query function `getLabelAccuracyReport` to `src/infrastructure/db/marketMessageStore.ts`. The function groups `market_messages` rows WHERE `verdict IS NOT NULL` by `from_agent`, computing per-agent accuracy statistics derived from human labels.
- Input: `db: Database`, `since_days?: number` (how many calendar days back to include, default 90, clamped 1–365)
- Output: `LabelAccuracyRow[]` — see type definition below

Type definition (added to `marketMessageStore.ts`):

```ts
/** Per-agent accuracy statistics derived from human verdict labels. */
export interface LabelAccuracyRow {
  /** Agent identifier matching MarketMessageAgent values */
  from_agent: string;
  /** Total messages reviewed (verdict IS NOT NULL) in the window */
  total_reviewed: number;
  /** Count of messages labelled verdict = 'signal' */
  signal_count: number;
  /** Count of messages labelled verdict = 'noise' */
  noise_count: number;
  /**
   * Signal accuracy rate = signal_count / total_reviewed.
   * Range [0.0, 1.0]. Null only if total_reviewed = 0 (guard; should never occur
   * given the WHERE clause, but TypeScript callers must handle it).
   */
  signal_rate: number | null;
  /** ISO 8601 UTC timestamp of the most recent reviewed_at for this agent */
  last_reviewed_at: string | null;
}
```

Exact SQL for `getLabelAccuracyReport`:

```sql
SELECT
  from_agent,
  COUNT(*)                                       AS total_reviewed,
  SUM(CASE WHEN verdict = 'signal' THEN 1 ELSE 0 END) AS signal_count,
  SUM(CASE WHEN verdict = 'noise'  THEN 1 ELSE 0 END) AS noise_count,
  CAST(SUM(CASE WHEN verdict = 'signal' THEN 1 ELSE 0 END) AS REAL)
    / COUNT(*)                                   AS signal_rate,
  MAX(reviewed_at)                               AS last_reviewed_at
FROM market_messages
WHERE verdict IS NOT NULL
  AND reviewed_at >= date('now', '-' || ? || ' days')
GROUP BY from_agent
ORDER BY signal_rate DESC, total_reviewed DESC
```

Parameter binding: `[since_days]` as a single integer parameter, clamped before the query runs.

Post-query transformation: cast `signal_count` and `noise_count` from SQLite integer to TypeScript `number`. `signal_rate` is returned as a `REAL` by SQLite — coerce to `number | null` (null if the value comes back as `null` due to an empty group, which the WHERE clause prevents in practice).

- Business rule: the function is read-only. It only counts rows where `reviewed_at IS NOT NULL` (the WHERE clause on `reviewed_at >= date(...)` already excludes null-reviewed_at rows). The `since_days` window of 90 days matches the calibration engine's existing 90-day window for `prediction_claims` — consistent framing for the user.
- DDD layer: infrastructure (`src/infrastructure/db/marketMessageStore.ts`)

```ts

  "Use this alongside get_calibration_report to understand which agents generate genuine signals. " +
  "since_days controls the lookback window (default 90 days, matching the calibration engine window).",
  {
    since_days: z.coerce.number().int().min(1).max(365).default(90).optional()
      .describe("Lookback window in calendar days (1-365, default 90)"),
  },
  async ({ since_days }) => { ... }
)
```

Output format (when rows exist):

```
Label Accuracy Report — 90 ngay gan nhat
=========================================

Agent                  Reviewed  Signal  Noise   Signal%   Last reviewed
--------------------   --------  ------  -----   -------   -------------------------
alert-commander              42      31     11    73.8%     2026-04-13T08:14:00Z
morning-briefing             14       9      5    64.3%     2026-04-12T03:02:00Z
```

Column widths:
- `Agent` column: left-padded to 22 characters
- `Reviewed`, `Signal`, `Noise` columns: right-aligned, width 8
- `Signal%` column: right-aligned, width 7, one decimal place (e.g. `73.8%`)
- `Last reviewed` column: full ISO timestamp, no truncation

Output format (when no reviewed rows in window):

```
Khong co tin nhan da review trong 90 ngay qua.
Hay su dung batch_review_market_messages de danh gia tin nhan.
```

Formatting rules:
- Header shows the actual `since_days` value (e.g. `90 ngay gan nhat`).
- Footer shows total agent count and total reviewed message count summed across all rows.
- Footer links to `get_calibration_report` as the complementary tool for Brier-scored data.
- `since_days` in the empty-state message uses the actual value passed.

- Business rule: the tool is read-only. It never modifies rows. `since_days` defaults to 90 to align with the calibration engine's 90-day `prediction_claims` window. Values above 365 are rejected by Zod — the market_messages table is expected to contain up to ~7000 rows/year; queries beyond 365 days are not supported for performance reasons.

3. In `sendCalibrationDigest`, append the label_accuracy block to `workLines` after the existing per-agent Brier section.

`CalibrationJobResult` extension:


- Business rule: the label_accuracy query runs inside the same `runCalibrationReport` call as the Polymarket claims query — both within the same `db` transaction context. ## Non-Functional Requirements

- Performance: `getLabelAccuracyReport` runs a single GROUP BY query against `market_messages`. The existing `idx_mm_verdict` index (Sprint 068) and `idx_mm_from_agent` index cover the WHERE and GROUP BY clauses. With a 90-day window and up to ~10,000 rows, expected < 10ms on local SQLite.
- Data freshness: `get_label_accuracy_report` reads live rows — no caching, no TTL. `calibrationReportJob` computes label accuracy at job execution time (Sunday 20:00 VN).
- Atomicity: `getLabelAccuracyReport` is read-only. No write coordination is required.
- Language: tool description in English (consistent with existing tools). Formatted output uses Vietnamese phrasing for user-facing strings mixed with English for technical terms — consistent with Sprint 068/069 patterns.
- Backward compatibility: existing `CalibrationJobResult` consumers (tests, `insertCalibrationSnapshot`) are unaffected because `label_accuracy` is an additive field. The snapshot store does NOT persist `label_accuracy` — it is a live-computed display metric only.
- Scope boundary: this sprint reads labels only. Writing labels (Sprints 068/069) and resolving Polymarket claims (Sprint 065) are not modified.

## Edge Cases and Data Quality

- [ ] No reviewed rows in the 90-day window: `getLabelAccuracyReport` returns `[]`. The MCP tool returns the empty-state Vietnamese message. `calibrationReportJob` appends `(no label data yet)` to the WORK post.
- [ ] Agent with 100% signal rate (e.g. only 1 reviewed row, verdict = 'signal'): `signal_rate = 1.0`, displayed as `100.0%`. Valid — no minimum sample size filter in Sprint 070 (low-volume agents are informative even with 1 review).
- [ ] Agent with 0% signal rate: `signal_rate = 0.0`, displayed as `0.0%`. Valid.
- [ ] `reviewed_at IS NULL` on a reviewed row: cannot occur by design — `reviewMarketMessage` and `batchReviewMarketMessages` always set `reviewed_at = datetime('now')` on update. The WHERE clause `reviewed_at >= date('now', '-N days')` excludes such rows if they somehow exist.
- [ ] `verdict` values outside 'signal'/'noise' in the DB: impossible by store-layer enforcement (both `reviewMarketMessage` and `batchReviewMarketMessages` validate the verdict at runtime). The SUM(CASE) expressions produce 0 for any unexpected value — no exception.
- [ ] `since_days` = 1 (minimum): returns only messages reviewed today UTC. May return 0 rows. Empty-state path handles this.
- [ ] Very large `since_days` (365): covered by Zod `max(365)`. The `idx_mm_verdict` index makes even a 365-day scan fast on a single-user local table.
- [ ] `getLabelAccuracyReport` raises an exception inside `calibrationReportJob`: caught, warning logged, `label_accuracy` defaults to `[]`. The WORK post shows `(no label data yet)` instead of failing the job.
- [ ] Vietnamese number format in content: not applicable here — this sprint only counts rows, does not parse content.
- [ ] `signal_rate` precision: SQLite returns a REAL. TypeScript receives a JS number (IEEE 754 double). Display with `.toFixed(1)` to avoid floating-point display artefacts (e.g. `0.7380000000000001` → `73.8%`).
