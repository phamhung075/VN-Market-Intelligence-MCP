## User Story

As a Vietnamese stock investor using Claude,
I want the foreign flow VPS script to ship without waiting for field confirmation,
and I want the system to automatically detect when insiders are accumulating a stock over multiple days,
So that I receive actionable leading signals ahead of price moves — the two most reliable smart-money indicators in VN markets.

## Functional Requirements

### FR-1: VPS foreign flow script with configurable field names (Track A)

- Description: Extend `vps-scripts/fetch-prices.sh` to include a foreign flow fetch step. The VPS API field names for foreign buy/sell are unknown, so they must be configurable via environment variables on the VPS host rather than hardcoded.
- Input: VPS environment variables `FOREIGN_FLOW_FBUY_FIELD` (default: `fbuyVol`), `FOREIGN_FLOW_FSELL_FIELD` (default: `fsellVol`), `FOREIGN_FLOW_ROOM_FIELD` (default: `currentRoom`). These are read at script runtime on the VPS host.
- Output: A POST to `POST /api/push-foreign-flow` with a `ForeignFlowUpsertItem[]` payload: `[{ code, date, foreign_volume, foreign_room, holding_ratio, fetched_at }]` where `foreign_volume = fbuyVol - fsellVol` (net foreign volume).
- Business rule: The script reads the same batch response already fetched in Step 2 of `fetch-prices.sh` (the `bgapidatafeed.vps.com.vn/getliststockdata/$CODES` call). Foreign flow fields are extracted from the same per-stock object using the configurable field name env vars. No second API call is made.
- Business rule: If `$FOREIGN_FLOW_FBUY_FIELD` is not set in the environment, the script logs "WARN: FOREIGN_FLOW_FBUY_FIELD not set, skipping foreign flow push" and exits the foreign flow step gracefully without error.
- Business rule: `foreign_volume` computed as `(.[$FBUY_FIELD] // 0) - (.[$FSELL_FIELD] // 0)` using jq. If either field is absent or null, treat as 0.
- DDD layer: infrastructure (VPS shell script, outside Bun process)

### FR-2: /api/foreign-flow-status diagnostic endpoint (Track A)

- Description: New GET endpoint on the MCP Bun server that returns the current foreign flow field configuration and the last received push summary. Allows the operator to confirm field mapping is correct post-deploy without SSH.
- Input: `GET /api/foreign-flow-status` with `X-API-Key` header (same `VPS_PUSH_API_KEY`).
- Output (JSON):
  ```json
  {
    "configuredFields": {
      "fbuyField": "fbuyVol",
      "fsellField": "fsellVol",
      "roomField": "currentRoom"
    },
    "lastPushSummary": {
      "receivedAt": "2026-04-12T10:30:00Z",
      "itemCount": 30,
      "sampleRow": { "code": "VNM", "foreign_volume": 123456, "foreign_room": 98765432, "holding_ratio": 0.49 }
    },
    "tableRowCount": 450,
    "staleSince": null
  }
  ```
  - `configuredFields`: reads `FOREIGN_FLOW_FBUY_FIELD` / `FOREIGN_FLOW_FSELL_FIELD` / `FOREIGN_FLOW_ROOM_FIELD` from `Bun.env` with defaults (`fbuyVol`, `fsellVol`, `currentRoom`). These env vars are written in the VPS script as comments — the MCP server side merely echoes back what it expects.
  - `lastPushSummary`: reads the most recent row from `vps_push_log` table where `service = 'foreign-flow'`, plus one sample row from `vnstock_trading_stats` with non-null `foreign_volume`.
  - `tableRowCount`: `SELECT COUNT(*) FROM vnstock_trading_stats WHERE foreign_volume IS NOT NULL AND foreign_volume != 0`.
  - `staleSince`: ISO timestamp if `lastPushSummary.receivedAt` is > 48h ago, else null.
- Business rule: Requires `VPS_PUSH_API_KEY` auth (same as `/api/push-foreign-flow`). Returns 401 if key missing or wrong.
- Business rule: Returns 200 even if no push has been received yet — `lastPushSummary` will be null and `tableRowCount` will be 0. This is a diagnostic endpoint, not a health gate.
- DDD layer: interface (HTTP endpoint in `server.ts`)

### FR-3: insider_transactions DDL in initDatabase() (Track B)

- Description: Add `CREATE TABLE IF NOT EXISTS insider_transactions` to `src/infrastructure/db/schema.ts`'s `initDatabase()`. Currently the table is described in a comment in `insiderStore.ts` but never created by `initDatabase()`, so a fresh database has no table and all inserts fail.
- Input: Called during server startup via `initDatabase()`.
- Output: Table created if not exists. Idempotent. Schema:
  ```sql
  CREATE TABLE IF NOT EXISTS insider_transactions (
    id                  TEXT PRIMARY KEY,
    code                TEXT NOT NULL,
    insider_name        TEXT NOT NULL,
    position            TEXT NOT NULL,
    type                TEXT NOT NULL CHECK(type IN ('buy','sell','other')),
    registered_volume   INTEGER NOT NULL DEFAULT 0,
    executed_volume     INTEGER NOT NULL DEFAULT 0,
    price               REAL NOT NULL DEFAULT 0,
    from_date           TEXT NOT NULL,
    to_date             TEXT NOT NULL,
    fetched_at          TEXT NOT NULL
  );
  CREATE INDEX IF NOT EXISTS idx_it_code_from_date
    ON insider_transactions(code, from_date DESC);
  CREATE INDEX IF NOT EXISTS idx_it_type_from_date
    ON insider_transactions(type, from_date DESC);
  ```
- Business rule: `id` is the stable dedup key: `{code}-{insider-name-slug}-{fromDate}` (already computed in `insiderCheckJob.ts::makeRowId()`).
- Business rule: No migration needed for existing production DB — `CREATE TABLE IF NOT EXISTS` is idempotent. However, if the table was manually created on prod with a different schema, an idempotent `ALTER TABLE ADD COLUMN IF NOT EXISTS` guard is not required (the schema is small and consistent with `insiderStore.ts`).
- DDD layer: infrastructure (schema.ts)

### FR-4: insiderCheckJob cron registration (Track B)

- Description: Register `runInsiderCheck` in `src/scheduler/jobs.ts`. Currently `insiderCheckJob.ts` exists with full logic but is never imported or scheduled — it is a dead file.
- Input: New cron entry in `CRONS` object + `cron.schedule()` call in `startScheduler()`.
- Output: `insiderCheckJob` fires daily at 08:00 VN (01:00 UTC) on all days (Mon-Sun — SSC disclosures can be published weekends).
- Business rule: Schedule: `0 1 * * *` UTC (= 08:00 Asia/Ho_Chi_Minh). Env var override: `CRON_INSIDER_CHECK`.
- Business rule: Wrap in `recordJobRun(getDb(), 'insiderCheckJob', ...)` following Sprint 062 pattern (all jobs must be observable).
- Business rule: `runInsiderCheck()` must be modified in FR-5 before it is registered — do not register the current version which violates Alert Commander exclusivity.
- DDD layer: interface/scheduler (jobs.ts)

### FR-5: Replace raw Telegram send with Alert Commander pipeline + evidence fragment (Track B)

- Description: The existing `runInsiderCheck()` in `insiderCheckJob.ts` calls `sendTelegramMarket()` directly, violating the rule that only Alert Commander sends to the MARKET channel for alerts. Additionally, it does not call `record_evidence_fragment` for accumulation streaks. Both must be fixed.
- Input: After steps 1–4 of existing `runInsiderCheck()` (fetch, store, classify, mass-buy detect).
- Output changes:
  1. Replace direct `sendTelegramMarket(msg)` call with `insertAlert(db, alertRow)` where `alertRow.severity = 'high'` and `alertRow.notified_telegram = 0`. Alert Commander will pick this up via `readUnnotifiedAlerts()` on its next cycle.
  2. Add accumulation streak detection: for each stock code where `type='buy'` transactions appear on 3 or more distinct calendar days within the last 30 days (by the same `position` category — director/officer), call `record_evidence_fragment` via the store (not the MCP tool — the scheduler is in the same process).
- Business rule: Streak threshold = 3 consecutive or near-consecutive buy days (within a 30-day rolling window). "Near-consecutive" = 3 or more distinct `from_date` values for the same `code + position` combination in the `insider_transactions` table.
- Business rule: Streak detected for `buy` type only. `sell` transactions are stored but NEVER trigger evidence fragments or alerts (sell-side insider is noise in VN markets — directors often sell for liquidity, not conviction reversal).
- Business rule: Evidence fragment call: `evidenceFragmentStore.insertEvidenceFragment(db, { ticker: code, type: 'insider_accumulation', value: streakDays, confidence: 0.85, source: 'insiderCheckJob', expiresAt: <30 days from now> })`. Confidence 0.85 is fixed (insider accumulation is high-confidence by definition).
- Business rule: `insertAlert` message format (Vietnamese): `"Tich luy noi bo {code}: {N} ngay mua lien tiep boi {position} — co hieu ung lon nhat trong thi truong VN"`. The message goes into `alerts.message` column; `signals_json` contains `["insider_accumulation"]`.
- Business rule: For significant single-transaction buys (>1% of shares outstanding, where default outstanding = 1_000_000_000 as currently hardcoded), also insert an alert row with severity 'high'. This replaces the existing Telegram-direct path.
- DDD layer: domain (streak logic), infrastructure/db (insertAlert, evidenceFragmentStore), interface/scheduler (insiderCheckJob.ts)

### FR-6: get_insider_transactions MCP tool (Track B)

- Description: New MCP tool returning last 30 days of insider transactions, optionally filtered by ticker or returning all watchlist stocks.
- Tool name: `get_insider_transactions`
- Input schema:
  ```
  {
    code?: string,        // optional ticker (e.g. "VNM"). If omitted, returns all watchlist stocks.
    days?: number,        // optional lookback window, default 30, max 90
    type?: "buy"|"sell"|"all"  // default "all"
  }
  ```
- Output schema:
  ```json
  {
    "transactions": [
      {
        "code": "VNM",
        "insiderName": "Nguyen Van A",
        "position": "Giam doc",
        "type": "buy",
        "executedVolume": 500000,
        "registeredVolume": 500000,
        "price": 85000,
        "fromDate": "2026-04-10",
        "toDate": "2026-04-15",
        "fetchedAt": "2026-04-12T01:05:00Z"
      }
    ],
    "streaks": [
      {
        "code": "VNM",
        "position": "Giam doc",
        "buyDays": 3,
        "totalExecutedVolume": 1500000,
        "firstDate": "2026-04-08",
        "latestDate": "2026-04-10",
        "signal": "insider_accumulation"
      }
    ],
    "totalCount": 5,
    "lookbackDays": 30
  }
  ```
- Business rule: `streaks` array is computed on the fly from the returned transactions (group by `code + position`, count distinct `from_date` values with `type='buy'`, include only groups with >= 2 distinct buy days). This is the read-path — FR-5 handles the write-path (evidence fragments).
- Business rule: If `code` is omitted, query `SELECT DISTINCT code FROM watchlist` and return transactions for all watchlist codes within the lookback window.
- Business rule: Result ordered by `from_date DESC`, then `code ASC`.
- Business rule: `days` is clamped to [1, 90]. Default 30.
- DDD layer: interface/mcp (tool registration in tools/), infrastructure/db (getInsiderTransactions query extended with date filter)

- Language: All Telegram alert messages in Vietnamese. MCP tool output in English (consistent with existing tools).

## Edge Cases & Data Quality

- [ ] SSC portal HTML structure change: `parseInsiderHtml()` in `sscInsider.ts` is regex-based. If SSC changes column order, all fields shift. Mitigation: log raw cell count warning if cells.length != 9.
- [ ] SSC portal geo-block from France: `sscInsider.ts` fetches directly from France (not via VPS). The SSC disclosure page (`congbothongtin.ssc.gov.vn`) is a public-facing portal, not a data API — it may or may not be geo-blocked. If it starts returning 403/empty, Track B silently produces zero rows. Mitigation: `recordJobRun` captures the run; if `executedVolume` stays zero for 3+ consecutive days, `cronHealthAlertJob` will flag degraded.
- [ ] Vietnamese number format in `price` field: dots as thousand separators (e.g. `85.000` = 85,000 VND). Already handled by `parseVnNumber()` in `sscInsider.ts`.
- [ ] `position` field variety: SSC uses inconsistent Vietnamese position labels (`Giam doc`, `Giam Doc`, `GIAM DOC`, `Thanh vien HDQT`, `Co dong lon`, etc.). Streak grouping in FR-5 and FR-6 groups by raw `position` string — this means the same person with a capitalisation variant would create two streak groups. Mitigation: normalise `position` to lowercase before grouping (`position.toLowerCase().trim()`).
- [ ] Empty `executedVolume` (registered but not yet executed): some SSC rows have `executedVolume = 0` and `registeredVolume > 0` (registration period open). These should be stored (for completeness) but should NOT count toward streak calculation or evidence fragments — only fully executed transactions count.
- [ ] Duplicate IDs across SSC pagination: SSC shows last 50 rows. If a stock has >50 transactions, older ones are never fetched. Accepted — the 30-day window fits within the 50-row limit in practice.
- [ ] VPS API field names unknown (FR-1): this is the exact reason for configurable env vars. If `FOREIGN_FLOW_FBUY_FIELD` is not set, the script skips gracefully. The diagnostic endpoint (FR-2) confirms post-deploy which fields are being used.
- [ ] Foreign flow `holding_ratio` normalisation: VPS API may return percentage form (e.g. `48.87` meaning 48.87%) or decimal form (e.g. `0.4887`). `upsertForeignFlow()` already normalises: if value > 1.0, divide by 100. No change needed.
- [ ] `insider_transactions` table missing on production: the table was defined in `insiderStore.ts` comments but never added to `initDatabase()`. On the production SQLite, this table may already exist (if it was created manually when the original `insiderCheckJob` was first deployed in Sprint 024) or may not exist. The `CREATE TABLE IF NOT EXISTS` in FR-3 is idempotent and safe in both cases.

## Acceptance Criteria

### AC-1: VPS script ships with field name config

**Given** `FOREIGN_FLOW_FBUY_FIELD=fbuyVol` and `FOREIGN_FLOW_FSELL_FIELD=fsellVol` are set on the VPS host
**When** `vps-scripts/fetch-prices.sh` runs
**Then**
- The script reads the VPS API batch response and extracts foreign flow columns using `jq` with the configured field names
- A `POST /api/push-foreign-flow` is made with a non-empty array of `ForeignFlowUpsertItem` objects
- The log contains `FOREIGN_FLOW: N items pushed` (where N > 0)

### AC-2: VPS script graceful skip when fields not configured

**Given** `FOREIGN_FLOW_FBUY_FIELD` is NOT set on the VPS host
**When** `vps-scripts/fetch-prices.sh` runs
**Then**
- The script logs `WARN: FOREIGN_FLOW_FBUY_FIELD not set, skipping foreign flow push`
- No POST to `/api/push-foreign-flow` is made
- The price push still completes normally (non-zero exit code only if price push fails)

### AC-3: Diagnostic endpoint returns field config

**Given** at least one successful foreign flow push has occurred
**When** `GET /api/foreign-flow-status` is called with valid `X-API-Key`
**Then**
- Response is 200 JSON
- `configuredFields.fbuyField` matches `FOREIGN_FLOW_FBUY_FIELD` env var value (or default `fbuyVol`)
- `lastPushSummary.itemCount > 0`
- `tableRowCount > 0`
- `staleSince` is null (push was recent)

### AC-4: insider_transactions table created on fresh database

**Given** a fresh in-memory SQLite database
**When** `initDatabase()` is called
**Then**
- `SELECT name FROM sqlite_master WHERE type='table' AND name='insider_transactions'` returns one row
- `idx_it_code_from_date` index exists
- `idx_it_type_from_date` index exists

### AC-5: insiderCheckJob fires and stores transactions

**Given** the SSC insider page returns at least one transaction row
**When** `runInsiderCheck()` is called
**Then**
- The transaction is inserted into `insider_transactions`
- `hasInsiderTransaction(db, id)` returns true for the inserted ID
- No direct `sendTelegramMarket()` call is made (removed in FR-5)
- `recordJobRun` records the run as 'success'

### AC-6: 3-day buy streak triggers evidence fragment

**Given** the `insider_transactions` table has buy rows for stock `VNM` by the same position on 3 distinct dates within 30 days, all with `executedVolume > 0`
**When** `runInsiderCheck()` runs
**Then**
- `evidenceFragmentStore.insertEvidenceFragment()` is called with `{ ticker: 'VNM', type: 'insider_accumulation', confidence: 0.85 }`
- An alert row is inserted into `alerts` table with `severity='high'` and `notified_telegram=0`
- No direct Telegram send occurs

### AC-7: get_insider_transactions returns structured rows

**Given** `insider_transactions` contains rows for `VNM` within the last 30 days
**When** MCP tool `get_insider_transactions({ code: "VNM" })` is called
**Then**
- Response contains `transactions` array with at least one row for `VNM`
- `streaks` array is populated if >= 2 buy days exist
- `totalCount` equals `transactions.length`

### AC-8: get_insider_transactions returns all watchlist stocks

**Given** `insider_transactions` has rows for multiple watchlist stocks
**When** MCP tool `get_insider_transactions({})` (no code param) is called
**Then**
- Transactions for all watchlist codes within last 30 days are returned
- Results ordered by `from_date DESC`

### AC-9: Tool count update

**Given** Sprint 063 Track B is complete
**Then**
- `docs/data/project-stats.json` `toolCount` = 91 (was 90)
- `GET /health` returns `toolCount: 91`
- `bun tsc --noEmit` exits 0
- All new tests pass
