# REQ-228: fix(foreign-flow): root-cause parse errors + add defensive validation

status: READY_FOR_ARCHITECT
sprint: 228
po_vision: System auditor detected 784 foreign_flow parse errors/24h (3740 total), all at JSON.parse(body) line 677 in POST /api/push-foreign-flow. Prior fixes (sprints 214–215) insufficient; recurring pattern indicates missing schema validation or VPS payload formatting issue. Root-cause fix: defensive truncation detection, strict schema validation before upsert, and retry backoff logic.

---

## User Story

As a Vietnamese market data pipeline operator,
I want the `/api/push-foreign-flow` endpoint to validate and parse VPS payloads defensively,
So that malformed, truncated, or schema-mismatched JSON bodies are caught early and logged with context for debugging, reducing silent parse errors and improving data pipeline observability.

## Functional Requirements

### FR-1: Truncation Detection & Input Validation Guard

- Description: Enhance `src/interface/mcp/server.ts:677` error context. Detect incomplete/truncated JSON payloads before attempting `JSON.parse()`. Add explicit guards that distinguish between truncation, malformed JSON, and schema violations. Log detailed error metadata to aid VPS debugging.
- Input: Raw HTTP request body (`body` variable), maximum expected payload size (recommend 1 MB), expected minimum item count (recommend ≥1 item for push to be worthwhile).
- Output:
  - Success: `{ ok: true, upserted: number, itemsCount: number }` (200 OK).
  - Truncation: `{ error: "Payload appears truncated: <reason>" }` (400 Bad Request), log to VPS_PUSH_LOG with `truncation_detected: true`.
  - Malformed JSON: `{ error: "Invalid JSON at position X: <cause>" }` (400 Bad Request), log exact char position.
  - Schema mismatch: `{ error: "Item N: missing required field <field>" }` (400 Bad Request), log item index + missing field name.
- Business rule: A payload is truncated if: (a) body ends with incomplete JSON syntax (e.g., `[{...],[{...` without closing `]`), or (b) body size is at max threshold and last char is not `]`, or (c) `JSON.parse()` succeeds but array item count is suspiciously low (e.g., expected 30 items, got 1) AND body ends with `...` (may indicate curl cutoff).
- Business rule: Schema validation must catch at parse time: missing `code` field in any array item, missing date (will default to today UTC if absent), missing or invalid numeric fields (buyVol, sellVol, room) must be coerced to 0, not rejected.
- DDD layer: interface/mcp (server handler, line 677 error context + input validation)

### FR-2: Strict Schema Validation Service

- Description: Create new domain service `src/domain/services/market-data/foreignFlowValidator.ts` (1–50 lines, pure logic, zero I/O). Implement strict type guard functions that validate each item in the VPS payload against the `ForeignFlowUpsertItem` contract. Distinguish between coercible fields (numeric, convert 0 on error) and mandatory fields (code, date).
- Input:
  - `validateForeignFlowPayload(items: unknown[]): { valid: ForeignFlowUpsertItem[]; errors: ValidationError[] }` where `ValidationError = { itemIndex: number; field: string; reason: string; originalValue: unknown }`.
  - `isForeignFlowUpsertItem(obj: unknown): obj is ForeignFlowUpsertItem` — type guard.
  - Helper: `coerceNumericField(value: unknown, fieldName: string): { value: number; error?: string }` — parse string/"123" to 123, return error if unparseable.
- Output:
  - Validation result object: `{ valid: [parsed items with coerced types], errors: [detailed error list] }`.
  - If any item fails on mandatory field (code, date), include in errors array; valid items that passed are still returned separately.
  - If `errors.length > 0`, the caller (server.ts) should log all errors before deciding to upsert only the valid subset OR reject the entire batch.
- Business rule: A field is **mandatory** if it prevents upsert SQL execution: `code` (stock symbol), `date` (YYYY-MM-DD). A field is **coercible** if it has a sensible zero default: `foreign_volume`, `foreign_room`, `holding_ratio`, `fetched_at`. If a coercible field is absent or unparseable (e.g., `"abc"` as number), set to 0 (or null for nullable fields) and log a warning, do not reject item.
- Business rule: `holding_ratio` normalization: if > 1.0, divide by 100 (VPS sends 48.87 instead of 0.4887). This logic should remain in `upsertForeignFlow()` but validator must flag if ratio is outside [0, 2.0] range (i.e., invalid after normalization).
- DDD layer: domain/services (pure functions, zero I/O, type guards)

### FR-3: Retry Backoff & Circuit Breaker Integration

- Description: Integrate foreign flow push endpoint with the existing circuit breaker registry (`src/infrastructure/circuitBreakerRegistry.ts`). Implement exponential backoff for transient errors (network timeouts, 5xx from MCP server itself should not happen, but plan for it). For permanent errors (malformed VPS output), do NOT retry — fail fast and alert.
- Input: Error type (parse error, validation error, network error, DB error).
- Output:
  - Transient (parse error due to network truncation): return 202 Accepted + `{ queued: true, retryAfter: 5 }`, store request in retry queue if one exists, or reject immediately if no queue.
  - Permanent (schema violation, invalid stock code): return 400 + detailed error, no retry.
  - Database error (upsert fails due to constraint, disk full): return 500 + error, log to WORK channel, mark service as degraded (circuit breaker opens).
- Business rule: Do NOT queue/retry if validation errors indicate corrupt VPS output (e.g., all items have wrong field names). Retry only if the issue is transient (truncation, timeout, temporary DB lock).
- Business rule: If circuit breaker detects >5 errors in 60 seconds, open breaker for 30 seconds. During open state, reject new requests with 503 Service Unavailable. Log to WORK channel when breaker opens/closes.
- DDD layer: infrastructure/circuitBreakerRegistry (existing); integration point in server.ts POST handler

### FR-4: Enhanced VPS Push Logging

- Description: Expand `logVpsPush()` call to include new metrics: `truncation_detected`, `schema_errors`, `item_indices_failed`, `parse_time_ms`, `validation_time_ms`, `db_time_ms`. Store in `vps_push_log` table with structured columns.
- Input:
  - Before: `{ service, itemsCount, status, errorMsg }`
  - After: `{ service, itemsCount, status, errorMsg, truncation_detected?, schema_errors?, failed_item_indices?, parse_time_ms?, validation_time_ms?, db_time_ms?, vps_response_size_bytes?, circuit_breaker_state? }`
- Output: SQLite row in `vps_push_log` (extends existing schema if needed).
- Business rule: Timestamp all events to millisecond precision. On circuit breaker state change, log event with `service: "foreign-flow", status: "circuit_breaker"`.
- DDD layer: infrastructure/db (logging only, extends existing vpsPushLogStore.ts)

### FR-5: TDD RED Test Suite

- DDD layer: test-only (no production code path)

## Edge Cases & Data Quality

- [ ] Empty array `[]` payload → return 400 + `"Expected non-empty array"` (current behavior, keep).
- [ ] Single-item array `[{...}]` → accept if item is valid (not a rejection case; some calls push 1 item).
- [ ] Large payload (10 MB, network timeout) → detect truncation, mark as truncated, log context, return 400.
- [ ] Partial JSON `[{code:"VNM","foreignBuyVol":100,...` (mid-item, missing closing brace) → detect at parse time, log exact char position where JSON error occurs.
- [ ] Invalid stock code (e.g., `code: "INVALID_EXCHANGE"`) → pass schema validation (code is string), but let downstream upsert fail if FOREIGN KEY exists; log as DB validation error not parse error.
- [ ] Negative foreign volume `foreignBuyVol: -100` → accept (may indicate API quirk), let domain validation in foreignFlowAnalyzer reject later.
- [ ] All-zero flow `foreignBuyVol: 0, foreignSellVol: 0, foreignRoom: 0` → accept per VPS script filter, but VPS should not send (fetch-foreign-flow.sh line 90 filters these out). If received, accept as valid item.
- [ ] Vietnamese number format (1.234.567 with dots as thousands separator) → VPS API returns English format (123456), no conversion needed.
- [ ] Missing `date` field → default to today UTC (current behavior in server.ts line 691, keep as is).
- [ ] `holding_ratio: 45` (appears to be %) → normalize (divide by 100 to 0.45) — log warning if normalization needed.
- [ ] NaN or Infinity in numeric fields → parse fails, item goes to error list, log as schema error.
- [ ] Duplicate stock codes in same payload `[{code:"VNM",...}, {code:"VNM",...}]` → both items accepted by validation, upsert will replace second occurrence (ON CONFLICT behavior), same-day duplicate is expected from VPS retries.

## Acceptance Criteria

### AC-1: Parse Error With Truncation Detection

**Given** a truncated JSON payload `[{code:"VNM",...},{code:"VCB"` (no closing bracket, body size at max)
**When** POST `/api/push-foreign-flow` with this payload
**Then**
- Response status is 400 Bad Request
- Response body contains `error` field with substring "Payload appears truncated"
- `vps_push_log` table has row with `service='foreign-flow'`, `status='error'`, `truncation_detected=1`

### AC-2: Schema Validation — Missing Required Field

**Given** a payload with valid JSON but missing `code` in item 2: `[{code:"VNM",...}, {foreignBuyVol:1000,...}, {code:"VCB",...}]`
**When** POST `/api/push-foreign-flow` with this payload
**Then**
- Response status is 400 Bad Request
- Response body contains `error` field mentioning "Item 1: missing required field 'code'"
- `vps_push_log` table has row with `service='foreign-flow'`, `status='error'`, `schema_errors=1`

### AC-3: Coercion of Numeric Fields

**Given** a payload with string numeric fields: `[{code:"VNM", foreignBuyVol:"5000", foreignSellVol:"2000", foreignRoom:"50000"}]` (all strings)
**When** POST `/api/push-foreign-flow` with this payload
**Then**
- Response status is 200 OK
- Response body contains `{ ok: true, upserted: 1 }`
- DB row has `foreign_volume = 3000` (5000 - 2000), `foreign_room = 50000` (coerced from string)

### AC-4: Retry Backoff on Transient Error

**Given** first POST returns 202 Accepted (request queued for retry)
**When** retry occurs after exponential backoff (5 seconds)
**Then**
- Retry request is sent to `/api/push-foreign-flow` with same payload
- Response status is 200 OK (assumed truncation is fixed on retry)
- `vps_push_log` has two rows: first with `status='retry'`, second with `status='ok'`

### AC-5: Idempotence — Duplicate Payloads

**Given** same payload posted twice with identical content (e.g., timestamp in Telegram logs shows same request)
**When** both POST requests complete successfully
**Then**
- Both return 200 OK with same `upserted` count
- DB contains no duplicate rows (ON CONFLICT behavior)
- Second upsert may return `upserted=0` (no new changes) or same count (both rows updated)

### AC-6: Circuit Breaker Opens on Repeated Errors

**Given** >5 POST requests fail with malformed JSON within 60 seconds
**When** 6th request arrives (before 60s window closes)
**Then**
- Response status is 503 Service Unavailable
- Response body contains `error: "Service temporarily unavailable (circuit breaker open)"`
- `vps_push_log` has row with `service='foreign-flow'`, `status='circuit_breaker'`, `circuit_breaker_state='open'`

### AC-7: No Regression — Existing Valid Payloads Still Work

**Given** the standard VPS payload format: `[{code:"VNM", foreignBuyVol:5000, foreignSellVol:2000, foreignRoom:50000}, {code:"VCB", ...}]`
**When** POST `/api/push-foreign-flow` with this payload
**Then**
- Response status is 200 OK
- All items are upserted successfully
- Signal latency (DB write to signal generation) ≤2 seconds
