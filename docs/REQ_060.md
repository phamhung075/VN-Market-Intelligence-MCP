## User Story

As a Vietnamese stock investor using Claude,
I want a weekly calibration report showing Brier score breakdowns by agent, stock, and direction — plus a Sunday evening Telegram digest — so that I can judge whether the system's predictions are improving or degrading and which evidence types I should trust.

## Context: What Phases A–C Shipped (Sprints 057–059)

The following are facts from production. Phase D reads from these — it does not modify them.

**Tables in `market.db`:**
- `evidence_fragments` — directional evidence rows per stock, written by analysis agents via `record_evidence_fragment`
- `evidence_scores` — nightly weighted aggregates per stock (bullish/bearish/neutral)
- `evidence_likelihood_ratios` — weekly-recomputed lift ratios per `(evidence_type, direction, horizon_days)`
- `prediction_claims` — agent-generated prediction rows with Brier scores once resolved

**Actual `prediction_claims` schema (shipped Task 1123 — differs from TECH-059 spec):**

```sql
CREATE TABLE IF NOT EXISTS prediction_claims (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  stock               TEXT NOT NULL,
  agent_id            TEXT NOT NULL,           -- e.g. "08-prediction-synthesizer"
  claim_text          TEXT NOT NULL,
  direction           TEXT NOT NULL,           -- "bullish" | "bearish" | "neutral"
  target_price        REAL,                    -- optional, VND absolute value
  resolution_date     TEXT NOT NULL,           -- ISO date YYYY-MM-DD
  confidence          REAL NOT NULL,           -- [0.0, 1.0] — same as "probability"
  resolution_outcome  INTEGER,                 -- NULL=pending, 1=correct, 0=incorrect
  actual_price        REAL,                    -- price at resolution time, VND
  brier_score         REAL,                    -- (outcome - confidence)^2, NULL until resolved
  created_at          TEXT NOT NULL,
  resolved_at         TEXT                     -- NULL while pending
)
```

**Shipped `predictionClaimStore.ts` API (Task 1123):**
- `insertPredictionClaim(db, params)` — INSERT OR IGNORE, returns new row id or 0
- `resolveClaim(db, id, outcome, actualPrice)` — sets outcome + computes Brier score
- `getPendingClaims(db, stock?)` — resolved_outcome IS NULL and resolution_date >= today
- `getResolvedClaims(db, stock?, limit?)` — resolved_outcome IS NOT NULL, resolved_at DESC
- `getClaimsByAgent(db, agentId)` — all claims by agent, created_at DESC

**Shipped domain functions in `baseRateComputer.ts` (Task 1122):**
- `computeBrierScore(probability, outcome)` — `(probability - outcome)^2`, pure function
- `computeRollingBaseRate(stock, horizonDays, db)` — fraction of ±3% windows
- `clampLikelihoodRatio(ratio)` — clamp to [0.1, 5.0], pure function

**Key implication for Phase D:** The `confidence` column is the probability field. `agent_id` identifies who made the claim. `direction` is the directional stance. There is no `synthesizer_version` column in the shipped schema — agent identity comes from `agent_id`.

## Functional Requirements

### FR-1: `calibration_snapshots` Table (DDL + Store)

- **Description:** Create the `calibration_snapshots` table to persist the output of each weekly calibration computation run. Rows are append-only — one row per run (one per Sunday). Reading history allows trend detection. The `get_calibration_report` tool reads from this table, not from raw `prediction_claims` on every call.
- **Input:** Written exclusively by `calibrationReportJob` (FR-2). Never written by agents directly.
- **Output:** Read by `get_calibration_report` MCP tool (FR-3).
- **DDL:**

```sql
CREATE TABLE IF NOT EXISTS calibration_snapshots (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  snapshot_date        TEXT NOT NULL,          -- ISO date YYYY-MM-DD (Sunday date of run)
  total_resolved       INTEGER NOT NULL,       -- count of resolved claims in the window
  avg_brier_score      REAL,                   -- overall mean Brier score (NULL if no data)
  avg_brier_by_agent   TEXT NOT NULL,          -- JSON: { "08-prediction-synthesizer": 0.12, ... }
  avg_brier_by_stock   TEXT NOT NULL,          -- JSON: { "VNM": 0.09, "FPT": 0.18, ... }
  avg_brier_by_direction TEXT NOT NULL,        -- JSON: { "bullish": 0.11, "bearish": 0.14, "neutral": 0.22 }
  calibration_curve    TEXT NOT NULL,          -- JSON array — see FR-2 for format
  trend_delta          REAL,                   -- this_week_avg_brier - prev_week_avg_brier (NULL for first run)
  top_predictions      TEXT NOT NULL,          -- JSON array of top 5 claims by lowest Brier (best)
  worst_predictions    TEXT NOT NULL,          -- JSON array of top 5 claims by highest Brier (worst)
  computed_at          TEXT NOT NULL           -- ISO 8601 UTC timestamp
);
CREATE INDEX IF NOT EXISTS idx_cs_snapshot_date ON calibration_snapshots(snapshot_date DESC);
```

- **Business rule:** `snapshot_date` is the Sunday wall-clock date when the job runs (VN time). `UNIQUE(snapshot_date)` is NOT enforced — re-runs produce additional rows but the latest row for a date is used by the query layer. If `total_resolved = 0` (no data yet), the row is still written with NULL `avg_brier_score`, empty JSON objects for breakdowns, and empty arrays for predictions.
- **DDD layer:** infrastructure — `src/infrastructure/db/calibrationSnapshotStore.ts`

### FR-2: `calibrationReportJob` (Weekly Scheduler)

- **Description:** A new scheduler job that runs every Sunday at 20:00 VN time (13:00 UTC). It reads resolved `prediction_claims` from the past rolling 90-day window, computes all calibration statistics, writes a `calibration_snapshots` row, and then triggers the Telegram digest (FR-4). Choosing 13:00 UTC (20:00 VN Sunday) ensures it runs after the existing `predictionOutcomeJob` (Sunday 08:00 UTC) and the weekly portfolio report (23:00 VN = 16:00 UTC Sunday) — there is no schedule conflict.
- **Input:** `prediction_claims WHERE resolved_outcome IS NOT NULL AND resolved_at >= date('now', '-90 days')`
- **Output:** One new row in `calibration_snapshots` + Telegram digest fired
- **Cron schedule:** `0 13 * * 0` (Sunday 13:00 UTC = 20:00 VN)
- **Computation logic — step by step:**

  1. **Fetch resolved claims window:** Query all rows from `prediction_claims` where `resolution_outcome IS NOT NULL` and `resolved_at >= date('now', '-90 days')`. If the result set is empty, write a zero-state snapshot row and send a "No resolved predictions yet" digest. Do not error.

  2. **Overall average Brier score:** `avg_brier_score = mean(brier_score)` across all rows in the window. Rows with `brier_score IS NULL` (unresolvable claims, marked by `predictionResolutionJob`) are excluded from all averages.

  3. **Brier score by agent:** Group by `agent_id`, compute `mean(brier_score)` per group. Serialise as JSON object `{ agent_id: avg_brier }`.

  4. **Brier score by stock:** Group by `stock`, compute `mean(brier_score)`. Include only stocks with at least 3 resolved claims in the window (fewer than 3 is not statistically meaningful). Serialise as JSON object `{ stock: avg_brier }`.

  5. **Brier score by direction:** Group by `direction`, compute `mean(brier_score)` per direction. Serialise as JSON `{ bullish: avg, bearish: avg, neutral: avg }`.

  6. **Calibration curve data:** Bucket predictions by their `confidence` value into 10 equal-width buckets: [0.0–0.1), [0.1–0.2), ..., [0.9–1.0]. For each non-empty bucket:
     - `predicted_prob` = bucket midpoint (0.05, 0.15, ..., 0.95)
     - `actual_hit_rate` = count of rows with `resolution_outcome = 1` / count of all rows in bucket
     - `sample_size` = count of rows in bucket
     Serialise as a JSON array sorted by bucket midpoint:
     ```json
     [
       { "bucket_midpoint": 0.05, "predicted_prob": 0.05, "actual_hit_rate": 0.03, "sample_size": 8 },
       { "bucket_midpoint": 0.25, "predicted_prob": 0.25, "actual_hit_rate": 0.20, "sample_size": 15 },
       ...
     ]
     ```
     Empty buckets (no claims) are omitted from the array. A perfectly calibrated system has `actual_hit_rate ≈ predicted_prob` for every bucket. This is the core data for detecting over/under-confidence.

  7. **Trend delta:** Query the previous `calibration_snapshots` row (latest `snapshot_date` before today). If it exists and has a non-NULL `avg_brier_score`, compute `trend_delta = this_run_avg_brier - prev_avg_brier`. A negative delta means improvement (Brier score decreased). NULL if no previous snapshot exists.

  8. **Top 5 best predictions:** From the current window, select the 5 rows with the lowest `brier_score`. Include: `id`, `stock`, `agent_id`, `direction`, `confidence`, `claim_text`, `brier_score`, `resolved_at`. Serialise as JSON array.

  9. **Top 5 worst predictions:** From the current window, select the 5 rows with the highest `brier_score`. Same fields. Serialise as JSON array.

  10. **Write snapshot:** Call `insertCalibrationSnapshot(db, { ... })` to persist the computed stats.

  11. **Fire Telegram digest:** Call `sendCalibrationDigest(snapshot, db)` (FR-4). This is a direct internal call, not a cron-to-cron event.

  12. **Call `recordJobRun` wrapper** (Task 1101 pattern) for cron health observability.

- **DDD layer:** scheduler — `src/scheduler/calibrationReportJob.ts`

### FR-3: `get_calibration_report` MCP Tool (+1 tool)

- **Description:** Returns the latest calibration snapshot on demand, or a historical snapshot for a specific date. Intended for use by the user via Claude, and by the `08-prediction-synthesizer` agent to self-assess performance before a new prediction run.
- **Input:**
  - `date?: string` — optional ISO date `YYYY-MM-DD`. If omitted, returns the latest snapshot.
- **Output (text block):**

```
Calibration Report — Sunday 2026-04-12 (90-day window)
Resolved predictions: 23 | Overall Brier score: 0.142 | Trend: -0.018 (improving)

Brier Score by Agent:
  08-prediction-synthesizer: 0.142 (n=23)

Brier Score by Direction:
  bullish: 0.121 (best calibrated)
  bearish: 0.168
  neutral: 0.210

Brier Score by Stock (min 3 resolved):
  VNM:  0.089  FPT:  0.132  VCB:  0.151  HPG:  0.178  MWG:  0.213

Calibration Curve (predicted vs actual hit rate):
  0.05 bucket: predicted=5%   actual=3%   (n=8)
  0.25 bucket: predicted=25%  actual=20%  (n=15)
  0.75 bucket: predicted=75%  actual=68%  (n=6)
  [slight over-confidence in high-probability buckets]

Top 5 Best Predictions:
  1. VNM bullish conf=0.80 → outcome=1 (Brier=0.040) [resolved 2026-04-07]
  2. FPT bullish conf=0.72 → outcome=1 (Brier=0.078) [resolved 2026-04-09]
  ...

Top 5 Worst Predictions:
  1. HPG bearish conf=0.85 → outcome=0 (Brier=0.723) [resolved 2026-04-05]
  2. MWG bullish conf=0.78 → outcome=0 (Brier=0.608) [resolved 2026-04-10]
  ...
```

- **Business rule — no data state:** If no snapshot exists (system is running but claims have not yet been resolved — expected in the first 1–2 weeks after Phase C deploy), return:
  `"No calibration data available yet. Prediction claims are being accumulated and will appear after the first resolution cycle completes (resolution_date + predictionResolutionJob run). Check back next Sunday."`
  Do not error.
- **Business rule — trend label:** Display a human-readable trend label:
  - `trend_delta < -0.01`: "improving" (Brier score decreased — better calibration)
  - `trend_delta > 0.01`: "degrading" (Brier score increased — worse calibration)
  - `|trend_delta| <= 0.01`: "stable"
  - `trend_delta IS NULL`: omit trend line
- **Business rule — calibration curve interpretation:** If any bucket has `|actual_hit_rate - predicted_prob| > 0.15`, append a plain-English note: "Note: [bucket] bucket shows [over/under]-confidence — predicted [X]% but actual hit rate was [Y]%."
- **DDD layer:** interface — `src/interface/mcp/tools/calibrationTools.ts` (new file)
- **Tool count delta:** +1

### FR-4: Weekly Telegram Digest (MARKET channel + WORK channel)

- **Description:** `calibrationReportJob` (FR-2) fires two Telegram messages at the end of each Sunday run — one to MARKET channel (user-facing prediction accuracy summary) and one to WORK channel (technical Brier breakdown for the Dev/Analysis team). The two messages have different content and different audiences.
- **Trigger:** Called internally by `calibrationReportJob` after writing the snapshot. Not a separate cron job — it is part of the same Sunday 13:00 UTC run.

**MARKET channel message format:**

```
Prediction Accuracy — This Week (2026-04-12)

23 predictions resolved (90-day window)
Overall accuracy score: 0.142/1.0 (lower = better)
Trend: improving (-0.018 vs last week)

Best calls this week:
• VNM tang gia: confidence 80% → correct (score: 0.040)
• FPT tang gia: confidence 72% → correct (score: 0.078)

Worst calls this week:
• HPG giam gia: confidence 85% → WRONG (score: 0.723)
• MWG tang gia: confidence 78% → WRONG (score: 0.608)

Calibration: slight over-confidence in high-probability predictions
```

**WORK channel message format:**

```
[calibrationReportJob] Sprint 060 — Sunday 2026-04-12 13:05 UTC

Brier scores (90-day, n=23):
  Overall:  0.142 | Trend: -0.018 (improving)
  bullish:  0.121 | bearish: 0.168 | neutral: 0.210
  by stock: VNM=0.089 FPT=0.132 VCB=0.151 HPG=0.178 MWG=0.213

Agent 08 accuracy: 0.142 (all 23 claims)
Calibration curve: 3 non-empty buckets, max deviation 7pp

Snapshot id=4 written. get_calibration_report available.
```

- **Business rule — MARKET channel:** Sends only if `total_resolved >= 1`. If `total_resolved = 0`, WORK channel still receives a "No resolved predictions yet" message, but MARKET channel is skipped (do not spam the user with empty reports).
- **Business rule — channel routing:** MARKET channel uses `TELEGRAM_INFO_MARKET_GROUP_ID`. WORK channel uses `TELEGRAM_INFO_WORK_CHANNEL_ID`. Both are existing env vars — no new secrets needed.
- **Business rule — Alert Commander exclusivity:** The Alert Commander exclusivity rule applies to alert-type messages only (stop-loss, conviction alerts). This digest is a scheduled report, not an alert — it is permitted to send directly to MARKET from the scheduler. Precedent: `alertDigestJob`, `morningBriefingJob`, `franceSummaryJob` all send to MARKET directly from the scheduler layer.
- **Business rule — claim text in digest:** The `claim_text` in `prediction_claims` is in Vietnamese. The digest reproduces it as-is in the MARKET message — no translation needed.
- **DDD layer:** scheduler — colocated in `src/scheduler/calibrationReportJob.ts` as private helper function `sendCalibrationDigest(snapshot, db)`. Not a separate file.

## Non-Functional Requirements

- **Performance:** `calibrationReportJob` queries at most ~90 * 5 = 450 resolved claims (30 watchlist stocks, one claim per stock per week maximum, 90-day window). This is a trivially small dataset. The entire job including Telegram sends must complete in under 10 seconds.
- **Data freshness:** `get_calibration_report` reads from `calibration_snapshots` — at most 7 days stale (written weekly). This is intentional and correct: calibration is a statistical measure, not a real-time feed.
- **Language:** MARKET channel digest in Vietnamese mixed with numbers. WORK channel digest in English. `claim_text` reproduced verbatim (Vietnamese).
- **Idempotency:** `calibrationReportJob` can be re-run on the same Sunday — it will write a second snapshot row for the same date. The query layer always reads the latest row (`ORDER BY id DESC LIMIT 1`), so duplicate rows do not cause incorrect behaviour. Acceptable for a weekly job.
- **Tool budget:** +1 tool (`get_calibration_report`). Tool count goes from 88 to 89. No tool removals.
- **Cron budget:** +1 job (`calibrationReportJob`, Sunday 13:00 UTC). Scheduler file count goes from 26 to 27.

## Edge Cases and Data Quality

- [ ] **No resolved claims yet (first 1–2 weeks after Phase C deploy):** `calibrationReportJob` writes a zero-state snapshot row (`total_resolved = 0`, `avg_brier_score = NULL`). WORK channel receives a digest. MARKET channel is skipped. `get_calibration_report` returns a human-readable "no data yet" message.
- [ ] **Fewer than 3 resolved claims per stock:** `avg_brier_by_stock` omits that stock (not statistically meaningful). The overall average is still computed from all resolved claims regardless of per-stock count.
- [ ] **All claims unresolvable (brier_score IS NULL):** `predictionResolutionJob` marks claims unresolvable after 5-day retry window. These rows have `brier_score = NULL` and are excluded from all averages. If 100% of claims in the window are unresolvable, `total_resolved > 0` but `avg_brier_score = NULL`. This is correctly handled — the report notes "0 scorable predictions" in that case.
- [ ] **Single-direction dominance:** Agent 08 currently targets only high-conviction stocks (bullish/bearish). `neutral` direction claims will be rare. The `avg_brier_by_direction` JSON may have `"neutral": null` (or key absent) — the tool output must handle missing keys gracefully with "n/a" substitution.
- [ ] **Calibration curve empty buckets:** The 90-day window with at most ~45 claims (30 stocks, some weeks) means most confidence buckets will be empty. The calibration curve array will have 3–5 non-empty entries, not 10. This is expected and correct — the report should not fake data for empty buckets.
- [ ] **trend_delta on first run:** `calibration_snapshots` has no previous row. `trend_delta = NULL`. The tool omits the trend line in output. No error.
- [ ] **`claim_text` encoding in JSON:** `top_predictions` and `worst_predictions` are JSON arrays stored as TEXT in SQLite. `claim_text` is Vietnamese and may contain Unicode. Standard `JSON.stringify` handles this correctly — no special encoding needed.
- [ ] **Sunday schedule conflicts:** `calibrationReportJob` runs Sunday 13:00 UTC. Existing Sunday jobs: `predictionOutcomeJob` at 08:00 UTC, `dataAuditWeekly` at 18:00 UTC (01:00 VN Sunday = Saturday-night), `devTeamHeartbeat` at 07:00 UTC, `weeklyPortfolioReportJob` at 16:00 UTC (23:00 VN Sunday). No conflicts — calibration (13:00 UTC) has a 3-hour buffer before the weekly portfolio report (16:00 UTC).
- [ ] **`baseRateComputationJob` vs `calibrationReportJob` ordering:** `baseRateComputationJob` runs Sunday 19:00 UTC. `calibrationReportJob` runs Sunday 13:00 UTC. They do not share data — calibration reads `prediction_claims`, base rate writes `evidence_likelihood_ratios`. No ordering dependency.
- [ ] **JSON column size:** `calibration_curve`, `top_predictions`, `worst_predictions` are JSON TEXT columns. With at most 50 claims in the window, these will be well under 10KB. SQLite TEXT columns have no practical size limit here.
- [ ] **VN number formatting in MARKET digest:** VND prices in `claim_text` use `80,000 VND` format (comma separator) as enforced by Agent 08 (FR-7, REQ-059). The digest reproduces `claim_text` verbatim — no reformatting needed.

## Blockers (STOP — user must answer before coding)

There are no blockers. All design decisions are resolved:

- **`prediction_claims` schema discrepancy (TECH-059 vs actual shipped code):** Resolved by direct reading of `src/infrastructure/db/predictionClaimStore.ts`. The shipped schema uses `confidence` (not `probability`), `agent_id` (not `synthesizer_version`), and `direction`. FR-2 computation uses `confidence` throughout. FR-3 tool output uses `confidence` as the displayed probability figure.
- **Which channel receives the digest:** MARKET gets the user-facing summary (FR-4). WORK gets the technical breakdown (FR-4). This follows the existing pattern of `alertDigestJob` and `morningBriefingJob`.
- **Alert Commander exclusivity for digest:** Scheduled digests are explicitly not subject to the Alert Commander exclusivity rule, which applies only to alert-type messages. Confirmed by existing precedents in `alertDigestJob.ts`, `morningBriefingJob.ts`.
- **Calibration snapshot as separate table vs. computed on-demand:** Separate table chosen. Rationale: `get_calibration_report` must be fast (tool call in Claude conversation); computing Brier aggregates on-demand over 90 days of raw claims on every tool call is unnecessary overhead when the job runs weekly.
- **90-day rolling window:** Chosen over "all-time" to avoid the first-run problem (sparse data from month 1 diluting forever) and to make trend detection meaningful. 90 days = approximately 13 weekly Synthesizer runs, which is enough statistical signal.
